## 1. 学习者核心问题 (Learner Question)

> “在一个现代软件项目中，我亲手编写的代码可能只占整个项目的 10%，剩下的 90% 全是直接或间接引入的开源第三方依赖包。当我敲下 `pip install` 或 `npm install` 时，我到底把多少权限拱手交给了互联网上的陌生人？版本号锁定（如 `requests==2.31.0`）真的能保证每次下载的代码一模一样吗？为什么即使软件包包含了正确的 SHA-256 哈希值，依然无法证明作者是谁？为什么代码拥有数字签名，也不等于代码是安全的、没有后门的？为什么独立复现构建（Reproducible Builds）无法证明源码本身不是恶意的？面对现代软件供应链的复杂生态，我们该如何构建一个不留盲区的 9 层纵深防御与审核模型？”

在掌握了身份认证（`L22-01`）与应用内解释器边界防护（`L22-02`）后，许多学习者会面临一个更深层次的信任危机：**我们费尽心机守卫的代码边界，其实运行在数千个非受信第三方开源包构成的庞大依赖树之上**。

初学者往往持有几种极度天真的默认信任假设：
1. **版本号即内容幻觉（Version-as-Identity Fallacy）**：误以为只要在依赖文件中写死版本号（`pkg==1.2.0`），每次安装就必然得到完全一致的代码；
2. **开源审查幻觉（Linus's Law Fallacy）**：误以为“只要开源，自然有成千上万的双眼睛帮我审计代码”，忽视了无数深层嵌套的微型库常年由单个匿名维护者甚至被弃置项目维系；
3. **安装时无害幻觉（Install-Time Harmlessness）**：误以为包管理器只在应用程序显式 `import` 时才会执行代码，不知道打包构建脚本（如 `setup.py`）在安装瞬间就会以当前用户特权执行任意指令；
4. **哈希即身份混同（Digest vs Identity Conflation）**：误以为只要校验了哈希一致，就能证明软件包出自合法机构，不知道哈希只能证明字节未变，根本无法证明发布者是谁。

本课带领学习者剖析软件供应链的攻击面，建立**9 层软件供应链完整性与信任评估模型**，并学会运用 OpenSSF SLSA v1.2 来源溯源标准（Provenance）做出理性、批判性的工程采纳决策。

## 3. 机制模型 (Mechanism Model)

### (1) 依赖树扩张与安装期环境特权

当项目声明依赖 `Package A` 时，`Package A` 会引入 `B` 和 `C`，`B` 又引入 `D` 和 `E`，最终形成一个深达数层、包含成百上千个文件的**传递依赖树（Transitive Dependency Tree）**。
在这个过程中存在两大致命结构性风险：
1. **爆炸的受攻击面**：攻击者无需攻破知名核心库，只需攻破依赖树深处一个不起眼、长期无人维护的微型辅助库，就能间接污染成千上万的下游顶层应用；
2. **安装期任意代码执行（Install-Time Ambient Authority）**：以 Python 为例，传统的源码分发包（sdist）在执行 `pip install` 时，会直接在宿主机的 Python 环境中**执行包内的 `setup.py` 脚本**！这意味着即便你的代码一行第三方模块都没 `import`，攻击者的后门已经在安装阶段获得了你的全部开发机权限（环境变量、SSH 私钥、AWS 云凭据）。

### (2) 常见现代软件供应链攻击剖析

- **拼写抢注（Typosquatting）**：攻击者在公共仓库（PyPI, npm）上注册与知名库名称高度相似的包（例如将 `requests` 注册为 `requsts` 或 `python-requests`），诱骗粗心的开发者输入错误命令；
- **依赖混淆（Dependency Confusion）**：企业内部通常使用私有库名称（如 `internal-auth-tool`）。如果包管理器的多源检索配置不当，攻击者可以在公网 PyPI 上用相同的名称注册一个高版本号包（`99.0.0`），导致客户端包管理器因“优先下载更高版本”而越过私有仓库直接拉取恶意公网代码；
- **维护者账号劫持（Account Takeover）**：开源库作者使用弱密码或未开启 2FA，导致账户在凭据撞库中沦陷，攻击者以合法作者身份上传植入恶意的最新版本；
- **构建基础设施污染（SolarWinds 模式）**：源码库完全开源且良性，但构建产物的 CI/CD 机器或打包机被攻陷，在源码被编译为 wheel/whl 或 npm tarball 时动态植入恶意 payload。

### (3) 9 层软件供应链完整性模型（The 9-Layer Supply Chain Model）

为了在没有万能假设的现实世界中防御供应链攻击，必须将信任逐层解耦为 9 个独立的关注点：

```
====================================================================================================
           FIG-M22-05: THE 9-LAYER SOFTWARE SUPPLY CHAIN INTEGRITY MODEL
====================================================================================================

  [ Layer 1: 版本锁定 (Resolution Pinning) ]
  锁定 lockfile 中的精确版本号 (e.g. requests==2.31.0)。
  * 局限与非保证: 无法阻止公共源被篡改或覆盖，版本号本身不包含内容承诺！
        │
        ▼
  [ Layer 2: 预期哈希归属 (Expected Digest Ownership) ]
  在受项目开发者严格版本控制的 lockfile 中记录每个包预期的 SHA-256 摘要。
  * 局限与非保证: 不证明预期的源码本身是无恶意的，仅确立了项目的基线指纹！
        │
        ▼
  [ Layer 3: 获取字节完整性 (Fetched-Byte Integrity) ]
  包管理器下载物理包后，计算其 SHA-256 并与 lockfile 预期哈希比对 (pip --require-hashes)。
  * 局限与非保证: 当“预期摘要”来自受信任的 Layer 2 基线时，摘要比对可以检测候选字节是否与该基线不一致；它不证明发布者身份，也不是碰撞/第二原像不可能性的物理证明！
        │
        ▼
  [ Layer 4: 构建可复现性 (Build Reproducibility) ]
  两台完全独立的机器从同一份源码构建，产出 bit-for-bit 完全一致的二进制包。
  * 局限与非保证: 匹配的独立重建结果支持“给定构建输入/环境下产物一致”的证据，但不能单独排除恶意源码、共同受污染的工具链或不独立的构建环境！
        │
        ▼
  [ Layer 5: 数字签名校验 (Signature Verification) ]
  验证发布包上附带的公钥密码学签名（如 Sigstore / PGP）。
  * 局限与非保证: 签名只证明私钥持有者签了名，绝对不能证明该人或机构是值得信任的！
        │
        ▼
  [ Layer 6: 签名者身份绑定 (Signer Identity Binding) ]
  核验签发该签名的公钥/证书是否真正属于经过身份鉴别的官方维护者团队。
  * 局限与非保证: 身份核实了“是谁”，依然无法证明作者的 CI 构建环境未被黑客污染！
        │
        ▼
  [ Layer 7: 构建与来源溯源 (Build/Source Provenance) ]
  附带符合 SLSA v1.2 数据模型的来源声明，并由独立的真实性/验证机制与本地 verifier policy 决定是否采信；JSON 字段本身不是“不可篡改”证明。
  * 局限与非保证: 溯源信息本身只是一段 JSON 声明，如果没有可信构建平台背书，形同虚设！
        │
        ▼
  [ Layer 8: 可信构建平台假设 (Trusted Builder Assumptions) ]
  verifier policy 只接受满足所要求 SLSA build-level 属性与身份/真实性验证的构建平台；本课 synthetic allowlist 不能证明真实平台已经隔离、短暂或防篡改。
  * 局限与非保证: 可信构建平台不能阻止维护者自己在源码 Git 仓库里故意提交恶意后门！
        │
        ▼
  [ Layer 9: 验证者准入策略 (Verifier Adoption Policy) ]
  本地部署/CI 门禁强制执行准入规则：拒绝任何未固定哈希、未签名或构建来源不可信的依赖。
  * 核心公理: 任何高大上的签名与溯源，如果没有本地验证者策略强制把关，等于零保护！
====================================================================================================
```

**Required-Core mechanism boundary:** 上述 Layer 5 的课程**概念模型**是公钥数字签名验证。但 Python 标准库 Core 不引入第三方签名库，因此 `activity_l22_03.py` 仅使用 HMAC 作为一个**合成的 keyed-authenticator / policy-ordering stand-in**，用于练习“认证结果”和“身份/准入策略”必须分层。HMAC 不是数字签名：没有公钥验证，也不能唯一归因到某一个共享秘密持有者。学习者不得把 Core HMAC PASS 当作 Layer 5 公钥签名已经被真实执行的证据。

### (4) SLSA v1.2 来源溯源规范（OpenSSF SLSA v1.2）

**SLSA（Supply-chain Levels for Software Artifacts，软件产物供应链级别）**是 Linux 基金会 OpenSSF 制定的核心规范（当前版本为 **SLSA v1.2，2025 年 11 月正式批准**）。

SLSA v1.2 按不同 tracks/levels 描述供应链保证。下面只摘取本课需要的 Source / Build 关注点，不把等级名称当成对某个真实平台的自动认证：
- **Source（源码层）**：版本控制、双人审查、保留完整历史；
- **Build（构建层）**：
  - *Build L1*：提供由构建平台生成的自动化构建溯源（Provenance）；
  - *Build L2*：由托管构建服务（Hosted Build Platform）签名并直接生成溯源，防止人为伪造；
  - *Build L3*：构建环境严格**隔离（Isolated）且短暂临时（Ephemeral）**，杜绝上一次构建污染下一次构建，并具备深度防篡改能力。

下面是一个**课程化、字段受限的代表性结构**，用于说明 subject / buildDefinition / resolvedDependencies / builder 的职责；它不是一份经过签名的真实 attestation envelope，也不是 SLSA level certification：
```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "predicateType": "https://slsa.dev/provenance/v1",
  "subject": [
    {
      "name": "trusted-auth-lib",
      "digest": {"sha256": "f208845cc1f2..."}
    }
  ],
  "predicate": {
    "buildDefinition": {
      "buildType": "https://slsa.dev/build-types/github-actions/v1",
      "externalParameters": {
        "source": "git+https://source.example/trusted-lib@refs/tags/v1.4.0"
      },
      "resolvedDependencies": [
        {
          "uri": "git+https://source.example/trusted-lib@refs/tags/v1.4.0",
          "digest": {"gitCommit": "a1b2c3d4e5f6..."}
        }
      ]
    },
    "runDetails": {
      "builder": {
        "id": "https://builder.example/essential-cs@v1"
      }
    }
  }
}
```

## 4. 论断分层 (Claim Layer)

| 序号 | 论断内容 | 性质 | 验证方式 |
| :--- | :--- | :--- | :--- |
| **C1** | 版本号锁定仅能约束包管理器的版本选择逻辑，不能防御公共仓库遭篡改或上游依赖混淆攻击 | **工程事实 (Engineering Fact)** | 审查公共仓库包覆盖与重命名现实，验证缺少哈希时恶意包仍可被下载 |
| **C2** | 在预期摘要由受信任的 Layer 2 基线控制、且采用 SHA-256 的安全假设成立时，摘要不匹配可以检测候选产物与预期字节不同；摘要一致不证明发布者身份，也不是“物理绝对保证” | **密码学边界 (Cryptographic Boundary)** | 运行 `activity_l22_03.py`，观察篡改候选字节导致与受信 expected digest 不匹配 |
| **C3** | 数字签名只能证明持有私钥的主体进行了签署，不能证明代码本身的安全性与无恶意性 | **安全公理 (Security Axiom)** | 以概念推演说明：即使真实数字签名验证通过，也只证明相应签名/密钥关系；Core HMAC stand-in 不能作为真实数字签名运行证据 |
| **C4** | 独立重建结果一致可以增加“给定输入/构建路径得到相同产物”的证据，但不能单独排除 malicious source、共同受污染的 compiler/toolchain、伪造的独立性或其他共享输入 | **逻辑界限 (Logical Boundary)** | 比较相同/不同 synthetic rebuild bytes，并写出独立性与共同依赖假设 |
| **C5** | SLSA v1.2 溯源信息如果缺乏本地验证者策略（Verifier Policy）的强制执行，无法起到任何阻断作用 | **工程事实 (Engineering Fact)** | 编写验证规则，对比策略开启与关闭时恶意未认证产物的准入结果 |

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

1. **破损场景 A：依赖范围模糊导致非预期拉取**
   - *破坏动作*：在 `lockfile` 中将版本写为范围 `requests>=2.0.0`，且省略 `expected_sha256`；
   - *观察现象*：策略引擎在 Layer 1 与 Layer 2 阶段全部标红，拒绝该依赖；
   - *工程结论*：范围版本号剥夺了系统的不可变性（Immutability），使得项目时刻暴露在上游意外升级破坏或恶意抢注的危险中。

2. **破损场景 B：只验签名不验身份（Signer Confusion）**
   - *破坏动作*：修改策略，只要签名能用任意密钥验过就放行，不核对 `authorized_signer_keys` 白名单；
   - *观察现象*：攻击者自己生成一对密钥对，把恶意包签名后上传，系统误以为“拥有数字签名”就等于“可信”，成功被恶意代码感染；
   - *安全结论*：**数字签名绝不等于信任度**！签名仅仅证明了私钥的存在。不与官方身份绑定的签名毫无安全价值。

## 9. 常见认知误区 (Common Misconceptions)

- **误区 1**：“只要我们在 `requirements.txt` 中锁定了版本号（如 `cryptography==42.0.0`），就绝不会安装到被篡改的包。”
  - *正解*：错误。如果包仓库允许覆盖（Overwriting）或镜像源被劫持，攻击者可以在保持版本号不变的前提下替换底层 wheel 文件。只有在 expected digest 本身来自受信任的项目基线时，哈希锁定才能让包管理器检测下载字节与该基线不一致；这仍不证明发布者身份或源码良性。
- **误区 2**：“如果一个二进制软件包是百分之百可复现构建出来的，我们就可以放心地把它部署上线。”
  - *正解*：错误。可复现构建并不会自动排除编译工具链木马；如果多个所谓“独立”重建共享同一个受污染工具链或共同输入，它们仍可能一致。如果源码本身包含作者故意写下的后门逻辑，可复现构建只会分毫不差地、百分之百忠实地将恶意后门编译出来。
- **误区 3**：“一个带数字签名的安装包，一定是由经过安全审查的善意组织发布的。”
  - *正解*：错误。任何拥有计算机的人都可以生成 RSA 或 Ed25519 密钥对并对任意恶意脚本签署数字签名。只有当签名被可信公钥基础设施（PKI / Sigstore）严格绑定到受信任的具体组织或维护者身份时，签名才具有认证意义；即使身份确认，代码依然可能因开发者疏忽而存在高危漏洞。
- **误区 4**：“只要我们把第三方的源码拉到公司内网私有仓库镜像，供应链安全问题就解决了。”
  - *正解*：错误。私有镜像仅仅隔离了外网的可用性风险（如网络断开或上游删库）。如果进入私有镜像的代码一开始就是恶意的或存在零日漏洞，私有镜像只会将毒药在公司内网各系统间高速复制传播。必须在镜像入库前执行严格的 9 层准入审计。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

- **思考问题 (Question)**：为什么仅凭开发者在 Git 仓库用个人 GPG 私钥对代码提交（Git Commit）进行了签名，依然无法证明最终发布在公共包管理器上的二进制 Wheel/Tarball 与该 Git 提交的源码是完全一致的？
- **提示 1 (Hint 1)**：二进制发布包是在哪里被编译和打包的？
- **提示 2 (Hint 2)**：开发者的本地机器可能中毒吗？CI 脚本在打包时可能从其他外部网络拉取了未经版本控制的二进制文件吗？
- **预期观察 (Expected Observation)**：Git 提交签名仅对 Git 仓库里的纯文本有效；它对编译、打包、上传整个过程完全不具备密码学见证能力。
- **完整解释 (Full Explanation)**：
  <details>
  <summary>展开查看深入解析</summary>

  这就是软件供应链中所谓的**“构建黑盒风险”**，也是促成 **SLSA（软件产物供应链级别）规范诞生**的核心动力。
  即便 Git 源码库里的每一行代码都被开发者仔细审查且签署了 GPG 签名，打包发布的过程依然存在巨大攻击面：
  1. 开发者在本地机器运行 `python setup.py bdist_wheel`，其本地电脑可能感染了专门污染构建产物的病毒；
  2. CI/CD 构建流水线在构建过程中，可能动态下载了未锁定的外部脚本或依赖；
  3. 恶意人员盗用了发布 Token，直接绕过 Git 仓库向包管理器上传了手写的恶意二进制包。
  **解决方案**：
  需要使用符合组织 verifier policy 的构建与 provenance 机制，并验证 attestation 的真实性、builder identity、subject digest、source/materials 与所需 build-level 属性。真实平台是否隔离/ephemeral/不可伪造必须由其实际 provenance/attestation 与 verifier policy 支持；本课不会用一个 JSON allowlist 自动替真实平台背书。
  </details>

## 15. 核心概念与重访关系 (Concepts & Revisits)

- **`EC-CON-017 Trust Boundary` (信任边界 - Revisit)**：
  - *第一原籍*：M07 `L07-01`。
  - *本课重访*：信任边界存在于开发者亲手编写的代码与外部第三方代码库之间。将一个外部库引入项目，就是在信任边界上打开了一个巨大的通道。必须通过强哈希锁定与来源审查来坚守这条边界。
- **`EC-CON-008 Invariant` (不变量 - Revisit)**：
  - *第一原籍*：M02 `L02-03`。
  - *本课重访*：本课的不变量是“项目受信基线中的 expected digest 应与被准入的 artifact bytes 相符”。这个关系依赖 expected-digest ownership 和所选哈希函数的安全假设；它不是“哈希天然代表官方身份”或“物理世界唯一事实锚点”。

## 17. 精确推断边界与禁止事项 (Exact Inference Limits)

为确保学术严肃性与工程严谨性，学习者与评审者必须严格遵守以下推断界限：

1. **严禁混淆哈希与身份**：严禁在报告中宣称“校验了文件的 SHA-256 摘要，就证明了该文件来自官方发布者”；
2. **严禁混淆签名、MAC 与信任**：概念 Layer 5 是公钥数字签名；Core HMAC 只是 keyed-authenticator stand-in。两者都不能自动证明代码善意或资源/组织信任；
3. **严禁将可复现性等同于源码良性**：可复现构建仅保证了二进制与源码的忠实对应，绝不能推导出源码没有逻辑漏洞；
4. **禁止宣称溯源信息能自动提供安全保护**：没有真实性验证、builder/source policy 与本地准入规则时，单独出现一段声称为 SLSA 的 JSON metadata 不能证明 provenance 已被信任；
5. **禁止在实验中拉取或运行真实的不可信代码**：所有依赖实验必须在纯本地、合成且受控的测试夹具中进行，严禁下载不受信任的真实可疑恶意包。
