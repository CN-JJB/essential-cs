## 1. 学习者核心问题 (Learner Question)

> “为什么在现代软件开发中，最致命的安全漏洞往往不是发生在密码算法本身，而是发生在前端页面、后端代码、数据库驱动与外部网络请求的连接交界处？为什么简单的字符串拼接（`f"SELECT ... '{username}'"`）会导致整个数据库被掏空？为什么用正则把输入中的单引号过滤掉并不能真正杜绝 SQL 注入？浏览器明明有同源策略（SOP），为什么还会遭受 XSS（跨站脚本）与 CSRF（跨站请求伪造）攻击？设置了 `SameSite=Lax` 的 Cookie 真的能一劳永逸防止 CSRF 吗？为什么只在发起网络请求前校验一下 URL 字符串，根本防不住 SSRF（服务端请求伪造）？”

在学习了操作系统隔离（`M07`）、数据库存储与事务（`M13`、`M14`）、网络协议（`M10`、`M11`）以及浏览器运行模型（`M12`）后，许多初学者容易以为将这些经过充分测试的成熟组件组合在一起，系统就能自然继承它们的安全性。

现实恰恰相反：**系统的脆弱性集中爆发在组件与解释器的“组合边界”（Composition Boundaries）上**。
当由一种语言编写的应用程序（如 Python），将来自外部的不可信数据拼装成另一种语言的指令流（如 SQL、HTML、OS Shell），并传递给下游解释器执行时，如果未能严格隔绝指令与数据，下游解释器就会发生**代码与数据混淆（Code-vs-Data Confusion）**——把攻击者输入的数据当成了可执行的代码语法！

本课带领学习者立足纯防御视角（Defense-First），通过完全课程自有、本地沙盒化的 Web 安全实验环境，透彻剖析 SQL 注入、XSS、CSRF 与 SSRF 的根本成因、形式边界与结构化防御方案。

## 3. 机制模型 (Mechanism Model)

### (1) 代码与数据混淆（Code vs. Data Confusion）

在多层计算体系中，各层组件由不同的语法解析器和状态机驱动：
- **Web 框架**：Python / Node.js 解释器；
- **持久化层**：SQL 语法解析器与执行计划生成器（AST）；
- **客户端呈现**：浏览器 HTML / CSS / DOM 解析器与 JavaScript V8 引擎；
- **系统层**：POSIX Shell / 操作系统内核系统调用；
- **网络层**：HTTP 客户端与 TCP 套接字引擎。

当高层系统将包含不可信用户输入的字符串通过直接拼接注入到下游文本流时，下游的词法分析器（Lexer）会解析所有字符。如果用户数据中包含语法控制符（如 SQL 中的 `'`、`--`、`OR`；HTML 中的 `<`、`>`、`"`），词法分析器就会提前闭合字符串字面量，使得用户数据晋升为抽象语法树（AST）中的操作符或指令节点。

```
====================================================================================================
           FIG-M22-03: CODE VS. DATA IN SQL PARSING & DRIVER BOUNDARIES
====================================================================================================

  [ 拼接路径 (VULNERABLE: String Concatenation across Boundary) ]
  输入 Payload:  admin' OR '1'='1
  拼接后的文本:  SELECT * FROM users WHERE username = 'admin' OR '1'='1'
                       │
                       ▼ 传入 SQL 词法与语法解析器 (Parser)
  解析后的 AST:        [Query]
                         └── [WHERE]
                               └── [BinaryOp: OR]   <=== 用户的输入直接篡改了 AST 语法树结构！
                                     ├── [Equals: username == 'admin']
                                     └── [Equals: '1' == '1'] (恒为真 True!)
  执行结果: 绕过身份校验，全量用户数据泄露！

  --------------------------------------------------------------------------------------------------

  [ 参数化路径 (SECURE: Parameterized API / Driver Binding Boundary) ]
  SQL 语句模板:  SELECT * FROM users WHERE username = ?
  输入 Payload:  admin' OR '1'='1  (作为独立的数据参数元组传递)
                       │
                       ▼ SQLite 参数化 API 保持 SQL 模板与参数值分离（具体解析/编译时序属于引擎实现细节）
  解析后的 AST:        [Query]
                         └── [WHERE]
                               └── [Equals: username == ParameterPlaceholder(#1)]
                       │
                       ▼ sqlite3 驱动/API 将参数作为值绑定到占位符 (Value Binding)
  本课观察:            对这个 `?` 值位置，输入作为参数值交给 SQLite，而不是被拼接回 SQL 文本；
                       因而其中的引号与 `OR` 不会在该参数位置改变这条语句模板的 SQL 语法。
  执行结果: 安全查询无匹配记录，语法结构不可篡改！

  * 核心公理 1: 参数化查询在驱动/API层确立“SQL 模板与参数值分离”的契约；具体 AST/字节码阶段属于引擎实现。
  * 核心公理 2: 参数化仅保护【值位置】(Value Literals)；表名、列名和 SQL 关键字不可参数化！
====================================================================================================
```

### (2) Web 应用三大经典前端/跨域脆弱性模型

```
====================================================================================================
         FIG-M22-04: BROWSER VULNERABILITIES & DEFENSIVE BOUNDARIES (XSS, CSRF, SSRF)
====================================================================================================

  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 1. XSS (Cross-Site Scripting, 跨站脚本)                                                     │
  ├─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 核心成因: 浏览器 HTML 解析器将非受信文本数据误判为可执行的 JavaScript 脚本。                │
  │ 常见分类:                                                                                   │
  │   - 存储型 (Stored): 恶意脚本存入数据库，任何浏览该页面的用户均受害；                      │
  │   - 反射型 (Reflected): 恶意脚本包含在 URL 参数中，经服务端原样回显在 HTML 响应中；        │
  │   - DOM 型 (DOM-based): 前端 JS 将 `location.search` 等数据直接 `innerHTML` 写入页面。      │
  │ 防御边界:                                                                                   │
  │   - 一级防线: 上下文感知转义 (Context-Aware Output Encoding, e.g. Jinja2 autoescape)；     │
  │   - 二级纵深: W3C CSP Level 3 严格随机数策略 (Content-Security-Policy: script-src 'nonce-X')│
  │ 限制边界: CSP 是纵深防御，不能代替服务端的正确输出编码；无法防范 DOM Clobbering。          │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 2. CSRF (Cross-Site Request Forgery, 跨站请求伪造)                                          │
  ├─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 核心成因: 浏览器的环境特权 (Ambient Authority)。当用户在第三方钓鱼网站点击链接或提交表单时，│
  │           浏览器向受信任目标网站发起跨站请求，并【自动附带目标网站的会话 Cookie】。         │
  │ 防御边界:                                                                                   │
  │   - 一级防线: SameSite Cookie 属性 (`SameSite=Lax` / `Strict`)；                            │
  │   - 二级防线: 服务端严格核对 `Origin` 与 `Referer` 标头；                                   │
  │   - 三级防线: Anti-CSRF 状态同步令牌 (Synchronizer Token Pattern)。                         │
  │ 限制边界: `SameSite=Lax` 允许从外部网站跳转的顶层 GET 导航携带 Cookie！如果服务器错误地用   │
  │           GET 请求执行状态变更（如修改密码、转账），`SameSite=Lax` 将完全失效！            │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────────────────────────────────────────┐
  │ 3. SSRF (Server-Side Request Forgery, 服务端请求伪造)                                       │
  ├─────────────────────────────────────────────────────────────────────────────────────────────┤
  │ 核心成因: 服务端根据客户端传入的 URL 去抓取远程资源，服务端将自身所处的受信任内网权限（如   │
  │           可访问云厂商元数据服务 `169.254.169.254`、内网 Redis `10.0.0.x`）暴露给了攻击者。  │
  │ 防御边界:                                                                                   │
  │   - 方案分析: 仅校验 URL 域名（如正则判断）会被 DNS 重绑定（DNS Rebinding）绕过！          │
  │   - 本课 bounded 机制: 解析 URL → DNS 获取候选 IP → 校验目标 IP 不落入被策略禁止的网段      │
  │               → HTTP-only fixture 直接连接已经校验的 IP，避免随后按 hostname 二次解析。      │
  │ 限制边界: 重定向（302 Redirect）可能逃逸！安全 HTTP 客户端必须对每次跳转重新执行出口校验。  │
  └─────────────────────────────────────────────────────────────────────────────────────────────┘
====================================================================================================
```

### (3) SSRF 深度机理：DNS 重绑定（DNS Rebinding / TOCTOU 竞争）

为什么很多大厂应用修复了 SSRF 依然被黑客攻破？关键在于**检查时与使用时竞争（TOCTOU, Time-of-Check to Time-of-Use）**：
1. 开发者编写代码：
   ```python
   # 错误示范：检查与发起连接分离
   ip = socket.gethostbyname(domain)
   if is_private_ip(ip):
       raise Forbidden("SSRF blocked")
   # 再次发起请求
   urllib.request.urlopen(f"http://{domain}/api")
   ```
2. 攻击者注册一个受控域名 `evil.attacker.com`，并将 DNS TTL 设置为 0 秒；
3. 当服务端的 `socket.gethostbyname` 第一次查询时，攻击者的 DNS 服务器返回一个公网合法 IP（如 `1.2.3.4`），安全检查通过；
4. 随后 `urllib.request.urlopen()` 真正发起 TCP 连接时，底层网络库由于 TTL 为 0 再次查询 DNS，此时攻击者的 DNS 服务器立刻返回内部元数据地址 `169.254.169.254`！
5. **本课 bounded 修复**：在这个 HTTP-only teaching path 中，应用在解析并校验候选 IP 后，**直接连接已经校验的 IP 地址**，并把原 hostname 仅用于 HTTP `Host` 字段，因此不会再把 hostname 交给高层 HTTP 客户端触发第二次 DNS 解析。这个证明只覆盖该条 direct-connect 路径；redirect、proxy、HTTPS/TLS service identity、连接池和其他协议路径都必须另行保持相同的 egress policy。

## 6. 动手实验验证 (Hands-on Activity)

本实验完全运行于本地沙盒 (`127.0.0.1`) 临时端口上，基于 Python 内置 `sqlite3` 与 `http.server`，零外部工具依赖。

### (1) 步骤一：SQL 注入攻防与参数化免疫

运行本地 Web 安全教学测试工具：
```bash
python labs/foundations/m22/activity_l22_02.py
```

观察控制台第一部分：
```python
# 1. 易受攻击的字符串拼接
query = f"SELECT * FROM users WHERE username = '{username}'"
# 传入: admin' OR '1'='1
# 结果: 泄露了全部 3 条用户记录 (INJECTION SUCCESSFUL)

# 2. 结构化参数化查询修复
query = "SELECT * FROM users WHERE username = ?"
cur.execute(query, (username,))
# 传入: admin' OR '1'='1
```

验证：
- 哪怕输入包含 SQL 单引号、注释符 `--` 和 `OR`，参数化查询均将其视作单一字符串进行整体比对；
- 真实用户 `alice` 能够被精确匹配检索出来。

### (2) 步骤二：SSRF 目的地与网络出口封锁

观察控制台第二部分：
测试出站安全客户端对恶意内网与元数据 URL 的识别能力：
- `http://169.254.169.254/latest/meta-data/`：被 RFC 3927 链路本地黑名单拦截；
- `http://10.0.0.1/admin`：被 RFC 1918 私网网段拦截；
- `http://192.168.1.1/router`：被私网黑名单拦截；
- `http://127.0.0.1:8080/internal`：在生产策略下被本地回环黑名单拦截。

### (3) 步骤三：本地回环 HTTP 服务、CSRF 与确定性资源回收

观察控制台第三部分：
1. 本地服务绑定在 `("127.0.0.1", 0)` 动态空闲端口；
2. 登录接口颁发 `SameSite=Lax` Cookie 以及 `csrf_token`；
3. 模拟跨域恶意 POST 请求（伪造 `Origin: http://evil-site.local`，无 CSRF 令牌），服务端直接拒绝并返回 **HTTP 403 Forbidden**；
4. 模拟正规同源请求（匹配 `Origin` 且提交有效 `X-CSRF-Token`），服务端返回 **HTTP 200 OK** 并成功更新数据；
5. 服务端执行确定性清理（`shutdown()`, `server_close()`, `thread.join()`），并执行后置端口释放嗅探测试，验证无悬挂后台监听进程。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

1. **破损场景 A：动态表名伪参数化（表名拼接注入）**
   - *破坏动作*：尝试使用参数化占位符替换表名：`cursor.execute("SELECT * FROM ? WHERE id = 1", (table_name,))`；
   - *观察现象*：底层 SQLite 驱动直接抛出语法错误异常：`sqlite3.OperationalError: near "?": syntax error`；
   - *安全结论*：**参数化不是万能的文本替换工具**！SQL 驱动只允许在数值字面量位置绑定参数，不能在表名、字段名或关键字位置绑定参数。如果表名必须动态选择，必须使用白名单映射，绝不能直接拼接用户输入！

2. **破损场景 B：GET 请求执行状态变更（`SameSite=Lax` 绕过）**
   - *破坏动作*：将更新邮箱的接口错误地写为 `GET /update_email?email=hacked@evil.local`，并依赖 `SameSite=Lax` Cookie；
   - *观察现象*：攻击者只需在外部钓鱼网站放置 `<a href="http://127.0.0.1:.../update_email?email=hacked@evil.local">查看福利</a>`，当受害者点击链接发生顶级页面跳转时，浏览器按照 RFC 规范会自动附带 `SameSite=Lax` Cookie，导致状态被恶意篡改；
   - *安全结论*：`SameSite=Lax` 绝不是免死金牌！**严禁使用安全幂等的 GET 请求执行任何写操作与状态变更**。

## 9. 常见认知误区 (Common Misconceptions)

- **误区 1**：“只要我用正则表达式把输入中的 `'` 替换成 `\'`，SQL 注入就能被防住。”
  - *正解*：错误。黑名单过滤极为脆弱。数字型注入（`WHERE id = 1 OR 1=1`）根本不需要单引号；二次注入（Second-Order Injection）和宽字节字符集转换可以轻松规避转义。对 SQL 值位置应使用驱动提供的参数绑定；表名、列名、排序方向等不同结构位置需要受控映射/白名单等不同机制。
- **误区 2**：“现代前端框架（如 React / Vue）完全不会产生 XSS 漏洞。”
  - *正解*：错误。虽然现代框架在默认插值（`{{ }}`）中提供了 HTML 转义，但开发者使用 `dangerouslySetInnerHTML`、`v-html`，或者将不可信 URL 绑定到 `<a href="...">`（导致 `javascript:` 伪协议执行）时，仍会引发严重的 XSS 漏洞。
- **误区 3**：“网站启用了 `SameSite=Strict` Cookie，就完全不需要 Anti-CSRF Token 了。”
  - *正解*：错误。纵深防御原则要求多层防护。某些老旧客户端或嵌入式 WebView 可能不支持 SameSite；同站点子域名（Subdomain）被劫持时可以绕过 SameSite 限制。关键业务必须实施 Origin 校验与 Anti-CSRF Token 双重把关。
- **误区 4**：“SSRF 防御只需判断 URL 字符串是否以 `https://mycompany.com` 开头即可。”
  - *正解*：错误。利用用户凭据格式（`https://mycompany.com@169.254.169.254`）、畸形 URL 解析差异（URL Parsing Ambiguities）或开放重定向（Open Redirect），攻击者可以轻松绕过简单的字符串前缀检查。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

- **思考问题 (Question)**：为什么在处理 SSRF 时，仅仅在代码里调用 `socket.gethostbyname(domain)` 确认了 IP 不是私网地址，然后再直接把 `domain` 传给 `requests.get(domain)` 依然会被黑客利用？
- **提示 1 (Hint 1)**：回忆操作系统缓存与 DNS TTL。如果域名的 TTL 是 0 秒，每次解析会发生什么？
- **提示 2 (Hint 2)**：在你的代码做完 IP 检查到 `requests.get()` 真正建立 TCP 连接的这几毫秒时间差内，DNS 服务器有可能改变其解析结果吗？
- **预期观察 (Expected Observation)**：攻击者在第一次查询时返回合法公网 IP，在第二次连接时返回私网 IP，导致安全检查形同虚设（DNS Rebinding 攻击）。
- **完整解释 (Full Explanation)**：
  <details>
  <summary>展开查看深入解析</summary>

  这就是经典的 **DNS 重绑定（DNS Rebinding）TOCTOU 竞争**。
  HTTP 高层库在发起请求时通常会自主触发底层操作系统的 DNS 解析。如果攻击者将域名的 TTL 设为 0，高层库在建立 TCP 连接时会发起第二次 DNS 请求，从而获取到攻击者恶意替换的内网 IP（如 `169.254.169.254`）。
  **标准工程防御闭环**：
  必须将 DNS 解析与套接字连接合二为一。应用层解析一次 DNS 后，对获得的 IP 数组进行严格的网段合规性检查；一旦通过，**直接调用 `socket.create_connection((validated_ip, port))` 连接该 IP**，在 HTTP 请求标头中显式塞入 `Host: original_domain`。这样在本课这条单次 direct-connect HTTP 路径中，后续连接不会再次按 hostname 解析到另一个地址；但 redirects、proxies、TLS、连接池和应用层再发起的请求不在这个单一证明里。
  </details>

## 15. 核心概念与重访关系 (Concepts & Revisits)

- **`EC-CON-017 Trust Boundary` (信任边界 - Revisit)**：
  - *第一原籍*：M07 `L07-01`。
  - *本课重访*：信任边界存在于应用程序业务逻辑与底层解释器之间（SQL 引擎、浏览器 DOM 渲染器、网络出站套接字）。信任边界要求接收方承担**严密的类型与语义约束责任**，不能允许非受信数据渗入控制平面。
- **`EC-CON-009 Correctness` (正确性 - Revisit)**：
  - *第一原籍*：M02 `L02-03`。
  - *本课重访*：系统的正确性不仅包含“正常良性输入下的正确输出”，更包含**对抗性输入下的行为不变量维持（Correctness under Adversarial Payloads）**。参数化查询从数学和结构上确保了无论输入包含何种字符，SQL 查询的不变量语义绝不发生偏移。
