## 1. 学习者核心问题 (Learner Question)

> “在构建一个 Web API 或微服务系统时，当一个 HTTP 请求打到服务端口并携带了一个 Token 时，我到底凭什么确信‘调用者是谁’？为什么‘证明你是谁’（Authentication）和‘你能访问什么数据’（Authorization）是两个截然不同、不可混淆的步骤？拥有合法的 Token 签名，难道不就等于用户有权读取数据吗？为什么数据库绝对不能存储明文密码，甚至连快速哈希值（如 SHA-256）都不能存？为什么所谓‘无状态’的 Bearer Token 一旦签发，就无法在不依赖外部状态的情况下立即吊销？OAuth 2.1 到底是在解决身份认证，还是在做权限授权？”

在学习了密码学基石（`M21`）、TLS 与 HTTP 状态（`M11`）以及浏览器同源策略（`M12`）后，许多初学者经常陷入一系列严重的系统级认知混淆：
1. **认证与授权混淆（Authn vs Authz Conflation）**：误以为验证了用户的密码或 Token 签名，就等于完成了安全检查，忽视了资源访问控制（导致严重的 IDOR / BOLA 漏洞）；
2. **凭据、身份与权力混为一谈（Credential vs Identity vs Authority）**：误以为拥有一个令牌（Credential）就等于实体本身（Identity），更误以为实体本身天生具有操作权力（Authority）；
3. **快速哈希充当密码凭据的灾难**：误以为用 SHA-256 加密/哈希密码就很安全，不知道并行硬件可以低成本重复执行大量离线口令猜测；实际速率依算法、实现、硬件与日期而变化；
4. **无状态令牌的“免死金牌”幻觉**：误以为 JWT 等无状态令牌既拥有无状态的高性能，又能像服务端 Session 一样随时一键登出并全网即时吊销；
5. **OAuth 角色倒置**：误以为 OAuth 2.0/2.1 是一种“单点登录身份认证”，忽视了它本质上是资源访问授权委托（Authorization Delegation）框架。

本课带领学习者跨越表象，建立严谨的**身份认证与权限决策双阶段解耦模型**，掌握符合现代规范（NIST SP 800-63B-4、RFC 9700 / BCP 240、RFC 7519 / 8725）的凭据校验与工程权衡。

| 维度 | 学习前状态 | 学习后状态 |
| :--- | :--- | :--- |
| **认证与授权概念分界** | 模糊地将登录、权限、鉴权通称为“Auth”，写在同一个函数或中间件里 | 严格在架构与代码层面切分 **Authn（证明身份）** 与 **Authz（评估权限）**，掌握凭据校验失败（HTTP 401）与权限不足（HTTP 403）的精确状态语义 |

## 3. 机制模型 (Mechanism Model)

### (1) 认证与授权的双阶段请求决策路径

计算系统中的安全访问控制由两个先后发生、职责解耦的阶段构成：

```
====================================================================================================
           FIG-M22-01: AUTHENTICATION VS AUTHORIZATION REQUEST DECISION PATH
====================================================================================================

  [ Incoming HTTP Request: Bearer Token / Session Cookie ]
                     │
                     ▼
       ┌───────────────────────────┐
       │ 1. 签名与格式校验         │ ─── 签名伪造 / 损坏 / alg: none ───► [ HTTP 401 Unauthorized ]
       │    (Signature / MAC OK?)  │
       └─────────────┬─────────────┘
                     │ 验证通过
                     ▼
       ┌───────────────────────────┐
       │ 2. 时效与状态校验         │ ─── exp 已过期 / 处于吊销黑名单 ────► [ HTTP 401 Unauthorized ]
       │    (exp > now? Revoked?)  │
       └─────────────┬─────────────┘
                     │ 验证通过
                     ▼
       ┌───────────────────────────┐
       │ 3. 受众与签发者校验       │ ─── aud != 本服务 / iss 不受信 ────► [ HTTP 401 Unauthorized ]
       │    (aud == this_service?) │
       └─────────────┬─────────────┘
                     │ 验证通过
                     ▼
         [ 确立已认证身份 (Authenticated Identity): Principal = "User #42" ]
         ================== 身份认证阶段完成 (Authn Complete) ==================
                     │
                     ▼
       ┌───────────────────────────┐
       │ 4. 资源权限决策 (Authz)   │
       │    Principal 对目标资源   │ ─── 无权限 (e.g. 试图读他人私有文档) ──► [ HTTP 403 Forbidden ]
       │    是否有执行指定操作权力?│
       └─────────────┬─────────────┘
                     │ 授权通过 (Authorized)
                     ▼
         [ 执行业务数据逻辑，返回数据: HTTP 200 OK ]

  * 核心公理 1: Authentication (401) 回答 "你是谁？凭据是否有效？"
  * 核心公理 2: Authorization  (403) 回答 "我知道你是谁，但你是否有权访问这行数据？"
  * 核心公理 3: 拥有有效签名仅证明令牌未被篡改，绝不等于已获得资源操作授权！
====================================================================================================
```

### (2) 密码凭据存储机理与慢速 KDF（NIST SP 800-63B-4）

密码本身是低熵的人类记忆口令。如果攻击者通过 SQL 注入或物理备份泄露拿到了用户口令库：
- **明文存储**：直接导致灾难性凭据泄露与全网撞库；
- **快速未加盐哈希（如 `sha256(password)`）**：攻击者可以利用预计算与并行硬件低成本地重复尝试候选口令；具体 guesses/second 与破解时间强烈依赖算法、实现、硬件、口令分布和日期，本课不冻结任何通用速率或“几分钟破解”常数；
- **通用加密（AES 存储密码）**：密钥一旦泄露（或在同一机器内存中），全量密码瞬间被全量解密。

#### 正确标准：加盐慢速密钥派生函数（Slow Password KDF）
根据 **NIST SP 800-63B-4 §3.1.1.2**：
1. **加盐（Salt）**：按 **NIST SP 800-63B-4 §3.1.1.2**，salt 至少 32 bits，并应选择为尽量减少不同存储记录之间的 salt 碰撞。本课用 `secrets.token_bytes(16)` 作为合成夹具的 128-bit 随机 salt。salt 不要求保密；随机生成使碰撞概率很低，但不能写成“数学保证唯一”。它的关键作用是让相同口令不再共享同一预计算结果，从而削弱跨记录预计算/复用优势；
2. **慢速计算（Compute-Hard / Memory-Hard）**：
   - **计算密集型（Compute-Hard）**：如 **PBKDF2**（NIST SP 800-132 / RFC 8018）。迭代数是策略参数；NIST SP 800-63B-4 要求 cost factor 在不负面影响 verifier 性能的前提下尽可能高，并随计算能力变化而调整。本课不把任何具体迭代数写成生产建议；
   - **内存密集型（Memory-Hard）**：如 **Argon2id**（RFC 9106）与 scrypt（RFC 7914）引入可调内存成本，使大规模并行猜测必须承担额外的内存容量、带宽与实现成本；这里不声称成本按某个通用“指数规律”增长；
3. **记录序列化**：教学夹具采用 `algo$params$salt$hash`，其中迭代参数必须记录真实运行值（示意：`pbkdf2_sha256$iterations=<policy_iterations>$<salt_hex>$<hash_hex>`），而不是复制一个永恒常数；
4. **敏感值比较**：Python 文档推荐 `hmac.compare_digest`，其实现方法旨在避免基于内容的短路比较，以降低 timing-analysis 风险。它不是对所有宿主/底层库/微架构执行时间的物理恒定时间证明；类型或长度差异仍可能理论上泄露类型/长度信息。

### (3) Bearer Token 剖析与校验规约（RFC 7519 / RFC 8725）

在分布式与微服务架构中，**Bearer Token（持有者令牌）**被广泛用于无状态服务间调用。
本课程定义了严格的教学参考配置文件 **`TeachingProfile-BearerV1`**（纯标准库实现），包含三个由点号连接的 Base64URL 串：
`Header.Payload.Authentication-Tag-Segment`

```
Header:  {"alg": "HS256", "typ": "JWT", "profile": "TeachingProfile-BearerV1"}
Payload: {"sub": "alice", "aud": "document-service", "iss": "idp.local", "iat": 1757000000, "exp": 1757000300}
```

校验器必须逐项执行强制校验，任何一项不满足必须立刻以安全失败（Fail-Closed）拒绝：
1. **严格算法白名单（Reject `alg: none`）**：校验器必须拥有固定的受支持算法配置（如仅允许 `HS256`）。绝不能根据 Token Header 声明的 `alg` 动态改变验证逻辑！如果 Token 声明 `alg: "none"`，必须无条件拒绝；
2. **密码学认证校验**：本教学 profile 固定使用 `HS256`，因此第三段是由共享秘密产生的 HMAC 认证标签，不是公钥数字签名。校验器用本地配置的共享秘密重新计算标签，并用 `hmac.compare_digest` 比对；通过只说明该 token 与配置的共享秘密一致，不能唯一归因给某个 signer；
3. **时效校验（`exp`）**：`exp` 必须为有效时间戳，且 `now < exp`；
4. **受众严格绑定（`aud`）**：必须校验 `aud` 严格等于当前服务的服务标识符。如果用户拿着给“计费服务”（billing）签发的有效 Token 来请求“文档服务”（document），必须予以拒绝。否则将引发**令牌替换跨服务攻击（Token Substitution Attack）**；
5. **签发者 / 主体绑定（`iss`, `sub`）**：因为本教学 profile 包含 `iss`，校验器必须确认 `iss` 等于配置的受信教学 issuer，并要求 `sub` 为非空主体标识；完成这些 profile 检查后才能建立受该 verifier policy 约束的认证上下文。随后仍必须把主体交给独立业务授权策略。

### (4) 状态化 Session vs. 无状态 Token 的架构抉择

| 架构维度 | 状态化服务存储 Session (Cookie + Store) | 无状态签名 Bearer Token (JWT) |
| :--- | :--- | :--- |
| **状态持有者** | 服务端（集中式数据库、缓存、内存） | 凭据本体由客户端携带；verifier 仍持有密钥/策略，若要提前吊销通常还需额外状态 |
| **提前吊销能力** | 删除/禁用服务端 Session 状态后，后续检查可拒绝该 Session（传播/缓存延迟仍属于系统边界） | 仅靠自包含 token 与本地验证规则，无法获知新的账户撤销事件；要在 `exp` 前撤销，需要 revocation list、epoch/version、session lookup 等带外状态 |
| **吊销应对方案** | 天生支持，无需额外机制 | 必须引入带外状态：短有效期（如 5 分钟）+ Refresh Token、黑名单（Revocation List）、版本代际号（Epoch Bumping） |
| **跨域与移动端** | 受浏览器同源策略与 Cookie 作用域限制 | 天生适合移动客户端、第三方 CLI 与多域名 API 网关 |
| **环境特权风险** | Cookie 默认被浏览器自动附加，极易遭受 CSRF 攻击 | 存储在 LocalStorage 易遭 XSS 窃取；必须由前端显式放入请求头 |

### (5) OAuth 2.1 授权码模式与 PKCE 架构（RFC 9700 / RFC 7636）

**OAuth 2.0/2.1 绝不是身份认证协议，而是授权委托框架（Authorization Delegation Framework）**。
例如：用户允许“图片打印应用”（Client）访问用户存储在“云相册”（Resource Server）里的照片，而无需把云相册的用户名密码交给打印应用。

#### 为什么公开客户端（SPA、手机 App）必须强制使用 PKCE？
根据 **RFC 9700 / BCP 240**（2025 年正式确立的 OAuth 2.0 安全最新现行最佳实践）与正在推进的 **OAuth 2.1 草案**：
- 传统的“密码凭据直接提交模式”（Resource Owner Password Credentials, ROPC）**严禁使用（MUST NOT）**；
- 传统的“隐式授权模式”（Implicit Grant）**不应使用（SHOULD NOT）**，在 OAuth 2.1 中已被移除；
- **Public clients MUST use PKCE** 来防止授权码注入/误用；对 confidential clients，RFC 9700 **RECOMMENDS** PKCE，并为满足额外条件的 confidential OpenID Connect clients 保留基于 ID Token `nonce` 的替代路径。Authorization servers MUST support PKCE。不要把这些不同规范强度压成“所有客户端一律 MUST 授权码 + PKCE”。

```
====================================================================================================
               FIG-M22-02: OAUTH 2.1 AUTHORIZATION CODE FLOW WITH PKCE
====================================================================================================

  Client Application (SPA / App)          Browser / User Agent         Authorization Server (IdP)
       │                                         │                                    │
       │ 1. 动态生成强随机 code_verifier        │                                    │
       │    计算 code_challenge = S256(verifier) │                                    │
       │    本地保存 code_verifier               │                                    │
       │                                         │                                    │
       │ 2. 重定向至授权端点 (携带 challenge) ──►│                                    │
       │    GET /authorize?client_id=...         │                                    │
       │    &code_challenge=...&method=S256 ────►│ 3. 浏览器发起授权请求 ────────────►│
       │                                         │                                    │
       │                                         │ 4. 用户登录并确认授权范围 (Consent) │
       │                                         │◄── 提示用户输入凭据与勾选授权 ─────┤
       │                                         │                                    │
       │                                         │ 5. 302 重定向携带 Authorization Code│
       │ 6. 捕获重定向，提取 auth_code ◄─────────┼─── Location: .../cb?code=XYZ... ───┘
       │                                         │
       │ 7. POST /token (直接后端通道，携带 auth_code + code_verifier) ──────────────►│
       │                                                                              │ 8. PKCE 校验:
       │                                                                              │    计算 S256(verifier)
       │                                                                              │    核对是否等于原 challenge!
       │                                                                              │    (证明 token exchange 持有与原授权事务 challenge 对应的 verifier；不是客户端身份认证)
       │ 9. 颁发 Access Token (JSON 响应) ◄───────────────────────────────────────────┤
       │
       ▼
  * 防御机理: 恶意应用即使在操作系统层窃听捕获了 auth_code，由于拿不到内存中的 code_verifier，
    向 /token 端点换取 Token 时必遭拒绝！
====================================================================================================
```

## 4. 论断分层 (Claim Layer)

| 序号 | 论断内容 | 性质 | 验证方式 |
| :--- | :--- | :--- | :--- |
| **C1** | 身份认证（Authn）确认的是“谁在调用”；资源授权（Authz）决定的是“该身份是否有权执行该操作” | **形式规范 (Specification)** | 检查接口返回状态码：身份验证失败为 HTTP 401，权限不足为 HTTP 403 |
| **C2** | 单向快速哈希（如 SHA-256）设计用于数据流完整性，无法抵御离线暴力字典碰撞，不能直接用于密码存储 | **工程事实 (Engineering Fact)** | 查阅 NIST SP 800-63B-4 与现代硬件算力现实，使用 PBKDF2/Argon2id 慢速算法替代 |
| **C3** | password-verifier salt 不要求保密；NIST 要求至少 32 bits 并选择为最小化存储记录间碰撞。随机 salt 使跨记录预计算复用困难，但不提供“永不碰撞”的数学保证 | **规范边界 (Specification Boundary)** | 观察本次两个独立随机 salt 是否不同，并明确该单次观察不能证明未来永不碰撞 |
| **C4** | 本课 HS256 token 的有效 HMAC 标签只说明验证输入与共享秘密一致；共享秘密的多个持有者都能生成标签，因此它不是唯一 signer attribution，更不等于 issuer trust 或资源授权 | **形式规范 (Specification)** | 在服务中模拟签名有效但受众（`aud`）不匹配或角色权限不足的拒绝场景 |
| **C5** | 纯无状态 Bearer Token 在不维护服务端带外状态的情况下，无法实现即时吊销 | **物理现实 (Physical Reality)** | 模拟已签发令牌在失效时间前在网络中重放，只要签名和时间有效，无状态端点必然接受 |
| **C6** | OAuth 2.0/2.1 是授权委托框架，不提供用户身份语义；OpenID Connect 才是建立在 OAuth 之上的身份层 | **形式规范 (Specification)** | 查阅 RFC 6749、RFC 9700 及 OIDC Core 1.0 规范定义 |

## 5. 先预测后观察 (Prediction-Before-Observation)

1. **预测 1（算法敏捷性陷阱）**：如果一个攻击者将有效 Token 的 Header 改为 `{"alg": "none", "typ": "JWT"}`，并将签名部分清空发送给服务端，一个未实现白名单限制的简单服务会做出什么反应？

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

为了深刻理解防御机制的不可或缺，进行以下受控破损测试：

1. **破损场景 A：禁用 `aud` 检查（受众混淆 / Token 替换攻击）**
   - *破坏动作*：在校验器中注释掉 `if aud != self.expected_audience:` 判定；
   - *观察现象*：原本只被授权调用低权限服务（如公开查询微服务）的客户端令牌，成功被高权限服务（如用户管理服务）接受；
   - *安全结论*：如果服务共用密钥（或信任同一个 IdP），没有受众锁定的令牌可以在任意内部微服务之间任意穿透使用，造成严重的特权跨越！

2. **破损场景 B：接受客户端自选算法（算法混淆攻击）**
   - *破坏动作*：允许客户端传入任意 `alg`，如果 `alg == "none"` 则直接跳过签名校验；
   - *观察现象*：攻击者只需在客户端随意构造任意 Payload（如 `sub: "admin"`），签名留空，即可完全绕过身份检查；
   - *安全结论*：绝不能由非受信输入决定服务端所采用的安全算法标准。

## 9. 常见认知误区 (Common Misconceptions)

- **误区 1**：“只要对密码做了 SHA-256 哈希，存入数据库就是绝对安全的。”
  - *正解*：错误。SHA-256 是为高吞吐数据流设计的快速哈希。攻击者利用专业 GPU/ASIC 可以极速尝试海量候选密码。必须使用带唯一随机盐的慢速密码派生函数（PBKDF2 或经相应环境支持的 memory-hard 方案）来提高离线口令猜测成本。
- **误区 2**：“PBKDF2 是内存密集型（Memory-Hard）算法。”
  - *正解*：错误。PBKDF2 仅仅是计算密集型（Iteration-Hard），它几乎不需要占用内存。专用集成电路（ASIC）可以极低成本高度并行化实现 PBKDF2。Argon2id（RFC 9106）与 scrypt 引入可调内存成本，用不同的时间/内存权衡提高大规模并行猜测成本；具体优势依参数与硬件而定。
- **误区 3**：“一个拥有合法有效签名的 JWT，证明用户已经被授权访问系统资源。”
  - *正解*：错误。对本课 HS256 profile，认证标签通过只说明 token 与配置的共享秘密一致；它不能唯一证明是哪一个共享密钥持有者生成，更不能单凭该结果建立 issuer trust。它既不证明签发者当前是否受信，更不代表该用户有权访问特定业务资源。必须由每个业务端点在认证后独立执行资源授权（Authorization）判定。
- **误区 4**：“无状态 JWT 可以在不查数据库的情况下被随时吊销。”
  - *正解*：错误。无状态性的本质就是服务端不记录状态。要在过期前吊销无状态令牌，必须引入中心化的带外状态（如黑名单、版本号或 Redis 记录），此时系统事实上又退化为了有状态系统。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

- **思考问题 (Question)**：如果一个系统签发了有效期为 2 小时的无状态 Bearer Token，当某个员工在 10 分钟后离职、管理员在后台注销了该员工账号，为什么该员工持有的 Token 仍然能够成功调用微服务接口？
- **提示 1 (Hint 1)**：微服务在验证 Bearer Token 时，需要查询中央数据库吗？
- **提示 2 (Hint 2)**：无状态令牌的校验依赖于什么？只要令牌里的 `exp` 还没有到期、签名是合法的，单独的微服务如何知道管理员执行了注销操作？
- **预期观察 (Expected Observation)**：微服务独立执行本地签名和时间戳计算，发现一切合法，因而继续放行请求并返回数据。
- **完整解释 (Full Explanation)**：
  <details>
  <summary>展开查看深入解析</summary>

  这就是无状态 Bearer Token 的固有物理限制：**去中心化的验证便利性是以牺牲即时吊销能力为代价的**。
  每个独立的微服务仅根据私钥/公钥和本地时钟校验令牌，根本不知道远端中心数据库发生了账号注销事件。
  解决这一问题必须引入妥协方案：
  1. **极短有效期 + Refresh Token**：将 Access Token 有效期压缩至 5~15 分钟，要求客户端定期拿 Refresh Token 去中心服务换新；
  2. **吊销黑名单（Revocation List）**：在分布式缓存（如 Redis）中维护已被撤销的 `jti`（Token 唯一编号），但这打破了纯无状态假设；
  3. **代际版本号（Epoch Bumping）**：用户记录中维护 `token_version`，修改密码或离职时版本号加 1，微服务在网关层校验版本。
  </details>

## 17. 精确推断边界与禁止事项 (Exact Inference Limits)

为确保学术严肃性与工程严谨性，学习者与评审者必须严格遵守以下推断红线：

1. **禁止混同认证与授权**：严禁在代码或回答中出现“用户登录成功，所以可以直接返回任意数据”的逻辑；
2. **禁止宣称 JWT 能够无状态即时吊销**：在未引入中心化状态（如分布式缓存黑名单或版本代际号）前，严禁宣称纯无状态 Token 可以被即时单向撤销；
3. **禁止将工作因子固化为绝对常数**：PBKDF2 的迭代次数或 Argon2id 的内存开销是随环境算力和业务延迟容忍度动态调整的政策参数，绝非课程不变定理；
4. **禁止宣称 OAuth 提供了用户认证**：OAuth 2.1 颁发的是访问资源服务器的委托令牌，若需确立用户身份 Profile，必须结合 OpenID Connect（OIDC）或专用身份层；
5. **禁止在生产中实现自定义加解密原语**：本课只讲授标准安全规约与调用接口（`secrets`, `hashlib`, `hmac`），严禁手写自定义哈希、伪随机发生器或加密算法。
