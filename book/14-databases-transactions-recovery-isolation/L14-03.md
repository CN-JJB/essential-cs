# L14-03｜如何设计原子写入：锁升级冲突、事务边界重试与幂等性

## 1. 学习者核心问题 (Learner Question)

> “当多个并发进程频繁向数据库写入时，我们该如何设计稳健的原子写入逻辑？为什么我的事务明明加了重试，系统却还是报锁冲突甚至死锁？遇到报错就盲目重试，会不会导致同一笔扣款被重复扣除好几次？”

在学会了基本事务语法（`BEGIN` / `COMMIT`）之后，许多工程师以为只要把写操作简单包裹在事务中就高枕无忧了。但在实际高并发生产环境中，事务往往面临着锁争用、升级冲突（Lock-Upgrade Collisions）以及网络重传导致的重复提交风险。如果不理解事务在何时加锁、在哪个边界重试，简单的“捕获异常就无脑重试”不仅会加剧锁风暴，还极易酿成灾难性的重复扣费或状态污染。

本课通过实测解剖 SQLite 回滚日志架构下的读-写升级碰撞机制，建立起基于 `BEGIN IMMEDIATE` 的预先写意图串行化、事务边界回滚与指数退避重试，以及防范重复执行的幂等性设计准则。

## 3. 机制模型 (Mechanism Model)

### (1) 单语句原子更新 vs. 多语句事务边界
在设计写操作时，工程师面对的第一道架构决策是：**这笔写入是否必须使用多语句事务？**
- **单语句原子条件更新 (Single-Statement Atomic Update)**：
  ```sql
  -- 将“读取、判断、扣减”压缩进单个原子语句
  UPDATE inventory
  SET stock = stock - 1
  WHERE id = 10 AND stock > 0;
  ```
  - **优势**：数据库内部直接对该行加写锁、检查 WHERE 条件、就地修改并释放，无需在客户端与数据库之间往返多次通信，天然规避了应用层的读写交错；
  - **局限**：仅适用于单一实体的简单原子步进；无法跨越多个具有关联不变式的表或行。
- **多语句事务边界 (Multi-Statement Transactions)**：
  - 当状态变迁涉及多张表、多个行，或者需要在应用层进行复杂校验时，必须使用显式事务边界（`BEGIN ... COMMIT`）。

### (2) 锁升级碰撞机制 (Lock-Upgrade Collisions in Rollback Journal)
在 SQLite 的回滚日志（`DELETE` 模式）基准下，锁状态机经历从 `UNLOCKED` $\to$ `SHARED` (共享读) $\to$ `RESERVED` (预留写意图) $\to$ `PENDING` $\to$ `EXCLUSIVE` (互斥写) 的演变。需要特别注意：**这些锁状态名称是 SQLite 回滚日志基准下的具体实现细节，绝非跨引擎通用的事务语义，亦不代表 WAL 模式的行为**。

- **`BEGIN DEFERRED` 的陷阱**：
  - 默认的 `BEGIN`（即 `BEGIN DEFERRED`）在启动时不获取任何锁；
  - 事务内执行第一条 `SELECT` 时，获取 `SHARED` 读锁；
  - 当后续执行 `UPDATE` 时，试图将当前的读锁“升级”为 `RESERVED` 写意图锁；
  - **碰撞场景**：如果连接 1 和连接 2 同时以 `BEGIN DEFERRED` 开启事务并执行了 `SELECT`，此时两方都持有 `SHARED` 锁；接着两方几乎同时尝试执行 `UPDATE` 进行锁升级。连接 1 申请保留锁，而连接 2 也申请保留锁——由于只能有一个连接持有写意图，且双方都持有共享读锁阻止对方晋升为互斥写锁，双方瞬间陷入锁升级碰撞，返回 `SQLITE_BUSY`。
  - **注意**：SQLite 并不运行通用的等待图（Wait-for-Graph）死锁环路检测算法，它通过锁争用立即返回 `SQLITE_BUSY`（本课仅保留概念性轻量死锁认知，确定性死锁实证保留给 M15）。
- **`BEGIN IMMEDIATE` 的架构解法**：
  - `BEGIN IMMEDIATE` 在事务启动的一瞬间就预先申请 `RESERVED` 写意图锁，在读取任何数据之前就把写竞争序列化；
  - 彻底消除了后续“由读转写”的锁升级碰撞。

### (3) 事务边界重试与幂等性预览 (Boundary Retry & Idempotency)
处理并发写冲突的黄金法则是：**在正确的事务边界上重试，并在重试前清理脏状态**。

1. **先 ROLLBACK，再重试**：
   - 遭遇并发冲突（`SQLITE_BUSY`）时，当前事务已经处于受阻或不确定状态；
   - 必须先显式调用 `ROLLBACK` 释放已持有的任何锁，使数据库连接恢复干净状态；
2. **退避机制 (Exponential Backoff with Jitter)**：
   - 冲突意味着当前系统存在写入热点；若所有失败连接立即同频重试，只会引发更猛烈的锁风暴；
   - 必须引入指数退避（如第 $k$ 次重试等待 $2^k \times \text{base}$ 毫秒）并叠加随机抖动；
3. **在事务边界重启，重新读取最新状态**：
   - 重试不是重试那一条失败的 `UPDATE` 语句，而是重试**整笔事务**（从 `BEGIN IMMEDIATE` 重新开始）；
   - 必须重新读取最新的业务数据，基于最新状态重新判断业务条件；
4. **幂等性令牌防重保证 ($f(f(x)) = f(x)$)**：
   - 客户端可能因为网络抖动、重试超时等原因重复发送同一笔请求；
   - 事务内部通过查询并插入唯一的 `idempotency_token`，确保重复请求直接幂等跳过，坚决杜绝“重试导致扣款两次”的灾难。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 幂等性数学定义：$f(f(x)) = f(x)$，即任意多次执行对系统状态产生的副作用与执行一次完全一致；
   - 任何重试逻辑都必须预设有限的重试预算（Max Retries / Timeout），防止系统在持久性故障中陷入自旋耗尽资源；
   - 错误必须精确分类：只有瞬态并发冲突（如锁争用）才具备重试价值；语法错误、业务约束破坏（如余额不足、外键违规）属于非瞬态错误，必须立刻失败（Fail-Fast），绝不可盲目重试。
2. **具名引擎实证 (Named Engine Evidence - SQLite 3.x)**：
   - `BEGIN IMMEDIATE` 能够消除同一数据库上的读写锁升级碰撞，但它将写操作串行化，从而限制了写入并发度；
   - `BEGIN IMMEDIATE` 本身在获取起始写锁时依然可能遭遇繁忙冲突（如果已有其他活跃写者），因此**绝不可宣称“使用了 BEGIN IMMEDIATE 写入就永远不会失败”**；
   - SQLite 忙处理超时（`busy_timeout`）是驱动层的等待机制，超时耗尽后仍会返回 `SQLITE_BUSY`。
3. **易变当前实践 (Current Practice & Distributed Patterns)**：
   - 在微服务与分布式存储中，幂等令牌（Idempotency Key）广泛应用于支付网关与分布式订单系统（如 Stripe API）；
   - 指数退避加抖动（Full Jitter）是网络与并发重试的标准工程实践。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验：盲目重试非瞬态约束错误
尝试编写一段错误的重试逻辑，在遇到任何异常时都不加区分地重试：
```python
# 致命错误示范：对业务约束失败进行重试
for attempt in range(5):
    try:
        conn.execute("BEGIN IMMEDIATE;")
        # 故意发起透支操作，严重破坏 CHECK 约束
        conn.execute("UPDATE accounts SET balance = -50 WHERE id = 'A';")
        conn.execute("COMMIT;")
        break
    except Exception as e:
        conn.execute("ROLLBACK;")
        time.sleep(0.1) # 毫无意义地盲目重试不可恢复的逻辑错误！
```
1. **观察现象**：
   - 系统无谓地重试了 5 次，每次都精确抛出 `IntegrityError: CHECK constraint failed`，白白耗费 CPU 与时间；
2. **机理剖析**：
   - 重试只能修复**由于外部并发时序造成的瞬态冲突**（Transient Conflicts）；
   - 语法错误、模式约束违背、数据非法等属于**确定性非瞬态错误**（Non-Transient Errors），必须立刻终止并向上层报错（Fail-Fast）。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“只要加了 `BEGIN IMMEDIATE`，我的写入操作就绝对不会遇到锁冲突而失败。”**
  - **纠正**：`BEGIN IMMEDIATE` 仅消除了“由读升写”时的内部交错死锁风险；如果当前已经有另一个活跃事务占有了写锁，`BEGIN IMMEDIATE` 本身在起步时就会立刻遭遇 `SQLITE_BUSY`。
- **谬误 2：“遇到写入失败，只需要在原来的连接上把最后那条失败的 SQL 重新执行一遍就行。”**
  - **纠正**：发生冲突后，事务上下文已经破损，且底层数据可能已被并发事务更改。必须先显式 `ROLLBACK`，然后从事务起始边界（`BEGIN IMMEDIATE`）重新启动，并重新读取最新数据。
- **谬误 3：“重试的次数越多越好，设置重试 100 次一定能保证成功。”**
  - **纠正**：在持续的高争用负载下，过度重试会引发重试风暴（Retry Storm），使系统雪崩。必须限制重试预算，并在持续超时后启动降级或熔断机制。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
为什么在 SQLite 中两个并发连接都使用默认的 `BEGIN DEFERRED` 先读后写极易引发 `SQLITE_BUSY`？改用 `BEGIN IMMEDIATE` 为什么能解决这一碰撞？

<details>
<summary>Hint 1</summary>
思考 `BEGIN DEFERRED` 在执行 `SELECT` 时获取的是什么类型的锁？多个连接可以同时持有该锁吗？
</details>

<details>
<summary>Hint 2</summary>
当两连接都持有共享读锁时，随后各自尝试执行 `UPDATE`，它们需要把锁升级为什么状态？升级能成功吗？
</details>

<details>
<summary>Expected Observation</summary>
两连接都持有了共享读锁，双方在升级互斥写锁时彼此阻碍，立即导致锁升级碰撞并返回 busy 冲突。
</details>

<details>
<summary>Full Explanation</summary>
在 SQLite 回滚日志架构下，`BEGIN DEFERRED` 初始不加锁，第一条 `SELECT` 会获取共享读锁（SHARED）。如果连接 1 和连接 2 都处于该状态，随后连接 1 执行 `UPDATE` 尝试升级为预留写锁（RESERVED），而连接 2 也同样尝试升级，或者由于连接 2 持有读锁导致连接 1 无法获取最终写入所需的排他锁（EXCLUSIVE），双方发生升级碰撞并返回 `SQLITE_BUSY`。使用 `BEGIN IMMEDIATE` 后，事务在第一条语句就直接获取 RESERVED 锁，从而把所有写意图在最前端串行化，消除了读后升级碰撞。但这限制了写并发，且必须搭配“显式回滚 + 边界退避重试”才能优雅应对其他活跃写者的瞬态竞争。
</details>

## 17. 严格推论边界 (Exact Inference Limits)

- `BEGIN IMMEDIATE` 规避了“读后升写”的内部碰撞，**但以牺牲写入并发度为代价**；严禁将其误解为“保证并发吞吐量最大化的通用银弹”；
- 事务边界重试仅能解决**瞬态并发锁冲突**，**绝不能解决程序自身的语法、模式、约束违规或业务逻辑缺陷**；
- 本实验所演示的本地幂等令牌机制，在分布式多节点无共享存储架构下，**必须依赖分布式协调锁或外部全局键值存储才能成立**。
