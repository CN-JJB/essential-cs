# L14-01｜什么是事务：状态转换、原子性与崩溃恢复的物理边界

## 1. 学习者核心问题 (Learner Question)

> “如果一个程序在两账户之间转账转到一半时突然崩溃或断电，数据库如何做到要么全做、要么全不做？事务的底层物理机制究竟是什么，它和简单的文件覆写有什么本质区别？”

在日常编程中，许多开发者把数据保存想象为“打开文件、写入新数据、关闭文件”。但现实中的业务操作往往包含多个逻辑步骤（例如“从账户 A 扣除 100 元，并向账户 B 增加 100 元”）。如果系统在执行完第一步之后、执行第二步之前突然崩溃，这笔钱难道就会凭空消失吗？

本课通过 SQLite 的具名回滚日志（Rollback Journal）物理机制，实测观察事务边界（`BEGIN`、`COMMIT`、`ROLLBACK`）、状态机变迁与崩溃恢复过程，建立起从“业务不变式”到“底层日志记录与崩溃恢复边界”的扎实系统心智模型。

## 3. 机制模型 (Mechanism Model)

### (1) 状态转换与不变式保持 (State Transitions & Invariants)
一个数据库系统在时刻 $t$ 的状态可表示为持久化存储中的一组数据集合。
- **合法状态与不变式**：在转账场景中，系统声明**业务不变式**：所有账户的总余额恒定（$\sum \text{balance} = 1000$）。
- **事务执行的瞬态与稳态**：
  - 稳态 $S_0$：$\text{balance}_A = 600, \text{balance}_B = 400$，不变式成立（总和 1000）；
  - 瞬态（内存/未提交状态）：从 A 扣除 100 后，$\text{balance}_A = 500, \text{balance}_B = 400$。此时总和为 900，不变式在易失性执行上下文中被破坏；
  - 稳态 $S_1$：向 B 增加 100 后，$\text{balance}_A = 500, \text{balance}_B = 500$。不变式恢复成立（总和 1000）。
- **事务边界的核心价值**：对外只暴露稳态（$S_0$ 或 $S_1$），中间破损的瞬态对其他观察者不可见；若中途发生故障，系统必须能够完全回退至 $S_0$。

```
稳态 S0 [不变式成立: 总额 1000]
   │
   ▼ BEGIN (开启事务边界)
[瞬态执行: 扣除 A 100 -> 内存总额 900 (不变式暂时破坏)]
   │
   ├─────────────┬────────────────────────────────┐
   ▼             ▼                                ▼
正常完成:        遇到错误: 显式 ROLLBACK          进程崩溃 / 强制中断
[增加 B 100]           │                                │
   │                   ▼                                ▼
   ▼ COMMIT      回滚至稳态 S0                   重启数据库检测未决日志
[持久化至 S1]     [总额恢复 1000]                  自动恢复至稳态 S0 [总额恢复 1000]
```

### (2) SQLite 具名实现：回滚日志 (Rollback Journal in DELETE Mode)
SQLite 在默认的 `DELETE` 日志模式下，采用的是典型的 **Undo 日志** 机制：
1. **写前保留原始页 (Preserve Before In-place Update)**：在修改数据库文件中的任何数据页之前，SQLite 必须先将这些页面在磁盘上的原始旧数据拷贝并写入一个独立的伴生文件 `<db>-journal`（回滚日志）；
2. **就地修改 (In-place Mutation)**：原始页面安全写入日志文件并落盘后，SQLite 才在数据库主文件中直接修改数据页；
3. **提交与清理 (Commit via Journal Invalidation)**：当发出 `COMMIT` 命令时，SQLite 确认所有修改已就位，随后删除或清空 `<db>-journal` 文件。一旦日志文件被删除，这次事务即视为成功提交；
4. **崩溃后恢复 (Recovery on Reopen)**：如果进程在修改主文件后、删除日志文件前异常退出，数据库文件中会遗留部分被修改的脏数据。当下一次任意连接打开该数据库文件时，SQLite 发现存在残留的 `<db>-journal`（热日志，Hot Journal），便会自动读取日志中的原始页并将它们写回主数据库文件，撤销所有未完成修改，随后清理该日志文件。

### (3) 对比机制：预写式日志 (Write-Ahead Logging / WAL)
WAL 模式是另一种主流的日志机制（采用 Redo 思想）：
- 事务修改并不直接覆盖主数据库文件，而是顺序追加到 `<db>-wal` 文件中；
- 读者读取时同时参考主数据库与 WAL 日志；
- 稍后通过 Checkpoint（检查点）操作，周期性地把 WAL 中的新版本数据批量刷回主文件；
- **注意**：WAL 模式是性能与并发权衡的现代备选，本课程的 Required 基准严格确立为经典的 **Rollback Journal (`DELETE` 模式)**。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 事务保证多步骤操作的原子性（All-or-Nothing）；
   - 业务正确性依赖于应用声明的不变式；数据库引擎提供事务边界机制，但不替应用程序判断业务数字本身的现实合理性；
   - 任何崩溃恢复算法都依赖于在修改未定数据之前，先行持久化恢复凭据（Write-Ahead Logging / Journaling 核心不变式）。
2. **具名引擎实证 (Named Engine Evidence - SQLite 3.x)**：
   - 在 `PRAGMA journal_mode = DELETE;` 下，未提交修改时磁盘上可观察到 `<db>-journal` 文件的存在；事务提交或回滚后该文件被删除；
   - 事务的主文件同步行为受 `PRAGMA synchronous` 影响（如 `FULL`、`NORMAL`、`OFF`）；
   - 回滚日志是 SQLite 的具体实现机制，不可外推为所有数据库引擎的普适规律（例如 PostgreSQL 采用基于 MVCC 的追加与 WAL，不使用单独的 Undo 回滚日志文件）。
3. **易变当前实践 (Current Practice & Hardware Realities)**：
   - 客户端进程被 `kill -9` 终止后成功回滚，只能证明“客户端崩溃恢复能力”，绝不等同于“物理掉电安全性”；
   - 真实掉电时的持久性受操作系统的文件系统缓存策略、硬盘硬件板载易失性写缓存（Disk Write Cache）以及断电保护电容（PLP）共同制约。

### 实践步骤：
1. **初始化与不变式基线审查**：
   - 脚本在 `PRAGMA journal_mode = DELETE;` 下初始化 `accounts` 表；
   - 检查基线状态 $S_0$：Account A = 600, Account B = 400，总余额 1000。
2. **模拟转账中途失败并显式回滚**：
   - 开启事务 `BEGIN IMMEDIATE;`，扣除 A 100 元；
   - 此时在内存中 A = 500, B = 400，总额破坏为 900；
   - 观察磁盘上 `<db>-journal` 伴生文件的存在；

   - 开启新事务，从 A 扣除 100 并向 B 增加 100；
   - 执行 `COMMIT;`；
   - 验证两账户余额变为 500 与 500，总额依然保持 1000（稳态 $S_1$）。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验：模拟业务逻辑错误与“伪成功”
编写一段故意绕过事务边界的代码，或在事务中写入错误业务逻辑：
```python
# 错误示范：缺乏事务边界的多步骤写入
conn.execute("UPDATE accounts SET balance = balance - 100 WHERE id = 'A';")
# 此处如果发生异常或断网，B 永远不会被增加，A 的 100 元永久蒸发！
raise RuntimeError("Network Timeout before crediting B")
conn.execute("UPDATE accounts SET balance = balance + 100 WHERE id = 'B';")
```
1. **观察现象**：
   - 数据库中的总余额变成 900，永久破坏了系统不变式；
2. **机理剖析**：
   - 没有事务边界的操作，每一个操作都是孤立的持久化变更；
   - 事务（Transaction）是应用程序与数据库系统签订的契约：应用程序将业务逻辑组织为完整的状态转换单元，数据库保证该单元的全部生效或全部撤销。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“事务能自动保证我的业务逻辑绝对正确。”**
  - **纠正**：事务提供的是技术层面的原子性与隔离性。如果你的代码在事务内写了 `UPDATE accounts SET balance = -999`，且表结构未定义 CHECK 约束，数据库会毫不犹豫地将该错误数字原子地持久化。
- **谬误 2：“只要执行了 ROLLBACK，就意味着数据库做过完整的全盘备份。”**
  - **纠正**：`ROLLBACK` 仅用于撤销**当前活动未提交事务**对数据页所做的修改（基于临时 Undo 日志），它不能替代对已提交历史数据的定期全量备份。
- **谬误 3：“只要代码捕获了异常并成功回滚，就证明数据库抵抗物理断电万无一失。”**
  - **纠正**：客户端进程退出或崩溃时，操作系统内核仍活着，文件系统驱动仍能正常落盘；但如果物理主机突然断电，写缓存未刷盘的数据可能会损坏或丢失。掉电持久性取决于硬件配置与 `fsync` / `PRAGMA synchronous`。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
如果脚本在从账户 A 扣除 100 元后、向账户 B 增加 100 元前被操作系统强制杀死（如 kill -9），下次打开数据库时，SQLite 是如何防止这 100 元凭空消失的？这是否等同于抗物理掉电？

<details>
<summary>Hint 1</summary>
思考在修改主数据库文件的数据页之前，SQLite 的回滚日志机制必须在磁盘上先做什么。
</details>

<details>
<summary>Hint 2</summary>
检查磁盘上的 `<db>-journal` 文件。如果该文件存在且包含有效头部，意味着上一次修改并未完成提交。
</details>

<details>
<summary>Expected Observation</summary>
下次重新打开数据库时，SQLite 发现热日志文件，自动将日志中记录的原始页面覆写回主数据文件，使 A 的余额恢复为原值。
</details>

<details>
<summary>Full Explanation</summary>
SQLite 遵循 Write-Ahead Logging / Undo Journal 不变式：在修改主数据文件之前，必须先将原始页面持久化到回滚日志。如果进程在提交前被强杀，主数据文件虽处于不一致状态，但下次任意连接重新打开数据库时，引擎会检测到遗留的日志文件并执行自动恢复，将原始页面重新写回主库，从而撤销部分完成的修改。但这仅证明了进程级崩溃恢复，若断电导致回滚日志本身未刷新到物理介质，则无法保证数据安全。
</details>

## 17. 严格推论边界 (Exact Inference Limits)

- 本实验基于 SQLite 的回滚日志（`DELETE` 模式），**不可外推为所有数据库都采用相同的文件与锁模型**；
- 显式 `ROLLBACK` 与客户端进程终止测试仅验证**客户端软件故障恢复能力**，**绝不能推论出操作系统内核崩溃或硬件物理断电下的持久性**；
- 真实物理持久性必须结合具体的硬件存储介质、驱动固件缓存策略与 `PRAGMA synchronous` 设置进行单独评测。
