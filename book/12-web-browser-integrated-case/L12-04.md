# L12-04｜执行循环与响应性：事件循环、微任务与卡顿根源（并发预习）

## 学习者问题

你在浏览网页或使用 Web 应用程序时，有时点击按钮页面毫无反应，鼠标指针变成沙漏或旋转光标，整个页面仿佛“冻结”了；几秒钟后，被冻结的页面突然像快进一样一次性响应了刚才的所有点击。

更奇妙的是，有时页面上的文字和输入框明明已经完全卡死，页面角落里的一个 CSS 旋转图标或手指触摸平滑滚动却依然能够丝滑运转！

为什么拥有 8 核甚至 16 核 CPU 的超级电脑，会被网页上短短几行 JavaScript 脚本拖垮？JavaScript 的事件循环（Event Loop）究竟是如何协调任务执行与屏幕画面更新的？

## 为什么重要

在现代系统设计与前端架构中，“响应性（Responsiveness）”是衡量系统交互品质的核心标尺。然而，由于历史概念的模糊和流行文章的误导，许多工程师对浏览器执行机制的认知存在严重偏差：
- **误以为“JavaScript 与浏览器全局单线程”**：忽视了浏览器本身由众多进程（Browser, Renderer, GPU）与大量后台工作线程（Compositor, I/O, Web Workers）组成的真实并发体系；混淆了“Window 代理的渲染主线程单线程”与“整机系统并发能力”；
- **误以为存在机械死板的“一宏任务一微任务一渲染”发条时钟**：将复杂的规范化事件循环调度模型误解为固定死板的齿轮轮转，不知道微任务队列在微任务检查点必须**一次性连续排空（Drain until empty）**，更不知道屏幕渲染是根据屏幕刷新率与页面可见性**按需有条件触发的（Conditional Rendering Opportunity）**；
- **误以为所有屏幕都拥有死板固定的 16.7ms 帧预算**：将 60Hz 传统显示器的刷新间隔作为物理铁律，无法适应当前主流的 90Hz、120Hz 高刷新屏（ProMotion）或可变刷新率（VRR）设备；
- **误以为发生卡顿即是所有动画全部停滞**：不了解渲染主线程与合成器线程（Compositor Thread）的并发协作，不知道哪些 CSS 属性能够绕开主线程卡顿实现流畅动画。

本课是走向并发世界（M15 并发系统）的**领域特定执行模型前哨预习**。本课**不定义**系统级的全局并发概念（`EC-CON-015` 保留给 M15），而是聚焦于 Web 代理环境下的事件循环调度实证。

## Mental Model｜代理作用域下的事件循环与并发协作

首先建立清醒的系统定位：**浏览器的事件循环不是全局统一的大时钟**。本课聚焦 Window/Document 所属的 window-agent / event-loop 语境；多个 Window、agent cluster 与 event loop 的具体关联由 HTML 规范决定，不能简单理解为“每个 Document 独占一个 OS 线程/事件循环”。

```

=========================================================================================

  +---------------------------+   +---------------------------+   +--------------------+

  | (click, keypress, touch)  |   | (setTimeout, setInterval) |   | (Fetch 响应到达)   |
  +---------------------------+   +---------------------------+   +--------------------+
                |                               |                           |
                +-------------------------------+---------------------------+
                                                |
                                                v
                              [ 1. 从任务队列中挑选并执行 1 个任务 ]
                                                |
                                                v
                                  [ 2. 微任务检查点 (Checkpoint) ]
                                  * 完整排空微任务队列 (Drain until EMPTY)
                                  * 包含: Promise.then(), queueMicrotask()
                                  * 若在微任务中继续添加新微任务，会连环吞吐直到彻底清空！
                                                |
                                                v
                           [ 3. 是否存在渲染机会？(Rendering Opportunity) ]
                                                |
                               +----------------+----------------+
                               |                                 |

     (requestAnimationFrame)         (Style -> Layout -> Paint)          |
              |                                 |                        |
              +----------------+----------------+                        |
                               |                                         |
                               +-----------------------------------------+
                                                |
                                                v
                                  [ 4. 继续规范事件循环的后续步骤 / 下一次迭代 ]
```

> 1. 上图只是从 HTML event-loop processing model 中抽出本课相关关系，**不是完整算法**。不要画成“一个任务 &rarr; 一个微任务 &rarr; 一次渲染”的固定时钟；微任务检查点可在规范定义的多个位置发生，rendering opportunity 也由用户代理按条件决定；
> 2. 绝不要声称“JavaScript 全局单线程”：Window 脚本的执行语境与整个浏览器的进程/线程体系不是一回事。

## Mechanism｜任务、微任务与帧预算的真实物理

### 1. 任务（Tasks）与微任务（Microtasks）的严格时序

WHATWG 规范对任务与微任务定义了明确的先后顺序语义：
- **任务（Task，历史曾俗称宏任务 Macrotask）**：
  来自离散任务源的离散工作单元。例如用户的鼠标点击回调、定时器（`setTimeout`）触发的回调、网络数据读取完成事件。
  **关键规则**：事件循环在每一轮循环中，只从候选任务队列中**选择一个任务**执行。
- **微任务（Microtask）**：
  专为更细粒度的异步反应而设计，典型来源包括：
  1. `Promise` 的成功/失败反应（`.then()`, `.catch()`, `await` 恢复点）；
  2. `queueMicrotask(...)` 显式入队；
  3. `MutationObserver` DOM 变动监听。
  **关键规则**：当一个任务执行完成后，引擎会立即触发**微任务检查点（Microtask Checkpoint）**。在此检查点，引擎会循环取出微任务执行，**直到微任务队列完全被清空**。如果在执行微任务的过程中又派生了新的微任务，新微任务会在同一个检查点被继续执行，直到彻底空空如也！

#### 经典时序实验推理
考虑以下经典代码片段：
```javascript
console.log("1_sync");

setTimeout(() => {
  console.log("2_timer");
}, 0);

Promise.resolve().then(() => {
  console.log("3_promise");
});

console.log("4_sync");
```

根据规范执行时序：
1. 主脚本作为一个初始任务启动，同步打印 `1_sync`；
2. `setTimeout(..., 0)` 向定时器任务队列注册一个定时任务（Timer Task）；
3. `Promise.resolve().then(...)` 向微任务队列注册一个反应回调（Microtask）；
4. 同步代码继续执行，打印 `4_sync`；
5. 当前任务结束，立即触发**微任务检查点**！引擎排空微任务队列，打印 `3_promise`；
6. 检查渲染机会（若此时无渲染需求则跳过）；
7. 事件循环进入下一轮，从任务队列中挑选出定时器任务执行，打印 `2_timer`。

**确定的输出顺序**：`1_sync` &rarr; `4_sync` &rarr; `3_promise` &rarr; `2_timer`。

### 2. 渲染机会（Rendering Opportunity）与帧预算

屏幕不会在每次微任务结束后都盲目重绘一次。渲染更新受制于硬件显示器的物理刷新节奏：
- **垂直同步信号（VSync）**：显示硬件按照固定的物理频率扫描像素。在传统的 60Hz 显示器上，屏幕每秒刷新 60 次，相邻两次刷新的物理间隔约为：
  $$\text{Interval}_{60\text{Hz}} \approx \frac{1000\text{ms}}{60} \approx 16.67\text{ms}$$
- **这绝不是自然铁律！**
  在现代 120Hz 电竞屏或移动设备上，物理刷新间隔为：
  $$\text{Interval}_{120\text{Hz}} \approx \frac{1000\text{ms}}{120} \approx 8.33\text{ms}$$
  页面处于后台/不可见状态时，浏览器可以对动画、timer、rendering opportunities 做显著节流或暂停；具体频率与策略是浏览器/平台 current practice，不使用固定 `1Hz` 作为课程常数。
- **渲染机会的触发**：HTML 规范让用户代理在 event-loop processing model 中判断是否存在 rendering opportunity；刷新节奏、文档可见性、rAF 注册、待处理更新与实现调度都会影响是否进入相关更新步骤。rAF、style/layout/paint/compositing 的具体内部执行与是否真的有每一阶段工作都属于实现/页面状态，不能写成“每个任务后固定跑五步”。

### 3. 长任务（Long Task）与 UI 卡顿的物理根源

**Long Tasks API** 当前 Working Draft 使用 50ms 阈值来报告符合其定义的 UI-thread long-task 工作（定义还覆盖 task 后紧随的 microtask checkpoint 等情况）。这是一项性能观测 API 的阈值，不是“超过 50ms 页面必然灾难”的自然定律。本课用 500ms 课程参数只是为了让 jank 易观察：
1. **输入被挂起**：用户的点击、按键事件虽然由操作系统内核捕捉并发送到了渲染进程的 IPC 队列，但因为主线程正在忙于执行死循环，事件循环无法挑选下一个输入任务；
2. **渲染被跳过**：即使硬件 VSync 信号频频到来，主线程也无法运行 rAF 或排版更新，导致显示画面出现掉帧（Drop Frame）或完全卡死；
3. **合成线程的独立运转（Compositor Concurrency）**：
   某些浏览器实现可让已满足 compositing 条件的 `transform` / `opacity` 动画在主线程忙碌时继续由 compositor 路径推进；但图层提升、硬件加速、动画类型与平台都影响结果。课程只能要求记录“可能继续/可能受影响”的实际观察，不能保证 spinner 一定流畅，也不能把它描述成直接操作 GPU 显存的 Web 规范。


浏览器打开打印出的动态端口地址（`http://127.0.0.1:<port>/`）。

### 2. 实验 Demonstration 1：微任务抢先排空验证

- 点击页面上的 **“Run Task/Microtask Test”**；
- 观察控制台与页面输出：
  `Step 1: 1_sync_start` &rarr; `Step 2: 2_sync_end` &rarr; `Step 3: 3a_microtask_promise_1` &rarr; `Step 4: 3b_microtask_queueMicrotask` &rarr; `Step 5: 3c_microtask_promise_chained` &rarr; `Step 6: 4_timer_task (setTimeout 0ms)`；
- **观测结论**：在本 fixture 中，同步代码结束后进入 microtask checkpoint。第一段 Promise reaction 先运行；它完成后才把 chained reaction 入队，因此此前已排队的 `queueMicrotask` 先于 chained reaction 执行。三者都在后续 timer task 之前完成。这个例子同时说明“Promise chain”并不会把后续 reaction 预先插到已有 microtask 前面。

### 3. 实验 Demonstration 2：安全长任务与合成线程并发

- 页面包含两个动态元素：
  1. 由 CSS `animation: spin 2s linear infinite` 驱动的 **compositor-friendly candidate**；是否真正独立合成由实际浏览器决定；
  2. 由 `requestAnimationFrame` 持续自增计数的数字面板（主线程）。
- 点击 **“Block Main Thread (500ms Bounded Loop)”**（受严格安全阈值保护，绝无死循环）：
  - **观测现象**：数字面板的计数器瞬间停滞 500ms（掉帧卡顿），任何按钮点击无法立刻响应；而在许多现代硬件加速浏览器中，旁边的旋转方块依然在平滑旋转！
- 点击 **“Run Chunked Yielding (500ms, 20ms Course Slices)”**：
  - fixture 将名义工作拆成 20ms 课程切片，并在切片之间通过 `setTimeout(doChunk, 0)` 让 event loop 获得处理其他任务/渲染机会的可能；
  - **观测要求**：比较单一长任务与分片方案下的实际交互/计数器表现。分片通常改善可响应机会，但不保证“始终流畅”，实际 wall time 也会因 timer 调度而变化。

<details>
<summary>Full Explanation</summary>
1. <b>卡顿的本质原因</b>：
   在 Window/Document 代理中，JavaScript 执行、DOM 事件调度、样式计算、布局以及 <code>requestAnimationFrame</code> 均受制于渲染主线程（Renderer Main Thread）。事件循环必须等待当前正在运行的任务完全退出，才能处理下一个输入事件或响应屏幕 VSync 刷新信号。一个持续 500ms 的同步计算完全剥夺了事件循环出让给其他任务的可能，导致这半秒内所有用户交互全部发生滞后（Jank）。
2. <b>合成器并发独立性（Compositor Concurrency）</b>：
   浏览器可以把某些动画/滚动工作放在与主线程不同的 compositor 路径上，因此主线程忙碌时并非所有视觉活动都必然停止。但是否发生层提升、是否需要主线程提交新状态、是否使用 GPU 都是实现/运行时条件；`transform`/`opacity` 只是常见的 compositor-friendly 候选，不是“保证永不依赖主线程”的 API 契约。
3. <b>标准工程解法</b>：
   - <b>时间切片与主动让出（Time Slicing & Yielding）</b>：课程 fixture 使用 <code>setTimeout(..., 0)</code> 在有界工作切片间重新排队；这创造其他任务/渲染被调度的机会，但 timer 延迟和切片预算必须实测。若讨论 <code>scheduler.yield()</code>，需标明其可用性/标准化状态而不能当成所有浏览器 Core 前提；
   - <b>Web Worker 卸载</b>：可把适合的 CPU 工作移到 Worker agent，减少 Window 主线程竞争；Worker 在具体浏览器中映射到何种线程/进程是实现细节，且数据传输/同步仍有成本。
</details>

## Common Misconceptions

- **“JavaScript 和整个浏览器都是绝对单线程的。”** 错。浏览器是多进程且高度多线程的体系。即便是单个渲染进程，也拥有 Main Thread、Compositor Thread、Raster Thread、I/O Thread 等众多后台线程。所谓的“单线程”仅是指单个 Window 代理上下文内的用户 JavaScript 脚本默认共享同一个主线程调度循环。
- **“事件循环是僵化机械的‘执行一个宏任务，执行一个微任务，刷一次屏幕’。”** 错。规范明确规定微任务队列在检查点必须被全量清空（可能连续处理几十个微任务）；而渲染更新是条件触发的，只有当硬件刷新时钟到来且页面需要重绘时才会触发，绝非每个任务之后都强制刷屏。
- **“`setTimeout(fn, 0)` 保证在 0 毫秒后立即执行。”** 错。`0` 是请求的 timeout 参数，不是 wall-clock 执行承诺；timer 初始化/嵌套节流、页面状态、当前任务、microtasks 和其他调度都会推迟 callback。课程只要求相对关系，不绑定一个固定 clamp 数字或实际延迟。
- **“只要主线程被长任务卡死，页面上所有 CSS 动画必定全部冻结。”** 错；但反过来也不能保证 `transform` / `opacity` 动画一定流畅。实际是否独立合成以及滚动/动画是否仍需主线程协作，应作为浏览器/平台 observation。

## What You Can Ignore—for Now

- WebAssembly 多线程 SharedArrayBuffer 底层 `Atomics.wait` 与互斥锁在浏览器宿主中的线程挂起机制；
- Chrome 调度器内部对不同输入源（Input Priority vs Timer Priority）实施的任务优先级启发式调优算法；
- V8 垃圾回收器并发标记（Concurrent Marking）与增量清除（Incremental Sweeping）的主线程暂停细节。

## Exit Criteria

- 能按准确顺序叙述 Window 事件循环从任务执行、微任务检查点排空到条件渲染机会的完整决策链条；
- 能独立分析包含同步代码、Promise、`queueMicrotask` 与 `setTimeout` 的代码片段并给出准确的确定性相对时序；
- 能从主线程垄断的角度解释长任务造成 UI 卡顿的底层机理，并指出合成线程动画能够保持独立的系统原因；
- 能说明 16.7ms 帧预算背后的物理假设，并指出高刷屏时代的估算差异。
