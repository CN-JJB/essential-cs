# L12-03｜Web 安全模型：同源策略、CORS 响应拦截与 CSP 纵深防御

## 学习者问题

你在浏览器中打开了网银或邮箱，保持登录状态；紧接着你在另一个标签页打开了一个未知的、甚至带有恶意的网站。为什么这个未知网站上的 JavaScript 代码不能直接读取你在网银标签页中的存款余额或窃取你的身份 Token？

为什么有时候在前端调用一个后端接口，浏览器控制台会弹红报错 `CORS policy violation`，但当你把这个完全相同的 URL 复制到终端用 `curl` 命令去请求时，却能顺畅拿到完整的 JSON 数据？难道 `curl` 能“绕过”后端安全防护？CORS 到底是在保护服务器，还是在保护谁？

## 为什么重要

Web 是人类历史上最大规模的分布式不可信代码执行环境。每当你加载一个网页，你实际上是在本地计算机的沙箱中直接执行来自陌生网络服务器的动态程序。如果不建立坚固严密的安全性防线，整个现代互联网的电子商务、数字身份与隐私体系将彻底崩溃。

然而，在广大工程技术人员中，对 Web 安全模型的误解屡见不鲜，甚至直接导致高危生产事故：
- **颠倒 CORS 的保护对象与职责**：误以为“开启了 CORS 就是给后端加上了安全防火墙”，不知道 CORS 本质上是**浏览器用户代理（User Agent）内部执行的跨源响应访问拦截机制**；对非浏览器客户端（如 Python 脚本、`curl`、攻击者原生爬虫），CORS 根本没有任何拦截能力；
- **混淆源（Origin）三元组与 Cookie 作用域**：误以为 Cookie 的作用域也是由 `scheme + host + port` 决定的，不知道 Cookie 历史悠久的匹配规则默认**完全忽略端口号**并遵循宽松的 `Domain` 和 `Path`，从而在微服务多端口部署时遭遇严重的 Cookie 覆盖或泄露；
- **混淆同源策略（SOP）与跨源资源共享（CORS）**：误以为同源策略是禁止向外源发送 HTTP 请求，不知道在简单跨域请求（Simple Request）中，HTTP 请求实际上已经完整到达了目标后端服务器并得到了执行，只是浏览器拒绝将响应交给 JavaScript 读取；
- **将 CSP 视为免死金牌**：误以为只要配置了 Content Security Policy 就能高枕无忧，忽视了 CSP 是一种**纵深防御（Defense-in-Depth）**策略，无法替代严谨的代码输入清洗和端点授权。

理解 Web 安全模型，就是理解现代操作系统与分布式网络交汇处最复杂的信任边界。本课正式复访核心系统概念：**信任边界（Trust Boundary，EC-CON-017）** 与 **隔离（Isolation，EC-CON-013）**。

## 学习目标

完成本课后，你应能：
- **Explain**：精确定义 Web 平台源（Origin）的三元组模型（`scheme + host + port`）与不透明源（Opaque Origin），并与站点（Site）及 Cookie 独立的作用域规则清晰剥离；
- **Judge**：从**信任边界（EC-CON-017）**角度批判性论述同源策略（SOP）的核心作用：它限制了不可信脚本跨源读取 DOM、存储及受保护响应的能力；
- **Explain**：准确阐述 Fetch CORS 协议的本质——它是**浏览器端执行的资源共享许可协商机制**，而非服务端的访问控制授权（Authorization）；区分简单请求（Simple Request）与预检请求（Preflight OPTIONS）；
- **Observe**：运行 `labs/foundations/m12/cors_fixture.py` 本地双源环境，在浏览器端观测到跨源拦截错误，同时在后端服务日志中验证简单 HTTP 请求已被实际接收，并对比非浏览器终端客户端直接获取响应的边界；在无 GUI 浏览器时如实记录 `NO LIVE BROWSER CORS OBSERVATION`；

## Mental Model｜Web 平台的安全边界拓扑

要彻底理清浏览器安全，必须在头脑中清晰绘制出这幅**三方交互信任拓扑图**：

```
+---------------------------------------------------------------------------------------+
|                                  BROWSER USER AGENT                                   |
|                                                                                       |
|  [ Origin A: http://127.0.0.1:<portA> ]                                               |
|      |                                                                                |
|      | 1. fetch('http://127.0.0.1:<portB>/api/data')                                  |
|      v                                                                                |
|  [ CORS 检查门禁 (Browser Enforcement Checkpoint) ]                                   |
|      | - 检查响应头中的 Access-Control-Allow-Origin 是否包含 Origin A                 |
|      | - 若匹配: 将响应数据解封交付给页面 JavaScript Promise 求解                    |
|      | - 若缺失/不匹配: 拦截响应体! 向控制台抛出 CORS Policy Violation 异常           |
+------|--------------------------------------------------------------------------------+
       |                                              ^
       | 2. 发起 HTTP 请求 (携带 Origin 头)          | 3. 返回 HTTP 响应 (200 OK, 业务数据)
       v                                              |
+---------------------------------------------------------------------------------------+
|  [ Origin B: http://127.0.0.1:<portB> ] (后端目标服务)                                |
|                                                                                       |
|  * 严正注意：在简单请求中，HTTP 请求已经到达 Origin B，数据库操作可能已经执行！       |
|  * 服务端安全底线：必须拥有独立于 CORS 的身份认证与业务鉴权 (Authn / Authz)！          |
+---------------------------------------------------------------------------------------+
       ^                                              ^
       |                                              |
       +--- curl http://127.0.0.1:<portB>/api/data ---+
            (非浏览器客户端: 不运行不可信 Web JS,
             不受浏览器 CORS 响应拦截门禁约束;
             但依然受制于服务端自身的身份鉴权!)
```

> **架构警示**：
> 绝不可给上图加上“curl 必定无条件成功”的片面推论！
> `curl` 只是**不受浏览器的 CORS 响应拦截机制限制**；如果目标服务设置了密码保护、JWT 鉴权或防火墙 IP 白名单，`curl` 同样会被服务端鉴权系统拒绝。

## Mechanism｜源、Cookie、CORS 与 CSP 细部机理

### 1. 源的三元组模型与不透明源

在 WHATWG 标准中，一个 Web 源（Origin）是定义安全沙箱的核心**信任边界（EC-CON-017）**：
- **元组源（Tuple Origin）**：由三个分量唯一确定：
  $$\text{Origin} = (\text{Scheme}, \text{Host}, \text{Port})$$
  若这三项中有任何一项不同，哪怕是在同一台电脑的不同端口上，在浏览器看来都是两个完全不同的源：
  - `http://127.0.0.1:3000` 与 `http://127.0.0.1:4000`：**不同源**（Port 不同）；
  - `http://example.com` 与 `https://example.com`：**不同源**（Scheme 不同，且隐含端口 80 与 443 不同）；
  - `http://example.com` 与 `http://api.example.com`：**不同源**（Host 不同）。
- **不透明源（Opaque Origin）**：
  某些上下文不具备稳定的网络元组源，浏览器为其分配一个内部独一无二的随机标识符（序列化为字符串 `"null"`）。例如通过 `data:` URL 载入的文档，或者配置了 `<iframe sandbox>` 且没有声明 `allow-same-origin` 的子框架。不透明源无法与任何其他源（包括其他不透明源）发生同源匹配。

### 2. 同源策略（SOP）与 Cookie 独立规则的决裂

同源策略（Same-Origin Policy, SOP）是浏览器对 DOM 树、`localStorage`、`sessionStorage`、`indexedDB` 以及网络响应访问施加的核心规则。

**关键陷阱：Cookie 规则完全不属于 SOP！**
许多开发者误以为 Cookie 也是按源三元组隔离的。事实是：
1. **Cookie 默认忽略端口号**：由 `http://example.com:8080` 设置的 Cookie，会被浏览器自动发送给 `http://example.com:9000`，甚至在没有 `Secure` 属性时发送给 `https://example.com`！
2. **Cookie 依赖 Domain 与 Path**：如果一个服务在 `.example.com` 上设置了 Cookie，所有子域名（`api.example.com`、`mail.example.com`）在符合 Path 时都会带上该 Cookie；
3. **Cookie 的安全属性**：
   - `HttpOnly`：禁止页面 JavaScript 通过 `document.cookie` 访问，防范 XSS 窃取会话凭证；
   - `Secure`：要求仅在 HTTPS 连接中传输；
   - `SameSite`：控制在跨站请求（Cross-Site）时是否自动携带该 Cookie（`Strict`、`Lax`、`None`）。

### 3. Fetch CORS：跨源资源共享与预检请求

当你从 `Origin A` 发起 `fetch('http://127.0.0.1:<portB>/api/data')` 时，浏览器是如何处理的？

#### 情况 A：简单请求（Simple Request）
如果请求方法是 `GET`、`HEAD` 或 `POST`，且 HTTP 请求头仅包含 CORS 安全列表项（如 `Accept`, `Accept-Language`, `Content-Language`，以及限制类型的 `Content-Type`），浏览器将其判定为简单请求：
1. 浏览器直接发出网络请求，并在请求头中强制附加：`Origin: http://127.0.0.1:<portA>`；
2. **目标服务器实际接收并处理了该请求**；
3. 服务器返回 HTTP 响应。此时浏览器拦截住响应报文，检查响应头中的 `Access-Control-Allow-Origin`（ACAO）：
   - 若 ACAO 值为 `*` 或精确等于 `http://127.0.0.1:<portA>`，浏览器放行，JavaScript 的 `fetch` Promise 成功拿到数据；
   - 若没有 ACAO 或值不匹配，**浏览器销毁响应体，在控制台抛出 CORS 错误**。

> **警醒**：简单请求意味着如果接口是执行转账或删除数据的 `POST`，即使浏览器最终报错拦截了响应，**后端的删除操作可能已经执行完成了**！因此后端修改状态的接口必须依靠 CSRF Token 或凭据校验，绝不能依赖 CORS。

#### 情况 B：预检请求（Preflighted Request）
如果请求包含了自定义请求头（如 `X-Course-Custom: 123`）或使用了非简单方法（如 `PUT`、`DELETE`），浏览器为了保护未适配 CORS 的老旧后端，会在真正请求发出前**先发送一个探测预检包**：
1. 浏览器向目标地址发送一个 `OPTIONS` 方法请求，携带：
   - `Origin: http://127.0.0.1:<portA>`
   - `Access-Control-Request-Method: POST`
   - `Access-Control-Request-Headers: x-course-custom`
2. 服务器如果认可该跨源请求，必须返回 `200` 或 `204`，并带上许可头：
   - `Access-Control-Allow-Origin: http://127.0.0.1:<portA>`
   - `Access-Control-Allow-Methods: GET, POST, OPTIONS`
   - `Access-Control-Allow-Headers: X-Course-Custom, Content-Type`
3. 预检请求通过后，浏览器才正式发送真正的业务请求；若预检被拒，真正的业务请求根本不会被发出！

### 4. 内容安全策略（CSP Level 3）：纵深防御

CSP（Content Security Policy，目前处于 **W3C Working Draft** 阶段，以 2026 年 8 月最新工作草案为基准）是服务端通过 HTTP 响应头向浏览器宣告的客户端安全策略：
- **典型指令**：
  `Content-Security-Policy: default-src 'self'; script-src 'self' https://trustedscripts.example.com; object-src 'none'`
- **纵深防御原理**：
  即使页面存在 XSS 漏洞，被黑客注入了一段 `<script src="http://evil.com/steal.js">`，受制于 CSP 策略，浏览器解析到该标签时也会坚决拒绝向 `evil.com` 发起网络请求；同时也能限制内联脚本（`unsafe-inline`）的执行。
- **边界**：
  CSP 是一道强大的纵深减损防线，但绝不能推导出“有了 CSP 就完全无需防范 XSS”的结论。宽松的策略（如随意开启 `unsafe-eval`）依然会留下破绽。

## Hands-on｜受控本地实验：双源 CORS 边界与终端对比

在本课配套的 `labs/foundations/m12/cors_fixture.py` 中，我们构建了纯原生的双源实验环境。

### 1. 运行本地双源服务

```bash
python labs/foundations/m12/cors_fixture.py
```

终端将打印动态分配的两个源地址：
- `Origin A: http://127.0.0.1:<portA>/`（客户端前端网页）
- `Origin B: http://127.0.0.1:<portB>/`（API 后端服务）

### 2. 核心实验观察项

1. **浏览器中的跨源拦截（Action 1）**：
   - 在支持的浏览器中打开 `http://127.0.0.1:<portA>/`；
   - 点击“Action 1: Simple Fetch without CORS”；
   - **现象**：页面捕获到错误，浏览器控制台打印跨源阻止红字。
2. **后端服务真实到达证据**：
   - 点击页面上的“Inspect Origin B Request Log”；
   - **现象**：你会惊奇地发现，Origin B 的服务器日志中清晰记录下了这条请求的到来（记录了 HTTP GET、路径与 `Origin` 头）！这证明了简单请求确实到达了后端，是浏览器在客户端卡住了响应。
3. **授权跨源放行（Action 2）**：
   - 点击“Action 2: Authorized Fetch”；
   - **现象**：Origin B 返回了 `Access-Control-Allow-Origin: http://127.0.0.1:<portA>`，JavaScript 顺利拿到 JSON 数据并在页面渲染。
4. **终端非浏览器对比**：
   - 在终端使用 Python 脚本或 `curl` 直接请求该地址：
     ```bash
     curl -v "http://127.0.0.1:<portB>/api/data?mode=unauthorized"
     ```
   - **现象**：命令行客户端不受任何阻碍，直接打印出完整的 JSON 响应体！

## Checkpoint Investigation

### Question

在上述受控本地实验中，当浏览器运行的 JavaScript 向 Origin B 发起简单请求时被判定为 CORS 错误，为什么使用终端命令行工具（如 `curl`）却能成功收到 Origin B 返回的完整响应数据？这是否意味着“`curl` 可以无条件绕过服务器的所有安全防护”？

<summary>Hint 1</summary>
思考 CORS 机制究竟是由谁来强制执行的：是 Origin B 的网络网卡，还是你的本地浏览器引擎？
</details>

<details>
<summary>Hint 2</summary>
命令行客户端（如 curl）会像浏览器一样运行页面里未经用户审查的恶意第三方脚本吗？curl 收到响应后，服务器的原生鉴权（账号密码、Token）还在起作用吗？
</details>

<details>
<summary>Expected Observation</summary>
浏览器控制台显示跨源安全策略拦截错误，脚本无法读取数据；而命令行 curl 能够直接输出该端点的 HTTP 状态码 200 和响应内容。这证实了 CORS 是浏览器用户代理在受信任客户端环境中强加的响应过滤契约，绝不等于服务器在 TCP/HTTP 网络层对请求做出的拒绝。同时，curl 绝非“无条件成功”，如果该端点要求认证头或 Cookie，curl 未携带凭证同样会失败。
</details>

<details>
<summary>Full Explanation</summary>
这是一个在全栈架构中关于<b>信任边界（EC-CON-017）</b>的关键辨析：
1. <b>CORS 是用户代理（浏览器）施加的防御契约</b>：
   浏览器是一个多租户运行环境，用户在一个标签页的登录凭证可能被另一个恶意网页的脚本所利用（如 CSRF 或未授权数据窥探）。为了防止网页脚本擅自读取其他站点的私密数据，浏览器规定：跨源响应必须得到目标服务器的显式 CORS 授权头（ACAO），否则浏览器拒绝将响应体喂给 JavaScript 代码。
2. <b>非浏览器客户端的执行语境完全不同</b>：
   终端中的 <code>curl</code> 是一个独立的命令行工具，它不运行任何不受信任的网页第三方 JavaScript，不存在“某个恶意网页借用 curl 偷窥另一个网页”的执行上下文。因此，<code>curl</code> 既没有实现、也不需要执行浏览器的跨源响应过滤逻辑，它自然会把网络上收到的所有字节原样打印出来。
3. <b>严厉纠正“curl 无条件绕过一切”的谬论</b>：
   绝不能宣称“curl 绕过了服务器安全”。在我们的实验端点中，Origin B 本身是一个公开提供数据的 HTTP 接口。如果 Origin B 是一个需要 Cookie、API Key 或 Bearer Token 的受保护资源，使用 <code>curl</code> 发起未携带凭证的请求同样会被服务端直接返回 <code>401 Unauthorized</code> 或 <code>403 Forbidden</code>。CORS 保护的是浏览器的脚本执行环境，而服务器的自身安全必须由服务端的认证与授权机制独立捍卫。
</details>

## Common Misconceptions

- **“CORS 是保护后端服务器免受黑客攻击的安全特性。”** 错。CORS 保护的是**在浏览器中冲浪的终端用户**，防止恶意站点在用户的浏览器中通过脚本读取用户在其他站点的私密数据。对于脱离浏览器的黑客脚本或自动化爬虫，CORS 毫无防范能力。
- **“浏览器显示 CORS 报错，说明这个网络请求根本没有发出去。”** 错。对于非预检的简单请求（Simple Request），请求已经在网络线缆上发出，且已经完整到达了目标服务器并被处理，只是服务器返回的响应头中没有合格的 ACAO，导致浏览器在交付给 JS 的最后一刻将其扣下。
- **“源（Origin）和域名（Domain）是同一个概念。”** 错。源是一个包含了协议、主机与端口的三元组。`http://localhost:3000` 与 `http://localhost:4000` 是两个完全隔离的源。
- **“站点隔离（Site Isolation）取代了同源策略（SOP）。”** 错。SOP 依然是 Web 平台顶层的逻辑访问控制规则；Site Isolation 是 Chromium 底层通过操作系统独立进程（OOPIF）对不同站点进行物理内存隔离的纵深防御实现。

## What You Can Ignore—for Now

- WebCrypto API 细粒度非对称非对称公钥证书密钥派生操作；
- Cross-Origin Opener Policy (COOP) 与 Cross-Origin Embedder Policy (COEP) 启用底层 SharedArrayBuffer 内存共享的复杂头部配对细节；
- Trusted Types API 在 DOM XSS 防护中的策略对象编译。

## Exit Criteria

- 能准确写出源（Origin）的三元组构成，并举例说明为什么不同端口的 localhost 属于不同源；
- 能透彻说明 Cookie 的作用域规则为什么独立于 SOP，指出其忽略端口号的潜在风险；
- 能以端到端时序图说明简单请求与预检请求（Preflight OPTIONS）的流转过程，并解释为什么简单请求被 CORS 拦截不等于请求未到达服务端；
- 能从信任边界（EC-CON-017）解释为什么 `curl` 能拿到未经 ACAO 授权的响应，同时反驳“`curl` 可以绕过服务端鉴权”的错误观点。

## Competency Mapping

- **Primary**: **Judge** (批判性辨析浏览器客户端安全门禁与服务端独立鉴权的信任边界)
- **Growth**: **Diagnose** (准确定位并排查跨源调用失败、预检头缺失及 Cookie 跨站丢失的根本原因)
