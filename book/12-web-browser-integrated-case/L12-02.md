# L12-02｜文档渲染流水线、排版与脚本加载调度

## 学习者问题

当你在浏览器中输入一个网址，几百毫秒后屏幕上呈现出图文并茂、具有精美排版和动画效果的网页。在这个极短的瞬间，从网络接收到的原始 HTML、CSS 与 JavaScript 文本字节流，是如何一步步蜕变为屏幕上每个像素点（Pixels）的？

为什么有时候在 `<head>` 中引入一段外部脚本，整个页面就会“白屏”卡住迟迟不显示内容？`defer`、`async` 与普通的 `<script>` 标签究竟在底层引擎的解析时序上有什么根本区别？浏览器的主线程与 GPU 合成线程又是如何协作分工的？

## 为什么重要

在前端开发与大型 Web 系统架构中，页面首屏加载速度与交互流畅度直接决定了产品的用户留存与商业成败。然而，许多开发者将浏览器渲染引擎视作一个瞬间完成转换的黑盒，由此引发了大量性能与排障误区：
- **混淆概念模型与引擎真实物理实现**：把教科书上的“DOM + CSSOM = 渲染树”当成所有浏览器内部唯一的物理数据结构，不理解现代引擎（Blink、Gecko、WebKit）高度复杂的增量更新与失效缓存优化；
- **误以为任何 DOM 修改都会重绘整张网页**：认为页面上哪怕修改一个字符的颜色，浏览器也要从头到尾对整张网页重新执行排版与绘制，不知道现代渲染引擎只对发生脏标记（Dirty Bit）的局部子树执行重排与图层重组；
- **混淆脚本加载特性的执行语义**：分不清经典外部同步脚本、`defer`、`async` 以及 ES Module 的本质区别，或者盲目宣称“加了 `defer` 就必定能先看到首屏绘制（FCP）”，忽略了不同网络条件和资源大小下的渲染机会竞争；
- **混淆主线程与合成线程的分工边界**：不知道样式计算、排版、主绘制（Paint）与 JavaScript 共享同一个渲染主线程，而图层滚动、透明度渐变与平移缩放可以被下沉到独立的 Compositor / GPU 线程高效并发执行。

掌握概念渲染流水线与脚本加载调度机制，是构建高性能 Web 系统和诊断渲染卡顿的必修课。本课正式复访核心系统概念：**接口（Interface，EC-CON-005）**。

## Mental Model｜概念渲染流水线与工程优化

请务必注意：下方的渲染流水线是一套**帮助人类理解转换阶段的概念流水线（CONCEPTUAL PIPELINE）**。真实世界的现代浏览器引擎（如 Chromium 的 Blink、Firefox 的 Gecko、Safari 的 WebKit）并不会机械地把整页数据一次性全量穿透这六个阶段，而是高度依赖增量计算、图层缓存、视口裁剪与管道化并行优化。

```
=========================================================================================
CONCEPTUAL PIPELINE — 概念文档渲染流水线 (非全部跨浏览器内部物理统一实现)
=========================================================================================

 1. [HTML 字节流] ---> Tokenizer / HTML Parser -------------> [DOM 树 (内存对象模型)]
                                                                      |
 2. [CSS 字节流]  ---> CSS Parser -------------------------> [CSSOM 树] |
                                                                      |
                                                                      v
 3. [样式计算 (Style Resolution)] <-----------------------------------+
    * 级联规则 (Cascade)、选择器匹配 (Selector Matching)
    * 输出: [排版树 (Layout Tree / Computed Styles)]
            |
            v
 4. [排版布局 (Layout / Reflow)]
    * 计算每个可视元素的几何尺寸与相对视口坐标 (X, Y, Width, Height)
    * 输出: [几何盒子模型 (Box Model)]
            |
            v
 5. [图层与绘制 (Paint)]
    * 确定绘制顺序 (Stacking Context, Z-Index)，生成绘制指令
    * 输出: [显示列表 (Display Lists / Skia Draw Calls)]
            |
            v
 6. [图层合成与光栅化 (Compositing & Rasterization)]
    * 由 Compositor 线程将页面切分成图块 (Tiles) 并下发给 GPU 光栅化
    * 输出: [屏幕物理像素帧 (Screen Framebuffer)]
=========================================================================================
```

### 1. 概念六阶段深度剖析

1. **HTML 解析与 DOM 构建（Document Object Model）**：
   - 渲染引擎的 HTML 解析器将网络接收到的网络字节流根据编码（如 UTF-8）转换为字符，随后经过分词器（Tokenizer）将字符转化为 Tag Token（例如 `StartTag: html`, `StartTag: body`, `Character`, `EndTag`）；
   - 词法 Token 经过树构建器（Tree Construction）在内存中实例化为由 C++ 对象构成的树状层次结构——**DOM 树**。DOM 既是网页内容的内部表示，也是暴露给 JavaScript 的操作**接口（EC-CON-005）**。
2. **CSS 解析与 CSSOM 构建（CSS Object Model）**：
   - 当遇到 `<style>` 标签或 `<link rel="stylesheet">` 时，CSS 解析器解析样式规则，生成带有继承和层叠规则的 CSSOM 树。
3. **样式计算（Style Resolution）**：
   - 引擎将 DOM 树与 CSSOM 树结合，遍历 DOM 节点并计算出最终适用于该节点的全部样式（Computed Styles）；
   - 注意：`display: none` 的节点不会进入后续的排版树，而 `<head>` 及其子元素默认也不参与可视渲染。
4. **排版布局（Layout / Reflow）**：
   - 拥有计算样式的节点需要确定其在设备视口中的空间几何信息。Layout 阶段根据 CSS 盒模型（Box Model）、Flex/Grid 规则和浮动等算法，计算出每个框（Box）的绝对坐标与像素尺寸。
5. **绘制（Paint）**：
   - 知道元素的位置还不等于画出了它。Paint 阶段遍历排版树，根据 CSS 的层叠上下文（Stacking Context）、`z-index` 以及绘制顺序，将视觉属性拆解为一系列绘制调用序列（如“先绘制背景色，再绘制边框，再绘制文本”），生成**显示列表（Display List）**。
6. **图层合成（Compositing）**：
   - 现代引擎绝不会在每次更新时全量重画整个位图。渲染主线程将页面划分为多个独立的**图层（Layers）**；
   - 主线程将图层及其绘制指令提交给 **Compositor 线程**；Compositor 线程将图层划分为图块（Tiles），并调度 GPU 进行快速硬件光栅化（Rasterization），最终将处理好的纹理（Textures）直接合成为一帧输出到屏幕显示缓冲区。

## Mechanism｜脚本加载对流水线的阻塞与调度

在整个流水线中，最大的“交通堵塞”往往来自于 JavaScript 脚本的引入。

```
HTML 解析时序对比：

1. 经典同步外部脚本 (Classic Synchronous Script):
   HTML 解析 ---> [暂停解析!] ==========================> 恢复解析 ---> DOM 完成
                   (网络下载 JS) ---> (执行 JS)

2. 经典 defer 脚本 (<script defer>):
   HTML 解析 ---------------------------------------------> DOM 完成 ---> 执行 defer 脚本
      (并行网络下载 JS) ----------------------> (完成下载，挂起等待)

3. 经典 async 脚本 (<script async>):
   HTML 解析 -----------------> [暂停!] ---> 恢复解析 ---> DOM 完成
      (并行网络下载 JS) --------> (执行 JS)
```

### 1. 为什么同步脚本是“Parser-Blocking”的？

当 HTML 解析器在解析文档流时遇到一个没有 `defer` 或 `async` 属性的经典 `<script src="...">` 标签时，解析器**必须立即暂停对后续 HTML 字符的解析**：
- **底层原因**：JavaScript 拥有强大的能力，它可以通过 `document.write(...)` 动态向当前未完成的文档流中写入新的 HTML 标签，或者立即调用 DOM API（如 `document.getElementById`）查询或修改刚建好的节点；
- **阻塞代价**：浏览器必须先等待该脚本通过网络完整下载，随后交由 V8 引擎编译并执行完毕，确认文档流没有被破坏，解析器才能继续向下解析后续的 HTML 标签；
- **优化机制（预解析器 Preload Scanner）**：现代引擎在后台运行一个轻量级预扫描器，在主解析器阻塞时提前扫描后面的 `<link>` 和 `<script>` 发起并发网络下载，但这只能缩短网络下载重叠时间，并不能解除同步脚本执行时的解析阻塞。

### 2. 脚本加载特性的精确语义对比

| 脚本声明方式 | 网络下载时机 | 执行时机与解析器关系 | 执行顺序保证 | 适用场景 |
|---|---|---|---|---|
| **经典同步脚本**<br>`<script src="...">` | 遇到标签时立即阻塞发起（受预解析器辅助提前下载） | **立刻执行**；执行期间彻底暂停 HTML 解析器。 | 严格按在 HTML 中出现的先后顺序执行。 | 强依赖即时执行、必须在后续 DOM 构建前生效的基础引导脚本。 |
| **经典 defer 脚本**<br>`<script defer src="...">` | 与 HTML 解析完全并行异步下载 | **等待 HTML 解析完全结束**、在 `DOMContentLoaded` 事件触发前执行。 | **严格按在 HTML 中声明的顺序执行**。 | 依赖完整 DOM 结构、或者多个脚本之间存在前后依赖的业务主逻辑。 |
| **经典 async 脚本**<br>`<script async src="...">` | 与 HTML 解析完全并行异步下载 | **一旦下载完毕立即执行**；如果此时 HTML 还在解析，则强行暂停解析执行脚本。 | **乱序（先下完先执行）**，不保证顺序。 | 独立、与 DOM 上下文及其他脚本完全无依赖的第三方统计/埋点脚本。 |
| **ES 模块脚本**<br>`<script type="module" src="...">` | 异步并行下载整个模块依赖图 | **默认具备类似 defer 的行为**（等待解析完成后按顺序执行）；若显式添加 `async` 则按 async 规则执行。 | 模块图拓扑排序。 | 现代原生模块化应用脚本。 |

> **关键推断边界（Negative Guardrail）**：
> 绝不要妄称“使用 `defer` 就必定能保证首屏绘制（First Contentful Paint, FCP）优先发生”。
> 虽然 `defer` 将脚本执行移出了关键解析路径，但 FCP 的发生取决于样式表加载完成、首屏 DOM 节点到达、字体加载以及引擎自适应的绘制调度机会。`defer` 保证的是不阻塞 HTML 解析器构建后续 DOM，而不是提供绝对的 FCP 毫秒先验承诺。

### 3. 运行现象验证

当你在浏览器中打开该页面并打开开发者工具控制台（DevTools Console）时，你将看到按以下确定性相对时序输出的日志：
1. `[L12-02 Event] head_start`
2. *(等待约 300ms)*
3. `[L12-02 Event] blocking_script_executed`
4. `[L12-02 Event] head_end`
5. `[L12-02 Event] body_content_parsed`

- 阻塞脚本在 `head_start` 之后强制暂停了解析，使得后续的 `head_end` 与 `body_content_parsed` 严格延后发生；
- 带有 `defer` 的脚本虽然早已下载完毕，但严格等待所有 HTML 节点解析完毕（`body_end`）之后才执行，且先于 `DOMContentLoaded` 事件完成。

### Question

为什么在 HTML 的 `<head>` 标签中引入带有 `defer` 属性的经典外部脚本，通常能让页面比引入同步外部脚本更早完成 DOM 树构建并呈现内容？在技术上能否宣称“只要使用了 `defer`，就绝对能在该脚本执行之前完成页面的首次绘制（FCP）”？

首屏渲染除了需要 DOM 树，还需要什么（CSSOM、样式计算、Layout）？浏览器在何时决定执行一次屏幕绘制？

<details>
<summary>Expected Observation</summary>
通过受控 fixture 中的事件标记（或在具备 GUI 浏览器下的 DevTools Timeline）观测，同步脚本在下载与执行期间会使后续 DOM 节点的解析进度完全停滞；而 <code>defer</code> 脚本允许 HTML 解析器不中断地一路解析至文档末尾，将 DOMContentLoaded 前的解析阻塞剥离出主干链路。但不能保证 FCP 一定发生在 defer 执行之前，因为首次绘制的时机还受到样式表网络加载、渲染管道绘制调度和显示刷新率的影响。
</details>

<details>
<summary>Full Explanation</summary>
1. <b>核心提速机制分析</b>：
   当 HTML 解析器遇到没有 <code>async</code> 或 <code>defer</code> 的经典外部脚本时，根据规范必须暂停解析（Parser-blocking），因为脚本执行可能通过 DOM/脚本接口动态修改未完成的文档结构。将脚本标记为 <code>defer</code> 后，浏览器在后台并行发起网络获取，且不在当前位置阻塞解析器；解析器得以顺畅执行词法分析并构建完整的 DOM 树。随后，<code>defer</code> 脚本在 HTML 解析完成之后、<code>DOMContentLoaded</code> 触发之前按声明顺序执行。
2. <b>不可泛化的推断边界（严禁误判 FCP）</b>：
   不能将“defer 移除了解析阻塞”等同于“FCP 必定先于 defer 脚本执行”。页面的可视绘制必须等待样式计算与布局就绪。如果页面的外部 CSS 样式表加载耗时极长，或者由于网络极快使得整个小型 HTML 解析与 defer 脚本几乎同时到达，浏览器完全可能在所有脚本执行完之后才统一触发第一次绘制机会。科学的态度是陈述其改变了关键解析路径，而不是给出虚假的绝对绘制时序保证。
</details>

## Common Misconceptions

- **“浏览器在解析 HTML 标签的同时，立刻就会在屏幕上把这个标签画出来。”** 错。屏幕像素来自 GPU 合成，而合成之前必须经历完整的样式计算、排版（确定几何位置）与图层绘制。在关键样式表就绪前，浏览器通常会延迟首次绘制以避免严重的无样式内容闪烁（FOUC, Flash of Unstyled Content）。
- **“每次对 DOM 进行微小修改（如修改一行文本），浏览器都会对整张网页全量重算排版和重绘。”** 错。现代渲染引擎采用脏标记（Dirty Bit）机制，仅标记受到影响的排版对象及其祖先链，执行增量排版（Incremental Layout）；同时利用独立的 Compositor 线程将已栅格化的图块缓存复用，绝大部分动画仅需调整图层变换矩阵即可完成。
- **“所有浏览器的开发者工具性能面板（Performance Panel）都使用统一标准的阶段行名称。”** 错。DevTools 的 UI 展示、录制阶段（Parse HTML, Recalculate Style, Layout, Pre-Paint, Paint, Composite Layers）属于各个浏览器开发者工具的内部实现呈现，并不是标准化的 Web API 规范。
- **“`async` 脚本总比 `defer` 脚本更快。”** 错。`async` 追求的是“下载完成立即抢占执行”，如果下载完成时 HTML 解析器正在忙碌，它会强行打断 HTML 解析；且多个 `async` 脚本无法保证执行顺序。对于存在依赖关系的业务代码，`async` 反而容易引发竞态错误与解析卡顿。
