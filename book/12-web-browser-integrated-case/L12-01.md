# L12-01｜浏览器系统架构、多进程拓扑与站点隔离

## 学习者问题

当你双击打开桌面上的浏览器并仅打开了一个简单的网页时，调出操作系统的任务管理器，为什么会赫然发现列表中弹出了十几个甚至数十个独立的系统进程？

民间常说的“一个标签页对应一个进程”究竟是对是错？如果不同的标签页甚至一个页面内的不同子框架（`<iframe>`）在不同进程中运行，它们是如何协同工作的？为什么现代浏览器要采用如此复杂的架构，甚至不惜消耗海量内存来换取什么？

## 为什么重要

在日常开发与计算机世界中，许多工程师将浏览器仅仅视为一个“网页展示器”或“DOM 解析引擎”。这种黑盒视角在面对现代复杂的 Web 应用排障、性能瓶颈调优与系统安全设计时，会产生严重的认知偏差：
- **迷信“一标签一进程”简化模型**：误以为浏览器每个 Tab 严格对应一个独立操作系统进程，无法解释为什么新建 Tab 进程数可能不增反降，或者一个 Tab 内却运行着来自多个域的独立子进程；
- **混淆 Web 平台标准规范与具体工程实现**：把特定浏览器（如 Chromium）的 `SiteInstance`、Mojo IPC、沙箱机制当成 W3C/WHATWG 的标准规定，无法区分哪些是所有浏览器遵循的 Web 规范，哪些是具体产品的工程权衡；
- **混淆站点隔离（Site Isolation）与同源策略（SOP）**：误以为同源策略就能自动在硬件层面阻断跨站数据嗅探，忽视了当恶意 JavaScript 利用 CPU 预测执行漏洞（如 Spectre）攻击同进程内存时，必须依赖操作系统级的进程地址空间实施物理隔离；
- **泛化“浏览器全局单线程”假象**：误以为由于 JavaScript 主线程是单线程事件循环，整个浏览器也是单线程运行的，忽视了浏览器内部的高度并发多进程与多线程协作。

理解现代浏览器的多进程系统架构，是理解现代操作系统进程抽象在应用层最宏大、最复杂落地的关键一步。本课正式复访核心系统概念：**进程（Process，EC-CON-018）** 与 **隔离（Isolation，EC-CON-013）**。

## 学习目标

完成本课后，你应能：
- **Explain**：准确阐明现代浏览器（以 Chromium 为典型实践）的多进程体系结构，区分浏览器协调进程（Browser Process）、沙箱化渲染进程（Renderer Process）、GPU 进程与网络/工具服务进程各自的核心职责与系统权限；
- **Explain**：严格区分 **Web 平台标准规范实体**（Document、Window、Browsing Context、Origin）与 **Chromium 内部实现实体**（Browser Process、SiteInfo、SiteInstance、Process Lock、Mojo IPC）；
- **Explain**：阐明站点隔离（Site Isolation）作为纵深防御（Defense-in-Depth）机制的系统级动机，解释其如何利用操作系统虚拟内存边界防范恶意渲染进程提权与 Spectre 类型的微架构侧信道攻击；

### 1. 为什么不能是单进程？

在早期浏览器（如 Internet Explorer 6）中，所有标签页、扩展插件、网络收发和页面渲染全部跑在同一个操作系统进程中。这种设计面临两大致命缺陷：
1. **可用性崩溃级联（Fault Cascading）**：任意一个网页的脚本死循环、内存泄漏或解析引擎崩溃，会导致整个浏览器窗口瞬间闪退，所有未保存工作全盘丢失；
2. **缺乏安全防护壁垒**：Web 页面本质上是来自互联网**完全不可信的第三方代码**。如果让不可信的 JavaScript 直接运行在具备操作系统磁盘写入、网络监听权限的主进程中，一旦渲染引擎存在任何缓冲区溢出漏洞（Memory Corruption），攻击者便可轻易接管宿主操作系统。

### 2. 进程职责切分：特权协调者与沙箱执行者

为了贯彻**最小权限原则（Principle of Least Privilege）**与**故障隔离（Fault Isolation）**，现代浏览器将系统功能解耦为多个专职进程：

| 进程类型 | 系统权限级别 | 核心职责 | 崩溃影响 |
|---|---|---|---|
| **Browser Process** (浏览器主进程) | **相对高**（相对受沙箱 Renderer；仍是宿主 OS 下的应用进程） | 协调顶层 UI、导航、进程选择以及需要较高权限的浏览器服务；具体网络/存储服务是否同进程属于版本/平台实现。 | 其故障通常影响更大范围，但实际恢复行为属于产品实现证据。 |
| **Renderer Process** (渲染进程) | **低权限沙箱**（具体限制因 OS/构建而异） | 承载 Blink/V8 等 Web 内容执行。沙箱限制其可用系统资源与高权限操作，许多能力需经浏览器侧服务/IPC 仲裁；不能概括成“完全不能发起任何系统调用”。 | 故障隔离范围取决于哪些文档/worker 共享该进程，不能固定等同一个标签页。 |
| **GPU / graphics service（Chromium case）** | **实现相关** | 在当前 Chromium 架构中承载部分图形/合成/光栅工作；是否使用独立 GPU 进程、软件光栅或硬件加速取决于平台、驱动和构建。 | 故障与恢复行为是 Chromium/平台运行时证据，不是 Web 规范。 |
| **Network / Utility Service（Chromium case）** | **实现相关** | Chromium 可把网络等服务放入独立 service process；进程内/进程外承载、名称与恢复策略可随版本/平台变化。 | 只记录实际构建所观察到的拓扑。 |

## Mechanism｜SiteInstance、站点隔离与 OOPIF

### 1. 什么是“站点”（Site）？

在 Web 规范中，**源（Origin）** 是一个三元组：`scheme + host + port`（如 `https://example.com:443` 与 `https://api.example.com:443` 是完全不同的源）。
在 Chromium 的 **Full Site Isolation / site-per-process** 当前实现文档中，进程锁使用的常见 site 粒度可表述为 **scheme + eTLD+1**；同一 registrable domain 下的不同子域可能因此属于同一 site。这个定义是**当前 Chromium 进程模型语境**，不是所有 Web API 的统一“site”定义，也不是 origin 的同义词。Chromium 还支持 origin isolation，Android/其他平台也存在 partial/no-site-isolation 模式，因此任何 site/process 结论都必须携带实现与平台边界。

### 2. SiteInstance 与进程锁（Process Lock）

在 Chromium 内部，`SiteInstance` 是管理浏览上下文与渲染进程映射的核心数据结构：
1. Chromium 用 `SiteInstance` / `SiteInstanceGroup` 等对象记录哪些 Document/worker 需要满足同步访问与进程分配约束；它们与 BrowsingInstance/浏览上下文关系共同参与分配，而不是简单的“一个 site 一个对象”。
2. 多个 SiteInstance 可能共享或不共享 Renderer process，取决于 Site Isolation 模式、process lock、process reuse policy、资源限制等当前实现条件。
3. **进程锁（Process Lock）**：Chromium 的浏览器侧安全策略会用进程安全状态与期望的 site/origin lock 参与诸如 origin-data access/commit 的检查；网络敏感响应、Cookie、文件权限等还有各自的策略与子系统。不能把 `CanAccessDataForOrigin()` 说成“所有 Cookie、密码、网络响应都统一经过这一函数”。

### 3. 为什么需要站点隔离（Site Isolation）？

同源策略（SOP）由渲染引擎中的逻辑代码强制执行。然而：
1. **渲染引擎漏洞（UXSS）**：WebKit/Blink 拥有数百万行复杂的 C++ 代码，历史上多次出现通用跨站脚本漏洞（Universal XSS）。如果攻击者攻破了渲染引擎逻辑，同进程内的不同页面内存便任其读取；
2. **Spectre-like 推测执行侧信道**：这类微架构攻击改变了“同一渲染进程内可放哪些站点数据”的威胁模型。站点隔离的目标之一，是尽量不把其他站点的敏感数据放进被攻击站点可执行代码所在的同一渲染进程/可访问数据边界。

**防御方案：站点隔离（Site Isolation）**。
在 Chromium **Full Site Isolation** 模式下，跨站文档通常会使用被锁到相应 site 的 Renderer process，跨站子框架可成为 **Out-Of-Process Iframe (OOPIF)**。但 Chromium 官方文档同时明确存在 Partial Site Isolation 与 No Site Isolation 平台模式。进程地址空间隔离与浏览器侧数据限制显著缩小被攻破 Renderer / Spectre-like 攻击可触达的跨站数据面；它是纵深防御，不是“彻底消灭所有 Spectre/侧信道攻击”的保证。

### 4. 并非“一标签一进程”的真实证据

现实中，进程拓扑远比“一标签一进程”复杂：
- **进程复用并非由 Tab 数量决定**：Chromium 存在多种 process reuse policy；同 site 的不同 SiteInstance 也不保证总是共享一个进程，达到进程限制或特定 process-per-site/current-policy 条件时可能发生复用。
- **单标签页多进程（OOPIF）**：一个标签页内如果嵌入了来自 3 个不同第三方站点的 `<iframe>`，该单个标签页便可能关联了 4 个不同的渲染进程；
- **平台差异与资源约束**：当前 Chromium 文档把桌面平台列为 Full Site Isolation；Chrome for Android 则存在 Partial/No Site Isolation 模式，并记录约 2GB RAM 的当前实现阈值与登录/密码等启发式隔离条件。该阈值和策略是**版本化 CURRENT PRACTICE**，不是课程常数，发布复核时必须重查。

## Hands-on｜观察真实浏览器中的进程模型

### 实验步骤（当 GUI 桌面环境可用时）

1. **启动浏览器**：打开 Google Chrome、Microsoft Edge 或 Chromium；
2. **打开内建任务管理器**：在浏览器窗口中按下 `Shift + Esc`（macOS 上为菜单栏 -> 窗口 -> 任务管理器）；
3. **打开操作系统任务管理器**：
   - Windows：按 `Ctrl + Shift + Esc` 打开任务管理器，展开浏览器条目；
   - Linux/macOS：在终端执行 `ps aux | grep -E 'chrome|chromium'`；
4. **对比观测**：
   - 查看进程类型：确认是否同时存在 "Browser"、"GPU Process"、"Network Service" 以及以网页标题命名的渲染进程；
   - 记录标签页数量与实际子进程总数：验证子进程总数是否远超标签页数量。

### 无 GUI / 纯终端环境的说明
在无图形界面的服务器或 CI 容器中，自动化工具无法弹出真实交互式桌面窗口。Essential CS 坚持**实证求真、绝不伪造输出**：
- 此时记录 `NO LIVE BROWSER OBSERVATION`；
- 进入本课配套的 **Source Expedition EXP-03**，直接在 Chromium 官方源码中检验 `SiteInstance` 与进程锁的真正实现逻辑。

</details>

<details>
<summary>Full Explanation</summary>
现代浏览器是一个运行不可信 Web 代码的操作系统级运行时容器。Chromium 采用多进程架构的核心动因是**容错与纵深安全防御（Defense-in-Depth）**：
1. **最小权限与故障遏制**：高权限操作（系统调用、窗口、网络、文件）收敛在 Browser 协调进程；高风险不可信代码（HTML/JS 解析）运行在受严格操作系统沙箱限制的 Renderer 进程中；驱动层不稳定的图形操作独立在 GPU 进程中。这不仅防止单个页面崩溃波及整个应用，更封锁了恶意代码越权访问宿主机资源的路径；
2. **进程边界强化 Spectre-like 防御**：SOP 的逻辑访问控制不足以覆盖被攻破 Renderer 或微架构侧信道威胁。Full Site Isolation 尝试把跨站敏感数据分离到不同进程/进程锁边界，并配合浏览器侧限制减少可达数据；这降低风险，但不宣称 MMU 单独“击碎所有 Spectre”。
3. **“一 Tab 一进程”的破产**：Chromium 的进程分配取决于 SiteInstance/SiteInstanceGroup、process locks、平台 Site Isolation 模式、process reuse policy 与资源约束。Tab 与 Renderer 之间不是固定一一映射；跨站 iframe 是否成为 OOPIF 同样取决于当前平台/模式。
</details>

## Common Misconceptions

- **“一个浏览器标签页就等于一个操作系统进程。”** 错。这是最流传甚广的谬误。如前所述，Chromium 依据 `SiteInstance`、平台站点隔离模式（Full vs Partial）以及系统内存水位线动态调度。多个相同站点的标签页可能复用同一个进程，而一个含有多个跨站 iframe 的单一标签页可能跨越数个渲染进程（OOPIF）。
- **“站点隔离（Site Isolation）就是同源策略（SOP）的别名。”** 错。同源策略是 Web 平台规范定义的逻辑层访问控制规则（限制 DOM 读取、LocalStorage 访问、Fetch 跨域读等）；站点隔离是 Chromium 为了防御渲染引擎漏洞（UXSS）和硬件侧信道攻击（Spectre）而采用的**操作系统进程物理地址空间隔离技术**。两者的抽象层次完全不同。
- **“所有浏览器的内部多进程拓扑都是完全相同的。”** 错。Chromium、Firefox（Gecko 架构，采用 Electrolysis / Fission 进程模型）以及 Safari（WebKit 架构）在进程划分、IPC 机制和隔离粒度上存在显著差异，并随着版本演进不断优化。
- **“浏览器多进程意味着它不需要考虑垃圾回收和内存占用。”** 错。多进程带来了显著的内存复制开销（每个进程都有独立的 V8 运行时和基础库镜像），这也是移动设备无法轻易开启全量站点隔离的根本原因。

## What You Can Ignore—for Now

- Chromium Mojo IPC 消息序列化管道的底层 shared-memory ring buffer 环形缓冲区实现；
- Windows Integrity Level、Linux namespaces/seccomp-bpf、macOS Seatbelt 沙箱底层系统调用过滤规则；
- ANGLE 图形层将 OpenGL 转换为 DirectX/Vulkan/Metal 驱动调用的底层翻译逻辑。

## Exit Criteria

- 能清晰解释 Chromium 多进程模型中 Browser 进程、Renderer 进程、GPU 进程与网络服务各自的分工与权限差异；
- 能从系统安全与 Spectre 硬件漏洞的角度，论述为什么逻辑同源策略不足以防范跨站攻击，必须在 OS 进程级实施站点隔离（Site Isolation）；
- 能列举出至少两种证明“一个标签页等于一个进程是伪命题”的现实场景（同站 Tab 复用与跨站 OOPIF）；
- 掌握在 live 浏览器环境下观察进程拓扑的方法，或在无 GUI 环境下准确阐释参考证据。

## Competency Mapping

- **Primary**: **Explain** (阐明浏览器多进程架构、特权划分与站点隔离纵深防御机制)
- **Growth**: **Observe** (在 live 浏览器或源码路径中观察和鉴别不同类型进程的分配行为)
