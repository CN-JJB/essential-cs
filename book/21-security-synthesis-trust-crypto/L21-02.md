## 1. 学习者核心问题 (Learner Question)

> “在现代软件架构中，密码学（Cryptography）是不是一种‘只要用上就能保证数据安全’的万能魔法？为什么给文件算一个 SHA-256 哈希值，根本防不住网络中间人的恶意篡改？为什么对消息进行了 AES 加密，攻击者依然可以翻转密文比特破坏数据？数字签名（Digital Signature）在数学上到底证明了什么，为什么它不能无条件等同于‘现实世界里的法律不可抵赖性’？我们在什么场景下该用 Hash、MAC、数字签名还是 AEAD？”

在构建网络通信与分布式应用时，软件开发者极易陷入对密码学工具的危险误用与概念混同：
1. **哈希即防伪误区（Hash-as-Authenticity Fallacy）**：误以为只要在数据包后面附带一个 SHA-256 摘要，接收方就能确信数据“未被黑客篡改”，完全忽略了若摘要和数据在同一非受信信道传输，在信道中的主动攻击者可以同时修改数据并重算摘要；
2. **加密即完整误区（Confidentiality-as-Integrity Fallacy）**：误以为“数据被加密了就没人能改”，忽视未经验证的传统对称密码（如 CBC 或 CTR 模式）具有**延展性（Malleability）**，攻击者可以通过比特翻转攻击操纵解密后的明文；
3. **签名即真人误区（Signature-as-Identity Fallacy）**：误以为数字签名能“直接证明某个人发了消息”，忽视数学验证仅证明“该消息由对应私钥持有者在某个时刻生成”，真人身份的绑定依赖于私钥保管、证书信任链与验证策略；
4. **快哈希存密码误区（Fast-Hash Password Fallacy）**：误以为拿 SHA-256 加盐就能安全存储用户口令，完全忽视 SHA-256 是为高速流处理设计的轻量级算法，在现代 GPU/ASIC 集群面前具有极高的离线碰撞与穷举速率（口令哈希存储属于 M22 `L22-01` 的专属领域）。

本课严格秉持**“只教密码学正确使用（Crypto-Use），绝不自行实现密码算法”**的最高工程铁律。我们基于 Python 标准库权威 API，解构四大核心基元的数学保证与非担保边界，并对 TLS 1.3 与 PKI 体系建立精确的 6 层验证认知模型。

## 3. 机制模型 (Mechanism Model)

### (1) 四大核心密码基元的职责与边界

密码学工具箱中的各类基元各司其职，**没有任何单一基元能同时满足所有安全目标**：

1. **无密钥密码哈希（Unkeyed Cryptographic Hash, 如 SHA-256）**：
   - 保证：将任意长度输入单向投影为固定长度摘要，具备抗原像（Pre-image resistance）与抗碰撞（Collision resistance）特性；
   - 适用场景：**检测数据偶然损坏**（如磁盘坏道），或**与通过受信带外信道获得的期望摘要进行比对**（如官方安全页面公布的 ISO 镜像哈希）；
   - 绝对不可证明：**无法抵御同时控制数据与摘要信道的主动攻击者**。攻击者修改数据后，重新计算哈希并一同发送，接收方校验必定通过！
2. **消息认证码（MAC / HMAC, 如 HMAC-SHA-256）**：
   - 保证：基于发送方与接收方共享的对称密钥，对消息生成认证标签。没有密钥的第三方无法伪造合法标签；
   - 适用场景：两方或微服务之间在不可信网络中防篡改通信；
   - 绝对不可证明：**对称密钥无法向第三方提供审计仲裁**。因为双方都拥有密钥，任何一方都无法向第三方证明“这个标签必定是对方生成的，而不是我自己伪造的”。
3. **数字签名（Digital Signature, 如 Ed25519 / FIPS 186-5 算法）**：
   - 保证：持有私钥的实体签名，全世界任何人均可使用公钥验证其数学一致性；
   - 适用场景：软件发布更新分发、公开审计日志防伪、跨系统公开验证；
   - 绝对不可证明：**数学签名不等于无条件不可抵赖性（Non-repudiation）**。不可抵赖性是一个涉及私钥妥善保管证明、时间戳凭证、吊销状态检查与法律约定的系统/组织属性，数学验证仅能证明“该签名与该公钥配对”。
4. **带有关联数据的认证加密（AEAD, 如 AES-GCM / ChaCha20-Poly1305）**：
   - 保证：同时提供载荷的**机密性（Confidentiality）**与**真实性（Authenticity）**，并可附加明文关联数据（Associated Data, AAD，如协议包头）进行防篡改保护；
   - 严禁行为：严禁在生产网络中使用纯加密（如未经 MAC 保护的 CBC 模式），防止密文填充攻击与比特延展破坏。

### (1b) Nonce、随机数来源与密钥生命周期不是同一件事

密码系统中的“随机”不能被压缩成一句“越随机越安全”。必须先问**具体算法 / profile 规定了什么不变量**：

- **Nonce uniqueness vs. unpredictability**：有些 AEAD / protocol profile 的关键要求是“同一密钥下不得重复 nonce”；这不等于所有 nonce 都必须不可预测。也有协议会额外要求随机或不可预测。工程实现必须遵循具体算法、协议和 API 的 nonce 规则，不能把“唯一性”和“不可预测性”互换成通用定理。
- **CSPRNG vs. simulation PRNG**：安全密钥、认证 token 等不可预测秘密应来自面向安全用途的 CSPRNG（本课使用 Python `secrets`）。面向仿真、游戏或可复现实验的普通伪随机生成器可以故意可重现，因此不能仅因“看起来随机”就用于生成秘密凭据。
- **Secret / key lifetime assumptions**：MAC、AEAD、签名或 PSK 的安全结论都依赖密钥在相应生命周期内保持秘密、按协议正确使用并在不再需要时被妥善淘汰。密钥泄露会改变可声称的真实性、机密性或前向保密边界。M21 不冻结一个适用于所有系统的轮换周期。

### (2) 时序攻击与 `hmac.compare_digest` 的 API 契约

在比较两个安全敏感的字符串（如 HMAC 标签）时，若使用普通的逐字符比较（如 Python 的 `==` 运算符）：
- **底层短路行为**：当遇到第一个不匹配的字符时，比较函数会立即短路返回 `False`；
- **时序信息泄露**：若第一个字符就错误，耗时为 $T$；若前 15 个字符匹配而第 16 个字符错误，耗时为 $T + 15\delta$。在高度受控的网络环境中，攻击者可能通过微小的响应耗时差异逐字节推断出正确的密钥或标签；
- **标准库 API 契约**：Python `hmac.compare_digest(a, b)` 使用一种**旨在避免基于内容的短路返回（avoiding content-based short-circuiting）**的方法，以降低 timing-analysis 风险；这是一项 API 设计契约，不是对所有宿主、底层库与微架构执行时间的绝对保证；
- **推断边界**：在标准操作系统与通用 CPU 环境下，受到缓存未命中、进程调度与垃圾回收抖动影响，软件层无法提供绝对的“物理恒定时间证明”。如果比较双方的类型不同或长度不匹配，该函数仍可能产生异常或因长度差异而提前返回。因此，`compare_digest` 是语言运行时层面的时序防护最佳实践，而非绝对的硬件恒温证明。

### (3) PKI / TLS 传输验证的 6 层解耦模型

在 `L11-01` 中我们接触了网络通信的传输安全。许多工程师将 HTTPS 视作一个黑盒，导致在配置证书、排查 mTLS 或对接云服务时频繁出现严重配置漏洞。在架构设计中，必须严格区分 **PKI 与 TLS 验证的 6 个层次**：

```
====================================================================================================
                 FIG-M21-03: PKI / TLS 6-LAYER VERIFICATION ARCHITECTURE
====================================================================================================

  [LAYER 1] Certificate Credential (X.509 ASN.1 Structure)
            - Asserted Subject, Issuer, Public Key, Validity Window, Key Usage Extensions.
            - Does NOT prove the remote server is who it claims!
                     │
                     ▼ (Chain Verification)
  [LAYER 2] Path Validation to Configured Trust Anchor
            - Cryptographic chain of signatures from Subject -> Intermediate(s) -> Root CA.
            - Revocation checks (CRL / OCSP where configured).
            - Proves the credential was issued by an authority trusted by the client.
                     │
                     ▼ (Identity Binding)
  [LAYER 3] Service-Identity Matching (RFC 9525)
            - Matches the intended reference identity (e.g. requested DNS hostname) against certificate identifiers.
            - SNI may carry a requested server name in TLS, but SNI itself is not the service-identity verification result.
                     │
                     ▼ (Cryptographic Handshake Proof)
  [LAYER 4] Live Proof of Private-Key Possession (Handshake Signature / Key Share)
            - Server signs ephemeral handshake transcript using its private key (TLS 1.3 CertificateVerify).
            - PROVES the remote peer actually POSSESSES the private key right now!
            - *Critical Axiom: A certificate credential alone != Live key possession!*
                     │
                     ▼ (Identity Established)
  [LAYER 5] Authentication (Who is connecting?)
            - Server authentication (default) or Mutual TLS / mTLS (both client and server).
            - Establishes verified identity context.
                     │
                     ▼ (Access Control)
  [LAYER 6] Authorization (What is the peer allowed to do?)
            - Maps verified peer identity to specific application permissions, roles, and endpoints.
            - *Critical Axiom: Authentication != Authorization! An authenticated user != Allowed to do anything!*

  * Forward Secrecy Boundary (RFC 9846):
    - DHE / ECDHE handshake modes: Ephemeral key shares provide Forward Secrecy.
    - PSK-Only (psk_ke) mode: does not provide the same forward-secrecy property as ephemeral (EC)DHE.
    - 0-RTT Early Data: RFC 9846 provides no forward-secrecy guarantee for early data and gives weaker replay guarantees.
====================================================================================================
```

#### 前向保密性（Forward Secrecy）的模式边界
现代 TLS 1.3 规范（**RFC 9846**，2026 年 7 月正式发布，全面废止 RFC 8446 等旧规范）：
- **具备前向保密性**：当使用 `(EC)DHE`（Diffie-Hellman 临时公钥协商）或 `PSK with (EC)DHE` 模式时，即使服务器长期私钥在未来泄露，攻击者也无法解密历史上捕获的加密流量；
- **缺乏同等前向保密性**：纯预共享密钥模式（PSK-only / `psk_ke`）没有 `(EC)DHE` 临时密钥协商提供的同等前向保密属性；静态 PSK 泄露会破坏依赖该 PSK、且未由临时 DH 提供独立前向保密性的相应会话保护；
- **0-RTT 早期数据弱点**：0-RTT 降低握手延迟，但 RFC 9846 明确不给早期数据提供前向保密保证，并且跨连接重放防护也弱于普通 1-RTT 数据；应用必须按协议与业务语义单独处理重放风险。

## 4. 论断分层 (Claim Layer)

- **论断 1（哈希不等于真实性）**：单向哈希函数仅能针对预先确立的可信期望摘要提供完整性检测；在不可信信道上，无密钥哈希无法抵御主动在途篡改。
- **论断 2（对称认证与非对称签名正交）**：MAC 依赖共享密钥，只能在信任彼此持有密钥的受限两方/多方中验证真实性；数字签名利用公私钥对，支持公开验证，但在没有完备密钥保管与组织策略时不能等同于无条件不可抵赖。
- **论断 3（加密必须伴随认证）**：未经认证保护的对称加密是具有延展性的。在网络协议和跨进程消息设计中，必须采用 AEAD（如 AES-GCM）或 Encrypt-then-MAC 架构。
- **论断 4（密钥协商不等于对端认证）**：Diffie-Hellman 机制建立的是双方共享的会话密钥，无法向任何一方证明对端真实身份；对端身份验证必须依赖证书链签名或预置身份绑定。
- **论断 5（PKI 凭证不等于在线持有）**：持有或出示公钥证书文件本身毫无意义；协议中必须存在在线私钥持有证明（如握手转录签名）方可完成身份认证。
- **论断 6（Nonce 要求是算法 / profile 相关的）**：nonce 的唯一性要求与不可预测性要求必须按具体规范区分；不能把“随机”当作一个不加限定的安全属性。
- **论断 7（安全随机源与仿真随机源职责不同）**：安全秘密应使用 CSPRNG；simulation PRNG 的可重复性可能正是其设计目标，因此不能替代安全随机源。
- **论断 8（密钥生命周期是安全假设的一部分）**：任何基于秘密密钥的保证都带有密钥保密、正确使用与生命周期管理前提；不存在 M21 可以冻结的通用轮换时长。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验 1：在途主动攻击者替换无密钥哈希
- **破坏行为**：模拟攻击者截获日志流，将关键事务从 `status=paid` 改为 `status=refunded`，并直接在本地调用 `hashlib.sha256()` 重新生成摘要覆盖数据包尾部；
- **失效后果**：下游验证方通过 `hashlib.sha256(data).hexdigest() == packet_digest` 校验，返回真！篡改未被察觉，导致账目灾难；
- **根因分析**：无密钥哈希不包含任何机密信息，任何计算节点均可自行求值。缺少对称秘密（MAC）或非对称私钥（签名），就不存在真实性保障。

### 失效实验 2：依赖普通 `==` 运算符比较认证标签
- **破坏行为**：在网络鉴权服务中使用 `if request_mac == expected_mac:`；
- **潜在隐患**：标准字符串比较在首个字符失配时立即退出。高精度分析者结合网络往返抖动统计建模，可能逐步推断认证信息；
- **防御机制**：改用 `hmac.compare_digest()`。

## 9. 常见认知误区 (Common Misconceptions)

### 误区 1：“文件计算了 SHA-256 哈希，所以这个文件就绝不可能被黑客篡改。”
**纠正**：哈希只有在与一个**通过可信安全信道获得的期望摘要**比对时，才能证明文件没有被篡改。如果黑客既能改你的文件，又能改你下载哈希的网页或数据包，黑客只需把两者一起换掉，哈希校验就会毫无察觉地通过。

### 误区 2：“数据用 AES-CTR 加密了，攻击者既看不到明文，自然也无法篡改数据。”
**纠正**：流密码与 CTR 模式的密文是明文与密钥流的逐比特异或（$C = P \oplus K$）。攻击者若知道明文第 10 个字节是 `0` 并想将其改为 `1`，只需直接将密文第 10 个字节翻转（$C' = C \oplus 1$）。解密时该字节将精确解密为 `1`。加密只管保密，不管防改！网络通信必须使用 AEAD。

### 误区 3：“只要调用了数字签名算法，该操作就具有了法律上的绝对不可抵赖性。”
**纠正**：数字签名在数学上仅证明“该消息由拥有对应私钥的实体签名”。要达到法律上的不可抵赖，还必须证明私钥未泄露、系统未受恶意软件控制、证书在签名时尚未被吊销且有受信时间戳服务器证明。不可抵赖性是综合系统属性，不是数学算法赠送的免费属性。

### 误区 4：“为了安全存密码，我用 SHA-256 加盐存数据库就行了。”
**纠正**：SHA-256 是面向通用快速摘要计算设计的函数；它没有为口令离线猜测场景提供专门的可调计算 / 内存成本机制。因此不能把“加盐后的快速通用哈希”当作口令 verifier 方案。具体 password-verifier 方案、参数与工作因子完全属于 M22 `L22-01`；M21 不冻结算法选择、硬件速率或参数常数。


### 误区 5：“Nonce 就是随机数，所以只要足够不可预测，就一定安全。”
**纠正**：错误。nonce 的安全条件取决于算法与 protocol profile。某些方案的核心不变量是**同一密钥下不得重复**，而不是要求 nonce 本身保密或不可预测；其他协议可能另有随机性要求。必须阅读具体规范 / API，而不是把 uniqueness 与 unpredictability 混成一个规则。

### 误区 6：“Python `random` 和 `secrets` 都能给出看似随机的值，所以生成安全 token 时可以互换。”
**纠正**：错误。simulation PRNG 常常为了可重复仿真而允许可预测 / 可设种子行为；安全秘密需要面向不可预测性的 CSPRNG。M21 Core 使用 `secrets` 生成合成密钥材料。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### 诊断关卡：Alice 发送的文件哈希为何没能挡住 Mallory？

- **Question**：Alice 编写了一个文件分发工具，在通过非加密 TCP 连接向 Bob 发送固件文件 `firmware.bin` 的同时，紧接着在同一个连接中发送了该文件的 SHA-256 摘要字符串。Bob 收到后在本地计算哈希并比对一致，宣布固件可信。为什么中间人 Mallory 依然可以给 Bob 植入后门固件？
- **Hint 1**：Mallory 在网络链路中间拥有读写所有数据包的能力。当 Alice 发送数据时，Mallory 能对传输流做什么？
- **Hint 2**：SHA-256 算法本身是公开的还是需要保密密钥的？Mallory 自己能在本地运行 SHA-256 吗？
- **Expected Observation**：`[Record the failure of unkeyed digests across an untrusted in-path channel where the active adversary modifies both the payload and the appended digest, showing that unkeyed hashing lacks authenticity.]`
- **Full Explanation**：SHA-256 是无密钥哈希函数，任何持有算法和数据的人都可以计算出完全合法的哈希值。因为 TCP 信道是非受信且未加密认证的，具有在途篡改能力的主动攻击者（Mallory）可以拦截 Alice 的数据包，将其中的固件替换为植入后门的版本，然后为后门固件重新计算一个全新的有效 SHA-256 摘要，并将其发送给 Bob。Bob 接收后比对后门固件与其对应的新摘要，两者完全吻合！若要防止此攻击，Alice 和 Bob 必须使用共享密钥的消息认证码（HMAC），或者 Alice 必须使用私钥进行数字签名，且 Bob 预先持有 Alice 受信的公钥。

## 17. 精确推断边界与禁止事项 (Exact Inference Limits)

为了维护求真务实的科学工程纪律，本课学习者与任何自动化代理必须遵守以下**绝对禁止事项**：

- **禁止事项 1**：严禁自行实现加密、解密、哈希或签名算法（“Never roll your own crypto”）。必须调用经过充分测试的经过同行评审的标准库；
- **禁止事项 2**：严禁在运行教学脚本时使用毫秒/微秒级软件时钟测量来宣称“证明了底层硬件恒定时间运行”。软件时序测试无法排除宿主操作系统调度抖动；
- **禁止事项 3**：严禁宣称“只要拥有数字签名就自动获得了不可抵赖性”。签名验证仅代表密钥配对数学有效；
- **禁止事项 4**：严禁将本课扩展至密码存储验证器的具体实现（如设计密码哈希库、调整工作因子）。口令哈希与慢速抗碰撞函数属于 M22 `L22-01` 的专属范围；
- **禁止事项 5**：严禁冻结任意固定数值的“通用硬件哈希穷举速率常数”。硬件算力随架构演进而剧烈变动，应理解其相对量级与设计原理；
- **禁止事项 6**：严禁在代码或活动中使用任何真实的生产密钥、商业私钥或个人密码。所有测试密钥必须是由 `secrets.token_bytes()` 动态生成的临时合成数据。
- **禁止事项 7**：严禁把 nonce “唯一性”与“不可预测性”写成对所有算法都相同的要求；必须按具体算法 / protocol profile 引用约束；
- **禁止事项 8**：严禁把 simulation PRNG 当作生成安全秘密的 CSPRNG 替代品；
- **禁止事项 9**：严禁冻结一个适用于所有密钥、证书、token 或 PSK 的通用生命周期 / 轮换周期；生命周期必须由威胁模型、协议与系统策略限定。
