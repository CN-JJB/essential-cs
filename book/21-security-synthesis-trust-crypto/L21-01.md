## 1. 学习者核心问题 (Learner Question)

> “在构建一个多层软件系统（客户端、API 网关、后端服务、本地存储）时，‘安全’到底是一道铸造在网络外围的防火墙高墙，还是分布在每个组件交界处的细粒度检查？为什么在 API 接口处验证了用户的合法身份后，依然绝对不能信任用户传入的文件名字符串？为什么仅仅在字符串中过滤掉 `../` 根本挡不住路径穿越？‘信任边界’（Trust Boundary）在操作系统、进程与网络协议中到底如何定义？”

在学习了操作系统虚拟内存隔离（`M07`）、网络传输（`M10`、`M11`）、文件持久化（`M09`）与 Web 浏览器同源策略（`M12`）后，许多初学者容易陷入一系列危险的直觉误区：
1. **城墙防御思维（Perimeter Fallacy）**：误以为只要在物理网络或机房入口架设了防火墙，内网或内部微服务之间的通信就是“绝对可信”的；
2. **身份与输入混同（Authentication Confusion）**：误以为对客户端完成了身份认证（Authentication），该客户端发来的所有参数与指令就变成了“合法的”，无需再做边界校验；
3. **语法过滤幻觉（Syntactic Whack-a-Mole）**：误以为防御路径穿越（Path Traversal）只需要在文件名中黑名单过滤 `../`，忽视了符号链接（Symlink）、绝对路径与字符串前缀混淆（Sibling-Prefix Confusion）；
4. **孤立检查与 TOCTOU 盲区**：误以为在用户空间做一次 `os.path.realpath()` 判定，就能一劳永逸地保证后续底层文件打开操作绝对安全。

本课带领学习者跳出单一系统维度的局限，建立跨越硬件、操作系统、网络传输与应用逻辑的**对抗性全景信任边界世界模型**（`EC-CON-017 Trust Boundary`）。我们通过完全课程自有、本地、合成的沙盒实验，彻底拆解路径禁闭（Path Confinement）的核心机理与推断边界。

## 3. 机制模型 (Mechanism Model)

### (1) 信任边界的核心定义与分层模型

**信任边界（Trust Boundary, `EC-CON-017`）**是计算系统中数据、控制流或执行上下文发生**权限等级（Privilege Level）、安全假设（Security Assumptions）或执行实体归属**发生改变的交界面。

与物理边界（如服务器机房外壳）不同，信任边界广泛存在于单台计算机的内存和软件架构内部：
- **硬件与内核边界**：CPU 执行环（Ring 3 用户态 vs. Ring 0 内核态）、特权指令集与页表配置权限；
- **进程与隔离边界**（`EC-CON-013`）：虚拟地址空间隔离（MMU）、用户 ID（UID/GID）、容器命名空间（Namespaces/cgroups）；
- **网络与传输边界**：公网不安全信道 vs. 本地回环接口（`127.0.0.1`）、TLS 加密通道的端点终结处；
- **应用与数据层边界**：前端非受信输入 vs. 后端业务逻辑、无特权应用进程 vs. POSIX 文件系统调用。

### (2) 隔离（Isolation）与信任边界（Trust Boundary）的根本区别

初学者常混淆这两个概念：
- **隔离（Isolation, `EC-CON-013`）**：是一种**防御性机制或状态**，通过技术手段（如页表隔离、进程地址空间、沙箱、虚拟化）切断或限制两个执行域之间的直接交互。隔离关注的是“如何把不同的东西隔开”；
- **信任边界（Trust Boundary, `EC-CON-017`）**：是一个**架构维度的逻辑交界面**。当数据、参数或控制流必须跨越隔离屏障时，信任边界规定了：谁在此处交出数据？谁接收？接收方必须承担何种**验证义务（Verification Obligation）**？接收方的环境赋予了其何种**环境特权（Ambient Authority）**？
- **简短表述**：隔离是墙，信任边界是开在墙上的门，而输入验证与访问控制是把守门洞的卫兵。

### (3) 经典失效案例：文件存储系统的路径禁闭与前缀混淆

考虑一个典型的文档存储服务：
用户通过 HTTP 接口请求下载或查看属于自己的笔记，参数形式为：`GET /api/notes?file=notes/hello.txt`。

存储守护进程的逻辑根目录位于：`/var/app/store/`。

如果守护进程直接执行拼接并打开文件：
```python
# 致命的脆弱实现
target = os.path.join("/var/app/store", user_input)
with open(target, "rb") as f:
    return f.read()
```

此时攻击者可以构造多种穿透载荷，暴露出不同防御机制的深层缺陷：

#### 缺陷 1：简单黑名单过滤（Blacklisting）
若代码检查 `if ".." in user_input: raise Error`：
- **失效场景 A（绝对路径覆盖）**：若传入绝对路径 `/var/app/outside.txt`，在 POSIX `os.path.join("a", "/b")` 规范中，遇到绝对路径参数将**直接丢弃前面的基准目录**，直接返回 `"/b"`！
- **失效场景 B（符号链接逃逸）**：若在合法目录内部存在一个名为 `escape_link` 的符号链接，其真实目标指向了上一层目录 `../outside.txt`。输入 `escape_link` 完全不包含任何 `..` 字符，黑名单语法检查直接放行，但在底层系统调用解析时依然逃逸到受权目录之外！

#### 缺陷 2：字符串前缀判断（Sibling-Prefix Confusion）
若开发者意识到路径需要先规范化，使用字符串 `startswith`：
```python
# 致命的逻辑缺陷
resolved = os.path.realpath(os.path.join(base_dir, user_input))
if not resolved.startswith(base_dir):
    raise PermissionError("Path traversal detected")
```
- **失效场景（兄弟目录混淆）**：
  假设受权基准目录为 `/var/app/store`。
  系统中恰好存在同级目录 `/var/app/store-evil/secret.txt`。
  攻击者输入 `../store-evil/secret.txt`。
  解析后的绝对路径为：`"/var/app/store-evil/secret.txt"`。
  此时执行 Python 字符串比较：
  ```python
  "/var/app/store-evil/secret.txt".startswith("/var/app/store")  # 结果为 True！
  ```
  字符串前缀检查被彻底欺骗，因为 `store-evil` 文本上以 `store` 开头，但文件系统拓扑上它们是**两个完全平行的独立目录**！

#### 正确的禁闭方案：已解析祖先关系判定（Resolved Commonpath Ancestry）
通过调用操作系统的规范化与真实路径解析（`Path.resolve()` / `os.path.realpath()`），并使用遵循文件系统语义的公共祖先判定（`os.path.commonpath()`，配合平台相关的 `normcase`）：
```python
root = Path(authorized_root).resolve()
candidate = (root / user_input).resolve()
# 只有当两者的公共祖先路径精确等于受权根目录本身时，候选路径才真正属于其子树
try:
    common = os.path.commonpath([os.path.normcase(root), os.path.normcase(candidate)])
    is_contained = (common == os.path.normcase(root))
except ValueError:
    # Windows 跨盘符路径无法计算公共路径，直接判定为不属于该目录
    is_contained = False
```

## 4. 论断分层 (Claim Layer)

- **论断 1（边界存在于转换处）**：信任边界严格定义在特权、身份、物理信道或数据验证假设发生改变的交接点。任何未经校验就接纳外部输入跨界执行的行为均属架构缺陷。
- **论断 2（身份认证不等于输入合法）**：验证调用者的身份（Authentication）只能证明请求来自特定主体；它绝不保证主体提供的数据在语义、范围和系统安全层面上是无害的。
- **论断 3（语法检查不等于语义禁闭）**：在字符串表面剔除 `../` 或执行 `startswith` 无法防御符号链接间接寻址与兄弟目录前缀混淆。必须依赖文件系统拓扑的真实路径规范化与公共祖先判定。
- **论断 4（单次解析不能消除所有并发竞争）**：在未引入原子禁闭系统调用（如特定环境下的 `openat2(..., RESOLVE_BENEATH)`）或严格不可变目录前提下，用户空间的“先解析后打开”（Check-then-Use）在理论上存在时间窗口（TOCTOU），不可将解析检查夸大为消除了所有并发竞态的数学定理。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验 1：字符串前缀比较与兄弟目录混淆（Sibling-Prefix Trap）
- **触发方式**：构建与目标目录共享前缀的邻居目录（如 `store` 与 `store-evil`）；
- **脆弱逻辑**：`str.startswith()` 执行逐字符标量比较，只要左侧子串相同即返回真；
- **失效后果**：攻击者通过跨目录引用访问邻居敏感数据，彻底击穿基于字符串前缀的伪禁闭。

### 失效实验 2：符号链接绕过（Symlink Escape）
- **触发方式**：在受权目录内放置指向外部敏感文件的软链接 `escape_link -> ../outside.txt`；
- **脆弱逻辑**：仅检查用户输入的文本参数，不跟随底层文件系统 inode 指针进行规范化；
- **失效后果**：系统调用在打开链接时被操作系统透明重定向至受限范围之外。

## 9. 常见认知误区 (Common Misconceptions)

### 误区 1：“在防火墙和网关验证了客户端的 JWT / 密码，传入的文件名就是安全的。”
**纠正**：身份认证（Authentication）仅证明“你是谁”，无法证明“你输入的数据符合系统安全约束”。哪怕是合法管理员，其传入的路径参数也可能包含越界穿越字符。在每一个跨越系统层次的边界处，必须执行强制验证。

### 误区 2：“只要路径字符串不以 `/` 开头且不包含 `..`，就绝对无法跳出当前目录。”
**纠正**：若受权目录内存在符号链接（或在支持的环境下被恶意构造），没有 `..` 的相对文件名同样可以通过解析符号链接指向根目录之外。

### 误区 3：“只要调用了 `os.path.realpath()` 并确认在目录内，后续调用 `open()` 就绝对安全了。”
**纠正**：在多进程并发或攻击者对中间目录拥有写权限的环境下，存在检查时与使用时（TOCTOU）的竞争条件——在 `realpath()` 判定完成之后、`open()` 发起之前的微秒级时间窗口内，攻击者可能迅速将该路径替换为符号链接。要彻底解决该问题，需依赖目录文件描述符与内核级原子禁闭操作（如 Linux `openat2`）。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### 诊断关卡：为什么拒绝 `../` 并不能证明路径安全？

- **Question**：如果一个存储微服务的接入网关在收到用户请求时，对文件名参数执行了严格检查，发现只要包含 `..` 或斜杠开头就直接拒绝。为什么运行在后端的存储进程如果直接使用该文件名打开本地文件，仍然可能发生非预期的越界访问？
- **Hint 1**：考虑文件系统自身除了普通文件之外，还支持哪些具有重定向特性的特殊文件节点？
- **Hint 2**：符号链接的路径是在什么时候被谁解析的？输入参数字符串本身是否需要包含 `..` 才能让文件系统发生跳转？
- **Expected Observation**：`[Record the distinction between syntactic string checking and filesystem inode resolution, explaining how symlinks or environment path joining can point outside without exposing '..' in the input string.]`
- **Full Explanation**：语法检查（Syntactic Checking）只能检查客户端提交的字面字符序列，无法洞察底层存储介质的拓扑结构。如果受权目录中预先存在指向外部目标的符号链接（Symlink），或者系统允许创建符号链接，用户仅需请求一个完全合法的相对文件名（如 `escape_link`），操作系统在执行 `open()` 系统调用时便会自动解引用并跳转至外部目标。因此，安全边界必须建立在文件系统的语义解析（Semantic Resolution）与公共祖先关系判定之上，而不能仅仅依赖字面黑名单过滤。

## 17. 精确推断边界与禁止事项 (Exact Inference Limits)

为了维护求真务实的科学工程纪律，本课学习者与任何自动化代理必须遵守以下**绝对禁止事项**：

- **禁止事项 1**：严禁宣称“只要拒绝 `../` 就足以防御路径穿越”。语法检查不等于语义解析；
- **禁止事项 2**：严禁宣称“`path.startswith(base)` 能够证明路径包含关系”。兄弟目录前缀混淆彻底推翻该假设；
- **禁止事项 3**：严禁断言“一次 `realpath()` 解析就能消除后续所有文件系统竞争（Race Conditions）”。TOCTOU 窗口依然存在；
- **禁止事项 4**：严禁宣称“通过了身份认证的调用者传入的文件名就是可信的”。身份与输入合法性必须正交分离；
- **禁止事项 5**：严禁将本课用于攻击任何真实宿主机、网络或未授权系统。本课所有操作严格限定在课程自有、合成、临时的安全沙盒内。
