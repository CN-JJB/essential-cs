## 1. 学习者核心问题 (Learner Question)

> “一段在本地开发机上跑通的代码，究竟如何安全、可控、不中断服务地发布到由几十上百台机器组成的生产集群中？为什么工程师把‘滚动更新（Rolling Update）’称为‘零停机发布’，却常常在上线瞬间遭遇海量 500 报错？新旧版本共存时的‘版本倾斜（Version Skew）’到底是如何破坏数据库与 API 兼容性的？为什么 Expand-Contract（膨胀-收缩）模式是数据库安全演进的唯一正解？镜像仓库中的 Tag 标签与 SHA-256 Digest 摘要在信任边界上有何本质差异？”

在初学者的想象中，软件发布就像点击一次“保存”：旧版本瞬间消失，新版本无缝生效。
然而，在真实生产分布式集群中：
- 机器必须逐台或按批次更新；
- 负载均衡器在毫秒级内将流量分发给处于不同更新阶段的机器；
- **新版本应用与旧版本应用必然会在同一时间段内并存，同时访问同一个底层数据库**；
- 容器镜像的拉取与执行面临软件供应链的篡改与假冒风险。

在 `M16` 中，我们掌握了 RPC 与接口演进风险；在 `L19-01` 与 `L19-02` 中，我们建立了单机受限进程与云端故障域的心智；在 `M13` 中，我们了解了数据库表结构与索引。

本课将带领学习者拆解现代持续交付与生产发布的机械全貌：
1. 掌握四种主流发布策略（**Recreate**、**Rolling Update**、**Blue-Green**、**Canary**）的运作机制与优缺点权衡；
2. 亲手通过真实代码重现**版本倾斜（Version Skew）**引发的生产雪崩；
3. 掌握保障零中断平滑演进的工业级标准——**Expand-Contract（膨胀-收缩）双写迁移三步法**；
4. 严格确立软件供应链的信任边界：透视**可变 Tag 标签 vs. 不可变内容摘要（Digest）**，并严密指出**摘要完整性不等于数字签名与出处证明（Provenance）**。

## 3. 机制模型 (Mechanism Model)

### (1) 四大发布策略对比 (Deployment Strategies)

当新版本代码打包就绪后，如何将其推向多节点集群？现代基础设施存在四种主流范式：

```
====================================================================================================
               FIG-M19-03: ROLLING DEPLOYMENT VERSION-SKEW & EXPAND-CONTRACT
====================================================================================================

  [PANEL A: ROLLING UPDATE WITH VERSION SKEW (THE DANGEROUS WINDOW)]
   Traffic Ingress (Round-Robin Router / Load Balancer)
     │
     ├── Req 1 ──> [ Node 1: v2.0-new ] ────┐  (Expects column: 'contact_phone')
     ├── Req 2 ──> [ Node 2: v1.0-old ] ────┼──> [ SHARED DATABASE ]
     └── Req 3 ──> [ Node 3: v1.0-old ] ────┘  (Expects column: 'phone')
   * The Skew Window: Node 1 expects new schema, while Node 2 & 3 expect old schema!
   * If DB column was renamed immediately: Node 2 & 3 crash on every customer request!

  --------------------------------------------------------------------------------------------------

  [PANEL B: THE EXPAND-CONTRACT (PARALLEL-RUN) MIGRATION PATTERN]

   Phase 1: EXPAND (Add without breaking old)
   +-----------------------------------------------------------------------------------------------+
   | Database Schema:  orders (id, customer, phone [OLD], contact_phone [NEW, NULLABLE])           |
   | Running Code:     v1.0 active everywhere. v1.1 deployed to dual-write both columns.           |
   +-----------------------------------------------------------------------------------------------+
                                                │
                                                ▼
   Phase 2: TRANSITION & ROLLING UPDATE (Version-Skew Tolerant)
   +-----------------------------------------------------------------------------------------------+
   | Rolling Deploy:   Node 1 -> v2, Node 2 -> v2, Node 3 -> v2.                                   |
   | Tolerant Logic:   v2 reads 'contact_phone' if present, falls back to 'phone'. Writes both.    |
   | Invariant:        Old v1 instances read/write 'phone' (OK). New v2 instances happy (OK).      |
   +-----------------------------------------------------------------------------------------------+
                                                │
                                                ▼
   Phase 3: CONTRACT (Clean up legacy debt after 100% v2 adoption)
   +-----------------------------------------------------------------------------------------------+
   | Database Schema:  orders (id, customer, contact_phone [FINAL])                                |
   | Cleanup Action:   Drop legacy column 'phone'. v2 code drops fallback logic.                   |
   +-----------------------------------------------------------------------------------------------+
====================================================================================================
```

#### 四种策略详细技术权衡表

| 策略模式 | 执行过程描述 | 停机时间 (Downtime) | 版本倾斜窗口 (Skew Window) | 回滚成本 (Rollback Cost) | 硬件成本 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Recreate (先停后起)** | 停止全部旧实例，待所有旧进程退出后，再启动所有新实例 | **存在确定性停机**（等于新服务启动就绪时间） | **无版本倾斜**（集群中永远只有单版本） | 较慢（需重新停止新版本并启动旧版本） | 100%（无需额外冗余机器） |
| **Rolling Update (滚动更新)** | 每次停止 1 台（或 1 个批次）旧实例，启动新实例并等待健康检查通过，再滚动下一批 | **可大幅降低感知停机** | **存在明显倾斜窗口**（新旧实例共同接收请求） | 中等（需逆向逐步回滚新实例） | 100% ~ 125%（仅需少量动态增量机器） |
| **Blue-Green (蓝绿部署)** | 同时维护蓝（当前在线）和绿（新版候选）两套完整集群。验证通过后，在路由器/负载均衡器上瞬间切换入口流量 | **理论切换停机趋近于 0** | **无运行时倾斜**（流量在某一时刻完全切向单一环境） | **极快**（路由器单次流量回切） | **200%**（必须长期或短期持有双倍硬件资源） |
| **Canary (金丝雀/灰度发布)** | 将极小比例流量（如 2% 或特定内部员工）引流到一台新版本机器，持续观察报错率与延迟指标；指标健康则逐步放大流量 | **零停机** | **存在可控的倾斜窗口** | **快速**（切断金丝雀实例流量即可止损） | 略高于 100% |

> **关键提醒**：虽然蓝绿部署在路由器层面没有请求级新旧实例共存，但**如果新旧版本共用底层同一个数据库**，一旦绿环境写入了新格式数据，瞬间回滚到蓝环境时，蓝环境依然必须能够解析这些新数据！因此，即使采用蓝绿部署，数据库演进依然必须遵守向前/向后兼容性法则。

### (2) 致命的假象：滚动发布中的版本倾斜 (Version Skew)

许多初入工业界的团队会遇到这样的惨剧：
> “我们使用了业内最先进的 Kubernetes 滚动发布，配置了 `maxSurge=25%, maxUnavailable=0`，号称零停机发布。
> 为什么每次一执行数据库表结构更新，监控大盘上 500 报错立即飙升？”

**根因解剖**：
假设工程团队决定重命名数据库字段：将 `orders` 表的 `phone` 字段重命名为 `contact_phone`。
由于缺乏向后兼容意识，团队执行了以下操作：
1. 数据库管理员在主库上直接执行 SQL：`ALTER TABLE orders RENAME COLUMN phone TO contact_phone;`
2. 开发者将应用代码更新为 Version 2（查询改为 `SELECT contact_phone FROM orders`），并触发滚动发布；
3. **版本倾斜窗口爆发**：
   - 负载均衡器后面有 3 台实例。实例 1 更新为 Version 2，而实例 2 和实例 3 **仍在运行 Version 1**！
   - 负载均衡器采用轮询（Round-Robin）将外部用户请求均匀打到 3 台机器上；
   - 当请求到达实例 2 和 3 时，Version 1 代码执行 `SELECT phone FROM orders`；
   - 数据库直接抛出致命异常：`OperationalError: no such column: phone`！
   - 线上立刻爆发大量 500 错误，用户下单失败。

**结论**：滚动发布的“平滑性”是建立在**新老代码能够与当前数据库状态双向兼容**的前提下的。只要破坏了接口兼容性，滚动发布只会拉长事故持续时间！

### (3) 安全演进基石：Expand-Contract (膨胀-收缩) 模式

为了彻底根除版本倾斜带来的破坏，工业界总结了必须严格执行的 **Expand-Contract（膨胀-收缩 / Parallel-Run）三阶段模式**：

#### 第一阶段：Expand (膨胀阶段)
- **数据库原则**：**只做增量，不做破坏**。
  - 执行 `ALTER TABLE orders ADD COLUMN contact_phone TEXT;`（新字段必须允许为 NULL，或具有安全的默认值）；
  - 严禁删除、重命名旧字段，严禁直接对现有老字段增加 NOT NULL 约束；
  - 启动后台脚本将老 `phone` 数据按批次同步/回填（Backfill）到 `contact_phone`。
- **应用代码原则**：部署中间过渡版本（v1.1）。
  - **写操作（Dual-Write）**：同时向 `phone` 和 `contact_phone` 写入数据；
  - **读操作（Fallback-Read）**：优先读 `contact_phone`，若为空则读取 `phone`。
- **状态保证**：此时即使全部运行老 v1.0 代码，老代码依然能读写 `phone`，不会发生任何报错。

#### 第二阶段：Transition & Rolling Deploy (过渡与滚动发布阶段)
- 在生产集群执行滚动发布，将所有节点逐步替换为 Version 2；
- **倾斜容忍**：在滚动过程中，v1 实例与 v2 实例并存：
  - v1 实例读写 `phone`，正常工作；
  - v2 实例通过双写和兜底逻辑正常工作；
  - 双方互不干扰，**请求错误率严格为 0%**！

#### 第三阶段：Contract (收缩与清理阶段)
- 确认线上 100% 实例已全部运行 Version 2，且所有异步任务/日志归档已消费完毕；
- 部署最终版代码（v2.1），移除对老字段 `phone` 的双写逻辑；
- 在数据库中安全地执行收缩清理：`ALTER TABLE orders DROP COLUMN phone;`；
- 系统平滑演进完毕，技术债务清零。

### (4) 软件供应链信任边界：Tag、Digest 与数字签名

现代基础设施以容器镜像或二进制制品为交付载体。然而，一个制品能够被计算机执行，绝不代表它是安全的（`EC-CON-017 Trust Boundary`）。

```
====================================================================================================
               SOFTWARE ARTIFACT INTEGRITY VS. CRYPTOGRAPHIC PROVENANCE
====================================================================================================

  1. MUTABLE TAG (可变指针 - 零不可变保证!):
     Reference: `my-service:v1.0`
     Time T0  ─── Points to ───> Image Digest: [ sha256:4a985e... (Commit A) ]
     Time T1  ─── REPOINTED! ──> Image Digest: [ sha256:b635a0... (Commit B / Malicious!) ]
     * Warning: Tag is just a movable label. Deploying with `:v1.0` is non-reproducible.

  2. CONTENT DIGEST (内容摘要 - 提供篡改检测/完整性):
     Reference: `my-service@sha256:4a985e97a3ef...`
     * Cryptographic hash of exact manifest bytes.
     * GUARANTEE: Byte-level immutability. If a single bit changes, digest changes.
     * LIMITATION: Does NOT tell you WHO built it, WHERE it came from, or IF it has malware!

  3. CRYPTOGRAPHIC SIGNATURE & SLSA PROVENANCE (密码学签名与出处证明 - 真正的信任边界):
     Signed by: [ cosign / sigstore ] with OIDC Identity: `ci-bot@company.internal`
     Provenance: Generated in GitHub Actions build #14285 from git commit `a1b2c3d`
     * GUARANTEE: Identity verification, non-repudiation, tamper-proof supply chain.
====================================================================================================
```

#### 严密区分四组概念：
1. **Tag（标签，如 `:v1.0`）**：
   - 本质是镜像仓库中的一个**动态指针（Mutable Pointer）**；
   - 任何人若拥有写权限，随时可以强行覆盖该标签。生产环境依赖可变 Tag 是发布非幂等与难以复现故障的头号元凶；
2. **Content Digest（内容摘要，如 `@sha256:...`）**：
   - 基于加密哈希算法对镜像 Manifest 计算得出的指纹；
   - **能保证什么**：**完整性（Integrity）与防篡改**。如果拉取时的摘要与目标摘要一致，保证从传输到落地没有发生 1 比特损坏；
   - **不能保证什么**：**不保证作者身份，不保证来源可信，不保证没有后门**！任何人都可以对一个植入挖矿木马的恶意镜像计算出合法的 SHA-256 摘要；
3. **Digital Signature（数字签名，如 Sigstore / Cosign）**：
   - 使用非对称密钥对制品摘要进行密码学私钥签名，通过公钥基础设施（PKI）或无密钥签署证明发布者的真实身份；
4. **Provenance / Attestation（出处证明，如 SLSA 框架）**：
   - 不可伪造的元数据声明：证明该二进制制品是由特定的受信任 CI/CD 平台（如独立托管的编译流水线）、从特定的源仓库、由特定的 Git Commit SHA 直接构建出来的，防止开发者本地私自编译投毒。

## 5. 关键误区与严密辨析

### 误区 1：“使用容器镜像的 `:latest` 标签可以保证拉到最新的稳定版本”
- **严密辨析**：**错！**
  `:latest` 只是构建系统默认打的一个普通可变标签，它不仅没有任何“稳定”的语义保证，甚至随时可能因为某次实验性构建失败被污染。生产环境基线要求：**严禁在生产部署配置中使用 `:latest`，生产清单必须显式锁定不可变的 Content Digest 或严格的 SemVer 冻结版本**。

### 误区 2：“只要采用了金丝雀发布，线上就绝对不会出现系统崩溃”
- **严密辨析**：**错！**
  金丝雀发布的作用是**控制爆炸半径（Blast Radius）**，它绝不等于“不会出错”。
  如果有毒的新版本包含了不可逆的数据库污染（例如写入了错误计算的金额或破坏了核心表约束），即使只有 1% 的金丝雀流量击中了它，这 1% 的用户依然会产生脏数据，甚至污染共享的主数据库，导致无法通过简单的流量切断来挽回。

### 误区 3：“只要镜像具有合法的 SHA-256 哈希值，说明该镜像来源可信”
- **严密辨析**：**错！**
  哈希算法只负责验证“你下载的这一串字节，与哈希值计算出来的结果是否匹配”。**恶意软件的作者也可以提供完全合法的哈希值**。证明“镜像没有被半路篡改”与证明“镜像是由公司受信任的官方流水线构建的”是两个完全不同的信任等级（`EC-CON-017 Trust Boundary`）。

## 7. 概念与思维模型小结

1. **版本倾斜是分布式系统的物理必然**：只要集群由多台机器构成，代码就无法做到超距瞬时切换。滚动发布必然出现新老代码共同运行的过渡期；
2. **Expand-Contract 是无损演进的不二法门**：增量扩展（Expand）$\to$ 双读双写并存演进（Transition）$\to$ 清理收缩债务（Contract）。永远不要在一个发布周期内直接重命名或删除已被老代码依赖的字段；
3. **标签是可变的，摘要是不变的**：生产交付应当锁定 Content Digest，避免标签被意外覆写；
4. **完整性不等于信任（Integrity $\neq$ Trust）**：SHA-256 哈希只能证明内容未被篡改，无法证明软件来自可信来源。真正的供应链安全必须依赖密码学签名（Signature）与自动化出处证明（Provenance）。

## 8. 渐进式支持与思考题

### 思考题
为什么蓝绿部署（Blue-Green Deployment）在发生非数据库相关的程序 Bug 时，回滚速度远远快于滚动发布？但如果新版本已经向共享数据库中写入了数千条新业务数据，为什么即使是蓝绿部署也无法保证能够“一键无损秒级回滚”？

### 思考指引
- **Hint 1**：在蓝绿部署中，旧版本（Blue）始终保持在热备运行状态。如果新版本（Green）发生纯代码层面的内存泄漏或死锁，负载均衡器只需修改一次路由指针（数十毫秒），流量即可立刻回到 Blue 环境，无需经历漫长的停止与重启过程；
- **Hint 2**：若 Green 运行期间向共享数据库写入了新格式的数据，或者触发了扣款、扣减了库存。当流量切回 Blue 时，Blue 环境的老代码可能**根本无法识别 Green 留下的新数据格式**，导致 Blue 批量抛出反序列化异常或产生重复结算；
- **核心结论**：**流量可以秒级切回，但状态（State）无法轻易逆转**！状态型系统的高可用演进永远受制于数据一致性与向前兼容规则（`EC-CON-014 Consistency`）。
