## 1. 学习者核心问题 (Learner Question)

> “为什么在 Kubernetes 或云上执行看似完美的‘滚动更新（Rolling Update）’时，生产环境经常出现短时间的 500 报错？当新旧两个版本的应用同时连接同一个数据库时，‘版本倾斜（Version Skew）’是如何悄无声息地击垮业务的？膨胀-收缩模式（Expand-Contract Pattern）是如何保障零破坏性迁移的？在软件供应链中，镜像 Digest、数字签名与 SLSA 凭证之间，究竟存在怎样不可混淆的信任边界？”

在现代软件工程中，写出可在本地运行的代码只是起点，将代码安全、可控、不可篡改地交付到生产集群，是另一半庞大而精密的工程科学。许多工程师误以为：
- 只要配置了滚动发布，系统就必然“零停机、零错误”；
- 只要打上镜像 Tag（如 `:v1.0.0`），镜像内容就永远固定；
- 只要镜像有了哈希 Digest，软件就自动获得了防篡改与不可抵赖的供应链安全性。

在 `L19-01` 中，我们掌握了容器进程与 OCI 镜像机制；在 `L19-02` 中，我们建立了分布式故障域与物理延迟边界。

本课将聚焦于应用交付的动态演进过程：通过确定性的版本倾斜与膨胀-收缩仿真，亲眼见证接口不兼容在滚动发布中的破坏力；并从密码学与供应链治理的高度，彻底厘清内容摘要、数字签名、制品溯源与信任策略决策之间的硬性边界。

## 3. 机制模型 (Mechanism Model)

### (1) 部署策略对比：机制与工程权衡

部署策略不是魔法，而是关于**资源开销、故障爆炸半径与版本倾斜窗口**的工程权衡机制。没有任何一种策略能无条件保证零停机或零错误：

| 部署策略 (Strategy) | 机制原理 (Mechanism) | 版本倾斜 (Version Skew) | 资源冗余成本 (Resource Overhead) | 回滚复杂度与风险 (Rollback) | 停机时间特征 (Downtime Profile) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **重建部署 (Recreate)** | 停止被替换的旧 serving set，再启动新 serving set | 被替换集合内通常不设计新旧重叠；若系统另有 serving path，整体行为取决于该架构 | 取决于是否存在额外 serving path、预留容量与启动方式 | 回滚需要恢复旧 artifact/config/state compatibility；速度不作通用保证 | **可能出现不可用窗口**；是否对用户可见取决于其它 serving path 与 readiness |
| **滚动更新 (Rolling)** | 按实现/策略定义的批次逐步替换实例 | 常见策略会形成新旧版本重叠窗口；窗口大小与持续时间是 policy-specific | 取决于 batch、surge、unavailable 与容量策略 | 反向替换只是机制之一；共享状态兼容性决定能否安全回滚 | 可减少一次性中断，但接口/状态不兼容时**可能产生部分错误**；无零停机保证 |
| **蓝绿部署 (Blue-Green)** | 同时保留 current 与 candidate serving environments，并执行流量转换 | 计算 serving set 可避免逐实例混合，但共享数据库/配置/外部依赖仍可能存在跨版本兼容窗口 | 取决于两套环境实际复制的资源与容量，不冻结“2×”常数 | 流量切回是否安全取决于状态、schema、config 与连接迁移；速度不作通用保证 | 切流机制本身不保证瞬时或无错误；长连接与共享状态都可能影响结果 |
| **金丝雀发布 (Canary)** | 按选定 routing/workload policy 将一部分请求或主体暴露给候选版本并观察信号 | 存在按所选策略限定的版本重叠/暴露窗口 | 取决于候选容量、镜像、观测与路由实现 | 停止/反转 canary 的速度与安全性取决于控制面、状态与策略 | 只在**选定流量策略与观测范围**内限制初始暴露；百分比/时长不是课程常数 |

### (2) 版本倾斜 (Version Skew) 与 膨胀-收缩模式 (Expand-Contract)

```
====================================================================================================
           FIG-M19-03: ROLLING VERSION SKEW VS. EXPAND-CONTRACT MIGRATION
====================================================================================================

  [PANEL A: THE BROKEN PATH (Immediate Column Rename during Rolling Update)]
   Time 0: [Node 1 (v1.0)] [Node 2 (v1.0)] [Node 3 (v1.0)] ---> DB Schema: { phone } (All OK)
   ------------------------------------------------------------------------------------------------
   DB Action: ALTER TABLE orders RENAME COLUMN phone TO contact_phone;
   Rollout:   Deploy Node 1 (v2.0)
   Time 1:    [Node 1 (v2.0)] [Node 2 (v1.0)] [Node 3 (v1.0)] (THE VERSION-SKEW CRASH WINDOW)
                 |                 |                 |
                 v                 v                 v
           SELECT contact    SELECT phone      SELECT phone
             [HTTP 200]     [CRASH: 500!]     [CRASH: 500!]  --> 66.7% Error Spike on Live Users!

  [PANEL B: THE PROTECTED PATH (Expand-Contract Three-Phase Migration)]
   PHASE 1 (EXPAND):
     1. DB Schema: ADD COLUMN contact_phone TEXT (Nullable / Defaulted)
     2. Backfill:  UPDATE orders SET contact_phone = phone; (Both columns exist & populated)

   PHASE 2 (TRANSITION & COEXISTENCE):
     1. Deploy v2-transition nodes with Dual-Write & Fallback-Read:
        - Read:  SELECT COALESCE(contact_phone, phone)
        - Write: INSERT INTO orders (phone, contact_phone) VALUES (?, ?) [Dual-Write!]
     2. Live Pool: [Node 1 (v2-trans)] [Node 2 (v1.0)] [Node 3 (v1.0)]
        - v1 reads v2's dual-write: OK!
        - v2 reads v1's write:      OK! (Zero errors under this deterministic contract)

   PHASE 3 (CONTRACT):
     1. Upgrade 100% of nodes to v2-final (queries ONLY contact_phone; zero references to phone).
     2. DB Schema: ALTER TABLE orders DROP COLUMN phone; (Safe cleanup!)
     3. Post-Contract requests execute cleanly on final schema.
====================================================================================================
```

#### 破坏路径的致命机理
当开发团队执行破坏性架构修改（如重命名数据库字段、删除 API 参数、变更消息反序列化格式）时，如果同时发起滚动更新：
- 在本课采用的“逐台替换且持续服务”的 rolling scenario 中，会出现**旧版本实例与新版本实例同时在线处理业务**的窗口；
- 此时若数据库模式已经被修改为新结构，所有依然在线的旧版本实例在执行旧 SQL 时，将立刻遭遇致命异常（如 `no such column: phone`），导致线上发生灾难性的周期性 500 报错。

#### 膨胀-收缩模式（Expand-Contract）工程三部曲
本课为“共享数据库字段重命名 + 新旧应用共存”的确定性场景采用三阶段 Expand-Contract 改造：
1. **第一阶段：膨胀（Expand）**
   - 模式变更必须是**向后兼容的增量变更**：新增可为空（nullable）或带有默认值的字段 `contact_phone`，保留旧字段 `phone`；
   - 执行历史数据异步对齐回填（Backfill）。
2. **第二阶段：过渡与共存（Transition & Coexistence）**
   - 上线具备过渡兼容能力的中间版本 `v2-transition`；
   - **容错读取（Fallback Read）**：优先读取新字段，若新字段为空则回退读取旧字段；
   - **双写机制（Dual-Write）**：在创建新数据时，同时写入旧字段与新字段，确保尚未升级的旧版本实例依然能够正确解析新写入的数据；
   - 完成所有节点的平滑滚动替换。
3. **第三阶段：收缩（Contract）**
   - 确认整个集群中**已经没有任何实例继续引用旧字段**，部署最终版应用 `v2-final`；
   - 从数据库中安全剥离并删除已废弃的旧字段 `phone`。

> **确定性与推断界限**：膨胀-收缩模式在测试夹具中消除了版本倾斜错误。但这**不等于普适的零停机保证**；未预料的数据库锁等待、网络超时或并发竞态依然可能导致实际系统出现故障。

### (3) 制品不可变性与供应链密码信任边界

在现代 CI/CD 流水线中，制品交付的安全性建立在严密的密码学边界之上。

#### 1. 可变 Tag 与 不可变 Content Digest
- **Tag / reference（课程可变引用示例：`myapp:v1.0.0`）**：
  - 本课的 course-owned registry map **刻意允许**把同一个 tag-like reference 从 Digest A 改指向 Digest B，用来证明“引用策略”与“内容身份”是两件事；
  - 真实 registry 是否允许更新某个 tag 由产品/仓库策略决定，有的环境可以实施 tag immutability。OCI Image Spec 本身不授予“所有 registry tag 永远可改”的通用保证；
- **内容摘要（Content Digest，如 `sha256:8d9e6...`）**：
  - OCI Descriptor digest 是带算法前缀的内容标识；最新正式发布 v1.1.1 定义 SHA-256 与 SHA-512，且要求实现 SHA-256 验证。当前未发布的 Image Spec `main` 另已加入 BLAKE3；
  - **内容验证前提**：对来自不可信来源的内容，需要重新计算摘要并与通过可信上下文获得的 expected digest 比较；Digest identity/integrity evidence 仍不等于作者身份、provenance 或信任策略通过。

#### 2. 四元信任边界公式 (The Four-Part Trust Boundary Formula)
在软件供应链安全中，严禁将不同维度的证据混为一谈：

$$\text{Digest 完整性证据} \neq \text{数字签名身份认证} \neq \text{Provenance 溯源凭据} \neq \text{准入信任决策}$$

1. **Digest 完整性证据（Integrity Evidence）**：
   - 仅证明“当前拿到的比特流，与其标称的哈希摘要完全吻合”；
   - **它绝不证明作者身份**，也不证明代码中没有后门或漏洞。
2. **数字签名验证（Signature Verification，例如 Sigstore/Cosign）**：
   - 验证的结论必须相对于**配置的 trust roots、expected identity/issuer 与签名对象**来表达。以 Sigstore keyless verification 为例，验证者需要约束预期 certificate identity 与 OIDC issuer，而不是只看“存在一个有效签名”；
   - **签名不等于无害**：合法身份同样可能签署有缺陷或恶意的内容。
3. **制品溯源凭据（Provenance / Attestation，例如 SLSA provenance）**：
   - 提供关于“制品如何被构建”的机器可读声明/证据；其真实性与适用保证取决于 attestation 验证、builder/platform 约束及所满足的 SLSA 要求；
   - **Provenance 不是自动信任**：它需要被认证并按 policy 评估。
4. **准入信任决策（Trust Policy Decision）**：
   - 组织根据 expected digest、签名身份、issuer、provenance claims 与其它风险规则作出准入决定。Kubernetes Admission Controller 之类机制只能作为 **Optional / Current Practice** 示例，不是 M19 Core 前置条件。

## 4. 断言层与边界 (Claim Layer)

- **断言 1（非确定性保证）**：没有一种部署策略能够脱离具体架构保证“绝对零停机”。任何声称滚动发布必然零停机的表述都是反工程科学的。
- **断言 2（版本倾斜普遍性）**：只要滚动发布中新旧实例共存，就必然存在版本倾斜窗口。接口变更必须在设计上满足双向兼容性。
- **断言 3（Digest 与 Tag 的本质差异）**：Tag 是镜像仓库中的可变引用，Digest 是基于密码哈希的内容标识。仅靠 Tag 无法防御中间人投毒或覆盖攻击。
- **断言 4（信任链独立性）**：内容摘要只证明完整性，数字签名只证明签名者身份，SLSA 凭据只记录构建事实。唯有组织定义的准入策略能够裁决是否予以信任。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 破坏性推演：收缩阶段提前引发崩溃 (Premature Contraction)
- 在仿真中，如果开发团队在第二阶段尚未完成（仍有 1 台 v1 实例在线处理流量）时，就因心急提前执行了第三阶段的 `ALTER TABLE DROP COLUMN phone`；
- 此时残留的 v1 实例在接收到下一次订单查询请求时，将立刻抛出 `OperationalError: no such column: phone`；
- 这一失效模式深刻证明：**收缩必须在旧版本代码 100% 下线且没有正在执行的长事务时才能触发**。

## 9. 常见认知误区 (Common Misconceptions)

### 误区 1：“我们用了金丝雀发布，就算接口改坏了也不会有用户受到影响。”
**纠正**：金丝雀只按照**所选 routing/workload policy**限制候选版本的初始暴露范围；比例、持续时间、主体选择与回退阈值都是策略输入，不是固定的 1%/2%。只要接口不兼容，被选中的那部分真实流量仍可能失败。

### 误区 2：“使用蓝绿部署只要一键切流，就绝不会出现版本倾斜。”
**纠正**：蓝绿可以避免逐实例替换造成的某类 serving-set 混合，但流量转换并不保证“瞬时”；数据库、存储、配置和外部依赖是否共享也由具体架构决定。若共享状态已发生不兼容变更，切回旧 serving environment 仍可能失败。

### 误区 3：“只要镜像被 Cosign 签署了，软件供应链就是完全防篡改、绝对安全的。”
**纠正**：数字签名只能证明“拥有签名密钥的主体对该摘要进行了背书”。如果攻击者窃取了开发者的私钥，或者恶意开源维护者蓄意植入后门并正常通过 CI 签署，签名依然是完全有效的。真正的安全需要把签名身份/issuer、经过验证的 provenance claims 与组织的准入策略组合起来评估；SLSA provenance 本身不是“不可篡改即自动可信”的凭证。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### 诊断关卡：如何诊断一次诡异的线上滚动发布“偶发性 500”报错？

- **Question**：某电商服务在发布新版本时，监控大盘显示错误率并没有变成 100%，而是维持在约 30% 上下波动，过了一会儿又自行恢复正常。请推断最可能的根本原因是什么？
- **Hint 1**：考虑集群的实例总数与滚动批次。假设集群一共有 3 台机器，每次滚动更新替换 1 台。
- **Hint 2**：考虑新旧版本共存期间的流量分发。负载均衡器以轮询（Round-Robin）方式将请求均分到存活的实例上。
- **Expected Observation**：在替换第 1 台机器时，存活实例为 1 台新版、2 台旧版。如果新版引入了破坏性数据库变更或不可逆状态，路由到旧实例的流量（占总流量的 $\frac{2}{3} \approx 66.7\%$）就会失败；如果是旧版写的数据新版读不懂，路由到新版的流量（占 $\frac{1}{3} \approx 33.3\%$）就会报错。随着滚动更新完成，所有节点统一，报错表象消失。
- **Full Explanation**：这是典型的**版本倾斜（Version Skew）引发的部分流量雪崩**。由于开发人员未遵守膨胀-收缩模式，直接发布了具备破坏性协议变更的代码，导致在滚动发布的过渡期内，请求被随机打到新版与旧版实例上。当请求打到无法处理该数据结构的实例时产生 500 报错。这一现象充分警示我们：必须将版本兼容性视为首要工程契约。

## 15. 核心概念与重访关系 (Concepts & Revisits)

- **`EC-CON-010 Failure`（故障）**：
  - *重访定位*：从硬件/节点失效拓展至版本共存期的接口不兼容故障。揭示了软件演进本身就是分布式系统最主要的故障来源之一；
- **`EC-CON-005 Interface`（接口）**：
  - *重访定位*：深化至系统演进中的动态契约管理。接口不仅要在静态代码中清晰，更必须在时间维度上支持向后兼容（Backward Compatibility）；
- **`EC-CON-017 Trust Boundary`（信任边界）**：
  - *重访定位*：从物理与网络边界扩展至软件供应链密码学边界。确立“不可变标识 $\neq$ 身份认证 $\neq$ 构建凭据 $\neq$ 策略准入”的学术公理。

## 17. 精确推断边界与禁止事项 (Exact Inference Limits)

- **禁止事项 1**：严禁宣称“只要使用了滚动更新、蓝绿部署或金丝雀发布，就能 100% 保证零停机或零错误”。

- **禁止事项 4**：严禁将本课确定性仿真中的 0 错误结果泛化为工程现实中的普适性零停机保证。
