## 1. 学习者核心问题 (Learner Question)

> “当我们在终端敲下 `docker run` 时，操作系统内部到底发生了什么？为什么工程师常说‘容器只是一种特殊的受限进程’，而不是一台迷你的轻量级虚拟机？Linux 内核是如何通过命名空间（Namespaces）和控制组（Cgroups）拼装出隔离幻觉的？这种隔离的真实安全边界与失效底线究竟在哪里？”

在现代软件工程中，“容器（Container）”与“Docker 镜像”已经成为应用交付的事实标准。然而，商业宣传和直觉隐喻常常让初学者产生严重的认知偏差：
- 误以为容器内部运行着一个“裁剪版的微型操作系统（Guest OS）”；
- 误以为容器拥有与虚拟机（VM）等同的强物理硬件隔离边界；
- 误以为 OCI 镜像本身就是一个已经挂载完毕的文件系统。

在 `M06` 中，我们掌握了进程（Process）、系统调用与内核执行上下文；在 `M07` 中，我们建立了虚拟内存与页表隔离心智；在 `M08` 中，我们理解了文件描述符与虚拟文件系统（VFS）。

本课将带领学习者穿透一切产品品牌与工具包装，回到操作系统内核机制本身：通过 Linux 原生的只读内核接口（`/proc/self/ns` 与 `/proc/self/cgroup`），亲手拆解“容器”的机械骨架，严密厘清普通进程、容器化进程与硬件虚拟机的本质界限。

| :--- | :--- | :--- |

## 3. 机制模型 (Mechanism Model)

### (1) 容器不是虚拟机：架构三元对立

为了彻底打破“容器是微型虚拟机”的思维定势，我们对比现代计算系统中的三种进程执行上下文：

```
====================================================================================================
               FIG-M19-01: PROCESS VS. CONTAINER VS. VIRTUAL MACHINE BOUNDARY
====================================================================================================

  [PANEL A: ORDINARY HOST PROCESS]
   +-------------------------------------------------------------+
   | Application Process (PID 1042)                              |
   +-------------------------------------------------------------+
   | Shared System Call Interface (POSIX: open, fork, read, etc) |
   +-------------------------------------------------------------+
   | Host Operating System Kernel (Linux Monolithic Kernel)      |
   +-------------------------------------------------------------+
   | Physical Hardware (CPU, Memory, Storage, NIC)               |
   +-------------------------------------------------------------+

  [PANEL B: CONTAINERIZED PROCESS (Linux Mechanisms)]
   +------------------------------+ +------------------------------+
   | Containerized App A          | | Containerized App B          |
   | (PID 1 inside Namespace)     | | (PID 1 inside Namespace)     |
   | [Namespaces: net, pid, mnt]  | | [Namespaces: net, pid, mnt]  |
   | [Cgroups: memory.max, cpu]   | | [Cgroups: memory.max, cpu]   |
   +------------------------------+ +------------------------------+
   | SHARED HOST OPERATING SYSTEM KERNEL (Zero Guest Kernel!)      |
   +---------------------------------------------------------------+
   | Physical Hardware (CPU, Memory, Storage, NIC)                 |
   +---------------------------------------------------------------+

  [PANEL C: HARDWARE VIRTUAL MACHINE (Full Virtualization)]
   +------------------------------+ +------------------------------+
   | Guest App A                  | | Guest App B                  |
   | +--------------------------+ | | +--------------------------+ |
   | | Independent Guest Kernel | | | | Independent Guest Kernel | |
   | +--------------------------+ | | +--------------------------+ |
   | Virtual Hardware (vCPU/vRAM) | | Virtual Hardware (vCPU/vRAM) |
   +------------------------------+ +------------------------------+
   | Hypervisor / Type-1/2 VMM (KVM, Xen, ESXi)                    |
   +---------------------------------------------------------------+
   | Physical Hardware (Hardware Virtualization: Intel VT-x, AMD-V)|
   +---------------------------------------------------------------+
====================================================================================================
```

从内核空间与执行模型推导其本质区别：
1. **普通宿主机进程（Ordinary Process）**：直接以宿主机的全局视图运行，能看到宿主机所有进程 PID、网络接口与完整根文件系统，资源占用由操作系统全局调度策略决定；
2. **容器化进程（Containerized Process）**：**依然是宿主机内核上的普通线程/进程**！内核通过特定标志位（`CLONE_NEW*`）为其赋予局部视图（Namespaces），并通过控制组（Cgroups）对其物理内存、CPU 配额进行记账与封顶。**不存在 Guest OS 内核**！
3. **硬件虚拟机（Virtual Machine）**：通过硬件辅助虚拟化（如 Intel VT-x / AMD-V）与虚拟机监控器（Hypervisor/VMM），模拟出一整套独立的虚拟 CPU、MMU 与外设；虚拟机内部运行着**完全独立的 Guest OS 内核**。

> **核心结论**：容器与宿主机之间不存在第二层内核。容器内的所有系统调用，最终都由**宿主机同一个内核**直接处理！

### (2) 视图分区：Linux 命名空间 (Linux Namespaces)

命名空间（Namespaces）是 Linux 内核提供的一种资源抽象机制：它将全局系统资源（如 PID、网络设备、挂载点）包裹在一个个隔离的视图空间中，使得处于某个命名空间内的进程只能看到分配给该空间的资源子集。

Linux 内核动态支持多种命名空间（请注意：现代内核不断演化，严禁死记固定命名空间总数）：

| 命名空间类型 | 典型隔离资源 | 隔离视角下的直接表现 |
| :--- | :--- | :--- |
| **PID (Process ID)** | 进程编号与进程树 | 容器内的主进程将自己视为 **PID 1**，无法看到宿主机上其他无关进程；而宿主机观察同一进程为一个普通的大 PID（如 4829） |
| **NET (Network)** | 网络设备、IP 地址、路由表、端口绑定 | 拥有独立的虚拟网卡（`eth0` / `veth`）、独立的 localhost 回环和完全隔离的 TCP/UDP 端口空间（容器内可绑定 80 端口而不与宿主机的 80 端口冲突） |
| **MNT (Mount)** | 文件系统挂载树 | 拥有独立的挂载点目录树；容器执行 `mount` 或 `chroot`/`pivot_root` 仅对本空间生效，形成完全私有的文件系统视图 |
| **UTS (UNIX Timesharing)** | 主机名与域名 | 允许容器拥有自己独立的 `hostname`，而不修改宿主机主机名 |
| **IPC (Inter-Process Comm)**| POSIX/SysV 消息队列、共享内存、信号量 | 隔离进程间通信资源，防止非授权进程读写共享内存段 |
| **USER (User ID)** | UID 与 GID 映射 | 允许进程在容器内拥有 UID 0 (root) 权限，但在宿主机内核层面映射为一个无特权的普通用户（如 UID 10001），大幅缩小攻击面 |
| **CGROUP (Cgroup)** | 控制组根视图 | 虚拟化 `/proc/self/cgroup` 的根路径观察 |
| **TIME (Time)** | 虚拟单调时间与引导时间偏差 | 允许容器拥有独立的单调时钟偏移量（自 Linux 5.6 引入） |

#### 内核如何标识命名空间？—— Inode 观察法
在 Linux 伪文件系统 `/proc` 中，每个进程目录下都有一个 `ns/` 目录：
```bash
$ ls -l /proc/self/ns
lrwxrwxrwx 1 user user 0 Sep  6 12:00 cgroup -> 'cgroup:[4026531835]'
lrwxrwxrwx 1 user user 0 Sep  6 12:00 ipc -> 'ipc:[4026531839]'
lrwxrwxrwx 1 user user 0 Sep  6 12:00 mnt -> 'mnt:[4026531840]'
lrwxrwxrwx 1 user user 0 Sep  6 12:00 net -> 'net:[4026531992]'
lrwxrwxrwx 1 user user 0 Sep  6 12:00 pid -> 'pid:[4026531836]'
lrwxrwxrwx 1 user user 0 Sep  6 12:00 user -> 'user:[4026531837]'
lrwxrwxrwx 1 user user 0 Sep  6 12:00 uts -> 'uts:[4026531838]'
```
- 每一个符号链接指向的目标格式为 `type:[inode_number]`；
- 这个**inode 编号**是 Linux 内核在内存中维护该命名空间数据结构的唯一标识符；
- **判等法则**：两个进程若在某个命名空间符号链接上读出**完全相同的 inode 编号**，则它们处于同一个命名空间内；若编号不同，则彼此处于独立的隔离视图之中。

### (3) 资源配额与记账：Linux Cgroups (Control Groups)

命名空间解决了“进程能看到什么”的问题，但完全没有解决“进程能消耗多少”的问题。
如果仅有命名空间，一个处于独立 PID 命名空间内的死循环或恶意内存泄漏脚本，能够瞬间耗尽宿主机的所有 CPU 和物理内存，导致整机崩溃（OOM）。

这就是 **控制组（Cgroups - Control Groups）** 登场的时刻：
- **Cgroups 的本质**：Linux 内核对一组进程进行资源分配、计量记账（Accounting）、优先级限制和配额冻结的机制；
- **核心控制维度**：
  - **内存（Memory）**：硬上限限制（`memory.max`）、软交换限制（`memory.swap.max`）。当进程内存达到硬上限时，由内核触发 cgroup 局部 OOM Killer，直接终止该组内的进程，保护宿主机不被拖垮；
  - **CPU 配额（CPU Bandwidth）**：通过 CFS 调度器周期与配额（`cpu.max = $QUOTA $PERIOD`），例如设置 `50000 100000` 表示在 100ms 周期内最多允许使用 50ms CPU 时间（即 0.5 核心）；
  - **I/O 节流（IO Quota）**：限制磁盘读写 IOPS 与字节吞吐量（`io.max`），防止单个租户打爆磁盘通道；
  - **进程数上限（PIDs Limit）**：限制组内可 `fork` 的最大子进程数量（`pids.max`），物理性防范 `fork 炸弹`。

#### Cgroup v1 vs. Cgroup v2 (Unified Hierarchy)
- **Cgroup v1（传统割裂层级）**：每个控制器（cpu, memory, blkio）各自挂载独立的树状目录。一个进程可以在 memory 树的 GroupA，同时在 cpu 树的 GroupB，导致控制器之间协同极其困难，容易死锁；
- **Cgroup v2（统一层级模型，现代 Linux 默认）**：所有控制器挂载在单一树状结构 `/sys/fs/cgroup` 下。采用“非根叶子节点规则”（只有叶子节点才能挂载进程，内部节点配置资源分布控制），逻辑自洽且支持跨资源协调（如缓存回写与内存限制的一致性追踪）。

### (4) 存储视角：OCI 镜像与只读/可写联合挂载

初学者常问：“为什么从 Docker Hub 下载一个 Ubuntu 镜像只要 70MB，而安装真正的 Ubuntu 镜像需要好几 GB？”
- **因为 OCI 镜像不包含内核！** 它只包含运行用户态程序所需的库、二进制工具与配置文件（Rootfs），宿主机内核早已在物理机上运行；
- **分层机制（Layering）**：
  - 镜像由多个只读层（Read-Only Layers）构成，每一层在磁盘上由 SHA-256 内容寻址哈希（Digest）唯一标识；
  - 容器启动时，底层存储驱动（如 Linux 的 **OverlayFS**）将这些只读层以 `lowerdir` 方式合并挂载；
  - 最顶层再挂载一个轻量级的可写层（`upperdir` / `workdir`）；
  - 当容器内部修改文件时，OverlayFS 使用**写时复制（Copy-on-Write, CoW）**：将底层文件复制到最顶层进行修改，底层只读镜像层永远保持洁净与共享。

## 5. 关键误区与严密辨析

### 误区 1：“容器具有与物理机/虚拟机完全等价的强安全隔离”
- **严密辨析**：**错！**
  虚拟机由硬件虚拟化指令与 Hypervisor 隔离，Guest OS 崩溃或被恶意代码控制，攻击者面对的是 Hypervisor 构筑的硬件模拟屏障。
  而在容器模型下，**所有容器共享同一个宿主机内核**！如果内核出现提权漏洞（如利用 Dirty COW 漏洞、未修复的系统调用缺陷）或者容器挂载了高危宿主机目录（如 `/var/run/docker.sock`），攻击者能够直接逃逸出容器视图，彻底接管整台宿主机。**容器绝不是万无一失的安全沙箱**。

### 误区 2：“容器启动很慢是因为它在启动一个微型操作系统”
- **严密辨析**：**错！**
  容器启动慢通常是因为网络下载大镜像、解压大量 IO 文件或应用自身 JVM/框架冷启动耗时。
  对于 Linux 内核而言，启动一个容器的底层开销，本质上仅仅是调用若干次 `clone()`、`unshare()` 和写入几个 cgroup 配置文件的**微秒级内核开销**。

### 误区 3：“只要镜像标签叫 `:v1.0`，我拉取的就永远是同一份代码”
- **严密辨析**：**错！**
  在 OCI 体系中，**标签（Tag）是完全可变指针（Mutable Pointer）**。开发者随时可以强制推送（Force Push）覆盖同一个 Tag！
  真正具备不可变保证的只有**内容哈希摘要（Content Digest）**，例如 `my-service@sha256:4a985e9...`。更重要的是：**摘要本身只保证完整性（Tamper-evidence），不代表来源可信（Provenance）**，只有结合数字签名（如 Sigstore / Cosign）与 SLSA 出处证明才能建立信任。

## 7. 概念与思维模型小结

1. **命名空间管“能看见什么”（Visibility）**：它为进程提供私有的视图副本。同一个内核任务，在容器内是 PID 1，在宿主机是 PID 4829；
2. **Cgroups 管“能用多少”（Accounting & Quotas）**：它限制进程组的物理内存、CPU 调度周期与 IO 吞吐，通过局部 OOM Killer 防止单进程拖垮宿主机；
3. **“容器”没有独立内核**：它不是硬件虚拟化，所有容器共享宿主机内核。容器的安全隔离边界，物理受限于 Linux 内核的漏洞与系统调用攻击面；
4. **OCI 镜像是不变分层，运行时是联合挂载**：容器基于 Copy-on-Write 机制共享基础镜像层，只有顶层工作目录记录增量变动。

## 8. 渐进式支持与思考题

### 思考题
为什么在未启用 User 命名空间（User Namespace）的情况下，容器内的 root 用户（UID 0）通常也是宿主机的 root 用户？如果容器挂载了宿主机的 `/` 根目录，容器内的进程能做什么？

### 思考指引
- **Hint 1**：回想 `M06` 与 `M07` 中的权限检查：Linux 内核判断某个进程是否有权限写文件或发送信号，本质上看的是该进程内核 `task_struct` 中的实际 UID（EUID）；
- **Hint 2**：若没有配置 User 命名空间映射，容器内的 UID 0 映射给内核的正是宿主机的数字 `0`；
- **核心结论**：容器内的 root 就是宿主机的 root！若其获得敏感宿主机目录挂载，即可直接修改宿主机 `/etc/shadow` 或定时任务，实现无阻碍宿主机提权逃逸。这正是为什么生产环境推行**无特权容器（Rootless Containers）**与严格限制容器权能（Capabilities）。

学完本课后，你已经看清了单机维度上“容器”的机械底牌：它不过是 Linux 内核进程经过命名空间视图封装与 Cgroups 配额约束后的运行形态。
