## 1. 学习者核心问题 (Learner Question)

> “当我们在终端敲下 `docker run` 时，操作系统内部到底发生了什么？为什么工程师常说‘容器只是一种特殊的受限进程’，而不是一台迷你的轻量级虚拟机？Linux 内核是如何通过命名空间（Namespaces）和控制组（Cgroups）拼装出隔离幻觉的？这种隔离的真实安全边界与失效底线究竟在哪里？”

在现代软件工程中，“容器（Container）”与“Docker 镜像”已经成为应用打包与交付的事实标准。然而，直觉隐喻和商业宣传往往让初学者形成失真的认知模型：
- 误以为容器内部运行着一个“裁剪版微型操作系统与独立内核（Guest Kernel）”；
- 误以为容器提供了与硬件虚拟机（VM）相同的强硬件隔离沙箱；
- 误以为 OCI 镜像本身就是一个已经挂载完毕的文件系统，或者必须与 OverlayFS 绑定。

在 `L06-01` 中，我们掌握了进程（`EC-CON-018 Process`）的概念与内核执行上下文；在 `L07-01` 中，我们理解了虚拟内存与地址空间隔离；在 `L08-01` 中，我们学习了文件描述符与虚拟文件系统（VFS）。在 `M16` 中，我们理解了端到端网络通信。

本课将带领学习者穿透一切产品品牌与工具外壳，回到操作系统内核机制本身：通过 Linux 原生的只读内核接口（`/proc/self/ns`、`/proc/self/cgroup`、`/proc/self/status`），亲手解构“容器”的机械骨架，严密厘清普通进程、容器化进程与硬件虚拟机的机制边界与隔离极限。

## 3. 机制模型 (Mechanism Model)

### (1) 容器不是虚拟机：架构三元对立

为了彻底打破“容器是微型虚拟机”的直觉错误，我们严格对比现代计算系统中的三种执行上下文：

```
====================================================================================================
               FIG-M19-01: PROCESS VS. CONTAINER VS. VIRTUAL MACHINE BOUNDARY
====================================================================================================

  [PANEL A: ORDINARY HOST PROCESS]
   +-------------------------------------------------------------+
   | Application Process (PID 1042)                              |
   +-------------------------------------------------------------+
   | Shared System Call Interface (POSIX: open, fork, read, etc) |
   +-------------------------------------------------------------+
   | Host Operating System Kernel (Linux Monolithic Kernel)      |
   +-------------------------------------------------------------+
   | Physical Hardware (CPU, Memory, Storage, NIC)               |
   +-------------------------------------------------------------+

  [PANEL B: CONTAINERIZED PROCESS (Linux Mechanisms)]
   +------------------------------+ +------------------------------+
   | Containerized Process A      | | Containerized Process B      |
   | (e.g. PID 1 in child PID ns) | | (e.g. PID 1 in child PID ns) |
   | [Namespaces: net, pid, mnt]  | | [Namespaces: net, pid, mnt]  |
   | [Cgroups: memory.max, cpu]   | | [Cgroups: memory.max, cpu]   |
   +------------------------------+ +------------------------------+
   | SHARED HOST OPERATING SYSTEM KERNEL (Zero Guest Kernel!)      |
   | [Boundaries: Namespaces, Cgroups, Seccomp, LSM, Capabilities] |
   +---------------------------------------------------------------+
   | Physical Hardware (CPU, Memory, Storage, NIC)                 |
   +---------------------------------------------------------------+
   * Explicit Note: Namespace/cgroup evidence != full security proof!

  [PANEL C: HARDWARE VIRTUAL MACHINE (Conventional Virtualization)]
   +------------------------------+ +------------------------------+
   | Guest Process A              | | Guest Process B              |
   | +--------------------------+ | | +--------------------------+ |
   | | Independent Guest Kernel | | | | Independent Guest Kernel | |
   | +--------------------------+ | | +--------------------------+ |
   | Virtual Hardware (vCPU/vRAM) | | Virtual Hardware (vCPU/vRAM) |
   +------------------------------+ +------------------------------+
   | Hypervisor / Type-1/2 VMM (KVM, Xen, ESXi)                    |
   +---------------------------------------------------------------+
   | Physical Hardware (Hardware-Assisted: Intel VT-x, AMD-V)      |
   +---------------------------------------------------------------+
====================================================================================================
```

从内核空间推导其本质区别：
1. **普通宿主机进程（Ordinary Process）**：以宿主机全局视图和当前用户凭据运行，其能够看到的文件、进程与网络取决于其凭据与挂载树；
2. **容器化进程（Containerized Process）**：**依然是宿主机内核上的普通线程/进程**！内核为其分配了受限的局部命名空间视图，并通过 Cgroups 对物理资源进行记账与封顶。**不存在独立的 Guest OS 内核**；
3. **硬件虚拟机（Virtual Machine）**：通过虚拟化监控器（Hypervisor/VMM）和硬件辅助虚拟化指令（Intel VT-x / AMD-V），为虚拟机模拟独立的虚拟硬件；虚拟机内部运行着**完全独立的 Guest OS 内核**。

> **核心机制结论**：容器与宿主机之间不存在第二层内核。容器内的每一个系统调用，最终都由**宿主机同一个内核**直接调度与处理。

### (2) 视图分区：Linux 命名空间 (Linux Namespaces)

命名空间（`EC-CON-013 Isolation`）是 Linux 内核提供的一种视图隔离机制：它将原本全局的系统资源（如 PID、网络接口、挂载点）分区，使得处于特定命名空间内的进程只能感知该命名空间内可见的资源。

当前 Linux 内核文档记载的常见命名空间类型包括：
- `pid`：隔离进程 ID 空间。在新的 PID 命名空间中创建的第一个进程成为该空间的 PID 1；
- `net`：隔离网络设备、IP 地址、路由表与端口绑定空间；
- `mnt`：隔离文件系统挂载点视图（挂载传播机制控制跨命名空间可见性）；
- `ipc`：隔离 System V IPC 与 POSIX 消息队列；
- `uts`：隔离主机名（hostname）与 NIS 域名；
- `user`：隔离用户 ID（UID）与组 ID（GID）映射；
- `cgroup`：隔离 cgroup 根目录视图；
- `time`：隔离系统单调时间与引导时间偏移量。

> **动态性原则**：Linux 内核不断演进，不同内核版本支持的命名空间种类不同。严禁死记固定数字（例如“Linux 只有 7 种命名空间”），而必须通过 `/proc/self/ns/*` 进行只读探查。

每个命名空间在内核中分配一个唯一的 inode 编号（如 `net:[4026531992]`）。当前进程与其子进程是否共享该命名空间，可通过比较符号链接目标中的 inode 编号精确判定。

### (3) 资源配额与记账：Linux 控制组 (Cgroups)

如果命名空间负责回答**“进程能看到什么”**，控制组（Cgroups）则负责回答**“进程能消耗多少物理资源”**。

#### Cgroup v1 vs. Cgroup v2
- **Cgroup v1**：早期设计，每个物理资源（CPU、Memory、blkio、pids）拥有独立的挂载层级与目录树。不同控制器之间缺乏统一协调，多控制器协作时层级错位；
- **Cgroup v2（Unified Hierarchy）**：现代 Linux 默认的统一单根层级树。所有启用的控制器挂载在同一个根层级（`/sys/fs/cgroup`）下。

#### Cgroup v2 的无内部进程约束 (No Internal Process Constraint)
当前 Linux 内核 cgroup v2 规范定义了精确的**“无内部进程约束（No Internal Process Constraint）”**：
- 在非根（non-root）的 domain cgroup 中，一旦该 cgroup 向其子目录启用了子树控制器（通过 `cgroup.subtree_control` 激活），则该 cgroup 自身**不能包含直接挂载的进程（member processes）**；
- 成员进程只能存在于叶子节点，或者尚未向子级分发控制器的节点中；
- **根控制组（Root cgroup）豁免此规则**。

#### 核心控制器接口举例
当相应控制器启用时，接口文件提供配额约束：
- `memory.max`：内存使用硬上限。注意：触碰上限时并非必定立刻触发 OOM Killer，内核会先尝试回收可丢弃的 Page Cache，只有在内存完全无法回收且配置了强制终止时才会触发 OOM 终止；
- `cpu.max`：以配额时间/周期（`quota period`）形式限制 CPU 时间片；
- `pids.max`：限制该控制组及其子组内可创建的进程/线程总数，防止 fork 炸弹。

### (4) OCI 镜像规范 vs. 运行时存储驱动

必须严密区分**制品规范**与**操作系统文件系统实现**：
1. **OCI 镜像规范（Image Format Specification，最新发布 v1.1.1）**：
   - 规定了镜像清单（Manifest）、配置（Config Blob）和层（Layers）的 JSON 格式与打包标准；
   - 每一层由内容摘要（Content Digest）唯一标识。OCI 摘要语法默认 baseline 为 SHA-256，但规范同样支持 SHA-512 和 BLAKE3；
   - **分层 Descriptor Digest 与 DiffID 的区别**：Descriptor Digest 是压缩打包归档（如 `.tar.gz`）的内容哈希；DiffID 则是解压后原始 tar 包未压缩内容（uncompressed tar archive）的内容哈希；
2. **OCI 运行时规范（Runtime Specification，最新发布 v1.3.0）**：
   - 规定了在解压的运行时目录包（Runtime Bundle）中如何组织 `config.json` 与 `rootfs` 目录；
3. **运行时联合文件系统（如 OverlayFS）**：
   - 是 Linux 内核的一种文件系统实现（通过 `lowerdir`、`upperdir`、`workdir` 叠加挂载）；
   - **OCI 规范本身完全不强制依赖 OverlayFS**！生产环境还可以使用 btrfs、zfs、devicemapper、甚至直接解包的只读 rootfs 目录。

## 4. 断言层与边界 (Claim Layer)

为了保证学术与工程推断的严密性，本课确立以下机制断言：

- **断言 1（进程模型本质）**：在 canonical Linux 环境下，容器内的运行实体是一个或多个共享宿主机内核的普通线程/进程。容器不存在独立的 Guest OS 内核。
- **断言 2（命名空间正交性）**：一个进程在每一种命名空间类型中必然属于且仅属于一个具体的命名空间实例；同一进程的不同命名空间之间相互正交。
- **断言 3（配额与视图分离）**：Cgroups 负责资源记账与物理配额，不改变命名空间视图；Namespaces 负责视图隔离，不提供物理资源消耗上限。
- **断言 4（只读无侵入性）**：探查本机的命名空间与 Cgroups 状态仅需读取 `/proc/self/ns/*`、`/proc/self/cgroup`、`/proc/self/status`，本课 Required Core 绝不向 `/sys/fs/cgroup` 写入任何数据，亦不调用需要 root 特权的挂载操作。

## 9. 常见认知误区 (Common Misconceptions)

### 误区 1：“容器启动快是因为容器镜像被秒级执行，虚拟机启动慢是因为它太重。”
**纠正**：容器启动快是因为创建容器本质上就是宿主机调用 `clone(2)` 系统调用派生一个受限进程，无需经历虚拟 BIOS 初始化、虚拟硬件枚举和 Guest OS 内核自举；但这并不意味着启动时间是恒定的微秒级，应用初始化的耗时同样取决于可执行文件依赖装载与存储驱动开销。

### 误区 2：“容器 root 用户和宿主机 root 用户完全一模一样，所以容器绝对不安全。”
**纠正**：如果不启用用户命名空间（User Namespaces）且不裁剪能力集，容器内的 UID 0 确实对应宿主机内核中的 UID 0；但是，通过启用 User Namespaces（将容器内 UID 0 映射为宿主机非特权 UID 100000+）、禁用特权能力（如 `CAP_SYS_ADMIN`）、应用 Seccomp 系统调用白名单以及 AppArmor/SELinux，容器可以被置于高度收敛的最小权限执行沙箱中。

### 误区 3：“Cgroup v2 规定只有叶子节点能包含进程。”
**纠正**：这是对内核文档的片面转述。内核精确规则是：**非根 domain cgroup 在通过 `cgroup.subtree_control` 向其子节点启用控制器后，其自身不能包含成员进程**。如果一个 cgroup 并没有向子目录启用控制器，或者属于根控制组，它可以直接容纳成员进程。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### 诊断关卡：如何从内核只读证据判定当前处于容器内还是裸机宿主机？

- **Question**：你在 SSH 连接到一个 Linux 环境后，手头没有任何 `docker` 或 `podman` CLI 工具，如何仅凭 `/proc` 文件系统中的只读证据，推断当前 shell 究竟是运行在一个受限的容器内，还是运行在裸机/虚拟机的初始宿主环境中？
- **Hint 1**：检查当前 shell 的 PID 1。在宿主机上，PID 1 通常是 `systemd`、`init` 或系统的初始引导进程；在标准容器内，PID 1 往往直接是应用进程或 entrypoint 脚本。
- **Hint 2**：查看 `/proc/1/cgroup` 或 `/proc/self/cgroup`。在容器内，cgroup 路径通常包含 `docker`、`containerd`、`kubepods` 或一个长 hash 字符串切片；在 systemd 托管的宿主机根层级下，路径通常呈现为 `/init.scope`、`/user.slice` 或类似形式。
- **Expected Observation**：在宿主机上，`/proc/self/ns/*` 中的 inode 编号通常与系统其它普通服务进程完全相同；在容器内，`net`、`pid`、`mnt` 的 inode 编号与宿主机上的其它进程截然不同。
- **Full Explanation**：容器并非神话，其所有“隔离”特征完全由内核暴露在 `/proc` 接口中。由于 PID 命名空间将容器初始进程重映射为 1，且其挂载了独立的 mnt 命名空间和独立的 cgroup 切片，因此仅通过分析 `/proc/self/cgroup` 的层级路径以及 `/proc/self/ns/*` 的 inode，即可在完全不依赖第三方监控工具的前提下确定当前进程的隔离边界。

### 核心要素要求
1. **普通进程 Panel A**：直通宿主机内核与系统调用表；
2. **容器化进程 Panel B**：严格标注其下方的 **SHARED HOST OPERATING SYSTEM KERNEL**，严禁画出任何 Guest Kernel；明确标注命名空间与 Cgroups 边界；明确附加安全声明：*Namespace/resource evidence != full security proof*；
3. **虚拟机 Panel C**：明确画出独立的 **Guest Kernel** 与硬件辅助虚拟化 Hypervisor 层。

## 15. 核心概念与重访关系 (Concepts & Revisits)

- **`EC-CON-013 Isolation`（隔离）**：
  - *重访定位*：深入至操作系统内核层级。揭示了命名空间仅实现了**视图分区**，Cgroups 仅实现了**资源用量限额**，两者均不构成物理硬件级别的完全隔离。
- **`EC-CON-018 Process`（进程）**：
  - *重访定位*：第一原籍在 `M06/L06-01`。本课重访并深化：容器内的执行单元本质上仍然是宿主机内核调度的进程，破除“容器内部包含一套微型系统”的思维定势。
- **`EC-CON-002 Abstraction`（抽象）**：
  - *重访定位*：解构容器技术的分层抽象。OCI 镜像抽象屏蔽了分发传输的复杂性，运行时联合文件系统抽象了存储分层，命名空间与 Cgroups 抽象了受限的计算环境。

## 17. 精确推断边界与禁止事项 (Exact Inference Limits)

为了维护严密求实的学术底线，本课学习者与任何自动化代理必须遵守以下**绝对禁止事项**：

- **禁止事项 1**：严禁断言“容器具有与虚拟机等价的安全隔离度”。容器共享宿主机内核，共享内核攻击面绝不等同于硬件虚拟化边界。
- **禁止事项 2**：严禁将 OCI 镜像分层规范与 OverlayFS 存储驱动划等号。OverlayFS 只是 Linux 内核的一种联合挂载实现，OCI 镜像并不强制要求 OverlayFS。
- **禁止事项 3**：严禁宣称“容器启动时间恒定为微秒级”。启动耗时取决于镜像解包、存储驱动准备、应用依赖加载等具体环境。
- **禁止事项 4**：严禁在非 Linux 环境中将检查器未运行或受限状态伪报为 PASS。必须如实填报 `ENVIRONMENT-BLOCKED / NOT RUN`。
