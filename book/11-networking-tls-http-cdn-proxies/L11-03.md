# L11-03｜缓存、条件验证与分层代理权衡：从 HTTP/1.1 到 H2 与 H3

## 学习者问题

当你刷新一个热门网站的页面时，为什么几兆字节的静态图片、样式表和脚本能够在短短几十毫秒内加载完毕？

你可能听过“浏览器把文件缓存下来了”。但如果服务器上的图片更新了，客户端怎么知道？当浏览器收到 `304 Not Modified` 时，为什么网络传输耗时几乎为零？当网络链路上存在 CDN 边缘节点、网关反向代理和正向代理时，请求首部是如何被转换和传递的？如果后端源站挂了，代理会向客户端返回什么？

更进一步，为什么业界从 HTTP/1.1 演进到 HTTP/2，再到 HTTP/3（QUIC）？新的协议代际是否在所有指标上都“绝对碾压”旧协议？如果不是，工程权衡的代价是什么？

## 为什么重要

在现代大规模互联网应用架构中，**缓存（Caching）**与**分层代理（Proxies/CDNs）**是支撑海量并发与低时延体验的核心支柱。没有严谨的缓存与代理设计，任何中心化的源站数据库和应用服务器都将在高并发流量下被瞬间击穿：
- **混淆新鲜度与条件验证**：误以为“缓存就是服务器让存多久就存多久，过期了就重新完整下载”，不知道**新鲜度（Freshness）**是在本地无网络往返判定的，而**条件验证（Validation）**是通过 `ETag` 与 `If-None-Match` 发起轻量级验证往返；
- **误读 ETag 与 304 规范契约**：误以为“ETag 必须是文件内容的 MD5 或 SHA-256 哈希”，不知道强 ETag 在规范上是**不透明验证器（Opaque Validator）**；误以为“304 响应必须包含 `Content-Length: 0`”，不知道规范严格要求的是**响应报文主体为 0 字节（Zero Body Bytes）**，而允许携带表述首部；
- **代理职责与首部穿透混淆**：在编写反向代理或网关时，盲目将客户端所有的 HTTP 首部原封不动透传给后端，将逐跳首部（Hop-by-hop headers，如 `Connection`）泄漏给后端，破坏连接复用；
- **盲目崇拜最新传输协议**：误以为“HTTP/3 绝对比 HTTP/2 好，HTTP/2 绝对比 HTTP/1.1 好”，不知道在丢包率极低的局域网内 HTTP/2 拥有极高效率，而在高丢包率移动网络下 TCP 队头阻塞才会让 QUIC 显现优势，同时 QUIC 的 UDP 方案在部分运营商网络中面临严苛的 QoS 丢包限速以及更高的用户态 CPU 开销。

要建立深度的现代 Web 性能与网络架构世界模型，必须深入理解缓存状态机、逐跳代理契约以及传输协议演进的技术权衡。本课正式复访核心系统概念：**缓存（Caching，EC-CON-011）**、**局部性（Locality，EC-CON-012）**、**接口（Interface，EC-CON-005）** 与 **故障（Failure，EC-CON-010）**。

## Mental Model｜新鲜度、验证器与分层中继

### 1. HTTP 缓存的两大独立支柱

HTTP 缓存（RFC 9111）的设计哲学是：**能不在网络上传输，就绝不在网络上传输；非要走网络传输，就绝不传输重复的报文主体**。

```
                           客户端发起资源请求
                                   |
                                   v
             [支柱 1: 本地新鲜度判定 (Freshness Check)]
                     (由 Cache-Control: max-age 计算)
                                   |
                   +---------------+---------------+
                   |                               |
              [仍在有效期内]                   [已过保鲜期]
                   |                               |
                   v                               v
           [本地直接命中 (Hit)]          [支柱 2: 条件验证 (Validation)]
           0 毫秒时延，0 网络字节       (发起带条件的轻量网络请求)
                                                   |
                                                   v
                                   发送: If-None-Match: <ETag>
                                                   |
                                   +---------------+---------------+
                                   |                               |
                            [资源内容未改动]                 [资源内容已更新]
                                   |                               |
                                   v                               v
                        服务端返回: 304 Not Modified    服务端返回: 200 OK
                        首部包含验证元数据              首部包含最新 ETag
                        响应正文: 0 字节 (Zero Body)    响应正文: 完整新数据
                        复用本地已有缓存表述            覆盖本地过期缓存
```

- **支柱 1：新鲜度（Freshness）**：缓存会依据显式 freshness 信息（如 `max-age` / `Expires`）以及适用的缓存规则判断 stored response 是否 fresh。满足当前请求的其他 cache-control 条件时，fresh response **可以**被复用而无需向源站重新验证；并非“只要 fresh 就永远零网络请求”。
- **支柱 2：条件验证（Validation）**：当缓存表述已过保鲜期（Stale），客户端不应直接丢弃缓存并重新全量下载，而是携带上一次服务端给予的**验证器（Validator，如 ETag）**发起条件请求：`If-None-Match: "v1-xyz"`。
  - 若服务端比对发现该资源在此期间未发生实质变更，则返回 **`304 Not Modified`**；
  - **核心机制**：`304` 响应通知客户端“你手里的版本依然合法有效，刷新你的新鲜度计时器即可”。`304` 响应报文中**严格不携带任何报文正文（Zero Body Bytes）**。一次网络往返仅消耗数百字节的首部传输，瞬间避免了数兆字节甚至数吉字节的重复数据拉取！

### 2. ETag：不透明的强/弱验证器 (Opaque Validator)

许多工程师以为 ETag 是“文件的 MD5 哈希值”。这是常见误解：
- 根据 RFC 9110 Section 8.8.3，**实体标签（Entity Tag, ETag）在协议标准中是一个不透明的 ASCII 字符串（Opaque Validator）**；
- 服务端完全可以自由决定 ETag 的生成算法：它可以是版本号（`"v1.0.4"`）、数据库自增 ID（`"doc-4021"`）、修改时间戳的高精度编码，或者内容的加密哈希；客户端**绝对不应该尝试解析 ETag 内部的字符串含义**，而只需在后续请求中原样回传。
- **强验证器 vs 弱验证器**：
  - **强 ETag（如 `"strong-v1"`）**：可用于 strong comparison，表示 origin 按强验证器要求区分 representation data；它不是“客户端可解析的内容哈希”，课程也不把某个字符串格式当成强验证器算法。
  - **弱 ETag（如 `W/"weak-v1"`）**：仅保证资源在业务语义层面等价，可能底层格式发生了不影响逻辑的微小重排（例如压缩算法微调或 HTML 空格清理）。

## Mechanism｜代理中继、逐跳首部与协议代际权衡

### 1. 代理、网关与中间人首部转换

在现代互联网链路中，客户端发出的请求往往需要穿越多层中间人（Intermediary）：

```
+----------+      Client Req      +----------------------+      Upstream Req      +---------------+
|  Client  | -------------------> | Intermediary Adapter | ---------------------> | Origin Server |
|  (curl)  | <------------------- |   (Reverse Proxy)    | <--------------------- |  (:origin)    |
+----------+     Client Resp      +----------------------+      Upstream Resp     +---------------+
                                  1. Strip Hop-by-hop headers
                                  2. Inject Via: 1.1 proxy
                                  3. Map Outage to 502 Bad Gateway
```

#### A. 逐跳首部（Hop-by-hop）与端到端首部（End-to-end）
RFC 9110 Section 7.6.1 做出了严格的接口隔离：
- **连接特定字段处理**：intermediary 必须解析 `Connection` 字段，并在转发前移除 `Connection` 本身及其列出的 connection-options；还要按当前 HTTP 规范处理已知 connection-specific 字段。课程不会把一张静态字段名单冒充完整算法。
  - 例如，客户端与代理之间采用 `Connection: close`，代理与后端源站之间完全可以使用长连接池 `Connection: keep-alive`；如果代理把客户端的 `close` 盲目透传给后端，将导致长连接池频繁断链。
- **端到端首部（End-to-end Headers）**：跨越整条链路传递给最终目标（如 `Accept`、`Cache-Control`、`If-None-Match`）。

#### B. 链路追踪首部：`Via`
中间人在适用的转发消息上维护 `Via`，其中 received-protocol 必须对应它**实际收到**的协议版本。LAB-REQ-01 的 HTTP/1.1 course hop 因此使用 `Via: 1.1 essential-cs-intermediary`；如果收到的协议不是 HTTP/1.1，就不能硬编码 `1.1`。

#### C. 上游故障映射：`502 Bad Gateway`
反向代理作为客户端与源站之间的网关，必须承担明确的故障隔离职责（EC-CON-010）：
- LAB-REQ-01 明确定义一个**课程故障映射**：当 course intermediary 无法建立到已停止 origin 的上游连接时，返回 `502 Bad Gateway`，并记录实际 host/runtime failure disposition。
- 这用于演示 gateway 失败位置，不意味着每个代理、每种 reset/timeout/协议错误都必须映射成 502；不同 intermediary 可以有更细的策略。

### 2. 传输协议代际演进与真实权衡 (No Universal Transport Winner)

为什么互联网会从 HTTP/1.1 走向 HTTP/2，再演进到 HTTP/3？每一代协议究竟解决了什么痛点，又付出了什么代价？

```
                               协议代际演进与队头阻塞权衡
+------------+-------------------------+-------------------------+-------------------------+
| 协议代际   | 底层传输协议             | 队头阻塞 (HOL) 表现     | 核心工程权衡与代价      |
+------------+-------------------------+-------------------------+-------------------------+
| HTTP/1.1   | TCP + HTTP/1.1 message syntax | 无 H2-style stream multiplexing；串行/流水线使用可能产生应用层等待 | 实现简单、可观察；并发策略由客户端/服务器决定 |
+------------+-------------------------+-------------------------+-------------------------+
| HTTP/2     | TCP + binary framing（HTTPS 场景通常结合 TLS；规范也有明文 prior-knowledge 路径） | HTTP streams 可多路复用；共享 TCP ordered byte stream 会让 loss/reordering 影响跨 stream 的可交付进度 | 减少 HTTP 层串行等待，但仍共享一条 TCP transport |
+------------+-------------------------+-------------------------+-------------------------+
| HTTP/3     | QUIC over UDP + TLS 1.3 key establishment | 一个 stream 缺失的数据不要求阻塞另一个 stream 的数据交付；仍共享拥塞控制、路径与实现资源 | 改变 cross-stream loss recovery；迁移、CPU 与网络策略收益/成本依部署而变 |
+------------+-------------------------+-------------------------+-------------------------+
```

#### 1. HTTP/1.1 的局限：应用层队头阻塞（Application-layer HOL）
HTTP/1.1 没有 HTTP/2 那种独立的多路复用 stream。一个连接可以串行发送请求，也存在 pipelining 语义，但响应顺序与现实实现支持会形成应用层等待；客户端也可以选择多个连接。**连接池数量是具体客户端/浏览器/version/current-practice 参数，不是课程固定的 6–8 常数。**

#### 2. HTTP/2 的突破与代价：多路复用与 TCP 队头阻塞
HTTP/2 引入二进制 framing 与 stream multiplexing，使多个 HTTP stream 可以在同一 TCP 连接上并发推进，消除了 HTTP/1.1 需要把应用交换简单串行化的主要限制；但 stream 仍共享 TCP 的 ordered byte stream。
**然而，代价转移到了传输层**：
- 由于底层依赖单一的 TCP 连接，TCP 协议栈强制维护全局单调递增的序号并提供严格保序递交；
- 当 TCP sequence space 中出现缺口时，后续 TCP 字节在补齐缺口前不能按序交付给上层。这可能延迟承载不同 HTTP/2 streams 的 frame，即使相关网络分组已经到达。
- 影响大小取决于 RTT、loss/reordering、拥塞控制、连接复用、客户端/服务器实现与 workload。课程不使用固定 `2%~5%` 阈值，也不预言 H2 必然比多连接 H1 更快或更慢。

#### 3. HTTP/3 (QUIC) 的解法与现实挑战
HTTP/3 把 HTTP 映射到 **QUIC** streams；QUIC 通常在用户态实现并运行在 UDP 之上，使用 TLS 1.3 key establishment 来保护连接。具体实现位置、offload 与 CPU 成本属于产品/平台证据，而不是协议要求：
- **跨流交付边界**：某个 QUIC stream 缺失的数据不要求另一个 stream 等待同一 sequence gap，因此避免 TCP 那种 connection-wide byte-order blocking；但 streams 仍共享拥塞控制、网络路径以及实现资源，不能说“完全互不影响”。
- **连接迁移（Connection Migration）**：QUIC Connection ID 与 path validation 机制支持连接在地址/路径变化后继续使用，但能否成功迁移取决于协议状态、路径可达性、实现和网络策略；不是“Wi‑Fi→5G 必定无缝”。
- **现实工程代价（Why it is NOT a universal winner）**：
  1. **实现/CPU 成本**：QUIC 的加密、loss recovery、拥塞控制和用户态/内核边界优化方式会影响 CPU 成本；不同实现与硬件 offload 能显著改变结果，因此没有固定 `2–3×` 常数。
  2. **网络策略兼容性**：某些网络会限制或阻断 UDP/QUIC，客户端/服务器也可能没有 H3 支持。回退策略属于具体 client deployment/current practice，不能说所有客户端“必须时刻”以某一种方式回退。

## Bounded Estimate Task｜缓存收益与时延量化

为了直观量化分层缓存体系对现代互联网基础设施的吞吐与时延收益，我们在此进行一项有界估算。

### 1. 显式参数与工程假设

- **源站物理部署**：部署于跨国数据中心，客户端与源站之间的往返时延（RTT）为 $\text{RTT}_{\text{origin}} = 100\text{ ms}$；
- **CDN 边缘节点部署**：部署于本地运营商城域网边缘，客户端到 CDN 节点的往返时延为 $\text{RTT}_{\text{edge}} = 5\text{ ms}$；
- **静态资源总量**：某页面包含 20 个静态资源（图标、样式、脚本），总大小 $S = 2\text{ MiB} = 2{,}097{,}152\text{ 字节}$；
- **请求并发度与访问规模**：每秒有 $N = 10{,}000$ 个用户并发请求该页面；
- **缓存命中率假设**：CDN 边缘节点经过热点预热后，综合缓存命中率达到 $H = 90\%$（即 $0.9$）。未命中（Cache Miss）的 $10\%$ 请求由 CDN 回源拉取。

### 2. 量化推导计算

1. **源站出口带宽削减量**：
   - **无缓存架构**：所有流量直达源站，源站出口所需带宽：
     $B_{\text{nocache}} = N \times S = 10{,}000 \times 2\text{ MiB/s} = 20{,}000\text{ MiB/s} \approx 19.53\text{ GiB/s}$
   - **分层缓存架构（90% 命中率）**：仅有 $10\%$ 的请求透穿至源站：
     $B_{\text{cached}} = N \times (1 - H) \times S = 10{,}000 \times 0.1 \times 2\text{ MiB/s} = 2{,}000\text{ MiB/s} \approx 1.95\text{ GiB/s}$
   - **模型结果**：在“每个请求都需要整份 2 MiB 表述、90% 命中且忽略填充/协议开销”等假设下，origin representation egress 降低 **90%**。这不等于服务器硬件或网络采购成本必然下降一个数量级。

2. **用户端平均往返时延（Average Latency）**：
   - **无缓存架构**：
     $$T_{\text{avg, nocache}} = \text{RTT}_{\text{origin}} = 100\text{ ms}$$
   - **分层缓存架构**：
     $$T_{\text{avg, cached}} = H \times \text{RTT}_{\text{edge}} + (1 - H) \times (\text{RTT}_{\text{edge}} + \text{RTT}_{\text{origin}})$$
     $$T_{\text{avg, cached}} = 0.9 \times 5\text{ ms} + 0.1 \times (5 + 100)\text{ ms} = 4.5\text{ ms} + 10.5\text{ ms} = 15\text{ ms}$$
   - **模型结果**：这个简化的“按命中率加权 RTT 分量”从 100 ms 变成 15 ms，数值降低 85%。它不是完整 page latency、TLS/HTTP handshake latency 或真实 CDN SLO。

### 3. 推断边界与局限（Inference Limits）

> **边界警示**：
> 以上推导建立在“静态资源不变且缓存命中模型完全独立”的简化假设之上。在真实生产系统中：
> 1. 动态生成且高度个性化的 API 数据无法简单配置长效静态缓存，其命中率通常显著低于纯静态文件；
> 2. CDN 边缘节点的内存与 SSD 存储容量有限，在面临长尾请求（Long Tail）时会发生缓存抖动（Cache Thrashing）与淘汰（Eviction）；
> 3. 大量对象同时变 stale/miss 时可能形成 cache stampede 并显著提高回源负载；放大倍数与系统是否失效取决于流量、缓存策略、origin capacity、request coalescing 等实际条件。

仔细辨析 <code>no-cache</code> 与 <code>no-store</code> 的区别：哪一个指示客户端“必须与服务器重新验证（Revalidate）后才能使用缓存”，哪一个指示“坚决不把数据写入任何磁盘或缓存存储”？
</details>

<summary>Hint 2</summary>
当服务端返回 <code>304 Not Modified</code> 时，响应报文中是否有数据正文（Body）？客户端收到 304 后，会渲染什么数据？
</details>

<details>
<summary>Expected Observation</summary>
<code>Cache-Control: no-cache</code> 允许存储响应，但要求 cache 在复用它满足请求前进行成功验证（除非有适用的更具体规则）；验证器不只限于 ETag。<code>no-store</code> 则禁止 cache 存储该响应/请求内容用于缓存。对实际已变化的表述错误返回 304 会让 cache 错误复用旧表述。内容指纹 URL + 长 freshness、入口文档短 freshness/`no-cache` 是**常见部署模式示例**，不是 RFC 强制的唯一“最佳实践”。
</details>

<details>
<summary>Full Explanation</summary>
这是关于 HTTP 缓存规范与现代工程发布流的经典面试与实战陷阱：

1. **<code>no-cache</code> 的精确语义（RFC 9111 Section 5.2.2.4）**：
   - 绝大多数初学者被其字面含义误导，以为 <code>no-cache</code> 等同于“不缓存”。
   - <code>no-cache</code> 允许 cache 存储响应，但在复用该响应满足后续请求前要求成功验证；验证可以使用适用的 ETag 或日期验证器，也可能经过 intermediary，而不是固定成“每次都直接向源站发送 If-None-Match”。
   - <code>no-store</code> 是缓存存储禁止指令，但敏感数据保护还需要认证、授权、客户端存储策略等其他控制；不要把一个 cache directive 写成完整的数据安全方案。

2. **错误强推 304 的语义后果**：
   - <code>304 Not Modified</code> 的核心契约是：服务端确认目标资源在语义和内容上与客户端持有的 ETag 完全一致，因此服务端**绝不发送任何正文数据（0 字节正文）**，指令客户端直接从本地缓存中解包出旧表述进行渲染。
   - 如果 representation 已变化却错误返回 304，拥有匹配 stored response 的 cache 会继续复用过期内容，造成应用版本错配。没有可用于该条件请求的 stored response 时客户端/cache 如何处置属于具体实现/协议状态，课程不预测“必然白屏”。

3. **常见的版本化静态资源部署模式（CURRENT PRACTICE EXAMPLE）**：
   - **入口文档示例**：可以使用较短 freshness 或 <code>no-cache</code> 让 cache 在复用前验证；具体策略按发布与离线需求设计；
   - **JS / CSS / 媒体文件**：文件名采用基于内容加密哈希的指纹命名（Content Hash，如 <code>vendor.a3b7c9.js</code>），并设置强缓存：
     <code>Cache-Control: public, max-age=31536000, immutable</code>
   - **架构收益与边界**：内容地址化 URL 可以把“新内容”变成新 cache key，从而支持较长 freshness；是否秒级发布、何时淘汰旧对象、离线客户端如何更新仍依赖 CDN/cache/browser 与发布系统。
</details>

## Common Misconceptions

- **“ETag 必须是文件的 MD5 或者哈希值。”** 错。根据 RFC 9110，ETag 只是一个由服务端生成的不透明字符串（Opaque Validator）。服务端可以将其设计为递增版本号、时间戳编码或业务 ID，客户端严禁猜测其算法。
- **“304 响应首部必须带有 `Content-Length: 0`。”** 错。RFC 9111 规范只严格约束 `304` 响应报文**必须不包含报文主体（Zero Body Bytes）**。由于 304 允许携带更新后的表述元数据（Representation Headers，如更新的 `ETag`、`Expires` 等），规范并未强制要求必须输出 `Content-Length: 0` 首部字段。
- **“HTTP/3 基于 UDP，所以在任何网络环境下都绝对比 HTTP/2 快。”** 错。在丢包率几乎为 0 的优质骨干网和数据中心局域网中，HTTP/2 凭借成熟的内核态 TCP 与网卡硬件卸载（TSO/GRO）通常具有更低的 CPU 消耗与同等优异的时延；而在企业防火墙或对 UDP 限速的劣质网络下，QUIC 甚至可能被降级或完全阻断。
- **“反向代理就是一个简单的网络端口转发工具。”** 错。合法的 HTTP 中间人必须承担严格的协议层职责：剥除逐跳首部（如 `Connection`）、注入链路跟踪首部（`Via`）、执行条件缓存验证、并将后端断链标准化映射为 `502 Bad Gateway`。

## What You Can Ignore—for Now

- HTTP/2 头部压缩 HPACK 与 HTTP/3 头部压缩 QPACK 的动态字典替换算法与 Huffman 树编码；
- QUIC 丢包探测与拥塞控制状态机（如 BBRv2、Cubic）在 UDP 层的数学收敛证明；
- Service Worker 离线缓存拦截规范。

## Exit Criteria

- 能阐明本地新鲜度判定（`Cache-Control`）与条件验证（`ETag` / `If-None-Match`）的根本差异；
- 能准确解释 `304 Not Modified` 响应报文主体为 0 字节的带宽节省机制；
- 能说明反向代理如何剥除逐跳首部、注入 `Via` 首部以及在源站离线时映射输出 `502 Bad Gateway`；
- 能深入对比 HTTP/1.1、HTTP/2、HTTP/3 在队头阻塞问题上的架构演进与权衡；
- 能完成给定制式下的缓存命中率与往返时延量化估算，并指出其推断边界。
