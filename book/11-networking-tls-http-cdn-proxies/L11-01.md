# L11-01｜TLS 1.3 握手、服务身份认证与信任边界

## 学习者问题

当你在浏览器中访问 `https://bank.example.com` 时，地址栏显示了一把“安全锁”。这把锁究竟保证了什么？

你可能听过“HTTPS 能够加密通信并防止窃听”。但如果网络中间有人搭建了一个代理服务器，或者伪造了 DNS 解析将你的流量引向恶意服务器，TLS 是如何发现并阻止假冒者的？为什么仅仅拥有一个受信任机构签发的有效证书，不足以证明一台服务器就是 `bank.example.com`？如果在开发测试时随手加上 `verify=False` 或 `curl -k`，你实际上撕开了一个多大的安全漏洞？

## 为什么重要

在现代系统设计与网络安全实践中，加密通信已经从“可选的高级特性”变成了基础设施的绝对基石。然而，许多工程师对 TLS 的理解仍然停留在“明文变乱码”的粗浅认知上，导致系统暴露在严重的安全威胁之下：
- **混淆传输加密与身份认证**：误以为“只要启用了加密通道就安全”，不知道若没有对服务端身份（Subject Alternative Name, SAN）进行严格校验，中间人攻击者（Man-in-the-Middle, MitM）完全可以与客户端建立合法的加密连接，在明文状态下捕获所有流量；
- **混淆信任链与身份匹配**：误以为“只要证书是由正规 CA 签发的就一定可信”，忽视了 CA 签发的仅仅是“公钥与特定域名的绑定声明”；若拿着给 `attacker.com` 签发的正规证书去冒充 `bank.example.com`，如果不比对域名就会全盘失守；
- **滥用跳过验证开关**：在遇到自签名证书、内网域名解析错误或过期报警时，直接在代码中设置 `verify=False`、`check_hostname=False` 或在命令行加上 `-k`，使整个系统的信任机制形同虚设；
- **泛化安全保障范围**：误以为 TLS 能保护数据库防注入、服务器防勒索或代码免受越权漏洞攻击，忽视了安全协议具有严格的物理与逻辑边界。

要建立现代网络安全体系的精确世界模型，必须深入理解 TLS 1.3 的握手设计、X.509 证书的验证状态机以及信任锚点的工程约束。本课正式复访核心系统概念：**信任边界（Trust Boundary，EC-CON-017）**、**接口（Interface，EC-CON-005）** 与 **故障（Failure，EC-CON-010）**。

## 学习目标

完成本课后，你应能：
- **Explain**：准确阐述 TLS 1.3 握手如何通过临时 Diffie-Hellman（(EC)DHE）密钥交换实现前向保密（Forward Secrecy），并对比 TLS 1.2 废除静态 RSA 密钥交换的技术演进逻辑；
- **Trace**：清晰追踪 X.509 证书链验证的两大独立判定支柱：从叶子证书向上回溯至本地受信任根证书（Root CA Trust Anchor）的**路径校验（Path Validation）**，以及比对请求域名与证书扩展项的**主体备用名称（SAN, Subject Alternative Name）身份比对**；
- **Observe / Build**：使用 `labs/foundations/m11/tls_fixture.py` 运行由测试根 CA 签发的受控 TLS 1.3 服务，在零跳过标志下分别触发并观测成功握手、主机名不匹配拒绝（Hostname Mismatch）和未受信任根证书拒绝（Untrusted Root）三种确定性状态；
- **Judge**：批判性评估“为什么任何生产代码严禁使用 `verify=False` / `-k`”，论证跳过验证不仅是关闭告警，而是彻底废除了系统的**信任边界（EC-CON-017）**；
- **Demarcate**：清晰划定 TLS 的安全边界：TLS 仅保障跨不可信网络的机密性、完整性与端点认证，不保障端点内存安全性、应用层业务逻辑正确性或客户端本地受信任证书库的完整性。

## Mental Model｜TLS 1.3 握手与 X.509 信任链

### 1. TLS 1.3 的握手交互与前向保密

在传输层 TCP 连接建立之后，TLS 在 TCP 字节流之上建立加密与认证会话。TLS 1.3 相比于早期的 TLS 1.2 进行了彻底的现代重构：移除了存在安全缺陷的旧算法套件（如 MD5、SHA-1、RC4、CBC 模式分组密码），**全面废除了静态 RSA 密钥交换**，强制采用具备**前向保密（Forward Secrecy）**的临时 Diffie-Hellman（(EC)DHE）密钥协商。

```
Client                                                              Server
  |                                                                   |
  |  1. ClientHello                                                   |
  |     + Supported Cipher Suites (AEAD only)                         |
  |     + Key Share (Client ephemeral ECDHE public key)               |
  |     + Server Name Indication (SNI)                                |
  | ----------------------------------------------------------------> |
  |                                                                   |
  |  2. ServerHello                                                   |
  |     + Selected Cipher Suite (e.g. TLS_AES_256_GCM_SHA384)        |
  |     + Key Share (Server ephemeral ECDHE public key)               |
  |     {EncryptedExtensions}                                         |
  |     {Certificate} (Server X.509 Certificate Chain)                |
  |     {CertificateVerify} (Signature over handshake transcript)     |
  |     {Finished} (HMAC over entire handshake)                       |
  | <---------------------------------------------------------------- |
  |                                                                   |
  |  [Client verifies Server Certificate Chain & SAN identity]        |
  |  [Client verifies CertificateVerify signature]                    |
  |  [Client derives Symmetric Keys: Application Traffic Keys]        |
  |                                                                   |
  |  3. {Finished}                                                    |
  | ----------------------------------------------------------------> |
  |                                                                   |
  | <========== 1-RTT Handshake Complete: Secure Channel ===========> |
  |                                                                   |
  |  4. {Application Data: HTTP/1.1 or HTTP/2 or HTTP/3 Frames}       |
  | <===============================================================> |
```

> **什么是前向保密（Forward Secrecy）？**
> 在旧式静态 RSA 握手模型中，客户端生成预主密钥（Pre-Master Secret）后使用服务器的静态公钥加密发送。如果攻击者多年来在光纤骨干网上持续录制并存储了所有的加密网络流量，只要未来某一天服务器的静态 RSA 私钥泄漏（例如被黑客入侵、硬件淘汰报废或通过法庭传票获取），攻击者就能解密历史上**录制的所有历史会话**！
> 
> 在 TLS 1.3 强制的临时 Diffie-Hellman 机制下：
> - 每次握手双方动态生成临时的密钥对（Ephemeral Key Pair）；
> - 会话对称密钥由双方的临时私钥和对端的临时公钥实时派生计算；
> - 握手完成后，临时的私钥在内存中被立即擦除销毁；
> - 即使服务器的长期证书私钥在未来泄露，攻击者也只能用来伪造未来的新连接，**绝不可能逆向解密过去已经完成的历史加密流量**。

### 2. X.509 证书的双支柱验证模型

当客户端收到服务端发来的 X.509 证书链时，必须且只能在**两大独立校验支柱全部通过**的前提下，才能确认对端身份：

```
                              X.509 证书校验状态机
                                       |
                   +-------------------+-------------------+
                   |                                       |
                   v                                       v
         [支柱 1: 路径有效性校验]                [支柱 2: 服务主体身份比对]
         Path / Chain Validation                 Identity / SAN Validation
                   |                                       |
        - 本地 Trust Store 存在根 CA            - 从 URL/SNI 获取期望的主机名
        - 上级证书对下级证书签名的合法性        - 提取叶子证书的 Subject Alternative Name
        - 证书链中各项有效期（Not Before / Not After） - 检查期望主机名是否在 SAN 列表内
        - X.509 扩展约束（BasicConstraints,     - (RFC 6125 规范：不建议回退至废弃的 CN)
          KeyUsage, ExtendedKeyUsage）                     |
                   |                                       |
                   +-------------------+-------------------+
                                       |
                        两个支柱必须同时满足 (AND)
                                       |
                         +-------------+-------------+
                         |                           |
                     全部通过                     任一失败
                         |                           |
                         v                           v
                  [信任建立: 放行握手]       [信任崩溃: 抛出验证异常]
                                             (SSLCertVerificationError)
                                             终止连接，绝不回退
```

这两大支柱的职责绝对不能相互替代：
1. **支柱 1（路径与信任锚）**：保证证书是由客户端显式信任的权威机构（CA）根据规范合法签发且未过期的。但这只能证明“持证者是一个经过 CA 审核的实体”，不能证明它就是你想要连接的目标；
2. **支柱 2（主体身份比对）**：根据 RFC 6125，客户端将发起的请求目标域名（如 `bank.example.com`）与叶子证书中的 **Subject Alternative Name (SAN)** 扩展列表进行严格字面量或通配符匹配。如果只做支柱 1 不做支柱 2，攻击者只需向合法 CA 申请一个 `attacker.com` 的有效证书，并劫持你的 DNS，就能无缝冒充 `bank.example.com`，而你的客户端若不校验 SAN 就会盲目信以为真！

## Mechanism｜从测试 PKI 到零跳过实验验证

### 1. X.509 v3 扩展与 RFC 5280 规范约束

在现代操作系统和 OpenSSL 3.x 协议栈中，X.509 证书不仅包含公钥与主体名称，更被严格的扩展字段所约束：

| 扩展项名称 (Extension) | 所在证书 | 核心作用与规范规则 (RFC 5280) | 违背后果 |
|---|---|---|---|
| **Basic Constraints** (`2.5.29.19`) | 根 CA / 中间 CA | `CA:TRUE` 标识该证书持有者有权签发下级证书；叶子证书必须为 `CA:FALSE` 或缺省。 | 若根 CA 证书未标记 `CA:TRUE`，OpenSSL 会直接报 `unable to get local issuer certificate` 并拒绝信任。 |
| **Key Usage** (`2.5.29.15`) | 全部 | 声明公钥的法定用途。CA 必须包含 `keyCertSign` 和 `cRLSign`；叶子证书通常包含 `digitalSignature` 和 `keyEncipherment`。 | 若 CA 缺少 `keyCertSign`，客户端将拒绝该 CA 签发的任何子证书。 |
| **Extended Key Usage (EKU)** (`2.5.29.37`) | 叶子证书 | 细化公钥应用场景。TLS 服务器证书必须包含 `serverAuth`（`1.3.6.1.5.5.7.3.1`）。 | 缺少 `serverAuth` 的证书无法通过现代 Web 客户端的服务器身份认证。 |
| **Subject Alternative Name (SAN)** (`2.5.29.17`) | 叶子证书 | 明确声明该证书合法绑定的主机名（`DNS:localhost`）或 IP 地址（`IP:127.0.0.1`）。 | 根据 RFC 6125，传统 Common Name (CN) 已被正式废弃，现代客户端若在 SAN 中找不到目标域名将直接终止连接。 |

### 2. 观察受控测试端点的三条路径

在 `labs/foundations/m11/tls_fixture.py` 中，我们构建了严谨的受控测试套件：
- 服务端加载由课程根 CA 签发的证书（SAN 包含 `localhost` 与 `127.0.0.1`），并在本地回环动态端口（`127.0.0.1:0`）提供 TLS 1.3 监听；
- 客户端严格通过 `ssl.SSLContext(ssl.PROTOCOL_TLS_CLIENT)` 配置，显式加载指定的 CA 信任文件，**严格开启 `check_hostname=True` 与 `verify_mode=CERT_REQUIRED`**；
- 运行三组实验：

```python
# 路径 1: 信任根 CA + 正确的主机名 -> 成功握手
ctx = ssl.create_default_context(cafile=CA_CERT_PATH)
with socket.create_connection(('127.0.0.1', port)) as sock:
    with ctx.wrap_socket(sock, server_hostname='localhost') as ssock:
        assert ssock.version() == 'TLSv1.3'

# 路径 2: 信任根 CA + 错误的主机名 (SAN mismatch) -> 抛出 SSLCertVerificationError
ctx = ssl.create_default_context(cafile=CA_CERT_PATH)
with socket.create_connection(('127.0.0.1', port)) as sock:
    try:
        with ctx.wrap_socket(sock, server_hostname='wrong.example.internal') as ssock:
            pass
    except ssl.SSLCertVerificationError as err:
        # 抛出 Certificate hostname mismatch 异常，连接被主动掐断
        pass

# 路径 3: 未受信任的根 CA + 正确的主机名 -> 抛出 SSLCertVerificationError
ctx_untrusted = ssl.create_default_context(cafile=UNTRUSTED_CA_PATH)
with socket.create_connection(('127.0.0.1', port)) as sock:
    try:
        with ctx_untrusted.wrap_socket(sock, server_hostname='localhost') as ssock:
            pass
    except ssl.SSLCertVerificationError as err:
        # 抛出 self-signed certificate in certificate chain 异常，拒绝握手
        pass
```

### 3. 为什么严禁使用跳过验证开关？

在开发或排障时，部分初学者因遇到证书报错，习惯性地加上 `verify=False`、`ssl._create_unverified_context()` 或 `curl -k`：

```python
# 致命错误示范：这不仅关闭了警告，而且彻底摧毁了信任边界！
response = requests.get("https://internal.service", verify=False)
```

**工程后果分析**：
1. `verify=False` 的实际语义是：**指令客户端接受网络对端发来的任何公钥，不校验签发机构，不校验域名归属**；
2. 一旦置为 `False`，局域网内的任何攻击者（ARP 欺骗、公共 WiFi、恶意 DNS 劫持）只需要随意自签名一个空证书，客户端就会开开心心地与攻击者建立加密连接，把包含用户 Cookie、Token、数据库密码和业务数据的明文完整发给攻击者；
3. **“加密”而不“认证”是彻底的假安全**：攻击者用自己的密钥解密客户端发来的数据，记录明文后，再与真正的后端建立 TLS 连接转交请求。在整个过程中，客户端毫无察觉，所谓的安全保护彻底化为乌有。

### 4. 元数据保护与 ECH (Encrypted Client Hello)

在标准 TLS 1.3 握手中，虽然证书（Certificate）、证书验证（CertificateVerify）和握手后的所有数据都经过了加密，但是**第一包 `ClientHello` 仍然是明文传输的**。
这导致了一个关键隐私泄露：`ClientHello` 中的 **SNI（Server Name Indication，服务器名称指示）** 扩展包含明文的主机域名（如 `visited-site.example.com`）。网络沿途的路由器、ISP 或监听者即使无法解密通信内容，也能清晰记录下用户正在访问哪一个网站。

为了解决这个最后的明文元数据泄露问题，现代 IETF 推出了 **ECH（Encrypted Client Hello）** 技术：
- 目标域名的权威 DNS 在 HTTPS/SVCB 记录中发布服务端的公钥（ECHConfig）；
- 客户端在发起握手前，通过受保护的 DNS（如 DoH / DoT）查询获取该公钥；
- 客户端构建外层公开的 ClientHelloOuter（仅指向中立的前置面向服务商），并将包含真实敏感 SNI 的 ClientHelloInner 加密封装在扩展字段中；
- 沿途监听者只能看见中立的外层域名，彻底抹除了基于明文 SNI 的网络审查与元数据嗅探可能。

1. 为什么该证书会被底层 SSL 引擎拒绝？
2. 为什么运维工程师“内网绝对安全、直接关闭验证”的提议存在致命架构缺陷？
3. 正确且符合规范的修复方案应该是什么？

</details>

<details>
<summary>Expected Observation</summary>
该错误发生在支柱 2（主体身份比对）。尽管证书可能由合法的私有 CA 签发，但该证书的 Subject Alternative Name (SAN) 扩展项中未包含 <code>IP:192.168.1.100</code>（或只配置了 DNS 域名而未配置 IP SAN），因此客户端判定对端身份与证书声明不符。关闭验证会导致内网容器失去互信防线，一旦局域网内任意容器被攻破或发生 DNS/ARP 欺骗，整网流量将完全裸奔。正确的解法是：重新生成符合 RFC 5280 规范的证书，将该内网 IP 或对应的内网服务域名显式加入到 SAN 列表中，并在客户端仅配置私有 CA 的受信任根证书文件。
</details>

<details>
<summary>Full Explanation</summary>
这是一个在分布式微服务架构中极为常见的身份认证与安全边界误区：

1. **底层失败机制分析**：
   根据 RFC 6125 与现代 TLS 实现（如 OpenSSL 3.x / Python 3.13 <code>ssl</code> 模块），客户端在建立 TLS 连接时，强制校验目标请求地址必须与证书中的 SAN 扩展项匹配。
   如果客户端通过 IP 地址（<code>https://192.168.1.100</code>）发起连接，证书的 SAN 中必须包含 <code>IP:192.168.1.100</code> 这一项属性（不能仅依赖传统的 <code>DNS:</code> 或已废弃的 <code>Common Name</code>）。当证书缺少该 IP 声明时，支柱 2 校验失败，抛出 <code>SSLCertVerificationError</code>。

2. **关闭验证的系统性危害（违背 EC-CON-017 信任边界）**：
   “内网等于安全”是典型的过时边界安全论。现代计算系统遵循**零信任（Zero Trust）**架构：网络基础设施始终被视为不可信介质。
   一旦客户端配置了 <code>verify_mode = ssl.CERT_NONE</code>，就等于拆除了所有的身份验证防线。内网中被渗透的边缘节点、配置错误的负载均衡器或恶意横向移动的攻击者，可以随意伪造自签名证书劫持该微服务的所有远程调用，盗取敏感凭证或注入恶意数据。

3. **标准工程解法**：
   - **修正证书签发脚本**：使用 OpenSSL 或 <code>cryptography</code> 库为该服务端重新签发证书，在扩展配置中显式声明：
     <code>subjectAltName = IP:192.168.1.100, DNS:service.internal.cluster</code>
   - **分发私有 CA 信任锚**：在客户端配置受信任的 CA 文件（如 <code>ssl_context.load_verify_locations('/etc/ssl/certs/internal_ca.pem')</code>），保持 <code>check_hostname = True</code> 与严格验证开启。
</details>

## Common Misconceptions

- **“只要启用了 HTTPS，我的系统就绝对安全，不会被攻击了。”** 错。TLS 仅保护通信信道上的机密性、完整性与端点认证（EC-CON-017）。它绝不保护服务器应用程序本身的漏洞（如 SQL 注入、越权访问、未授权 API 调用），也不保护客户端本地被植入木马或内存被读取。
- **“证书验证就是看 CA 签名对不对，只要签名有效就说明身份匹配。”** 错。CA 签名只能证明“公钥与主体声明的关系得到了 CA 背书”。如果攻击者拿着合法 CA 给 `evil.com` 签发的证书来拦截发往 `bank.com` 的流量，CA 签名同样是有效通过的！必须同时严格校验证书中的 SAN 扩展与请求的目标域名完全一致。
- **“自签名证书加 `verify=False` 是测试阶段的标准常规手段，上线前删掉就行。”** 错。这种不严谨的代码经常会被带入生产环境或遗留在脚本中；严谨的测试应当建立受控的测试专用根 CA（Local Test PKI），在客户端加载该测试 CA 的信任上下文，以 100% 真实严格的生产级状态运行测试（正如我们在 `labs/foundations/m11/tls_fixture.py` 中所实现的）。
- **“TLS 1.3 握手全部内容都是加密的，网络监听者什么都看不见。”** 错。在未开启 ECH 的常规 TLS 1.3 握手中，初始的 `ClientHello` 包含明文的 SNI 主机名扩展，网络监听者仍然可以精准捕获你正在连接哪一个服务域名。

## What You Can Ignore—for Now

- 椭圆曲线密码学中 Curve25519 与 NIST P-256 的具体标量乘法数学点运算实现；
- OCSP Stapling 与 CRL 证书吊销列表的实时分布式树状检索同步；
- ECH 的密钥配置（ECHConfig）在 DNS SVCB/HTTPS 记录中的二进制 RDATA 编码细节。

## Exit Criteria

- 能阐明 TLS 1.3 废除静态 RSA 并强制要求临时 Diffie-Hellman（ECDHE）的前向保密意义；
- 能准确列出 X.509 验证状态机的两大独立支柱：路径校验（Path Validation）与主体身份比对（SAN Validation）；
- 能独立运行 `labs/foundations/m11/tls_fixture.py` 并说明三种握手分支（成功、主机名不匹配、未受信任 CA）的观察现象与底层原因；
- 能在代码审查中一眼识别出 `verify=False`、`check_hostname=False` 和 `curl -k` 的安全漏洞，并从信任边界角度论述其工程危害。

## Competency Mapping

- **Primary**: **Explain** (解释 TLS 1.3 前向保密机制、X.509 证书双支柱校验与信任边界约束)
- **Growth**: **Trace** (追踪从 TCP 握手到 ClientHello、ServerHello、证书链校验与会话密钥派生的全链路状态)

## Provenance

- **RFC 5280**: *Internet X.509 Public Key Infrastructure Certificate and Certificate Revocation List (CRL) Profile*, May 2008.
