# L11-02｜HTTP 统一接口、语义契约与部分失败现实

## 学习者问题

当你调用一个远程 HTTP API，收到客户端报出的网络超时（`Timeout`）或者看到了 HTTP 状态码 `200 OK` 时，底层究竟发生了什么？

你可能在很多教程中读到过：“GET 是用来查数据的，POST 是用来创建数据的，PUT 是用来更新数据的，它们是幂等的，所以重试很安全；如果返回了 200，就说明调用成功了。”
真的是这样吗？
- 为什么在发生网络超时（Timeout）后，盲目重试一个被标准定义为“幂等”的 PUT 或 DELETE 请求，可能会引发严重的线上资损？
- 为什么很多现代 API 明明执行失败（例如“账户余额不足”），返回的 HTTP 状态码却赫然写着 `200 OK`？
- 为什么不能把“HTTP 协议通信成功”等同于“业务层执行成功”？

## 为什么重要

HTTP 是现代万维网与微服务互联的事实标准应用层协议。然而，绝大多数开发人员在初学阶段接触到的都是高度封装的高级 HTTP 客户端库（如 `requests`、`fetch`、`axios`）。这种便利的高层抽象往往遮蔽了协议的底层物理事实与核心设计契约：
- **混淆资源与表述**：误以为“URI 指向的就是服务器磁盘上的某个具体文件或特定的 JSON 对象”，不理解**资源（Resource）**是概念性的语义实体，而**表述（Representation）**只是该资源在特定时刻由特定媒体类型（Media Type）序列化后的字节切片；
- **将“幂等”误读为“绝对无脑重试安全”**：死记硬背“PUT 是幂等的”，但在遇到分布式**部分失败（Partial Failure，EC-CON-010）**时，不经思考地自动重试，导致下游系统触发非幂等的连锁更新或遭遇写冲突覆盖；
- **混淆协议状态与业务状态**：将 HTTP 传输层的成功响应（`200 OK`）直接判定为业务成功，忽略了业务体内部可能包含的业务错误码，导致严重的反向逻辑漏洞；
- **对线缆文本帧格式缺乏底层敬畏**：不知道 HTTP/1.1 是建立在严格的 ASCII 字符集、CRLF（`\r\n`）行定界与空行（`\r\n\r\n`）分隔之上的文本协议，在手工拼装协议时因换行符错误导致连接挂起。

要建立健壮的分布式调用世界模型，必须严格区分应用层协议契约与业务执行边界。本课正式复访核心系统概念：**接口（Interface，EC-CON-005）** 与 **故障（Failure，EC-CON-010）**。

## 学习目标

完成本课后，你应能：
- **Explain**：准确阐述 HTTP **统一接口（Uniform Interface，EC-CON-005）** 的核心机制，深刻界定资源（Resource）与表述（Representation）的解耦关系；
- **Explain**：严格区分 HTTP 方法的安全（Safe）与幂等（Idempotent）语义契约，给出 GET、HEAD、PUT、DELETE、POST 在本课范围内的预期效果；

- **Explain**：清晰解耦 HTTP 状态语义与业务执行结果，指出 `200 OK` 表示请求按该方法的 HTTP 语义获得成功响应，但绝不天然背书业务领域结果；

## Mental Model｜资源、表述与状态码分层

### 1. 资源（Resource）与表述（Representation）的解耦

REST 架构风格的核心公理是：**客户端操作的是资源的表述，而不是直接操作服务端内部的物理对象**。

```
                                [逻辑概念: 资源 (Resource)]
                               URI: /api/v1/accounts/user-101
                                              |
                   +--------------------------+--------------------------+
                   |                                                     |
                   | 内容协商 (Content Negotiation)                       |
                   | Accept: application/json                            | Accept: text/csv
                   v                                                     v
       [表述 1: JSON 序列化]                                  [表述 2: CSV 序列化]
+------------------------------------+               +------------------------------------+
| HTTP/1.1 200 OK                    |               | HTTP/1.1 200 OK                    |
| Content-Type: application/json     |               | Content-Type: text/csv             |
| Content-Length: 48                 |               | Content-Length: 32                 |
|                                    |               |                                    |
| {"id": 101, "balance": 5000.0}     |               | id,balance\r\n101,5000.0\r\n       |
+------------------------------------+               +------------------------------------+
```

- **资源（Resource）**：是 HTTP 请求所指向的信息/概念目标。URI 用于标识资源，但不能把“一个资源只能有一个 URI”或“URI 等于服务器磁盘对象”当成协议不变量。
- **表述（Representation）**：是在给定元数据与媒体类型下传递、反映或描述资源当前/期望状态的一组表示数据；它不是服务端内部对象本身。
- **解耦的系统价值**：服务端内部实现可以演进而不要求客户端直接理解其数据库/进程布局；前提是对外 HTTP 接口、表述与业务契约保持兼容。内部重构是否真的对客户端无影响，仍取决于这些外部契约是否被保存。

### 2. 方法语义：安全（Safe）与幂等（Idempotent）

RFC 9110 对 HTTP 方法赋予了极其严格的语义规范：

```
                           HTTP 方法语义全景矩阵
+-----------+----------------------+----------------------+-------------------------------+
|  HTTP 方法 | 安全性 (Safe)         | 幂等性 (Idempotent)   | 状态机核心语义                |
+-----------+----------------------+----------------------+-------------------------------+
|   GET     | YES                  | YES                  | 仅检索表述，不改变资源语义状态 |
|   HEAD    | YES                  | YES                  | 仅检索首部，无响应主体        |
|   PUT     | NO                   | YES                  | 以请求表述全量替换/创建目标资源|
|  DELETE   | NO                   | YES                  | 删除由 URI 指定的目标资源     |
|   POST    | NO                   | NO                   | 提交表述由目标资源按自身语义处理|
+-----------+----------------------+----------------------+-------------------------------+
```

- **安全方法（Safe Methods）**：客户端选择该方法时，**不请求也不期望产生 unsafe 的状态改变**。服务器仍可能做日志、计费统计、缓存填充等附带动作，所以 `safe` 绝不是“服务器物理上没有任何副作用”，爬虫/预加载器也仍应遵守应用访问与负载边界。
- **幂等方法（Idempotent Methods）**：对同一个请求，**客户端所请求的 intended effect** 在重复执行时与执行一次相同。日志、版本记录或其他非请求效果可能不同；幂等也不代表无限重试一定合适。
  - 例如 `PUT /accounts/101 {"balance": 100}`：无论你执行 1 次还是 10 次，最终用户 101 的余额状态都是 100。
  - `POST` 并未由 RFC 9110 定义为幂等；它让目标资源按自身语义处理所附内容。本课的 `/items` course fixture **选择**把每次 POST 实现为创建一个新资源，因此在该 fixture 中重复 POST 会产生不同资源。

## Mechanism｜部分失败真相与线缆文本帧结构

### 1. 致命误区：幂等 != 盲目重试安全 (Idempotent != Retry-Safe)

需要避免的误读是：**“因为 PUT 和 DELETE 是幂等的，所以任何网络错误后都可以无限制、无条件地重试。”** RFC 的幂等语义确实让这类方法在通信失败后更适合自动重试，但客户端仍需要考虑应用并发控制、认证/配额、请求版本、外部联动与重试预算。

**为什么这是完全错误的？**
复访分布式系统中的核心概念：**故障与部分失败（Partial Failure，EC-CON-010）**。
当客户端执行一次 PUT 后发生本地 read deadline/communication failure，仅凭这个 client-visible disposition，通常不能唯一判断远端在什么阶段完成了处理：
1. **可能的情况 A**：网络在请求到达服务器前就断了，服务器什么也没做；
2. **可能的情况 B**：服务器已经按接口契约处理了请求，甚至完成了应用层提交，但客户端没有在 deadline 前获得响应。这里不把“写入磁盘”与 HTTP 200 的语义绑定。

```
Client                                                              Server
  |                                                                   |
  |  1. PUT /doc/1 {"content": "v2"}                                  |
  | ----------------------------------------------------------------> |
  |                                                  [Written to Disk!|
  |                                                  Version is now v2|
  |                                                  Triggered Webhook]
  |                     X (Response Lost in Cable)                    |
  | < - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - - |
  |                                                                   |
  |  [Client Read Timeout Expired!]                                   |
  |  [Naively Retries: PUT /doc/1 {"content": "v2"}]                  |
  | ----------------------------------------------------------------> |
  |                                                [Re-executed!     |
  |                                                 Side effects triggered AGAIN!]
```

如果服务端在执行 `PUT` 时，伴随有非幂等的下游联动行为（例如触发了一条“文档更新通知”微服务消息，或者更新了修改时间审计日志），盲目重试就会导致下游系统产生重复事件。更严重的是，如果有并发的其他客户端正在修改该资源，盲目重试可能会覆盖掉别人刚刚提交的新状态。
**结论**：通信失败不会赋予客户端“无限重试”的绝对通行证。对于 RFC 定义的幂等方法，自动重试通常具有更好的语义基础；但应用仍应定义重试预算、版本/并发条件与 outcome contract。`If-Match`、operation ID、查询/对账等只是可选机制，不能写成唯一方案。

### 2. 协议层状态码与业务执行结果彻底解耦

在 HTTP 协议的体系中：
- **HTTP 状态码（Status Code）**：是 HTTP 应用协议的一部分。`200 OK` 表示目标请求依照该方法的 HTTP 语义获得成功响应；它不等于“TCP 一定如何传输”，也不证明某个业务领域不变量（例如只扣款一次）成立。
- **业务执行结果（Business Outcome）**：是运行在 Web 服务器之上的具体应用程序逻辑的产物。

```json
// HTTP 响应首部
HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 78

// HTTP 响应正文
{
  "success": false,
  "code": "ERR_INSUFFICIENT_FUNDS",
  "message": "Transaction failed: balance cannot cover transfer amount."
}
```

在上面的真实案例中：
- HTTP 语义层面：这个 course fixture **选择**用 `200 OK` 表示该 HTTP 请求成功产生了一个业务结果表述；表述内容本身却明确标记业务失败。真实 API 可以选择不同状态设计，本课只证明“200 不自动等于业务不变量成功”。
- 业务逻辑层面：用户的转账操作**彻底失败了**（余额不足）。

> **架构红线**：
> 客户端程序绝对不能仅凭 `response.status_code == 200` 就向用户展示“转账成功！”或者在数据库里打上“交易成功”标记。必须解析响应体中的业务字段（如 `success: true`），将**协议交付契约**与**领域业务契约**完全解耦。

### 3. 深入线缆：HTTP/1.1 的 CRLF 文本定界

在 `labs/foundations/m11/http_semantics_observer.py` 中，我们直接通过 TCP socket 观察课程 fixture 的 HTTP/1.1 message syntax：

```text
GET /health HTTP/1.1\r\n
Host: 127.0.0.1\r\n
Connection: close\r\n
\r\n
```

- **行定界（Line Endings）**：RFC 9112 的 HTTP/1.1 message syntax 使用 CRLF 作为 field-line / request/status-line 的标准行结尾。接收端可能存在兼容性解析规则，但发送端不应依赖宽松解析；
- **首部与内容 framing（Header/Content Demarcation）**：header section 由一个空行结束；随后是否存在以及如何确定 message content，还要结合方法/状态码以及 Content-Length / Transfer-Encoding / connection close 等 framing 规则。`\r\n\r\n` 不是完整 HTTP 消息长度协议。

课程 raw trace 采用规范 CRLF。若手工构造非规范换行或缺少 header-section 终止空行，具体服务器可能拒绝、容忍或等待更多字节；不要把某个解析器的宽松/超时行为泛化成协议不变量。

## Checkpoint Investigation

### Question

某电商平台在“双十一”秒杀活动中，开发团队上线了一套基于 HTTP 的下单扣库存服务。客户端调用如下：
`POST /api/v1/orders/submit`

在压测过程中，客户端频繁报告超时（Timeout）。为了“提高下单成功率”，一名新员工在客户端编写了一个重试切面：
```python
# 客户端自动化重试逻辑
for attempt in range(3):
    try:
        resp = call_order_api()
        if resp.status_code == 200:
            break
    except TimeoutError:
        time.sleep(0.5)
        continue
```
上线后，出现了大量的“用户只点了一次购买，但账户被扣了 3 次钱、生成了 3 笔相同订单”的恶性线上事故。

请结合本课所学的 HTTP 方法语义、部分失败（EC-CON-010）与协议状态码解耦，回答：
1. 为什么 `POST` 请求遭遇超时后绝不能直接重试？
2. 为什么即便重试返回了 `200 OK`，也不能证明只生成了一笔订单？
3. 如果必须支持超时安全重试，系统应当如何通过**接口设计（EC-CON-005）**进行改造？

<details>
<summary>Hint 1</summary>
回顾 POST 的语义：它是安全（Safe）方法吗？是幂等（Idempotent）方法吗？每一次 POST 在服务端目标资源上承诺了什么？
</details>

<details>
<summary>Hint 2</summary>
当客户端遇到 <code>TimeoutError</code> 时，请求究竟是在到达服务端前丢了，还是在服务端写完数据库后响应丢了？如果服务端已经写了数据库，再次发起相同的 POST 会发生什么？
</details>

<details>
<summary>Expected Observation</summary>
`POST` 未被 HTTP 规范定义为幂等；本题的下单接口又明确把每次 POST 设计成一个新的业务操作，因此超时后无条件重复提交可能产生重复效果。`200 OK` 只描述收到的那次 HTTP 响应，不能证明先前超时调用没有生效。可选解决方案包括稳定 operation ID + 去重、查询/对账、把接口重新设计为具有幂等 intended effect 等；`Idempotency-Key` 是常见模式之一，不是 HTTP 自动提供的万能保证。
</details>

<details>
<summary>Full Explanation</summary>
这是由于混淆“传输层超时”与“业务层实际执行状态”所导致的经典分布式部分失败灾难：

1. **POST 的非幂等本质**：
   RFC 9110 **没有把 POST 定义为幂等方法**。POST 的实际处理语义由目标资源决定；本题接口契约规定每次提交代表一次新的下单操作，因此重复 POST 可能产生重复业务效果。

2. **部分失败（EC-CON-010）的歧义性**：
   当客户端在第 1 次调用后遇到 <code>TimeoutError</code> 时，这仅仅证明“客户端的本地读取计时器到期了”，**绝不证明服务端没有执行成功**！
   timeout 只说明客户端没有在 deadline 前得到所需结果；它不能给“服务端已经提交”或“服务端完全没收到”赋予固定概率。若接口把每次 POST 视为新的下单操作，无条件再次提交就有重复业务效果的风险。

3. **健壮的接口设计改造方案（EC-CON-005）**：
   - **引入幂等键机制（Idempotency-Key）**：
     客户端在发起秒杀时，必须生成一个与该次用户点击严格绑定的全局唯一业务标识（如 <code>Idempotency-Key: req_uuid_98765</code>）。
   - **服务端去重与状态回放**：
     服务端接收到请求后，首先在分布式缓存或数据库唯一索引中以该键占位。如果发现该键已在处理中或已处理完成，直接返回上一次的处理结果（或者返回防重冲突错误），绝对不再重复执行扣款事务。
   - **先查后试（Read-Then-Retry）**：
     客户端超时后，应先调用幂等的查询接口（如 <code>GET /orders/by-client-token?token=...</code>）核实真实业务状态，确认未创建后再行重试。
</details>

## Common Misconceptions

- **“PUT 方法天然就是重试安全的，只要是 PUT 请求就可以在框架里无脑无限重试。”** 错。PUT 的幂等性仅保证“单独多次执行与单次执行对目标资源最终期望状态相同”。但在存在并发修改的场景下，超时盲目重试可能把后发生的并发更新冲掉；若服务端在更新资源时触发了非幂等的外部联动（如发送短信），重试依然会产生破坏性副作用。
- **“HTTP 状态码是 200，说明业务一定做成了；状态码是 500，说明业务一定完全没做。”** 错。HTTP 状态码是协议层概念。200 里面可能包裹着业务层抛出的 `{"success": false, "reason": "balance_too_low"}`；而 500 可能是服务端代码在执行完数据库事务、提交完持久化后，在渲染最后一步模板时抛出的异常，业务数据可能已经改写成功了！
- **“HTTP 是文本协议，所以随便用 `\n` 换行就能正常解析。”** 错。HTTP/1.1 标准发送语法使用 CRLF；接收实现对非规范输入可能拒绝、兼容或采取其他策略，课程不预测具体产品行为。

## What You Can Ignore—for Now

- HTTP 状态码 103 Early Hints 与 426 Upgrade 的握手协商流程；
- 分块传输编码（Chunked Transfer Encoding）中动态尾部首部（Trailers）的异步签名流转；
- MIME 多部分表单数据（multipart/form-data）复杂多段嵌套编码。
