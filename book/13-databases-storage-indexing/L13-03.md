# L13-03｜为什么模式设计至关重要：约束不变式、渐进式演进与单一真实源

## 1. 学习者核心问题 (Learner Question)

> “为什么在多人协作或长期维护的系统中，直接修改已有表的列定义可能会导致正在运行的服务抛出异常？如果在已存数据的表上执行一条 `ALTER TABLE ... ADD COLUMN ... NOT NULL`，SQLite 会如何响应？我们该如何在服务演进过程中平滑演进数据库模式（Schema）并守护数据完整性与正确性？”

在个人开发阶段，改动数据库表结构通常十分随意：直接删除表重建，或者执行修改语句。然而在由多个服务或多个客户端共享访问的系统中，数据库不仅承载着业务数据，还面临着新老版本程序共存访问的过渡期。

一个未加考虑的 Schema 修改，可能导致旧版服务读取失败，或者破坏存储层的不变式。本课通过受控的实验，探讨关系型模式设计的核心价值：如何利用数据库原生约束守护系统状态正确性（`EC-CON-009 Correctness`），如何通过**渐进式演进（Expand-Contract 兼容模式）**实现跨版本的平滑过渡，以及如何界定**单一真实源（Source of Truth）**与**可重算派生视图（Derived View）**的边界。

## 3. 机制模型 (Mechanism Model)

### (1) 数据库约束作为系统不变式 (Invariants & Correctness)
应用代码可能存在逻辑漏洞或版本差异。如果仅在应用层做校验，任何其他管理脚本、修复脚本或并发异常都可能写入不合法数据。
- 关系型数据库的一大系统特性在于：**在存储引擎层强制维持数据结构的不变式（`EC-CON-008 Invariant`）**；
- `NOT NULL` 约束确保列值必须有确定表示，杜绝缺失语义的二义性；
- `UNIQUE` 与主键在物理索引树上维持实体唯一性；
- 存储层约束构成了独立于应用层版本生命周期的底层防御边界。

### (2) 渐进式模式演进：Expand-Contract 兼容模式
在多服务共存或滚动升级的过渡期，如果直接原地替换列名或直接添加无默认值的非空约束，未更新的代码可能会因假设破裂而崩溃。
**Expand-Contract（展开-收缩）是一种工程兼容模式**，用于在过渡期间保持读者与写者的版本兼容：

```
Phase 1: [ EXPAND ] (展开兼容)
  - 在数据库中新增列（保持 NULLABLE 或带有安全的默认值 DEFAULT）；
  - 新老版本的服务均可在过渡期正常读取或写入数据，维持向后兼容性；
  - 注意：这是一种应用与数据库的兼容设计模式，并不等同于在所有数据库上都提供无锁或零停机的底层保证。

Phase 2: [ BACKFILL ] (分批回填)
  - 通过受控的后台批处理更新，将历史记录的数据回填或计算填入新列；
  - 避免一次性巨量事务造成长锁占用。

Phase 3: [ CONTRACT ] (收缩清理)
  - 当所有相关的读写服务均已升级至使用新列后，应用层停止访问旧列；
  - 数据库清理或废弃旧列，完成模式演进闭环。
```

### (3) 单一真实源（Source of Truth）与可重算派生视图（Derived View）
在课程设计的 R6 业务模型中：
- **单一真实源（Source of Truth）**：存储基础业务事实的表（例如 `orders` 表中记录的每一笔订单详情）；
- **可重算派生视图（Derived View）**：根据明确声明的转换规则从源数据计算出的汇总数据（例如 `user_order_summary` 表中的用户订单总数与总消费）；
- **溯源元数据（Provenance Record）**：本课的派生表设计为**仅从指定的源数据（`orders`）和声明的计算规则中确定性重算**，并在每行附加轻量级 JSON 溯源信息（记录源表名、重算时间戳与规则版本）。
- *边界说明*：派生视图的可重算性严格限定在“拥有完整源数据且转换规则确定”的前提下，绝非宣称世间所有派生数据都可以凭空万能恢复。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 数据库约束提供了独立于应用程序代码版本的数据完整性边界；
   - 模式演化必须考虑并存读者与写者对表结构的兼容假设；
   - **在本课指定的 R6 模式中**，`user_order_summary` 被明确设计为从 `orders` 与已声明转换输入重算的派生视图；只有这些源数据与转换/版本输入被保留时，课程才声称它可重算。
2. **具名引擎实证 (Named Engine Evidence - SQLite)**：
   - SQLite 的 `ALTER TABLE ... ADD COLUMN` 语言限制规定：若新增列带 `NOT NULL`，则必须提供一个非 NULL 的默认值；否则操作会失败。学习者记录自己宿主机/驱动实际返回的错误类型与消息，不把某个固定 Python 异常字符串写成课程答案；
   - 提供合法的默认值即可顺利完成列的新增；
   - 学习者应如实记录宿主机 SQLite 驱动返回的实际异常类型与错误描述，不将特定 Python 错误字符串作为先验真理。
3. **易变当前实践 (Current Practice)**：
   - 不同数据库对 DDL 的实现差异巨大（例如部分引擎支持原子 DDL，部分引擎在 DDL 期间对表加排他锁）；
   - Expand-Contract 模式是系统架构层面的兼容设计，其实际执行特征必须结合所用数据库引擎的具体 DDL 机制来评估。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 实测报错行为剖析：
在已包含数据行的表上执行未经默认值保护的非空列新增：
```sql
ALTER TABLE users ADD COLUMN phone_number TEXT NOT NULL;
```
- **真实观测**：
  记录 SQLite 返回的具体异常（例如在 Python sqlite3 驱动下观测到 `sqlite3.OperationalError`）；
- **规范与实现剖析**：
  - 根据 SQLite 的 `ALTER TABLE` 语言契约，当表已存在数据行时，新增 `NOT NULL` 列必须伴随一个非空的常量 `DEFAULT`；
  - 若不提供默认值，新列对现有历史行的默认取值是 `NULL`，这与 `NOT NULL` 约束直接冲突；
  - SQLite 按 `ADD COLUMN` 的具名语言限制拒绝该 DDL 并返回错误；课程不推断某个未由本实验直接证明的内部检查阶段；
  - 这是具名引擎的明确语言规范（Specification & Contract），不是对其他数据库 DDL 行为的普适描述。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“反正应用层已经做了参数校验，数据库底层的约束可以随意省略。”**
  - **纠正**：应用代码会重构、会更新，甚至存在 bug；且数据库往往面临来自维护脚本、数据修复通道等多种不同来源的写入。数据库约束是守护系统状态合法性的最后屏障。
- **谬误 2：“Expand-Contract 模式保证了任何数据库的任何 DDL 操作都是绝对零停机的。”**
  - **纠正**：Expand-Contract 是一种跨版本读写兼容的应用架构模式，负责解决过渡期代码与模式的向后兼容；至于 DDL 本身是否阻塞读写、是否全表拷贝，则取决于具体数据库引擎的底层元数据锁和物理存储实现。
- **谬误 3：“派生聚合数据可以在业务中任意手工修改，之后也不会有问题。”**
  - **纠正**：派生数据是基于源数据计算的。如果在派生表上进行不受控的手工修改，一旦触发基于真实源的重新计算，手工改动就会被重算结果覆盖。

## 15. 核心概念引用与重温 (Concepts & Revisits)

- `EC-CON-001 State`: 数据库模式定义了系统合法状态的结构与约束边界；
- `EC-CON-003 Representation`: 列类型、空值表达与默认值设定直接约束底层数据的存储形态；
- `EC-CON-005 Interface`: 数据库表结构是服务之间共享通信的数据契约；
- `EC-CON-008 Invariant`: 模式约束构成了跨代码版本持续有效的硬性系统不变式；
- `EC-CON-009 Correctness`: 模式防御帮助保证系统状态变迁满足已声明的合法性与正确性条件。

## 17. 严格推论边界 (Exact Inference Limits)

- Expand-Contract 模式展示了应用在模式演变中的过渡兼容逻辑，**不能推断出所有数据库的 DDL 操作均完全无阻塞或无锁**；
- 派生数据的重算依赖于源数据的完整存在与规则的确定性，**在源数据缺失或转换非确定时无法凭空恢复**；
- 本实验中的轻量级 JSON 溯源是教学实证方案，**不能替代高合规金融或医疗场景中经过密码学签名的全链路审计日志**。
