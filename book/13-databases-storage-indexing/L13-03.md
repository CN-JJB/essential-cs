# L13-03｜为什么模式设计至关重要：约束不变式、渐进式演进与单一真实源

## 1. 学习者核心问题 (Learner Question)

> “为什么在真实生产系统中，给一张存有数亿行数据的表新增或重命名字段，会被资深架构师视为高危操作？如果不小心在已有表上执行了一条 `ALTER TABLE ... ADD COLUMN ... NOT NULL`，为什么系统会直接报错甚至导致服务崩溃？我们该如何在不停机的前提下，安全演进数据库模式（Schema）并保证数据一致性？”

在个人开发或玩具项目中，改动数据库表结构就像改改代码里的变量名一样轻而易举：删掉数据库重建、或者直接执行一条修改语句。然而在企业级长期运行的系统中，数据库不仅承载着业务的绝对核心资产，而且正以每秒成千上万次的并发被各种版本的微服务同时读写。

一个未经深思熟虑的 Schema 改动，轻则锁死大表导致线上雪崩，重则破坏数据不变式引发静默数据污染。本课探讨关系型模式设计的核心价值：如何利用数据库原生约束守护系统正确性（`EC-CON-009 Correctness`），如何通过**渐进式演进（Expand-Contract 模式）**安全升级表结构，以及如何厘清**单一真实源（Source of Truth）**与**可重算派生视图（Derived View）**的边界。

## 3. 机制模型 (Mechanism Model)

### (1) 数据库约束作为核心系统不变式 (Invariants & Correctness)
应用代码会频繁重构、发布新版，甚至包含错误逻辑。如果仅在应用层做校验，任何绕过应用层的直接写入、未同步的旧版本服务或并发竞争，都会瞬间破坏数据完整性。
- 关系型数据库的真正威力在于：**它在存储层强行执行数学级的不变式（`EC-CON-008 Invariant`）**；
- `NOT NULL` 杜绝了空指针与缺失状态的模糊性；
- `UNIQUE` 与主键在物理树上维持唯一性保证；
- `FOREIGN KEY` 强制维护实体间引用的一致性，防止“孤儿数据”。

### (2) 渐进式模式演进：Expand-Contract 模式
当系统承载活跃流量时，直接“原地替换”列（例如重命名列、直接添加无默认值的非空列）会破坏旧版本服务的读写操作。
工程上的规范解法是**展开-收缩（Expand-Contract / Parallel Run）生命周期**：

```
Phase 1: [ EXPAND ] (展开)
  - 在数据库中新增列（保持 NULLABLE 或带有安全 DEFAULT）；
  - 此时旧版本服务继续读写旧列，新部署服务开始双写（Dual-Write）或优先读取新列；
  - 系统的向后兼容性（Backward Compatibility）得以完全维持。

Phase 2: [ BACKFILL ] (数据回填)
  - 通过分批（Batching）后台作业，将历史遗留行的数据迁移或计算填入新列；
  - 避免单次巨量全表更新产生超长事务与锁冲突。

Phase 3: [ CONTRACT ] (收缩)
  - 当所有运行中的服务均已升级到使用新列后，应用层停止对旧列的访问；
  - 数据库正式移除旧列（或标记废弃），完成闭环演进。
```

### (3) 单一真实源（Source of Truth）与派生视图（Derived View）
为了满足快速查询，系统常需展示聚合结果（如用户的总消费额、订单统计）。
- **单一真实源（Source of Truth）**：原始业务事件的规范不可变记录（如 `orders` 表每一笔交易）；
- **可重算派生视图（Derived View）**：从真实源经过确定性转换函数计算出的中间状态（如 `user_order_summary` 表）；
- **溯源元数据（Provenance Metadata）**：派生状态必须携带明确的溯源标记（如计算源表、计算时间戳、转换算法版本号）。一旦派生数据出现歧义或逻辑升级，系统能够完全依赖真实源执行无损重新计算。

*注意：本课所指的派生视图是指在业务架构中**显式设计为可重算**的确定性视图，不能推论为世间所有派生数据都可以无条件万能重算（例如当上游原始日志已被物理销毁时）。*

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 数据库约束提供了独立于应用程序生命周期的数据完整性硬边界；
   - 在并发系统演进中，读者与作者对数据模式的假设必须在过渡期内保持兼容；
   - 原始不可变事实构成业务的单一真实源，衍生聚合在数学上从属于真实源。
2. **具名引擎实证 (Named Engine Evidence - SQLite)**：
   - 在 SQLite 中，对已包含数据的表执行 `ALTER TABLE users ADD COLUMN phone TEXT NOT NULL;` 会直接触发 `OperationalError: Cannot add a NOT NULL column with default value NULL`；
   - 通过提供默认值 `DEFAULT ''` 即可顺利完成非阻塞 Expand 演进。
3. **易变当前实践 (Current Practice)**：
   - 现代云原生数据库（如 Spanner、CockroachDB、MySQL 8.0+ Instant DDL）对特定表结构变更已实现元数据级秒级执行，但读者/写者的版本兼容逻辑依然必须严格遵守 Expand-Contract 准则。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 实证报错输出剖析：
在已有记录的表上执行原生 `NOT NULL` 列新增：
```sql
ALTER TABLE users ADD COLUMN phone_number TEXT NOT NULL;
```
- **真实观测结果**：
  ```text
  sqlite3.OperationalError: Cannot add a NOT NULL column with default value NULL
  ```
- **破坏机理剖析**：
  - 数据库引擎检测到表中已经存在有效数据行；
  - 新增列时，引擎必须决定已存各行在该新列中的取值；
  - 既然定义了 `NOT NULL`，且未提供合法的非空默认值（`DEFAULT`），引擎将面临逻辑矛盾：如果填入 NULL 则公然践踏 `NOT NULL` 约束，如果凭空捏造值则缺乏依据；
  - 因此，数据库选择立即抛出异常拒绝变更，以钢铁般的纪律守护了状态一致性（`EC-CON-001 State` & `EC-CON-009 Correctness`）。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“反正应用层（如 Spring/Django/Node.js）已经写了 validation 校验，数据库里的约束（Constraint）全都可以不设。”**
  - **纠正**：致命错误。应用层逻辑不仅存在漏洞，而且随着时间推移会被其他运维脚本、数据修复工具、第三方同步通道乃至其他微服务绕过。一旦脏数据绕过应用层持久化进磁盘，清理成本往往极其巨大。存储层约束是数据正确性的最后一道坚固防线。
- **谬误 2：“生产环境重命名字段很简单，直接跑一条 `ALTER TABLE t RENAME COLUMN old TO new;` 即可。”**
  - **纠正**：在微服务集群滚动更新（Rolling Update）过程中，总有一段时间新旧版本的容器/进程同时在线。如果瞬间原地改名，旧版代码由于引用的旧列消失会瞬间大面积报错崩溃。必须使用 Expand-Contract 模式逐步过渡。
- **谬误 3：“派生数据也可以当作真实源随意手动修改。”**
  - **纠正**：派生数据是确定性转换的产物。如果在派生表上直接做非受控的手工篡改，当下一次全量重新计算触发时，所有手工改动都将被无情覆盖，造成不可逆的数据混乱。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
在一个每天处理数千万写入的支付系统中，为什么财务总账表必须严格依赖不可变的原始流水明细（Source of Truth），而不能直接通过在用户账户行上执行 `balance = balance + amount` 来代替流水表？

<details>
<summary>Hint 1</summary>
思考并发冲突与可审计性。如果系统发生网络抖动或服务崩溃重试，在没有流水明细的情况下，如何证明当前的 balance 是否多加或者少加了一笔钱？
</details>

<details>
<summary>Hint 2</summary>
对比“状态覆盖”与“事实追加”。当审计人员要求追溯三个月前某一天系统的账目历史时，直接存结果的表能推演出过去每个时刻的精确账目吗？
</details>

<details>
<summary>Expected Observation</summary>
学习者阐明：直接在余额上做原地累加丢失了导致状态发生变化的全部历史因果上下文；而将每笔交易作为不可变事实（Source of Truth）进行追加记录，余额只是明细历史的一种求和派生状态。一旦怀疑余额计算出错，可以根据原始事实完整复盘和重算。
</details>

<details>
<summary>Full Explanation</summary>
这是**单一真实源（Source of Truth）与可重算派生状态（Derived State）的经典实践**。原始事实（如每笔不可变的交易记录）是业务的不可伪造源头。通过将“事件事实”与“派生视图”解耦，系统获得了重放历史、故障审计、错误回滚与无损演进的非凡能力。如果直接将汇总值当成唯一存储，一旦计算产生单点错误（如并发竞争或程序 bug），历史真相将永久湮灭，无法恢复。
</details>

## 15. 核心概念引用与重温 (Concepts & Revisits)

- `EC-CON-001 State`: 数据库模式定义了系统合法状态的结构与转换边界；
- `EC-CON-003 Representation`: 列类型、空值表达与默认值设定直接约束底层数据的表示形态；
- `EC-CON-005 Interface`: 数据库表结构是服务之间通信的数据接口契约；
- `EC-CON-008 Invariant`: 约束规则构成了跨越时间与代码版本演进的硬性不变式；
- `EC-CON-009 Correctness`: 模式防御确保了系统状态从一个合法状态转移至另一个合法状态。

## 17. 严格推论边界 (Exact Inference Limits)

- Expand-Contract 模式展示了应用与数据库在单一节点上的模式演化逻辑，**不能推断出所有分布式数据库的 DDL 执行机制均无锁**；
- 派生数据在具有完整不可变源头数据时是可重算的，**但当上游数据被彻底截断或不可逆覆盖时，派生数据无法凭空再生**；
- 本实验中的轻量级 JSON 溯源是教学实证方案，**不能替代高合规金融或医疗场景中经过严格密码学签名的全链路审计日志**。
