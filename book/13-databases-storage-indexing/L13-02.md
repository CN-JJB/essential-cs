# L13-02｜SQL 究竟在做什么：关系意图、具名引擎执行与 Sargability 边界

## 1. 学习者核心问题 (Learner Question)

> “SQL 到底是一门‘执行指令’还是一个‘愿望清单’？为什么写了相同的逻辑意图（例如找用户名等于 Alice 的用户），仅仅把条件写成 `WHERE UPPER(username) = 'ALICE'`，查询速度就会发生断崖式下跌？SQL 引擎究竟是如何将我们的声明式意图翻译为具体机器步骤的？”

许多初学者常常误以为 SQL 语句就是执行引擎一行行直接跑的“脚本指令”，类似 Python 或 C 语言中的 `for` 循环。然而，SQL 是一门**声明式关系语言（Declarative Relational Language）**：你告诉数据库“你想要什么”（意图），而数据库的优化器与执行引擎则自行决定“如何去取”（执行策略）。

本课通过具体的具名引擎（SQLite 与 PostgreSQL）实证，解析关系声明与物理执行之间的抽象边界，并剖析为何不当的表达式会刺穿这层抽象，摧毁原本高效的索引访问路径（Sargability 边界）。

## 3. 机制模型 (Mechanism Model)

### (1) 声明式抽象与具名引擎现实 (Declarative Intent vs Named Engine Reality)
在计算机科学中，抽象（`EC-CON-005 Interface`）用于隐藏复杂性。SQL 就是最成功的声明式接口之一。
然而，**不存在跨所有数据库完全一致的通用执行管道**。不同具名引擎在实现上存在本质差异：
- **SQLite 架构**：将 SQL 编译为虚拟数据库引擎（VDBE, Virtual Database Engine）的寄存器式**字节码（Bytecode）**。你可以通过 `EXPLAIN SELECT ...` 直接看到生成的底层操作码（如 `OpenRead`, `SeekGE`, `Column`, `ResultRow`）。
- **PostgreSQL 架构**：将 SQL 解析为抽象语法树（AST），生成查询树（Query Tree），再通过路径生成器（Path Generator）基于代价模型生成物理计划树（Plan Tree），由执行器通过节点递归拉取元组。

*警告：教材中流传的所谓“AST → 逻辑计划 → 物理计划 → 火山模型迭代器”只是一种经典的教科书教学概括，绝非所有现代数据库的通用事实。*

### (2) Sargability（可搜索参数）的系统本质
**Sargable** 源自 “Search-Argument-Able” 的缩写，意为“能够作为索引搜索参数的谓词”。
- **Sargable 谓词**：形如 `column = literal`，`column >= literal AND column < literal`。这类谓词允许存储引擎直接提取边界值，在 B-Tree 根节点与分支节点上进行快速二分比对，直达匹配叶子节点。
- **Non-Sargable 谓词**：形如 `UPPER(column) = literal`，`column + 10 > literal`，`SUBSTR(column, 1, 3) = 'ABC'`。
  - **为什么包裹函数会破坏索引？** B-Tree 索引是按照**原始列值**排序构建的，而不是按照 `UPPER(column)` 计算后的值排序的！
  - 关系意图虽然等价，但从数学和信息论上，优化器在不进行全表计算的情况下，无法预先知道哪个原始字符串经过 `UPPER()` 后会等于目标值；
  - 物理结果：引擎无法在 B-Tree 上做有序寻道，只能退化为**全表扫描（Table Scan）**，逐行从磁盘读取数据并在 CPU 中执行函数计算。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 关系模型中，查询表达的是集合关系意图，而非物理遍历算法；
   - 基于原始列值构建的单列 B-Tree 索引，无法直接为未建立表达式索引的非单调函数转换提供有序剪枝能力；
   - 谓词的 Sargability 是数据库索引访问路径成立的前提条件。
2. **具名引擎实证 (Named Engine Evidence - SQLite)**：
   - 在我们的 M13 SQLite 夹具中，对 `users(username)` 建立了普通唯一索引；
   - `SELECT * FROM users WHERE username = 'user_42';` 触发 `INDEX_SEARCH`；
   - `SELECT * FROM users WHERE UPPER(username) = 'USER_42';` 触发 `TABLE_SCAN`。
3. **易变当前实践 (Current Practice)**：
   - 现代高级数据库可能支持“表达式索引 / 函数索引（Expression Index）”或“虚拟列（Generated Column）”来拯救特定函数的索引查找，但这需要显式定义特定的物理存储结构。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效案例：隐式类型转换导致的“隐形”非 Sargable 陷阱
如果在 SQLite 或其他数据库中，字段定义为字符串类型（如 `VARCHAR`），但查询条件传入了未加引号的数值：
```sql
SELECT * FROM users WHERE phone_number = 13800000000;
```
1. **触发行为**：为了比较不同类型，数据库引擎被迫对每一行的 `phone_number` 调用内置类型转换函数（如 `CAST`）；
2. **破坏后果**：尽管代码表面上没有显式写任何函数，但引擎内部插入的隐式转换等价于 `WHERE CAST(phone_number AS NUMERIC) = 13800000000`；
3. **计划崩溃**：索引静悄悄地失效了，系统全面退化为全表扫描。这是生产环境中最常见、最隐蔽的慢查询雪崩来源之一。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“现代数据库优化器已经高度智能化，能自动把 `WHERE UPPER(name) = 'ALICE'` 优化成走普通 `name` 索引。”**
  - **纠正**：错。`UPPER()` 是一个值变换。普通 B-Tree 索引按照原始大小写排序，如果要在不扫全表的情况下找到所有可能变体，引擎就必须遍历所有大小写组合，这在算法和工程上是不可行的。除非创建专门的表达式索引（如 `CREATE INDEX idx_upper ON users(UPPER(name));`），否则引擎别无选择只能全表扫描。
- **谬误 2：“所有关系型数据库的内部执行流程都是一模一样的。”**
  - **纠正**：错。不同数据库引擎的内部计算管道截然不同。SQLite 编译为寄存器字节码（VDBE）；PostgreSQL 采用节点树解释执行；DuckDB 采用向量化块执行；HyPer/ClickHouse 采用 LLVM 运行时代码生成（Codegen）。绝不能把教科书单一模型当成宇宙通用事实。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
为什么查询 `WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'` 是 Sargable 的，而 `WHERE strftime('%m', created_at) = '01'` 是 Non-Sargable 的？两者在语义上不都是“筛选一月份的记录”吗？

<details>
<summary>Hint 1</summary>
思考 B-Tree 的物理有序性。按 `created_at` 排序的数据在磁盘叶子页上是连续存储的吗？一月份的数据在时间轴上是一段连续区间，还是离散散落的？
</details>

<details>
<summary>Hint 2</summary>
前一种写法能否在 B-Tree 上确定一个明确的“起始搜索点”（Seek Key）和一个“终止停止点”？而后一种写法中，引擎在不计算每一行字符串的情况下，能仅凭索引直接跳过二月份的数据吗？
</details>

<details>
<summary>Expected Observation</summary>
学习者指出：前一种范围查询定义了一个连续的闭合区间 `[2026-01-01, 2026-02-01)`，B-Tree 可以通过根节点快速定位到区间的起点，并顺着叶子链表连续读取直到终点；而 `strftime` 函数破坏了这种直接的区间映射，导致不同年份的一月份数据在时间索引上跨越多个不连续区域，且必须对每行执行函数求值，无法直接利用 B-Tree 的区间检索能力。
</details>

<details>
<summary>Full Explanation</summary>
Sargability 的关键在于**谓词能否映射为 B-Tree 上的有限有序范围寻道（Range Seek）**。直接的范围谓词 `created_at >= A AND created_at < B` 让存储引擎只需执行 1 次对数寻道找到 A 的叶节点，然后按物理顺序遍历连续页直到 B，多余的页完全不用碰。而当包裹了 `strftime` 函数后，即使语义想表达相同的意图，物理索引中也没有直接存储该函数的计算结果，引擎失去了直接定位连续区间的能力，被迫退化为检查全表所有记录。
</details>

## 17. 严格推论边界 (Exact Inference Limits)

- 本课展示的非 Sargable 现象基于 SQLite 默认未建立表达式索引的表结构，**不代表在所有配置了特殊计算列/函数索引的数据库中均不能优化**；
- VDBE 字节码是 SQLite 内部实现私有协议，**不可直接套用到其他关系型数据库上**；
- 查询性能的高低不仅受 Sargability 影响，还受数据分布、系统负载与缓存状态综合约束。
