# L13-02｜SQL 究竟在做什么：关系意图、具名引擎执行与 Sargability 边界

## 1. 学习者核心问题 (Learner Question)

> “SQL 到底是一门‘执行指令’还是一个‘愿望清单’？为什么写了相同的逻辑意图（例如找用户名等于 Alice 的用户），仅仅把条件写成 `WHERE UPPER(username) = 'ALICE'`，查询的访问路径就可能发生根本改变？SQL 引擎究竟是如何将我们的声明式意图翻译为具体执行策略的？”

许多初学者常常误以为 SQL 语句就是执行引擎一行行直接跑的“脚本指令”，类似命令式编程中的 `for` 循环。然而，SQL 是一门**声明式关系语言（Declarative Relational Language）**：你告诉数据库“你想要什么”（意图），而数据库的编译器、规划器与执行引擎则自行决定“如何去取”（执行策略）。

本课通过具体的具名引擎（SQLite 与 PostgreSQL）实证，解析声明式关系意图与物理执行策略之间的抽象边界，并通过受控的实验夹具，剖析特定表达式如何在特定索引结构下影响优化器的访问路径选择（Sargability 边界）。

## 3. 机制模型 (Mechanism Model)

### (1) 声明式抽象与具名引擎现实 (Declarative Intent vs Named Engine Reality)
在计算机科学中，抽象（`EC-CON-005 Interface`）用于隐藏实现复杂性。SQL 就是最成功的声明式接口之一。
然而，**不存在跨所有数据库完全一致的通用执行流水线**。不同具名引擎在实现上存在本质差异：
- **SQLite 架构**：将 SQL 编译为虚拟数据库引擎（VDBE, Virtual Database Engine）的寄存器式**字节码（Bytecode）**。你可以通过 `EXPLAIN SELECT ...` 直接看到生成的底层操作码（如 `OpenRead`, `SeekGE`, `Column`, `ResultRow`）。
- **PostgreSQL 架构**：将 SQL 解析为抽象语法树（AST），生成查询树（Query Tree），再通过路径生成器（Path Generator）基于代价模型生成计划树（Plan Tree），由执行器通过节点递归拉取元组。

*警告：教材中流传的所谓通用物理管道只是一种教学抽象概括，具名引擎的具体架构各有其工程特化。*

### (2) Sargability（可搜索参数）在特定夹具下的机制
**Sargable** 源自 “Search-Argument-Able” 的缩写，意为“能够作为索引搜索参数的谓词”。
在针对特定列构建普通单列 B-Tree 索引的场景下：
- **可作为搜索参数的简单谓词**：形如 `column = literal`，`column >= literal AND column < literal`。这类谓词允许存储引擎直接提取搜索边界键，在 B-Tree 索引树上进行有序寻道定位；
- **包裹未索引函数的表达式**：形如 `UPPER(column) = literal`。
  - 普通 B-Tree 索引是按照**列的原始存储值**排序构建的，并不包含 `UPPER(column)` 后的计算结果；
  - 关系意图虽然明确，但优化器若未被配置专门的**表达式索引（Expression Index）**或**生成列（Generated Column）**，就无法直接把函数计算后的目标值映射到普通索引的有序键上；
  - 在本课的 SQLite 夹具中，引擎无法利用普通索引直接进行对数寻道，因而倾向于退化为扫描整张表并在评估每行时执行函数运算。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 关系模型中，查询表达的是集合关系意图，而非命令式遍历算法；
   - 基于原始列值构建的普通单列 B-Tree 索引，无法直接为未建立表达式索引的任意函数转换提供索引键寻道；
   - 索引变更改变执行策略，不改变声明式关系语义。
2. **具名引擎实证 (Named Engine Evidence - SQLite)**：
   - 在我们的 M13 SQLite 夹具中，对 `users(username)` 建立了普通唯一索引；
   - 执行 `SELECT * FROM users WHERE username = 'user_42';` 观察到 `SEARCH` 分类；
   - 执行 `SELECT * FROM users WHERE UPPER(username) = 'USER_42';` 在该普通索引下观察到 `SCAN` 分类；
   - 如果显式创建表达式索引（如 `CREATE INDEX idx_users_upper ON users(UPPER(username));`），SQLite 同样能够对该特定表达式执行索引搜索。
3. **易变当前实践 (Current Practice)**：
   - 现代数据库普遍提供表达式索引（Expression Index / Functional Index）或虚拟生成列（Virtual / Stored Generated Column）作为显式优化手段；
   - 函数包裹是否必然导致全表扫描取决于是否存在对应表达式索引、覆盖索引或子查询重写规则，不可将“包裹函数必导致全表扫描”作为无条件系统定理。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 受控对比：普通索引面对未索引表达式的访问路径变化
在 `users` 表上仅建立普通列索引 `CREATE UNIQUE INDEX idx_users_username ON users(username);`：
1. **执行查询对比**：
   - 比较 `WHERE username = 'user_42'` 与 `WHERE SUBSTR(username, 1, 7) = 'user_42'`；
2. **观察真实计划变化**：
   - 优化器在面对 `SUBSTR(...)` 或 `UPPER(...)` 等表达式时，由于普通索引的 B-Tree 键只按原始字符串排序，优化器无法将前缀或函数结果直接作为普通索引的二分寻道键；
   - 记录两条查询各自的实际计划；若本夹具中观察到由索引搜索变为 `SCAN`，解释为什么**这个普通索引 + 这个表达式**没有提供直接的表达式键寻道，而不要推广成“所有函数都必然扫描”；
3. **修复与替代方案**：
   - 若业务确实频繁按大写或子串查询，显式替代方案为创建对应的表达式索引：
     ```sql
     CREATE INDEX idx_users_upper ON users(UPPER(username));
     ```
     此时再执行 `WHERE UPPER(username) = 'USER_42'`，该表达式索引会成为一个可供优化器考虑的相关访问路径；仍须记录实际 EQP，而不能预填最终选择。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“现代数据库优化器能够自动推导并把 `WHERE UPPER(name) = 'ALICE'` 优化为利用普通 `name` 索引。”**
  - **纠正**：在本课的 SQLite 普通单列索引夹具中，索引键是原始列值；`UPPER(name)` 的计算结果并不直接存储在该普通索引中，因此该索引不能直接提供等价的表达式键寻道。其他引擎、查询改写规则或专用表达式索引必须分别具名验证。
- **谬误 2：“所有关系型数据库的内部执行流程和计划生成都是完全一致的。”**
  - **纠正**：不同数据库引擎的内部计算管道存在显著实现差异。SQLite 编译为寄存器字节码（VDBE）；PostgreSQL 采用节点树解释执行；不可将单一教学抽象当成通用事实。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
为什么查询 `WHERE created_at >= '2026-01-01' AND created_at < '2026-02-01'` 在普通索引上可以作为连续范围寻道参数，而 `WHERE strftime('%m', created_at) = '01'` 在普通索引上却往往导致全表扫描？

<details>
<summary>Hint 1</summary>
思考普通 B-Tree 索引的有序键结构。按 `created_at` 排序存储的数据，其时间范围在逻辑键空间上是否构成连续闭区间？
</details>

<details>
<summary>Hint 2</summary>
前一种写法能否在普通索引树上确定明确的起始键（Seek Key）与终止键？而后一种写法中，不同年份的一月份记录在时间索引树上是集中在单一段落，还是分散在各个年份之间？
</details>

<details>
<summary>Expected Observation</summary>
学习者指出：前一种范围查询定义了一个按时间有序排列的连续键区间 `[2026-01-01, 2026-02-01)`，普通索引可以通过树查找定位到起始键并沿着索引顺序读取直至结束键；而 `strftime` 提取月份破坏了直接的键映射，不同年份的 1 月份分散在索引树的不同位置，且需要逐行执行函数求值，因此普通时间索引无法直接作为有序寻道参数。
</details>

<details>
<summary>Full Explanation</summary>
在本课给定的普通时间索引上，可搜索参数（Sargable）的关键问题是：谓词能否直接映射为该索引键空间上的范围。直接的日期范围谓词能给出明确的起止键；`strftime('%m', created_at)` 的结果并未存储在这个普通索引中，因此它不能直接提供同样的单一区间定位。工程上可以**改写查询为直接日期范围**，也可以在具名引擎支持时建立对应的表达式索引/生成列；最终访问路径仍以实际计划为准。
</details>

## 17. 严格推论边界 (Exact Inference Limits)

- 本课展示的访问路径变化基于普通列索引的特定夹具，**不可推论为所有配置了表达式索引或智能查询重写的系统均无法利用索引**；
- VDBE 字节码是 SQLite 内部实现私有协议，**不可直接套用到其他关系型数据库上**；
- 谓词的可搜索性是访问路径选择的重要考量，但最终计划依然受数据分布与成本模型综合约束。
