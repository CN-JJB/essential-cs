# L13-01｜为什么我的查询时快时慢：索引、访问路径与存储引擎的心智模型

## 1. 学习者核心问题 (Learner Question)

> “为什么在数据库里执行相同的 `SELECT` 查询，有时几毫秒就返回，有时却需要耗费数秒甚至导致系统卡顿？给每一列都建上索引，查询就一定会变快吗？数据库在底层到底是如何决定用不用索引的？”

在初学数据库时，许多开发者把数据库当成一个黑盒的“字典”或“键值存储”：以为只要加上 `WHERE` 条件，数据库就能神奇地瞬间拿到数据；遇到慢查询时，第一反应往往是“给相关字段随手加个索引”。然而在生产环境中，盲目加索引不仅常常无法加速查询，反而会导致写入严重变慢、磁盘空间膨胀，甚至让查询优化器产生误判。

本课通过真实的 SQLite 数据库物理访问路径实测，剥开数据库执行查询的底层机制，建立起从“SQL 意图”到“存储页 I/O”的完整心智模型。

## 3. 机制模型 (Mechanism Model)

现代关系型数据库的执行并非直接在磁盘物理字节上做字符串搜索，而是遵循清晰的层次化机制：

```
SQL 声明式意图 (SELECT ...)
      │
      ▼
查询编译器 / 解析器 (Parser & Planner in a Named Engine)
      │
      ▼ [优化器依据代价模型权衡]
物理访问路径选择 (Access Path: SCAN vs SEARCH USING INDEX)
      │
      ▼
页面与缓存交互 (Buffer Pool / OS Page Cache: Page Fetch & Pinning)
      │
      ▼
物理存储设备 (Sequential I/O vs Random I/O on Storage Media)
```

### (1) 页面存储与局部性原理 (Pages & Locality)
数据库表在物理介质上不是连续的无限字符流，而是切分为固定大小的**数据页（Pages）**（例如 SQLite 默认 4096 字节，PostgreSQL 默认 8192 字节，MySQL InnoDB 默认 16384 字节——**注意：页大小属于具体引擎的实现参数，绝非跨系统常数**）。
- 每次从磁盘读取数据，最小 I/O 单位是整个页面；
- 当执行没有可用索引的查询时，存储引擎必须执行**全表扫描（Table Scan）**：逐一将包含表记录的所有数据页装入内存，并在 CPU 中逐行评估过滤条件。

### (2) B-Tree 索引机制与回表代价 (Index Lookup & Heap Access)
索引本身也是一组组织为平衡树（B-Tree / B+Tree）的数据页。
- 索引页内部按索引列的值有序排列；
- 索引查找通过根节点到叶节点的二分/多分查找，将 $O(N)$ 的页面扫描降低为 $O(\log N)$ 的树高遍历；
- **回表代价（Rowid / Heap Lookup）**：二级索引叶节点通常仅保存“索引列的值 + 主键/Rowid”。如果查询需要的列不在该索引内，引擎在命中索引叶子后，必须拿着主键再次寻址主表数据页（回表）。若查询命中成千上万行，数千次随机回表 I/O 的总开销可能会远远超过一次性顺序读取整张表的所有页！

## 4. 认知声称层 (Claim Layer)

为了避免将某一数据库的偶然表现当成普适真理，Essential CS 严格划分三个认知层次：

1. **核心系统不变式 (Core Invariants)**：
   - 数据在持久化介质上以页（Page）为基本 I/O 块；
   - 顺序 I/O 与随机 I/O 存在显著的物理性能特征差异；
   - 增加二级索引必然增加存储占用，并在每次 `INSERT` / `UPDATE` / `DELETE` 时引入额外的写入开销（写放大）；
   - 索引改变物理执行路径，绝不改变声明式关系语义与最终结果集。
2. **具名引擎实证 (Named Engine Evidence - SQLite 3.x / PostgreSQL)**：
   - 在 SQLite 中，`EXPLAIN QUERY PLAN` 使用 `SCAN` 表示全表扫描，使用 `SEARCH ... USING INDEX` 表示利用索引；
   - SQLite 使用 B-Tree 组织表与索引，主键使用内部 `rowid`；
   - PostgreSQL 代价模型通过 `seq_page_cost` 与 `random_page_cost` 显式量化顺序读与随机读。
3. **易变当前实践 (Current Practice & Workload Context)**：
   - 具体查询耗时取决于 CPU 频率、内存总线带宽、SSD 控制器缓存与操作系统 Page Cache 命中率；
   - “当过滤结果少于 10% 时索引一定更快”是一个粗糙的工程经验规则，绝非通用物理常数。

## 5. 观察前预测 (Prediction-Before-Observation)

在执行任何实测命令之前，请先对以下场景做出明确预测并记录在实验单上：

1. **场景 A**：一张包含 5,000 条订单的表 `orders`，未建立任何二级索引。执行 `SELECT * FROM orders WHERE user_id = 42;`。
   - **你的预测**：优化器会报告 `SCAN` 还是 `SEARCH`？引擎需要读取多少数据页？
2. **场景 B**：执行 `CREATE INDEX idx_orders_user ON orders(user_id);` 后，再次执行相同查询。
   - **你的预测**：返回的结果行数和具体内容会改变吗？优化器给出的计划会有何变化？
3. **场景 C**：执行 `SELECT * FROM orders WHERE amount > 0.0;`（几乎所有订单金额都大于 0）。
   - **你的预测**：即使存在索引，优化器会使用索引还是全表扫描？为什么？

```bash

python labs/foundations/m13/fixture_l13.py
```

### 实践步骤：
1. **未建立索引时的执行计划观察**：
   观察未加索引时 `orders.user_id = 42` 的 EQP 输出：
   ```text
   detail: SCAN orders
   ```
   记录此时的物理访问分类为 `TABLE_SCAN`。
2. **创建二级索引并对比计划**：
   通过 `CREATE INDEX idx_orders_user ON orders(user_id);` 创建索引后，再次观察 EQP 输出：
   ```text
   detail: SEARCH orders USING INDEX idx_orders_user (user_id=?)
   ```
   记录物理访问分类跃迁为 `INDEX_SEARCH`。
3. **验证结果集等价性 ($\Delta = 0$)**：
   比对建立索引前后查询输出的行数与每行数据。结果集必须完全一致，证明索引仅改变物理效率，不改变逻辑结果。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验：低选择率下的索引失效与扫描倾向
如果在 `orders` 表上执行一个几乎命中全部数据的查询：
```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE amount > 0.0;
```
即使我们在 `amount` 上建立了索引：
1. 观察计划器输出：计划器仍然选择 `SCAN orders`，而不是 `SEARCH USING INDEX`！
2. **失效机理剖析**：
   - 遍历索引需要读取索引数据页；
   - 命中索引后，由于 `SELECT *` 需要非索引列，引擎必须对每一条记录执行一次主表随机 I/O（回表）；
   - 如果 95% 以上的行都需要回表，索引遍历加上几千次离散随机回表的总代价，将远远高出直接将整个表线性读一遍的全表扫描代价。
   - **系统启示**：“有索引可用”绝不等于“优化器必须用索引”。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“索引越多越好，给表上的每个字段都加上索引系统就会变快。”**
  - **纠正**：每个二级索引都是一棵独立的 B-Tree 物理存储实体。每次插入新行、删除行或修改索引列时，数据库都必须同步修改每一棵相关的 B-Tree，并承担分裂节点与刷盘开销。过多的索引会导致写入性能急剧恶化，并占用大量磁盘空间与内存缓冲。
- **谬误 2：“只要建立了索引，数据库就一定会使用它来加速查询。”**
  - **纠正**：优化器是基于代价或规则做决定的。当查询选择率较低（需要返回大量行）时，通过二级索引回表的随机 I/O 成本远大于直接全表顺序扫描。
- **谬误 3：“只要加了索引，查询就一定能获得固定倍数（如 100 倍）的加速。”**
  - **纠正**：性能提升倍数取决于数据规模、树高、冷热数据分布以及操作系统缓存命中率。对于小表（如仅占 1~2 个页面的表），全表扫描通常比索引查找更快。严禁在课程中宣称固定的性能倍数常数。

## 10. 现阶段可暂缓深入的内容 (What You Can Ignore — For Now)

- B+Tree 叶子节点的双向链表并发重平衡（SMO, Structure Modification Operation）加锁细节；
- LSM-Tree（如 RocksDB）与 B-Tree 的写放大（WAF）对比（将在后续高级存储专题讨论）；
- 复杂覆盖索引（Covering Index）与位图扫描（Bitmap Index Scan）在多核并行环境下的调度。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
为什么对于只有几十条记录的配置表，即使给查询条件建立了索引，查询优化器也往往会选择直接全表扫描（`SCAN`）？

<details>
<summary>Hint 1</summary>
回顾数据页（Page）的物理尺寸与磁盘 I/O 的最小粒度。整张几十条记录的表一共占用了几个数据页？
</details>

<details>
<summary>Hint 2</summary>
对比两种访问路径的 I/O 次数：全表扫描需要读取几个页面？而走索引树需要先读索引根节点、叶节点，然后再读数据页，一共需要读取几个页面？
</details>

<details>
<summary>Expected Observation</summary>
学习者观察到或推导出：当表体积极小时（例如整张表仅占 1 个物理页面），全表扫描只需要单次 I/O 即可将整表读入内存并瞬间完成 CPU 过滤；而走索引则需要先读取索引页，再寻址数据页，I/O 步骤反而更多。因此优化器明智地拒绝使用索引。
</details>

<details>
<summary>Full Explanation</summary>
优化器的决策核心是**物理代价最小化**。对于极小规模的表，全表记录通常完全容纳在单一数据页内。全表扫描仅需 1 次页面读取（且极易常驻在内存缓存中）。如果强行使用二级索引，引擎必须先读取索引页解析出 Rowid，再回表读取数据页，至少引入 2 次页面寻址。因此，在小数据集上全表扫描在逻辑和物理上都比索引更经济。这再次证明：**访问路径的选择高度依赖于实际工作负载与物理存储规模，绝不存在孤立于环境的“绝对最优”路径**。
</details>

## 15. 核心概念引用与重温 (Concepts & Revisits)

- `EC-CON-001 State`: 数据库表与索引是持久化在磁盘数据页上的状态集合；
- `EC-CON-005 Interface`: SQL 声明式查询接口屏蔽了底层具体是用全表扫描还是 B-Tree 索引的细节；
- `EC-CON-006 Trade-off`: 读性能加速（利用索引）与写性能/空间开销（维护多棵 B-Tree）之间的根本权衡；
- `EC-CON-011 Caching`: 缓冲池缓存数据页，减少物理磁盘 I/O。

## 17. 严格推论边界 (Exact Inference Limits)

- 本实验的毫秒级耗时受操作系统调度、宿主机内存缓存与 SSD 垃圾回收影响，**不可作为跨平台通用性能基准**；
- SQLite 的 EQP 输出格式是 SQLite 特有的可读表示，**不可假定其他数据库（如 MySQL 或 Oracle）具有相同的语法输出**；
- 观察到索引在 5,000 行表上带来加速，**不可推论出在任意规模、任意硬件的所有表上索引都能带来同等增益**。
