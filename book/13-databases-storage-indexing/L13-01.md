# L13-01｜为什么我的查询时快时慢：索引、访问路径与存储引擎的心智模型

## 1. 学习者核心问题 (Learner Question)

> “为什么在数据库里执行相同的 `SELECT` 查询，有时几毫秒就返回，有时却需要耗费数秒甚至导致系统卡顿？给每一列都建上索引，查询就一定会变快吗？数据库在底层到底是如何决定用不用索引的？”

在初学数据库时，许多开发者把数据库当成一个黑盒的“字典”或“键值存储”：以为只要加上 `WHERE` 条件，数据库就能神奇地瞬间拿到数据；遇到慢查询时，第一反应往往是“给相关字段随手加个索引”。然而在实际工程中，盲目加索引不仅常常无法加速查询，反而可能增加写入维护成本、占用更多磁盘空间，甚至让查询优化器在不同访问路径之间做出出人意料的权衡。

本课通过真实的 SQLite 数据库物理访问路径实测，剥开数据库执行查询的底层机制，建立起从“SQL 意图”到“存储页与访问路径”的完整心智模型。

## 3. 机制模型 (Mechanism Model)

现代关系型数据库的执行并非直接在磁盘物理字节上做简单的字符串匹配，而是遵循分层的执行机制：

```
SQL 声明式意图 (SELECT ...)
      │
      ▼
查询编译器 / 解析器 (Parser & Planner in a Named Engine)
      │
      ▼ [优化器依据代价模型或规则进行权衡]
访问路径选择 (Access Path: SCAN vs SEARCH USING INDEX)
      │
      ▼
页面与缓存交互 (Buffer Pool / OS Page Cache: Page Fetch)
      │
      ▼
物理存储设备 (Storage Media I/O)
```

### (1) 页面存储与局部性原理 (Pages & Locality)
数据库表在物理介质上不是连续的无限字符流，而是切分为固定大小的**数据页（Pages）**。
- **页面大小是具名引擎的实现与配置参数，绝非跨引擎的普适常数**（例如 SQLite 默认通常为 4096 字节，PostgreSQL 默认通常为 8192 字节，MySQL InnoDB 默认通常为 16384 字节）；
- 数据库访问介质时，通常以页面为基本数据交换块；
- 当执行没有可用索引或优化器判定不走索引的查询时，存储引擎通常执行**全表扫描（Table Scan）**：逐一检查包含该表记录的数据页，并在 CPU 中逐行评估过滤条件；
- **区分逻辑访问路径与物理 I/O**：SQLite 的 `EXPLAIN QUERY PLAN` 描述的是查询规划器选择的**高层逻辑访问路径**（例如 `SCAN` 或 `SEARCH`），并不等同于物理磁盘 I/O 次数。如果数据页已在操作系统 Page Cache 或数据库内部缓存中，即使是 `SCAN` 也可能不发生任何物理磁盘读取；反之，若发生缓存未命中，逻辑上的单次查找也可能需要从介质加载页面。

### (2) B-Tree 索引机制与回表代价 (Index Lookup & Heap Access)
索引本身也是一组组织为平衡树（如 B-Tree / B+Tree）的数据页。
- 索引页内部按索引列的值维护有序结构；
- 索引查找通过根节点到叶节点的键值比对，将无序扫描转换为树遍历；
- **回表代价（Rowid / Heap Lookup）**：二级索引叶节点通常仅保存“索引列的值 + 主键/Rowid”。如果查询所需的字段未被该索引完全覆盖，引擎在命中索引叶子项后，必须拿着主键再次寻址主表数据页以获取其余列。若查询匹配的行数较多，多次离散的回表寻址与页面加载总开销，完全可能高出直接线性读取整张表页面的代价。

## 4. 认知声称层 (Claim Layer)

为了避免将某一数据库的偶然表现当成普适真理，Essential CS 严格划分三个认知层次：

1. **核心系统不变式 (Core Invariants)**：
   - 数据在持久化介质上以页（Page）为基本组织块；
   - 顺序访问与随机访问存在显著的系统性能特征差异；
   - 增加二级索引必然增加存储空间占用；当执行涉及该索引列的 `INSERT`、`UPDATE` 或 `DELETE` 操作时，引擎必须同步维护该索引树，带来额外的写维护成本（写放大）。若 `UPDATE` 操作未触及任何被索引的列，则通常无需更新该二级索引树；
   - 索引改变物理执行策略，绝不改变声明式关系语义与最终结果集。
2. **具名引擎实证 (Named Engine Evidence - SQLite 3.x / PostgreSQL)**：
   - 在 SQLite 中，`EXPLAIN QUERY PLAN` 使用 `SCAN` 表示全表扫描，使用 `SEARCH ... USING INDEX` 表示利用索引；
   - SQLite 官方文档明确指出：EQP 的输出格式在不同版本间可能调整，且其内容仅表示规划器的高层计划描述，不作为低层物理 I/O 或执行时间的稳定证明；
   - PostgreSQL 代价模型通过 `seq_page_cost` 与 `random_page_cost` 参数显式量化顺序页面读取与随机页面寻道的相对权重。
3. **易变当前实践 (Current Practice & Workload Context)**：
   - 具体查询耗时取决于硬件平台、CPU 频率、操作系统 Page Cache 状态与缓存命中率；
   - 所谓“选择率超过 X% 索引一定不生效”是特定工作负载下的工程经验启发，绝非系统级常数。
   - 严禁宣称任何固定的性能倍数、固定页大小常数或固定的文件膨胀比例。

   - **你的预测**：优化器会报告扫描（`SCAN`）还是索引搜索（`SEARCH`）？

3. **场景 C**：在存在相关索引的情况下，执行一个匹配绝大多数记录的低选择率查询（例如在订单表上执行过滤条件宽松的范围查询）。
   - **你的预测**：优化器一定会使用索引吗？为什么可能出现全表扫描？

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验：低选择率与工作负载变化下的访问路径权衡
在包含相关索引的表上，执行一个低选择率（匹配极高比例行数）的查询：
```sql
EXPLAIN QUERY PLAN SELECT * FROM orders WHERE amount > 0.0;
```
1. **观察计划器输出**：
   记录计划器实际报告的路径。观察计划器是否选择了 `SCAN orders`，还是依然尝试使用索引。
2. **失效与权衡机理剖析**：
   - 遍历二级索引需要读取索引页；
   - 命中索引后，如果查询需要非索引列，引擎必须对每一条匹配记录执行一次主表数据页寻址（回表）；
   - 当查询需要返回大量记录时，大量离散的回表寻址总代价完全可能高出直接全表扫描所有页面的代价；
   - **核心启示**：存在可用的索引，并不意味着优化器必然选择该索引。优化器的决策取决于其成本模型、统计信息以及具体工作负载特征。无论是 `SCAN` 还是 `SEARCH`，都必须如实记录实际观测，绝不强行预设单一结果。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“索引越多越好，给表上的每个字段都加上索引系统就会变快。”**
  - **纠正**：每个二级索引都是一棵独立的 B-Tree 物理存储结构。当插入新行、删除行或更新被索引列时，数据库都必须同步维护对应的索引树并承担相应开销。不必要的索引会导致写维护成本上升与存储空间膨胀。
- **谬误 2：“只要建立了索引，数据库就一定会使用它来加速查询。”**
  - **纠正**：优化器根据代价估算或内部规则做决策。当查询选择率较低（需要返回大量行）时，通过二级索引回表的开销可能大于全表连续扫描。
- **谬误 3：“只要加了索引，查询就一定能获得固定倍数（如 100 倍）的加速。”**
  - **纠正**：性能变化取决于数据规模、树高、冷热数据分布、缓存命中率以及工作负载。对于规模极小的表，全表扫描往往比走索引树更加经济。课程中严禁宣称任何固定的性能倍数常数。

- 复杂多列联合覆盖索引与位图索引扫描（Bitmap Index Scan）的底层位图合并算法。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
为什么对于规模极小的表（例如仅占一两个数据页的配置表），即使给查询条件建立了索引，查询优化器也往往会选择直接执行全表扫描（`SCAN`）？

<details>
<summary>Hint 1</summary>
思考数据页（Page）的组织粒度。如果整张表的数据仅存放在极少数数据页中，全表扫描需要触及多少页面？
</details>

<details>
<summary>Hint 2</summary>
对比两种访问路径的逻辑寻址步骤：全表扫描只需连续扫描这些数据页；而走二级索引需要先在索引树中寻道，再回表寻址主表数据页，其寻道和逻辑操作步骤是否真的更少？
</details>

<details>
<summary>Expected Observation</summary>
学习者指出或推导出：当表规模极小时，全表扫描仅需读取极少数数据页并在内存中完成过滤；而走二级索引需要先遍历索引页获取 Rowid，再回表寻址数据页，逻辑寻址步骤反而增多。因此优化器根据代价模型评估后，会合理倾向于选择全表扫描。
</details>

<details>
<summary>Full Explanation</summary>
优化器的目标是在候选路径中寻找**估计代价更低**的策略。对于极小规模的表，全表记录通常仅占用极少的数据页（且这些页面极易被操作系统或引擎缓存保留）。全表扫描的逻辑访问开销极小。如果使用二级索引，引擎需要额外遍历索引树，随后再回表加载数据页，增加了额外的访问层次。因此，优化器倾向于直接扫描小表。这印证了核心系统规律：**访问路径的选择高度依赖于实际工作负载与数据规模，绝不存在脱离具体环境的“绝对最优”路径**。
</details>

## 15. 核心概念引用与重温 (Concepts & Revisits)

- `EC-CON-001 State`: 数据库表与索引是持久化在磁盘数据页上的结构化状态集合；
- `EC-CON-003 Representation`: 索引是按键值排序的辅助数据表示，用于加速特定条件的检索；
- `EC-CON-005 Interface`: SQL 声明式查询接口屏蔽了底层具体采用全表扫描还是 B-Tree 索引的细节；
- `EC-CON-006 Trade-off`: 读性能加速（利用索引）与写维护/存储空间开销（维护多棵 B-Tree）之间的根本权衡；
- `EC-CON-008 Invariant`: 关系查询结果集在加索引前后保持一致；
- `EC-CON-009 Correctness`: 索引变更不改变查询关系语义（$\Delta = 0$）；
- `EC-CON-011 Caching`: 缓冲池缓存数据页，减少对物理存储设备的重复读取；
- `EC-CON-012 Locality`: 顺序扫描与索引区间检索分别依赖空间局部性与树有序性。

## 17. 严格推论边界 (Exact Inference Limits)

- 本实验的耗时受操作系统调度、宿主机内存缓存与底层硬件影响，**不可作为跨平台通用性能基准**；
- SQLite 的 EQP 输出格式是 SQLite 特有的可读表示，**不可假定其他数据库具有相同的语法输出或判定逻辑**；
- 在特定测试数据集上观察到的索引行为，**不可推论为在任意规模、任意硬件的所有表上索引都能带来同等增益**；
- 严禁宣称任何普适的选择率阈值、固定页大小常数、确定性 I/O 次数或固定的文件大小增长比例。
