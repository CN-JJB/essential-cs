## 1. 学习者核心问题 (Learner Question)

> “在单机程序中，函数调用要么返回结果，要么抛出异常，要么导致整个进程崩溃——调用者和被调用者同生共死。为什么一旦把函数调用拆分到两台不同的物理机器上，被调用机器没有响应时，我们竟然无法知道那段远程代码到底执行了没有？为什么客户端设置的‘超时时间’，在服务端看来什么都不是？”

在学习单机操作系统与并发编程时（回顾 `L06-01` 进程模型与 `L15-01` 并发），我们习惯了一个确定性的假设：所有指令在同一个由硬件时钟驱动的主板和内存空间中推进。即便两个线程交替执行引发逻辑竞态，其共享内存的状态在任意时刻仍然服从物理内存控制器的仲裁。

然而，一旦跨越网络边界，物理世界的基本面貌发生了断裂：
- **独立的物理生命周期**：客户端机器与服务端机器拥有独立的电源、CPU、时钟和操作系统内核。服务端可能在崩溃的同时，客户端却完好无损地继续运行；
- **非零且无界的网络延迟**：光纤与交换机中的数据传输需要物理时间，而排队、拥塞和重传使得网络单程延迟在数学上是**无上界的（Unbounded Delay）**；
- **静默无应答的根本歧义**：当客户端发出一个网络请求后陷入长时间的寂静，无论等待了 500 毫秒还是 50 秒，客户端从“静默”本身**绝对无法推导出服务端的真实状态**。

本课将带领学习者打破单机思维惯性，通过实证直面分布式系统第一法则：**部分失效（Partial Failure）**与**静默无应答的根本歧义**。

## 3. 机制模型 (Mechanism Model)

### (1) 部分失效与无应答四态 (The Four States of Remote Silence)

在单机环境中，如果进程 A 调用模块 B：
- 若模块 B 死循环或崩溃，操作系统或硬件异常捕获机制会将崩溃反馈给调用方，或者由于共享同一个硬件电源，整个机器一同宕机。

在由异步网络连接的分布式系统中（重温 `EC-CON-010 Failure`），调用方与被调用方驻留在物理隔离的两个 `EC-CON-018 Process` 中。当客户端发出请求后，如果网络陷入寂静，系统存在**四种客观存在但对客户端完全不可区分的状态**：

1. **状态 1（请求在入站途中丢失或受阻）**：请求在网络传输中被丢弃或阻塞，服务端**从未收到过**该请求，业务代码**未执行**；
2. **状态 2（服务端在执行前崩溃）**：请求已送达服务端网卡，但在应用进程读取处理之前，服务端操作系统崩溃或断电，业务代码**未执行**；
3. **状态 3（业务已执行完成，但响应在出站途中丢失或受阻）**：服务端完整且成功地执行了业务状态变更（例如已扣款），但在将响应包写回网络时链路中断，客户端**未收到响应**，但业务**已生效**；
4. **状态 4（服务端或链路仅仅是迟缓）**：网络拥塞严重，或者服务端正在执行深度垃圾回收（GC Pause）/排队积压，服务端正在处理或尚未处理，响应**仍在途中**。

### (2) 泄漏的抽象：为什么 RPC 无法真正像本地函数调用？

回顾 **`EC-CON-002 Abstraction`**：
计算机科学中最强大的思想是将复杂机制隐藏在清晰的接口之下。20 世纪 80 年代（Birrell & Nelson, 1984），计算机系统先驱提出了**远程过程调用（RPC, Remote Procedure Call）**，试图构建一个精妙的抽象：让程序员调用位于千里之外的远程机器上的函数，就像调用本地内存中的 `add(a, b)` 一样自然。

然而，Waldo 等人在 1994 年的经典论文 *A Note on Distributed Computing* 中尖锐地指出了这一抽象的不可弥合性：
1. **延迟数量级的断层**：本地内存调用耗时在纳秒级别（1–10 ns），而跨越数据中心或互联网的网络往返耗时在毫秒级别（1–100 ms），相差 $10^5 \sim 10^7$ 倍；
2. **内存地址空间隔离**：本地调用可以通过指针传递复杂的数据结构（重温 `EC-CON-018 Process` 虚拟地址空间隔离）；远程调用必须将数据逐层序列化（Marshal）为无指针的字节流（重温 `EC-CON-003 Representation`），深层对象图与指针别名无法透明传递；
3. **部分失效的本质泄漏**：本地调用中，调用者与被调用者共享同一个宿命；分布式调用中，网络随时断裂，服务随时宕机。试图掩盖网络失败的 RPC 抽象，必然在真实世界的静默面前彻底破产。

### (3) 超时的本质：本地放弃等待决策

客户端为远程调用配置的 `timeout = 500ms`，究竟是什么？
- **它不是向服务端的广播命令**：客户端并没有在 500ms 瞬间把一根物理控制线拉低；
- **它不是远程执行的撤销器**：客户端超时抛出 `TimeoutError` 时，服务端内核与进程可能毫无知觉，正在全速写入磁盘；
- **它仅仅是客户端本地调度器的单方面决裂**：客户端认定“根据我的业务截止期限（Deadline），我不能无限期挂起当前线程，我必须在此刻停止等待并进入异常处理流程”。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 在异步网络通信中，单凭网络通道的沉默，在逻辑上完全不可能推断出远端状态机的确切状态；
   - 客户端超时是本地时钟与控制流的放弃等待决策，对远端物理主机的状态迁移不具备自动取消约束力；
   - 传输层连接建立（TCP Handshake）或数据分节确认（TCP ACK）仅证明操作系统内核收到了字节，绝不证明应用层业务逻辑处理成功或完成持久化（`EC-CON-016 Durability`）。
2. **具名规范与实证 (Specification & Evidence)**：
   - POSIX.1-2024 定义了套接字超时语义（`SO_RCVTIMEO` / `SO_SNDTIMEO`），在超时后返回 `EAGAIN` / `EWOULDBLOCK`；
   - 经典分布式理论中，两军问题（Two Generals Problem, Jim Gray 1978）在数学上证明了在不可靠信道上无法达成确定性的无条件一致共识；
   - 课程实验通过本机回环套接字（`127.0.0.1` 临时端口）与应用层故障注入垫片，确定性观察到“客户端已超时抛出异常，服务端在稍后完成该请求业务记录”的时间线偏离事实。
3. **推论边界与当前实践 (Current Practice & Inference Limits)**：
   - 本课通过应用层垫片引入的处理延迟，**属于进程内控制流调度模拟，绝不可外推宣称为真实的物理网线断开或物理包丢失**；
   - 现代微服务框架（如 gRPC、Envoy）通过请求上下文向下传递超时期限（`grpc-timeout` / Context Deadline Propagation），但这依赖于显式协议协作与应用层主动检查，并非由网络协议栈自动保证。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效示范：将超时当成失败直接重试的资金翻倍故障

审查以下朴素转账伪代码：

```python
# 致命错误：误以为超时就等于没有扣款
def pay_merchant(order_id, amount):
    attempts = 0
    while attempts < 3:
        try:
            # 客户端设置 500ms 超时
            return rpc_client.call("transfer", {"order": order_id, "amount": amount}, timeout=0.5)
        except TimeoutError:
            attempts += 1
            print(f"调用超时，第 {attempts} 次重试...")
    raise PaymentFailed("支付失败")
```

1. **破坏现象**：商户促销高并发，服务端数据库处理变慢，转账耗时从 50ms 激增至 800ms。用户点击一次支付，客户端每隔 500ms 超时一次并触发重试。最终客户端虽然看到“支付失败”，但银行卡却被**连续扣了 3 次款**！
2. **机理剖析**：每次超时仅仅是客户端本地停止等待。服务端收到了第 1 个请求并在 800ms 时完成扣款；在完成前，客户端又递交了第 2 个相同请求；紧接着递交了第 3 个相同请求。服务端缺乏幂等防线，将这 3 次重试当作 3 笔相互独立的业务请求依次扣款。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“客户端收到 TimeoutError，说明请求根本没有到达服务端，因此安全无害。”**
  - **纠正**：无应答涵盖四种物理状态。请求可能早已入库，只是返回确认包丢了，或者服务端仍在缓慢执行。盲目重试非幂等操作将直接导致数据重复与资损。
- **谬误 2：“只要底层是 TCP 协议，TCP 会保证可靠重传，应用层就不用管丢包或超时了。”**
  - **纠正**：TCP 仅负责端到端字节流的可靠传输；若服务端进程阻塞、应用发生死锁、或网络彻底断开超过 TCP 重传限制，TCP 只能抛出连接重置或超时。更重要的是，TCP ACK 仅代表操作系统协议栈收到了字节，绝不代表应用层业务逻辑完成了事务提交。
- **谬误 3：“微服务链条越长，架构越解耦，系统就越强大、越稳定。”**
  - **纠正**：若一个请求必须顺序经过 10 个独立服务（每个服务可用性为 99.9%），整体系统的理论可用性上限为 $0.999^{10} \approx 99.0\%（不可用时间翻了整整 10 倍）。部分失效会随着调用深度的增加呈指数级放大。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
在 `activity_l16_01.py` 中，为什么客户端已经捕获到了 `TimeoutError` 并打印了放弃等待日志，服务端进程的控制台随后依然打印出了 `[SERVER] Execution completed`，且请求 ID 与客户端完全一致？

<details>
<summary>Hint 1</summary>
审视操作系统中两个独立进程的生命周期。客户端进程中的套接字超时计时器触发时，操作系统内核是否会向服务端发送任何网络控制帧？
</details>

<details>
<summary>Hint 2</summary>
客户端调用 `sock.settimeout(0.3)` 只是配置了本机套接字在经过 0.3 秒未收到数据时解除阻塞并唤醒 Python 解释器。远端机器上的套接字接收缓冲区中早已收到了请求，其服务端工作线程正在按既定计划执行 `time.sleep(0.6)`。
</details>

<details>
<summary>Expected Observation</summary>
客户端按配置在约 300 毫秒时主动放弃等待并退出调用上下文；服务端线程按照自身的执行耗时在约 600 毫秒时执行完毕并完成状态更新。两个事件在时间线上分离，证明了客户端超时仅具有本地作用域。
</details>

<details>
<summary>Full Explanation</summary>
这正是分布式系统与单机系统的分水岭。在由网络连接的独立进程之间，不存在能够即时取消远端操作的共享内存机制。客户端的超时是一个完全本地化的“停止等待”决策，它不会自动撤回已经发送到网络上的请求，也不会强行中断服务端的运行。除非应用层协议专门设计了协同取消信号（如 gRPC Cancellation 或两阶段终止协议），否则远端状态机将完全按照自身的步调推进。将单机“调用未返回即未发生”的心智模型套用到网络环境中，是导致分布式竞态与重复副作用的根本根源。
</details>

## 13. 达标退出标准 (Exit Criteria)

- 能准确画出并讲清“静默无应答”背后的 4 种不可区分物理状态；
- 能基于实证时间戳证明“客户端本地超时不等于服务端未执行”；
- 能以两军问题和独立进程生命周期解释为什么透明 RPC 必然存在抽象泄漏；
- 能够运用串行可用性公式推导调用链路加长对系统总可用性的削弱效应。

## 14. 规范能力映射 (Competency Mapping)

- **Primary**:
  - `Judge`: 在面对网络静默时，能够准确评估并识别潜在的状态歧义，严禁将超时等同于执行失败；
  - `Explain`: 清晰阐述无界网络延迟、独立进程时钟与部分失效如何打破透明 RPC 抽象；
  - `Trace`: 完整追踪一个请求从客户端套接字发送、网络滞留、服务端延后处理到客户端本地超时的端到端时序生命周期。
- **Secondary**:
  - `Diagnose`: 诊断由于缺乏幂等性保护和盲目重试导致的生产资金翻倍扣减事故。

## 15. 核心概念引用与重温 (Concepts & Revisits)

- **`EC-CON-010 Failure (故障)`**: 重温并深化为分布式“部分失效”——系统中的某一台节点坏掉了，但其他节点依然存活且无法确知坏掉节点的当前状态；
- **`EC-CON-002 Abstraction (抽象)`**: 剖析透明 RPC 的抽象泄漏，理解为什么不能把网络调用包装成本地指针调用；
- **`EC-CON-018 Process (进程)`**: 强化跨越物理主机的独立进程生命周期与物理内存隔离；
- **`EC-CON-015 Concurrency (并发)`**: 扩展并发概念至跨网络无界延迟下的操作重叠与非确定性时序交替。

## 17. 严格推论边界 (Exact Inference Limits)

- 本实验在 Localhost 上通过 Python 垫片注入的处理延迟，**仅用于构造控制流时序分离的教学实证**，**绝不能推论出当前宿主机物理网卡或网络硬件发生故障**；
- 观测到的单次超时时长（如 307ms）包含当前操作系统的线程调度开销，**绝不可宣称超时时间在微秒级上是数学绝对刚性的**；
- 客户端放弃等待并不代表网络连接本身立即关闭，操作系统底层 TCP 连接可能会继续完成传输与双向挥手，**绝不可将应用层超时等同于物理链路断开**。
