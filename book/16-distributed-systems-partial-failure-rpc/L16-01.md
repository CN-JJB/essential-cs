## 1. 学习者核心问题 (Learner Question)

> “本地函数调用通常共享一个进程内的控制流与故障边界；远程调用则跨越独立进程与网络。为什么客户端没有收到响应时，单凭静默无法知道远端代码到底执行到哪里？为什么客户端自己的超时决定不会自动撤销远端已经开始的工作？”

本地调用已经会遇到异常、进程崩溃、线程阻塞等故障；真正新增的分布式困难，是**调用方仍然活着，而远端结果变得不可知**。跨越网络边界后：
- **生命周期独立**：客户端与服务端进程可以独立崩溃、重启或继续运行；
- **异步模型中的延迟没有可依赖的已知上界**：真实网络延迟当然是有限的，但课程的异步故障模型不允许调用方把某个固定等待时间当成“远端必然已失败”的证明；
- **静默无应答具有歧义**：只看“在截止时间前没有响应”，调用方不能判定请求未执行、已执行、正在执行，还是响应只是更晚到达。

本课将带领学习者打破单机思维惯性，通过实证直面分布式系统第一法则：**部分失效（Partial Failure）**与**静默无应答的根本歧义**。

## 3. 机制模型 (Mechanism Model)

### (1) 部分失效与无应答四态 (The Four States of Remote Silence)

本地函数调用与远程调用都可能失败，但本地调用通常共享更直接的进程内控制流与故障信号。远程调用跨越独立的 `EC-CON-018 Process` 与网络边界（重温 `EC-CON-010 Failure`）。当客户端只观察到“没有响应”时，下面四种**代表性情况**都可能产生相同的客户端观测；它们不是对所有故障原因的穷举：

1. **状态 1（请求在入站途中丢失或受阻）**：请求在网络传输中被丢弃或阻塞，服务端**从未收到过**该请求，业务代码**未执行**；
2. **状态 2（服务端在执行前崩溃）**：请求已送达服务端网卡，但在应用进程读取处理之前，服务端操作系统崩溃或断电，业务代码**未执行**；
3. **状态 3（业务已执行完成，但响应在出站途中丢失或受阻）**：服务端完整且成功地执行了业务状态变更（例如已扣款），但在将响应包写回网络时链路中断，客户端**未收到响应**，但业务**已生效**；
4. **状态 4（服务端或链路仅仅是迟缓）**：网络拥塞严重，或者服务端正在执行深度垃圾回收（GC Pause）/排队积压，服务端正在处理或尚未处理，响应**仍在途中**。

```

     (Lifecycle Domain A)                                                 (Lifecycle Domain B)

     Not Done │                                   │                                 │

     Crashed  │                                   │                                 ✘

              │                                   │                                 │

              │                                   │                                 │
```

### (2) 泄漏的抽象：为什么 RPC 无法真正像本地函数调用？

回顾 **`EC-CON-002 Abstraction`**：
计算机科学中最强大的思想是将复杂机制隐藏在清晰的接口之下。20 世纪 80 年代（Birrell & Nelson, 1984），计算机系统先驱提出了**远程过程调用（RPC, Remote Procedure Call）**，试图构建一个精妙的抽象：让程序员调用位于千里之外的远程机器上的函数，就像调用本地内存中的 `add(a, b)` 一样自然。

然而，Waldo 等人在 1994 年的经典论文 *A Note on Distributed Computing* 中尖锐地指出了这一抽象的不可弥合性：
1. **延迟边界不同**：远程调用必须承担网络传输、排队和远端调度，不能把本地调用的成本模型直接外推；具体数量级必须由实际环境测量；
2. **地址空间与表示边界**：远程调用不能透明传递本进程指针；参数与结果需要一个明确的线缆表示/序列化契约。这里仅作为机制说明，不新增 L16-01 的正式 Concept 映射；
3. **部分失效会暴露抽象边界**：远端进程、网络与调用方可以独立失败或延迟，因此 RPC 可以简化接口形状，却不能消除超时、重复、取消与未知结果等协议义务。

### (3) 超时的本质：本地放弃等待决策

客户端为远程调用配置一个本地 deadline/timeout，究竟是什么？
- **它不是自动发送给服务端的取消命令**：是否传播 deadline/cancellation 取决于应用协议；
- **它不是远程执行的撤销器**：客户端出现 timeout-class 结果时，远端可能尚未执行、正在执行，或已经完成；
- **它仅仅是客户端本地调度器的单方面决裂**：客户端认定“根据我的业务截止期限（Deadline），我不能无限期挂起当前线程，我必须在此刻停止等待并进入异常处理流程”。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 在异步网络通信中，单凭网络通道的沉默，在逻辑上完全不可能推断出远端状态机的确切状态；
   - 客户端超时是本地时钟与控制流的放弃等待决策，对远端物理主机的状态迁移不具备自动取消约束力；
   - TCP 连接建立或 ACK 只提供传输层证据；它们不证明应用进程已经处理请求，更不证明某个业务状态已经按其持久化契约提交。
2. **具名规范与实证 (Specification & Evidence)**：
   - Python 3.14 文档说明：对设置了 timeout 的 socket，操作超时会抛出 `TimeoutError`（`socket.timeout` 为其别名）；底层 OS 仍可能返回其他连接错误，因此课程不绑定某个固定 errno/错误字符串；
   - POSIX socket 选项与 Python `settimeout()` 是不同证据层；课程只在引用具体接口时陈述其具名语义，不把应用 deadline 与 TCP 重传定时器混为一谈；
   - 课程实验通过 `127.0.0.1` 临时端口与**应用层**请求延迟垫片，观察“客户端先停止等待，服务端随后完成同一 request ID 的 handler”这一受控事实；L16-01 本身不声称发生了数据库持久化提交。
3. **推论边界与当前实践 (Current Practice & Inference Limits)**：
   - 本课通过应用层垫片引入的处理延迟，**属于进程内控制流调度模拟，绝不可外推宣称为真实的物理网线断开或物理包丢失**；
   - 现代微服务框架（如 gRPC、Envoy）通过请求上下文向下传递超时期限（`grpc-timeout` / Context Deadline Propagation），但这依赖于显式协议协作与应用层主动检查，并非由网络协议栈自动保证。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效示范：将超时当成失败直接重试的资金翻倍故障

审查以下朴素转账伪代码：

```python
# 致命错误：误以为超时就等于没有扣款
def pay_merchant(order_id, amount):
    attempts = 0
    while attempts < 3:
        try:
            # 客户端设置 500ms 超时
            return rpc_client.call("transfer", {"order": order_id, "amount": amount}, timeout=0.5)
        except TimeoutError:
            attempts += 1
            print(f"调用超时，第 {attempts} 次重试...")
    raise PaymentFailed("支付失败")
```

这是一个**说明性伪代码模型**，其中尝试预算和 timeout 都是场景参数，不是课程常量。若原始 mutation 已经执行，而调用方因未知结果再次提交相同业务意图，服务端又没有 retry-safety/idempotency contract，则重复副作用是可能结果之一。真正的重复次数必须由本次 fixture 的实际尝试数与 server audit 记录决定，不能从 timeout 本身推断。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“客户端收到 TimeoutError，说明请求根本没有到达服务端，因此安全无害。”**
  - **纠正**：无应答涵盖四种物理状态。请求可能早已入库，只是返回确认包丢了，或者服务端仍在缓慢执行。盲目重试非幂等操作将直接导致数据重复与资损。
- **谬误 2：“只要底层是 TCP 协议，TCP 会保证可靠重传，应用层就不用管丢包或超时了。”**
  - **纠正**：TCP 仅负责端到端字节流的可靠传输；若服务端进程阻塞、应用发生死锁、或网络彻底断开超过 TCP 重传限制，TCP 只能抛出连接重置或超时。更重要的是，TCP ACK 仅代表操作系统协议栈收到了字节，绝不代表应用层业务逻辑完成了事务提交。
- **谬误 3：“微服务链条越长，架构越解耦，系统就越强大、越稳定。”**
  - **纠正**：在一个**明确假设各服务独立、请求必须全部成功、每段可用性均为 $a$** 的简化模型中，串联系统可写成 $A_{total}=a^k$。这只是模型算术，不代表真实微服务故障独立，也不能推出“调用深度必然按某个固定倍数放大故障”。

## 15. 核心概念引用与重温 (Concepts & Revisits)

- **`EC-CON-010 Failure (故障)`**: 重温并深化为分布式“部分失效”——系统中的某一台节点坏掉了，但其他节点依然存活且无法确知坏掉节点的当前状态；
- **`EC-CON-002 Abstraction (抽象)`**: 剖析透明 RPC 的抽象泄漏，理解为什么不能把网络调用包装成本地指针调用；
- **`EC-CON-018 Process (进程)`**: 强化跨越物理主机的独立进程生命周期与物理内存隔离；
- **`EC-CON-015 Concurrency (并发)`**: 扩展并发概念至跨网络无界延迟下的操作重叠与非确定性时序交替。

## 17. 严格推论边界 (Exact Inference Limits)

- 本实验在 Localhost 上通过 Python 垫片注入的处理延迟，**仅用于构造控制流时序分离的教学实证**，**绝不能推论出当前宿主机物理网卡或网络硬件发生故障**；
- 观测到的单次 timeout 时刻包含当前运行时与 OS 调度行为；记录实际值，不把 fixture 默认值或一次测量当成普遍延迟常量；
- 客户端放弃等待并不代表网络连接本身立即关闭，操作系统底层 TCP 连接可能会继续完成传输与双向挥手，**绝不可将应用层超时等同于物理链路断开**。
