## 1. 学习者核心问题 (Learner Question)

> “既然网络调用超时后我们无法知道服务端到底有没有执行，那我们到底该不该重试？如果不重试，网络抖动就会让本来能成功的请求失败；如果重试，又可能导致扣两次款或重复发货。到底怎样的机制，才能让我们在充满不确定性的网络中，安全地调用一个远程接口？”

在 `L16-01` 中，我们直面了分布式系统冷酷的物理现实：**静默并不揭示远端状态**。客户端本地超时决定停止等待，绝不等于远端操作没有生效。

结果未知以后并不存在一个“永远正确”的自动策略：有的调用应该不重试，有的可以在明确条件下做有限重试，有的需要先查询状态或升级给上层处理。无界重试会放大负载；对结果未知的 mutation 盲目重试还可能重复副作用。

本课因此要求先定义**retry-safety contract**，再选择 total-attempt budget、deadline、可选的 backoff/jitter，以及在需要时使用自然幂等、幂等键/去重记录或其他具名机制。

## 3. 机制模型 (Mechanism Model)

### (1) 重试放大效应与雪崩级联 (Retry Amplification & Cascading Collapse)

在分层的微服务架构中，调用通常沿着服务树向下延伸：服务 A 调用服务 B，服务 B 调用服务 C，服务 C 调用数据库 D。

先分析一个**纯教学模型**：若每一层都独立把同一个下游动作派发为 $k$ 个尝试，且每个上层尝试都会完整触发下一层，那么深度为 $n$ 的最坏派发数可按 $k^n$ 计算。下面仅取 $k=3, n=3$ 作为画图示例，不是生产默认值：

```
====================================================================================================
               FIG-M16-02 (TOP): RETRY AMPLIFICATION TREE (k^n MULTIPLICATION)
====================================================================================================

      [ Service A ] (Initiates 1 user request; on timeout retries k=3 times)
            │
            ├───────────────────────┬───────────────────────┐  (3 requests dispatched to B)
            ▼                       ▼                       ▼
      [ Service B_1 ]         [ Service B_2 ]         [ Service B_3 ]  (Each retries k=3 to C)
            │                       │                       │
         ┌──┼──┐                 ┌──┼──┐                 ┌──┼──┐       (9 requests dispatched to C)
         ▼  ▼  ▼                 ▼  ▼  ▼                 ▼  ▼  ▼
       [ C1 C2 C3 ]            [ C4 C5 C6 ]            [ C7 C8 C9 ]    (Each retries k=3 to D)
         │  │  │                 │  │  │                 │  │  │
        27 Requests hammer downstream Database D!                      (Traffic multiplied by 3^3 = 27!)
====================================================================================================
```

如果下游数据库 D 因瞬时锁竞争或慢查询出现短暂延迟：
1. 服务 C 判定超时，对 D 发起 3 倍重试；
2. 服务 B 判定 C 超时，对 C 发起 3 倍重试（产生 $3 \times 3 = 9$ 倍请求）；
3. 服务 A 判定 B 超时，对 B 发起 3 倍重试（产生 $3 \times 3 \times 3 = 27$ 倍请求）；
4. 在这些**明确假设**下，下游工作量呈乘法放大；真实系统会受到缓存、并发限制、熔断、超时传播、不同 retry policy 等影响，因此不能把 $k^n$ 当成必然观测值。

重试策略必须成为明确的**系统规格（重温 `EC-CON-007 Specification`）**：
- 决定哪一层拥有 retry responsibility，避免层层独立重试；
- 给调用定义 total-attempt / retry budget，但课程不规定固定次数或固定百分比；
- 若体系传播 deadline/cancellation，则由具名协议定义剩余预算与停止条件；没有传播协议时不要假设下游自动知道上游截止时间。

### (2) 指数退避与全抖动：打破周期性共振

如果大量客户端在相近时刻失败，并采用相同固定间隔重试，它们可能持续保持相关性并形成重试峰值；是否同步取决于初始相位、网络与调度等条件。

为了打散重试流量，系统采用**指数退避（Exponential Backoff）**配合**全抖动（Full Jitter）**（Marc Brooker, AWS 2015）：

$$t_{\text{sleep}} = \text{random}\left(0, \; \min\left(t_{\text{max}}, \; t_{\text{base}} \times 2^{\text{attempt}-1}\right)\right)$$

- **指数递增**：随着连续失败次数的增加，退避等待时间的上限呈指数级递增，给服务端留出恢复喘息的窗口；
- **全抖动（Full Jitter）**：在 0 到当前上限之间随机抽取休眠值。AWS 2015 文章在其 OCC 模拟中显示 jitter 能显著降低同步竞争与总工作量；它不是对所有 workload 的数学最优性证明，Full/Equal/Decorrelated Jitter 之间也存在不同完成时间/工作量权衡。

### (3) 核心防线：幂等性原理 (The Idempotency Principle)

处理“结果未知后再次尝试”需要一个明确的 **retry-safety contract**。幂等性/去重是常见手段，但不是唯一可能策略：也可以选择不重试、查询操作状态、使用业务唯一约束，或把不可原子协调的外部副作用交给其他工作流处理。

回顾数学中的幂等映射：一个函数作用两次与作用一次效果相同：
$$f(f(x)) = f(x)$$

在计算机系统中（重温 **`EC-CON-008 Invariant`**），**幂等性是不变式状态迁移**：
> **在一个具名操作契约中，重复尝试不应仅因为“重试”而产生额外的预期业务副作用。** 数学式 $f(f(x))=f(x)$ 是帮助理解的类比，真实 API 还必须说明请求身份、状态边界、响应语义与保留期。

#### 自然幂等 vs. 人工合成幂等：
1. **自然幂等（Natural Idempotency）**：
   - 绝对状态覆写：`SET status = 'CANCELLED'`，无论执行 1 次还是 100 次，订单最终状态都是 `CANCELLED`；
   - 绝对值赋值：`UPDATE config SET max_threads = 64`；
   - 只读查询：HTTP `GET`，不产生业务状态突变；
2. **非自然幂等（Non-Idempotent）**：
   - 相对增量运算：`UPDATE accounts SET balance = balance - 100`；
   - 列表追加：`INSERT INTO transfer_logs VALUES (...)`；
   - 每执行一次，业务状态都在发生新的不可逆累加！
3. **人工合成幂等：引入幂等键（Idempotency Key）**：
   - 对某些非自然幂等 mutation，可以让客户端携带在该 API 契约内唯一/稳定的请求身份；是否必须由该接口规范决定，不是所有写操作的普遍规则；
   - 服务端需把“重复请求如何识别、保留多久、冲突如何处理”写进契约，并确保所声称保护的业务状态与去重状态处于可证明的一致边界。

### (4) 关键机制：单次原子事务边界中的幂等记录

在服务端设计幂等保护时，最常见的架构败笔是将“幂等记录”与“业务更新”拆分成两个独立的步骤（例如先写 Redis 记录幂等键，再写 MySQL 扣款）。如果写完 Redis 后机器断电，MySQL 从未执行，后续重试却会被 Redis 拦截，导致业务永远无法执行！

**本课程 SQLite 机制边界**：
> 当我们选择“数据库幂等键表保护同库业务 mutation”这一模式时，key claim 与被保护的 mutation 必须参加**同一个 SQLite 事务**，否则 fixture 无法证明二者原子一致。跨库、外部 API、邮件/支付等副作用需要另外的协调或业务契约，不能靠这一条规则泛化。

```
====================================================================================================
               FIG-M16-02 (BOTTOM): ATOMIC IDEMPOTENCY TRANSACTION WORKFLOW
====================================================================================================

      Client Dispatch                                 Server SQLite Transaction
    (Idempotency-Key: K)                               (BEGIN IMMEDIATE Mode)
            │                                                    │
    Attempt 1 ──────────────────────────────────────────────────>│ [1] Check: SELECT status WHERE key = K
            │                                                    │      -> Not found!
            │                                                    │ [2] Claim: INSERT INTO idempotency_keys
            │                                                    │      (key, status='IN_PROGRESS')
            │                                                    │ [3] Mutate: UPDATE counter = counter + 1
            │                                                    │ [4] Complete: UPDATE status = 'COMPLETED'
            │                                                    │ [5] COMMIT Transaction!
            │ <─── [Response Dropped by Fault Shim!] ─────────── ✘
            │
      (Client Times Out -> Applies Jittered Backoff)
            │
    Attempt 2 ──────────────────────────────────────────────────>│ [1] Check: SELECT status WHERE key = K
   (Same Key: K)                                                 │      -> Found! status == 'COMPLETED'
            │                                                    │ [2] Skip Business Mutation!
            │ <─── Return Cached Prior Response (OK) ────────────│ [3] COMMIT / Close
            │
====================================================================================================
* RESULT IN THIS SCOPED SQLITE FIXTURE: duplicate attempts produced ONE intended counter effect.   *
* This is NOT an unbounded exactly-once claim for external side effects.                            *
====================================================================================================
```

### (5) 幂等存储的物理边界：保留期（Retention Horizon / TTL）

很多初学者误以为幂等键能够“保护数据直到宇宙尽头”。
去重设计必须声明自己的**保留/淘汰边界**：可以是 TTL、按业务生命周期保留、永久业务唯一键，或其他策略；课程不规定固定小时/天数。

若所选策略已经淘汰某个 key，而系统又没有其他持久业务身份阻止重复执行，那么更晚到达的重复请求可能再次被当成新请求。fixture 用可注入“未来时间”的 purge API 确定性演示这一**策略边界**，而不是靠真实等待若干毫秒来证明网络规律。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 幂等性断言针对的是系统持久化状态（`EC-CON-008 Invariant`），**绝不要求网络响应的字节流必须完全逐位一致**（响应中的处理时间戳、跟踪 Trace ID、或者动态签名可以不同）；
   - 若使用本课的“同库幂等记录 + 业务 mutation”模式，两者必须处在该 SQLite 原子事务边界内；
   - 自动 retry loop 必须有明确停止条件/总尝试边界；这不等于所有调用都必须重试，也不要求所有系统都使用同一种熔断器。
2. **具名规范与实证 (Specification & Evidence)**：
   - RFC 9110 §9.2 明确界定了 HTTP 标准方法的幂等规范（`GET`, `HEAD`, `PUT`, `DELETE` 具有幂等规格；`POST` 默认不具有幂等规格）；
   - IETF 正在推进的草案 `draft-ietf-httpapi-idempotency-key-header-07` 为现代 HTTP API 提供了标准请求头 `Idempotency-Key` 的操作模式参考（注：该文档截至 2026 年属于已过期的 Internet-Draft，不可被误当作已发布的正式 RFC 标准引用）；
   - 课程 fixture 为每个 worker transaction 使用独立 SQLite connection，并通过 `BEGIN IMMEDIATE` 串行化写事务；在这一**具名本地边界**中，测试验证相同 idempotency key 的重复尝试只产生一个预期 counter effect。
3. **推论边界与当前实践 (Current Practice & Inference Limits)**：
   - 本实验证明的幂等性保证，**严格受限于受控的本地 SQLite 数据库事务边界**，**绝不能外推宣称为支持任意第三方外部系统（如发送物理短信、调用外部第三方支付网关）的绝对“精确一次（Exactly-Once）”神话**；
   - 指数退避与全抖动属于工程最佳实践策略，其底数、上限与种子分布是具体的策略选择，不是普遍的物理定律。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效示范：将幂等性检查写在数据库事务之外的并发击穿

审查以下看似正确的伪代码：

```python
# 典型设计缺陷：Check-then-Act 跨越了非原子边界
def handle_payment(request):
    key = request.headers.get("Idempotency-Key")

    # [1] 在事务外检查是否已经执行过
    existing = redis_client.get(key)
    if existing:
        return json.loads(existing)

    # [!] 危险窗口：两个相同的重试请求同时并发到达此处！
    # 都发现 existing 为 None！

    # [2] 独立的数据库扣款
    with db.begin_transaction():
        db.execute("UPDATE account SET balance = balance - 100")

    # [3] 写入缓存
    redis_client.set(key, json.dumps({"status": "SUCCESS"}), ex=86400)
    return {"status": "SUCCESS"}
```

这是一个说明 **check-then-act 非原子窗口** 的伪代码：若两个调用在 key check 与业务 mutation 之间交错，它们可能都继续执行。具体解决方案取决于存储/外部副作用边界；本课只证明“同一 SQLite 数据库内使用唯一 key + 同一事务保护 counter mutation”这一模式，不宣称 Redis/MySQL/跨服务都能用同一事务解决。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“幂等性意味着客户端多次重试拿到的 HTTP 响应必须逐字节一模一样。”**
  - **纠正**：幂等性保证的是系统**内部业务状态的不变式**（$f(f(x)) = f(x)$）。第二次请求返回的响应中，响应头的时间戳（`Date`）、服务端生成的当前日志追踪编号（`Trace-ID`）完全可以不同，只要业务状态不发生多余变更即可。
- **谬误 2：“只要加了幂等键，系统就彻底实现了‘精确一次（Exactly-Once）’，永远不会出错了。”**
  - **纠正**：在分布式系统中，没有跨越任意物理异构系统的无条件 Exactly-Once。幂等性要求底层存储能够原子地协同记录键与业务状态；如果业务还涉及到发送物理信件、调用没有幂等键的第三方银行接口，网络重试依然会产生外部不可逆副作用。
- **谬误 3：“重试次数越多越好，反正有幂等保护，超时了就一直重试。”**
  - **纠正**：哪怕有幂等保护，每一次重试也会消耗网络带宽、建立 TCP 连接、占用服务端的连接池与线程资源。不设上限的重试依然会引发重试风暴和拒绝服务（DoS）。

<details>
<summary>Full Explanation</summary>
在这个 course-owned SQLite 模式里，每次 worker 使用独立 connection；第一次成功事务把 key claim、counter mutation 与 `COMPLETED` 状态一起提交。后续相同 key 的事务读取已提交记录并跳过 counter mutation。这个结论只覆盖该本地事务范围；如果 key 已被淘汰、mutation 在别的系统、或外部副作用不参与同一契约，则必须重新分析。
</details>

## 15. 核心概念引用与重温 (Concepts & Revisits)

- **`EC-CON-005 Interface (接口)`**: 强化接口契约（Interface Contract）——一个好的远程接口设计必须在其方法签名中显式纳入超时、幂等键与错误模型；

## 17. 严格推论边界 (Exact Inference Limits)

- 在 fixture 的 stated assumptions 下，同一 SQLite 事务边界能证明 duplicate attempts 只产生一个预期 counter effect；这不是任意外部系统的无限 Exactly-Once；
- retention/eviction 是 API 设计的一部分：若 key 被淘汰且没有其他业务唯一性机制，更晚的 duplicate **可能**重新执行；不同系统不必都使用 TTL；
- backoff/jitter 只改变重试时机/相关性与负载形状，不能修复永久错误或容量不足；最终处置取决于 retryable error classification、budget、deadline 和业务策略。
