# L15-02｜如何让并发程序保持正确？互斥锁、条件变量与死锁预防

## 1. 学习者核心问题 (Learner Question)

> “既然原子读写无法保护复合状态转换，我们该用什么机制保护临界区？当一个线程必须等待另一个线程产生数据时，如何避免 CPU 100% 空转的死循环轮询？为什么看似简单的多锁加锁顺序颠倒，就会导致整个系统瞬间卡死、永远无法唤醒？”

在上一课（L15-01）中，我们亲眼见证了多线程任意交替执行如何轻而易举地破坏无保护的复合状态变迁。然而，解决并发混乱的直觉反应往往带来更深层的问题：
- 有人试图用 `while (!flag) {}` 空循环轮询状态，结果耗尽 CPU 并引发调度饥饿；
- 有人使用条件变量（Condition Variable）却省略了重评条件的外层循环，遭遇假唤醒（Spurious Wakeup）导致非法数据消费；
- 有人在不同函数中以任意次序申请多个互斥锁，偶发性地陷入不可逆的死锁（Deadlock）。

本课深入 POSIX 线程标准（IEEE Std 1003.1-2024），实测掌握**互斥锁（Mutex）**对系统不变式的修复机制、**条件变量（Condition Variable）**的事件会合与谓词重检守卫协议，并通过受控子进程看门狗（Watchdog）实证本夹具中的圆环等待前提与系统边界。

## 3. 机制模型 (Mechanism Model)

### (1) 互斥锁：临界区排他性与不变式恢复 (Mutex & Dijkstra Critical Section)

为了保护复合状态变迁（如自增中的 Read $\to$ Compute $\to$ Store），必须划定**临界区（Critical Section）**：
- **互斥锁不变式**：在任何时间切片内，最多只有一个线程持有该互斥锁处于临界区内；
- **POSIX 实现机制 (`pthread_mutex_t`)**：
  1. 线程通过 `pthread_mutex_lock(&mutex)` 请求锁。若锁已被占用，调用线程被内核挂起并加入等待队列，让出 CPU；
  2. 持锁线程退出临界区前调用 `pthread_mutex_unlock(&mutex)`，将锁标记为可用，并由内核唤醒一个等待线程；
  3. **内存可见性边界**：`pthread_mutex_lock` 具备获得语义（Acquire），`pthread_mutex_unlock` 具备释放语义（Release），确保前一持锁线程的所有修改对后续持锁线程完全可见。
- **无公平性保证警示**：POSIX 标准默认的互斥锁**并不保证先进先出（FIFO）公平性**。一个刚运行完毕的活跃线程可能比已经排队等待数毫秒的挂起线程更快地重新夺取锁，因此互斥锁不自动等同于防饥饿（Starvation-freedom）。

---

### (2) 条件变量：事件会合与谓词重检契约 (Condition Variable Rendezvous)

当一个消费者线程需要等待特定业务状态（例如“缓冲区已产生数据”）时，空转轮询（Spinning）是毁灭系统性能的反模式。POSIX 提供**条件变量 (`pthread_cond_t`)** 作为纯粹的信令会合机制：
- **核心契约三步法**：
  1. **原子性释放与睡眠**：消费者在持有互斥锁的前提下调用 `pthread_cond_wait(&cond, &mutex)`。内核**原子地释放互斥锁并将该线程挂入条件等待队列**；
  2. **生产与信令唤醒**：生产者获取互斥锁，修改共享业务数据并更新谓词状态（如 `ready = true`），随后通过 `pthread_cond_signal(&cond)` 发送唤醒信号，最后释放互斥锁；
  3. **重新竞争与锁恢复**：被唤醒的消费者线程在 `pthread_cond_wait` 内部**必须重新夺取该互斥锁**，获取成功后方从函数返回。
- **为什么必须使用 `while (!predicate)` 循环守卫？**
  - **规范现实**：POSIX 允许 condition wait 出现 **spurious wakeup**，而且函数返回本身不代表共享 predicate 已经成立；课程不为这种返回预设单一内核原因。
  - **状态漂移**：在消费者被唤醒与真正重新抢到锁的时间差内，可能有第三个线程抢先介入并消费了该状态；
  - **课程标准范式**：
    ```c
    pthread_mutex_lock(&mutex);
    while (!predicate_is_true) {
        pthread_cond_wait(&cond, &mutex); // 唤醒后必须重检谓词！
    }
    // [!] 此时可安全断言：predicate_is_true 恒成立，且受锁保护
    consume_data();
    pthread_mutex_unlock(&mutex);
    ```
  - *(声明：POSIX 规范定义的是“返回并不保证谓词为真，必须重新评估条件”的语义要求，并不规定代码字面必须写 while 关键字；while 循环是实现该契约的规范工程范式)*。

---

### (3) 死锁：Coffman 条件与受控看门狗验证 (Deadlock Preconditions & Watchdog)

当多个线程需要同时获取多个互斥锁时，如果加锁顺序不一致，系统将面临死锁：
- **Coffman 四大充要条件**：
  1. **互斥（Mutual Exclusion）**：资源不能共享，一次只能由一个线程占有；
  2. **占有且等待（Hold and Wait）**：线程持有至少一个资源，并正在等待获取被其他线程持有的新资源；
  3. **非抢占（No Preemption）**：资源不能被强制剥离，只能由持有者主动释放；
  4. **循环等待（Circular Wait）**：存在一组线程 $\{T_1, T_2, \dots, T_n\}$，其中 $T_1$ 等待 $T_2$ 持有的资源，$T_2$ 等待 $T_3$，…… $T_n$ 等待 $T_1$。
- **死锁预防原则**：打破循环等待。全局定义一致的锁获取层级（Lock Acquisition Hierarchy），所有线程必须严格按照相同次序申请锁（例如一律先拿 Lock A，再拿 Lock B）。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 互斥锁提供临界区的排他性保证；业务不变式的成立依赖于临界区边界的完备闭合；
   - 条件变量仅为等待通道；业务状态的有效性必须由互斥锁保护下的显式谓词承载；
   - 循环死锁源于无序多锁嵌套；一致的锁获取层级可完全消除环路等待。
2. **具名标准与实现 (Specification & Implementation)**：
   - IEEE Std 1003.1-2024（POSIX Issue 8）明确规范了 `pthread_mutex_*` 与 `pthread_cond_*` 的函数行为与返回值约定；
   - Linux 环境下 glibc 基于内核 `futex`（Fast Userspace Mutex）系统调用实现高效的用户态无竞争快速通道与内核态阻塞队列。
3. **系统推论边界 (System Inference Limits)**：
   - 互斥锁测试通过只能证明该临界区排他有效，**不证明高并发下的调度公平性或无饥饿**；
   - 子进程看门狗超时**本身不是死锁的充要证明**（慢死循环或 I/O 阻塞也能触发超时）；机器证据必须首先确证环路锁持有前置条件（线程 1 持 A 索 B，线程 2 持 B 索 A），随后发生的超时方可被合法推论为死锁！

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验：逆序加锁死锁陷阱
审查以下死锁代码核心模型：
```c
// Thread 1
pthread_mutex_lock(&lock_a);
pthread_mutex_lock(&lock_b); // 若 Thread 2 抢先拿到 lock_b，Thread 1 在此挂起

// Thread 2
pthread_mutex_lock(&lock_b);
pthread_mutex_lock(&lock_a); // Thread 2 在此挂起，等待 Thread 1 释放 lock_a
```
1. **破坏现象**：两个线程均无法前进一步，CPU 使用率瞬间降为 0%，子进程控制台停止输出任何日志。终端失去响应，若无外部看门狗介入，进程将永久挂死；
2. **机理剖析**：Thread 1 占有 A 等待 B，Thread 2 占有 B 等待 A，形成闭合环路等待图（Circular Wait-For Graph）。没有任何一个线程能够释放已经占有的资源，破坏了系统的活性（Liveness）。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“互斥锁能确保多个线程按先来后到的顺序绝对公平地执行。”**
  - **纠正**：POSIX 标准默认的互斥锁为非公平锁（Non-fair Lock），正在 CPU 核心上运行的线程重新申请锁的成功率极高，等待队列中的线程可能发生暂时性饥饿。
- **谬误 2：“条件变量 `signal()` 通知发送后，被唤醒的线程醒来时条件必定为真，所以不用写循环。”**
  - **纠正**：在唤醒到重获锁之间存在调度间隙，其他线程可能中途改写条件；此外操作系统允许假唤醒，必须使用 `while (!predicate)` 强制重评。
- **谬误 3：“只要一个程序没有卡死，就说明代码中绝对不存在死锁风险。”**
  - **纠正**：死锁的发生依赖于特定的时间窗口重叠。在低并发下不暴露的锁次序倒置，在高并发、网络延迟波动或硬件负载突增时可能随时引爆。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
在编写多线程同步代码时，为什么 IEEE Std 1003.1-2024 强烈建议用循环结构将 `pthread_cond_wait` 包裹起来，而不是简单地在 `if (!condition)` 下调用？

<details>
<summary>Hint 1</summary>
查阅 POSIX 手册关于“Spurious Wakeups”（假唤醒）的说明。即使没有任何线程调用 signal，等待函数是否也可能返回？
</details>

<details>
<summary>Hint 2</summary>
考虑有两个消费者同时被唤醒，但共享队列中只有一个数据项的竞争场景。
</details>

<details>
<summary>Expected Observation</summary>
被唤醒的线程从 `pthread_cond_wait` 返回并不意味着被等待的业务条件在当前绝对成立。
</details>

<details>
<summary>Full Explanation</summary>
原因有二：第一，现代多核操作系统的内核底层优化与信号打断机制允许 `pthread_cond_wait` 发生假唤醒；第二，当条件被 signal 广播唤醒后，多个等待线程必须依次串行获取互斥锁。最先拿到锁的线程把数据取走后，后续拿到锁的线程醒来时条件已经重新变为假。如果仅仅使用单次 `if` 判断，后续线程将带着不成立的假条件继续执行，直接引发非法内存解引用或逻辑崩溃。因此，必须在循环中重检谓词。
</details>

## 17. 严格推论边界 (Exact Inference Limits)

- 互斥锁测试通过**只能证明当前临界区排他有效**，**不保证极端竞争下的无饥饿或公平推进**；
- 子进程超时停顿**必须配合锁持有与环路索取前置条件证据**，**绝不能单一依据超时时间推断系统发生死锁**；
- 父进程看门狗机制是**课程受控实验的自动化保障手段**，**绝不可作为生产级系统防止死锁挂死的替代方案**。
