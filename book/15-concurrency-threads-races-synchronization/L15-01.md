# L15-01｜为什么我的多线程程序总是算错？并发、交替执行与逻辑竞态

## 1. 学习者核心问题 (Learner Question)

> “为什么一段在单线程中运行完全正确的自增代码，拆分给两个线程并发执行后，跑一次一个结果、跑一万次少几千？为什么变量加了原子类型（Atomic），多步复合操作依然算错？这究竟是硬件故障、编译器 Bug，还是我们对‘并发’的基本理解从一开始就存在偏差？”

许多从顺序编程迈入多线程编程的学习者，直觉上认为计算是“一条时间线上的单行道”：前一行指令执行完毕，后一行指令才会发生。当把两段代码交给两个线程时，直觉会把它们想象成两条互不干扰的平行轨道。

然而在真实系统中，同一进程内的线程共享地址空间中的大量状态，而抢占式调度器可以在运行期间切换可运行线程；具体时间片长度与切换点是宿主实现事实，不能从源代码预先写死。高级语言中看似单步的更新也可能映射为多个实现步骤。本课使用 C11 原子访问构造一个**不依赖共享计数器数据竞争 UB**的确定性交替实验，拆解并发、交替执行与逻辑竞态，正式确立 **EC-CON-015 并发 (Concurrency)** 的规范第一原籍。

## 3. 机制模型 (Mechanism Model)

### (1) 核心概念第一原籍：EC-CON-015 并发 (Concurrency)

在此，**EC-CON-015 并发 (Concurrency)** 正式入驻其规范第一原籍：

> **“Overlapping progress or interleaving of operations, whether or not they execute simultaneously on hardware. Concurrency creates ordering and shared-state obligations.”**
>
> （**“操作的重叠推进或交替执行，无论它们在硬件物理上是否同时发生。并发带来了时序与共享状态的履约义务。”**）

#### 规范辨析与概念边界：
1. **并发（Concurrency） $\ne$ 并行（Parallelism）**：
   - **并发**是程序的**逻辑结构与推进模型**：系统容许两个或多个任务处于“已开始但未全部完成”的重叠状态，其执行通过时间片交替（Interleaving）推进；
   - **并行**是硬件的**物理执行状态**：多个物理 CPU 核心在同一绝对时刻分别执行不同的电路指令；
   - **单核也能并发**：单个硬件执行核心也可以通过时间片/抢占等机制交替推进多个线程。逻辑竞态并不要求两个线程物理同时执行；具体某次 bug 是否显现仍取决于实际交替与同步。
2. **逻辑竞态条件（Logical Race Condition） $\ne$ C 语言数据竞争未定义行为（Data Race UB）**：
   - ISO C11 标准 §5.1.2.4 规定：若两个线程并发访问同一非原子内存位置，且至少一个是写操作，且没有通过同步机制建立 happens-before 关系，则构成 **Data Race**，这是语言层面的 **Undefined Behavior (UB)**。现代编译器一旦检测到 UB，可能会将整个循环或写操作优化抹去；
   - 真正的计算机科学教学，绝不能用未定义行为的编译器优化产物来糊弄学习者；
   - **Essential CS 教学方案**：Required broken-counter 的并发计数器访问使用 C11 `atomic_int` 与 `atomic_load_explicit` / `atomic_store_explicit`（`memory_order_relaxed`），因此教学中的 lost update **不依赖 plain shared counter 的 C data-race UB**。课程控制的 barrier/phase handoff 让两个真实 pthread 在每轮都先读取、再写回，从而确定性暴露复合 Read $\to$ Compute $\to$ Store 缺乏互斥的问题。

### (2) 线程状态空间与复合操作解构 (Thread State Space & Compound Transitions)

在进程模型中（重温 `EC-CON-001 State`），每个线程拥有私有的执行状态，但共享整个进程地址空间：
- **线程私有**：程序计数器（PC / IP）、CPU 寄存器集合、调用栈（Stack Frame）；
- **线程共享**：堆内存（Heap）、全局变量/静态数据段（Data/BSS）、打开的文件描述符表。

当线程执行一次业务自增时，底层执行序列由三个分离的步骤构成：
1. **步骤 1（读取，Read）**：将共享内存中的数值加载至线程私有的 CPU 寄存器中；
2. **步骤 2（计算，Compute）**：在私有寄存器中执行算术加 1；
3. **步骤 3（写回，Store）**：将私有寄存器中的新值写入共享内存。

```
Thread 1 执行流                    共享内存 Counter                Thread 2 执行流
-----------------                 ----------------              -----------------
[1] Read: 读入 42至 reg1    <----      Counter = 42
                                       Counter = 42      ---->   [2] Read: 读入 42 至 reg2
[3] Compute: reg1 = 43                                           [4] Compute: reg2 = 43
[5] Store: 将 43 写入       ---->      Counter = 43
                                       Counter = 43      <----   [6] Store: 将 43 写入 (覆写!)
---------------------------------------------------------------------------------
结果：两个线程各执行了一次加法（预期 44），最终 Counter 却仅为 43！一次增量永久丢失！
```

即使步骤 1 和步骤 3 分别通过原子指令完成，两步之间依然容许任意的指令交替。这就是复合操作非原子性导致的典型“丢失更新”（Lost Update）。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 共享可变状态与抢占式调度的结合，必然引入交替执行时序义务；
   - 原子读写指令只保证单次内存访问的完备性与非撕裂（Non-tearing），绝不赋予多步复合业务变迁以原子性；
   - 业务逻辑正确性（重温 `EC-CON-009 Correctness`）取决于状态变迁是否在所有合法的线程交替序列下均保持系统不变式。
2. **具名规范与实证 (Specification & Evidence - ISO C11 & POSIX)**：
   - ISO/IEC 9899:2011 (C11) §5.1.2.4 明确定义了内存模型与数据竞争的边界；
   - POSIX IEEE Std 1003.1-2024 定义了线程执行环境与调度语义；
   - 在确定性实验中，使用屏障控制让两个真实 POSIX 线程交替读写原子变量，每次均确定性丢失更新，证明竞态与硬件核数无关。
3. **推论边界与当前实践 (Current Practice & Inference Limits)**：
   - 在宽松内存序（Relaxed Memory Order）下观察到的丢更新，证明的是复合操作的非原子性，**绝不证明 CPU 缓存一致性失效或内存可见性损坏**；
   - 依赖自然调度的随机观察（如循环 10000 次配合 `sched_yield()`）受机器负载与多核数量影响，**不可设定固定的失败概率或错误区间**；若自然测试未复现，属于合法观察事实，不可判定为测试失败。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效示范：未受保护的多步复合变迁
审查以下代码片段：
```c
// 伪代码：以为声明了原子变量就万事大吉
atomic_int balance = 100;

void* withdraw(void* arg) {
    int current = atomic_load(&balance); // 原子读
    if (current >= 60) {
        // [!] 危险窗口：调度器在此处发生上下文切换！
        atomic_store(&balance, current - 60); // 原子写
    }
    return NULL;
}
```
1. **破坏现象**：两个线程同时取款 60 元。两个线程都读到了 `current = 100`，都通过了 `current >= 60` 的判断。最终余额变成了 40 元（甚至透支为负值），本应只能成功一次的取款被成功执行了两次！
2. **机理剖析**：原子变量只保证 `load` 和 `store` 自身是瞬时完成的。但“检查条件并据此决定是否扣款”（Check-then-Act）是一个横跨多个机器周期的复合状态变迁。只要状态变迁包含时间跨度，并发交替就会在变迁缝隙中撕裂系统不变式。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“并发就是并行，单核机器绝对写不出多线程竞态 Bug。”**
  - **纠正**：并发是操作交替推进的程序结构，单核抢占式操作系统完全能在单指令级别切出并发交替。
- **谬误 2：“变量声明为原子类型后，整段代码就自动变成线程安全的了。”**
  - **纠正**：原子类型仅消除单个内存单元的读写撕裂与 Data Race UB。复合读-改-写或查-后-行操作依然是分离步骤，必须借助高级同步原语（如互斥锁）。
- **谬误 3：“测试跑了 10 万次都没出错，说明多线程逻辑肯定没问题。”**
  - **纠正**：自然调度的交替概率极度依赖机器配置与瞬时负载。未经确定性证明或互斥保护的并发代码，可能在特定云服务器高负载下瞬间崩溃。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
为什么在 `broken_counter.c` 中，明明每一次加载和存储都使用了标准 C11 原子函数（零未定义行为），最终 5 轮交替自增后计数值依然从期望的 10 变成了 5？

<details>
<summary>Hint 1</summary>
追踪线程 1 读取当前值 0 之后、写回 1 之前，线程 2 正在干什么？
</details>

<details>
<summary>Hint 2</summary>
线程 1 读出 0，此时尚未写回；线程 2 也介入读取，它读到的旧值是多少？
</details>

<details>
<summary>Expected Observation</summary>
两线程各自在私有寄存器中读到了相同数值 0，各自独立算出 1，随后交替写回，后写的 1 覆盖了先写的 1，导致一次自增白白丢失。
</details>

<details>
<summary>Full Explanation</summary>
单个内存单元的原子访问只确保单个读取或写入动作不可分割。但自增是一个由“读共享值 $\to$ 计算增量 $\to$ 存新值”组成的复合状态变迁。在屏障协调下，两线程在同一时刻持有相同的旧状态，计算出相同的新状态，并在写回阶段彼此覆写。这证明了并发竞态属于业务逻辑上的状态机交替缺陷，即便共享计数器的每次读写都是具名的 C11 原子访问，这个复合操作仍未获得互斥原子性；若业务正确性要求整个状态转换不可交错，就需要适当的同步或原子 read-modify-write 机制。
</details>

## 17. 严格推论边界 (Exact Inference Limits)

- 宽松原子操作下观察到的更新丢失，**仅证明复合读-改-写变迁缺乏互斥原子性**，**绝不能推论出硬件 CPU 缓存一致性失效或物理总线故障**；
- 自然调度的随机运行记录**仅属于当前宿主机瞬时执行事实**，**绝不可宣称具有普适的复现概率（如 95% 或 100%）**；
- 绝不可将此实验外推为“原子操作无用论”——原子操作是构建一切高级锁机制与无锁数据结构的基本物理砖石。
