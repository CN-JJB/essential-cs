## 3. 机制模型 (Mechanism Model)

### (1) 操作系统抢占式线程 vs 协作式异步事件循环 (OS Threads vs Async Event Loops)

| 维度 | OS 抢占式线程 (`pthread` / OS Thread) | 协作式异步事件循环 (`asyncio` / Event Loop) |
| :--- | :--- | :--- |
| **调度主体** | 操作系统内核调度器（Preemptive Kernel Scheduler） | 用户态单线程事件循环（Cooperative Event Loop） |
| **调度时机** | 由 OS/运行时的抢占规则决定；不能把源代码的每一行或每一机器指令都当成保证的切换点 | 当协程实际到达会挂起并把控制权交还事件循环的 awaitable 时发生协作切换；并非每个语法上的 `await` 都必然挂起 |
| **任务内存** | 每个线程需要独立执行栈及运行时线程状态；实际栈保留/提交策略与大小由 OS、运行时和配置决定 | Task/协程通常不需要每个任务各自的 OS 线程栈；实际对象与捕获状态大小取决于程序和运行时 |
| **任务并发规模** | 受线程栈、内核线程资源、调度和同步开销等共同约束；必须实测 | 对大量等待型任务往往能降低每任务调度/栈成本，但可承载规模仍受连接、内存、FD、服务端与工作负载限制 |
| **多核并行能力** | OS 线程可以并行运行，但语言运行时/解释器锁/扩展实现可能限制同一工作负载的并行度 | 单个事件循环本身一次推进一个 Task；CPU 并行需要具名的线程、进程、子解释器或其他执行器能力 |
| **阻塞风险** | 单个线程执行阻塞 I/O 时仅挂起自身，其他线程继续推进 | 任何同步阻塞操作（如 `time.sleep` 或重算）将导致整个循环瞬间冻结 |

#### 异步系统中的“执行器委派”架构 (Executor Delegation)
在真实的生产级异步系统中，绝非所有任务都是非阻塞的。当不可避免地调用传统阻塞 I/O 或执行繁重的 CPU 密集型计算时，标准的系统模式是将该任务**委派至底层线程池或进程池**（例如 Python 的 `loop.run_in_executor`）：
- **I/O 密集任务**：由单线程主事件循环通过多路复用（`epoll`/`kqueue`）高效轮询；
- **阻塞/重算任务**：交由后台工作线程/进程池处理，完成后通过 Future 回调将结果通知主事件循环。

### (2) CPython 运行时真相：GIL 现实与 Python 3.14 自由线程演进

#### 1. 全局解释器锁（GIL）的真实物理边界：
- **它是实现细节，不是语言规范**：GIL 是 CPython 解释器为了保护其自身的内部内存结构（如引用计数、对象字典等）免受破坏而设计的互斥锁，并不是 Python 语言定义的一部分（如 Jython、IronPython 均无 GIL）；
- **GIL 不能替代业务同步**：在 GIL 启用的 CPython 中，同一解释器内 Python bytecode 的执行受 GIL 约束，但这不构成 Python 语言级的“复合业务操作原子性”保证。线程切换/锁释放点必须按具名运行时与被调用操作分析，不能由一段 `dis` 输出推断任意 opcode 边界都会切换。
- **I/O / 扩展行为必须具名**：CPython 的许多阻塞型标准库 I/O 路径会在等待期间释放/分离 GIL；C 扩展也可以显式这样做。但“所有 I/O”或“所有原生库调用”都会释放 GIL 不是通用保证，需以实际 API/扩展文档为准。

#### 2. Python 3.14 / PEP 779 现时性审查（2026-09-05 Checkpoint）：
根据 2026-09-05 最新官方文档与 PEP 779 规范（来源：`https://docs.python.org/3.14/howto/free-threading-python.html`）：
- **官方支持第二阶段（Supported Phase II）**：Python 3.14 官方正式支持并维护**自由线程构建（Free-threaded Build）**，这是针对多核 CPU 扩展设计的重磅里程碑；
- **依然是可选构建**：自由线程构建仍然是**非默认的可选二进制安装包**，默认的主流发行版依然是启用了 GIL 的经典 CPython；
- **运行时的动态 GIL 行为**：即使在自由线程构建的 Python 解释器中，如果用户加载或导入了一个尚未声明“支持自由线程”的第三方 C 扩展模块，Python 运行时为了保护该扩展的安全性，会**在运行时自动重新启用 GIL**！因此，真实的自由线程并行能力必须在运行时通过检查才能确认。

### (3) 字节码反汇编证据：为什么 `x += 1` 不是原子的？

使用 Python 标准库 `dis` 模块反汇编一段最简短的自增代码：
```python
import dis
dis.dis("x += 1")
```
在现代 CPython 运行时上，输出展现为一条由多个独立步骤构成的指令流：
```
  1           LOAD_NAME                0 (x)
              LOAD_CONST               0 (1)
              BINARY_OP               13 (+=)
              STORE_NAME               0 (x)
              RETURN_CONST             1 (None)
```
- **关键推论**：即便在有 GIL 的环境下，线程在执行完 `LOAD_NAME` 和 `LOAD_CONST` 后完全可能被调度器抢占挂起。另一线程介入读取同一个旧值并写回，同样发生业务丢更新！
- **实证界限**：反汇编证明了复合操作在虚拟机指令层面是多步的，但**并不保证在一段随机代码中必定能抓到竞态**；它属于机制证据，不是概率保证。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效实验：在异步事件循环中直接调用同步阻塞函数
审查以下错误示范代码：
```python
import asyncio
import time

async def bad_worker():
    print("Worker started")
    # [!] 致命错误：在异步协程中调用同步阻塞函数！
    time.sleep(3.0)
    print("Worker finished")

async def heartbeat():
    while True:
        print("Heartbeat ping...")
        await asyncio.sleep(0.5)
```
1. **破坏现象**：当 `bad_worker` 运行时，整整 3 秒内，原本每 0.5 秒打印一次的 `heartbeat` 彻底停止跳动！整个事件循环被单颗核心上的同步 `sleep` 硬生生“卡死”；
2. **机理剖析**：单线程事件循环依赖各协程**主动协作让出（Cooperative Yield via `await`）**。如果调用了无感知让出的内核阻塞 API（如 `time.sleep` 或同步套接字读写），当前物理线程被操作系统内核直接睡眠，事件循环无法处理任何后续事件，整个服务的全部在线连接全部停摆！
3. **正确修复方案**：使用 `await asyncio.sleep(3.0)` 或使用 `loop.run_in_executor(None, sync_function)` 将同步代码委派至独立工作线程。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“Python 因为有 GIL，所以在任何多线程程序中都绝对无法利用多核。”**
  - **纠正**：在调用底层 I/O、NumPy、OpenCV 或自行编写释放了 GIL 的 C/Rust 扩展时，各线程可以在不同物理核心上全速并行计算；此外在 Python 3.14 自由线程构建下，纯 Python 代码亦可并行。
- **谬误 2：“异步编程不需要线程，所以在代码里随便怎么写都不会有竞态。”**
  - **纠正**：异步单循环消除了不可预测的指令级抢占，但在横跨 `await` 挂起点的多步业务逻辑中，其他协程完全可以在中途修改共享数据，依然需要使用逻辑锁（如 `asyncio.Lock`）。
- **谬误 3：“在异步 Web 服务里用 `async` 包装一下任何历史旧库，性能就能提升十倍。”**
  - **纠正**：如果底层调用的库依然是同步阻塞的网络或数据库读写，单靠给外层函数加 `async def` 不但不能提速，反而会由于阻塞事件循环导致服务瞬间瘫痪。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
在传统 GIL 启用的 CPython 中，既然任意时刻只有一个线程持有 GIL 并解释执行字节码，为什么两个线程并发执行 `count += 1` 依然可能会算错，甚至丢失大部分自增？

<details>
<summary>Hint 1</summary>
反汇编 `count += 1`，它是一条单一的机器指令，还是多条字节码？
</details>

<details>
<summary>Hint 2</summary>
CPython 解释器在执行一个耗时较长的线程时，是否允许在两条相邻的字节码指令之间释放 GIL 并切换到另一个线程？
</details>

<details>
<summary>Expected Observation</summary>
GIL 只对正在执行的单条字节码指令提供互斥保护，线程切换可能发生在 `LOAD` 与 `STORE` 字节码之间。
</details>

<details>
<summary>Full Explanation</summary>
虽然 CPython 的 GIL 保证了内存访问不会撕裂 Python 对象本身，但应用层面的状态变迁（如自增）需要先通过 LOAD 字节码把对象压栈，再通过 BINARY_OP 计算，最后通过 STORE 字节码绑定。CPython 调度器会在每执行一定数量的指令（或经过特定时间）后主动释放并重新争抢 GIL。一旦线程在读取了旧值之后被强制切换，另一个线程完全可以趁机读取并完成写入。当原线程重新获得调度时，它会把基于旧值计算出的结果无情覆盖。因此，GIL 保障的是解释器自身的安全，绝不替应用程序的业务逻辑背书！
</details>

- 能准确引用 2026-09-05 Python 3.14 PEP 779 现状：自由线程已进入官方支持第二阶段，但仍为可选构建且受第三方扩展安全性约束；

## 17. 严格推论边界 (Exact Inference Limits)

- 反汇编只能证明**字节码是多步执行的**，**绝不能推论出特定随机代码必定会在特定秒数内复现丢失更新**；
- 单事件循环消除了指令级上下文抢占，**绝不意味着异步代码完全不需要锁**——跨越 `await` 的多步业务流程依然可能遭遇状态不一致；
- 绝不能得出“异步在任何情况下都优于多线程”的绝对结论；高计算负载与深层原生库调用依然属于抢占式线程和多进程架构的主场。
