# L00-01｜一条路径，不是“整个系统”

## 学习者问题

当一个很小的程序接收输入、改变状态并产生输出时，**信息和控制到底经过了哪些边界？**

这不是要你背“计算机由哪些部件组成”。我们先建立一个能指导调查的地图：沿着一条有目的的路径，看见输入、接口、状态、间接关系和输出，同时明确哪些机制现在故意不展开。

## 为什么重要

以后你会遇到编译器、操作系统、网络、数据库、并发和分布式系统。它们都更复杂。如果一开始把“图上的盒子”误当成系统本身，或者把“数据在某处”直接等同于“状态/存储/持久性”，后面的推理会不断错位。

本课先建立四个 canonical concept 的第一教学位置：

- **EC-CON-001 状态（State）**
- **EC-CON-002 抽象（Abstraction）**
- **EC-CON-004 间接（Indirection）**
- **EC-CON-005 接口（Interface）**

## 学习目标

完成本课后，你应能：

1. 沿一个受限本地 fixture 画出 `input → interface → process-local state → output` 的路径；
2. 正确区分状态、接口、抽象与间接；
3. 指出地图中至少一个**故意不透明**的机制；
4. 解释为什么“地图是为某个问题服务的模型”，而不是系统本身。

## 前置知识

- 能读懂变量、函数、字典/对象一类的基础代码；
- 能运行一条给出的 Python 命令。

不要求 Shell、Git、Linux、网络、数据库或操作系统知识。

## Mental Model｜路径 + 边界 + 明确省略

```mermaid
flowchart TB
    I[输入 input.json] -->|跨越输入边界| IF[接口 Interface\naccept_record]
    IF --> S[进程内状态 State\nrecords = [...]]
    S --> R[表示边界\nserialize_record]
    R --> OPAQUE[[课程提供的 save/load 边界\n内部机制故意不透明]]
    R --> OUT[可观察输出\nbytes / hex / round-trip]
    OPAQUE -. later load .-> OUT

    classDef opaque stroke-dasharray: 5 5;
    class OPAQUE opaque;
```

**图的教学目的：**让你沿一条真实可运行的局部路径定位边界，同时看见一个明确的模型停止点。

这张图不是“计算机系统架构全图”。它没有讲进程如何被操作系统管理、文件如何落盘、网络如何传输、数据库如何提交，也没有声称那些机制不重要。这里只是当前问题不需要它们。

## Mechanism｜四个概念怎样进入这条路径

### 1. 状态（State）— EC-CON-001

**Canonical definition：**能够影响未来行为或观察的信息。

在本活动里，`accept_record` 接受输入后创建的 `records` 是进程内状态，因为随后取出的 current record 会影响序列化和输出。

注意：**状态不等于“存在磁盘上的东西”。** 一个变量、缓存中的值、内存里的记录，都可能是状态；是否存储、存在哪里，是另一个问题。

### 2. 抽象（Abstraction）— EC-CON-002

**Canonical definition：**为特定目的省略细节、同时保留相关行为的模型或边界；被省略的机制并不因此永远无关。

上图就是一个抽象。它保留了本课关心的“路径和边界”，省略了 save/load 内部机制。

模型的限制：如果你的问题变成“突然断电后数据是否还在？”，这张图就不够用了。那需要后续课程中的不同模型与证据。

### 3. 接口（Interface）— EC-CON-005

**Canonical definition：**对外可见的交互契约：接受什么形式、含义是什么、提供什么保证/错误、边界在哪里。接口不是它的实现。

本活动中，`accept_record` 要求输入**恰好**包含 `id`、`delta`、`text`，并对整数范围与 text 类型进行检查。调用者面对的是这组可见要求，不需要先理解每一行实现代码。

### 4. 间接（Indirection）— EC-CON-004

**Canonical definition：**通过引用、名字、映射或中介去到达资源/动作，使位置或实现可以变化而不必改动每个调用者；同时它也增加查找与失败点。

这里 `save_payload(...)` / `load_payload()` 是一层简单间接：活动代码通过这两个名字访问课程提供的保存/取回能力，而不是把内部实现散落在每个调用位置。

本课只识别这层间接，不研究它里面的存储机制。

## Judge｜什么时候该展开黑盒？

下面四个问题中，哪些可以继续使用当前模型，哪些必须换更细的模型？说明理由。

1. “输入字段名错了为什么被拒绝？”
2. “为什么 `A中` 变成 4 个 UTF-8 bytes？”
3. “断电后这个数据是否一定还在？”
4. “两台机器之间怎样传输这个记录？”

你不需要回答 3、4 的机制。正确的能力是**知道当前模型在哪里失效**。

## Common Misconceptions｜常见误解

### “图上画了什么，系统就只有什么”

错。抽象是为一个问题选择细节。未画出的机制仍然存在，也可能在别的问题里成为关键。

### “State 就是文件/数据库里的数据”

错。State 的关键是“能否影响未来行为或观察”，不是“存在哪里”。

### “Interface 就是函数名”

函数名只是入口的一部分。接口关心可接受形式、含义、边界、错误与保证。

### “有一层 indirection 就一定更好”

不是。间接可以隔离实现变化，也会增加查找和失败点。现在只识别它，不做普遍价值判断。

## What You Can Ignore—for Now

现在可以明确忽略：

- OS 如何调度程序；
- 文件系统如何实现文件；
- 写回、fsync、崩溃/断电保证；
- SQL、数据库页、事务、WAL；
- 网络协议；
- 并发与分布式状态。

这些不是“不重要”，而是当前路径模型的停止点。
