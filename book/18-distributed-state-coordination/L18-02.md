## 1. 学习者核心问题 (Learner Question)

> “跨越多个独立资源时，2PC 在什么状态会出现 decision uncertainty？Saga 为什么不能自动提供覆盖整条 workflow 的 ACID Isolation？基于时间的 lease 为什么可能留下陈旧持有者，而 resource-side fencing token 又能在什么前提下拒绝已经被更高 token 超越的旧写？”

在 `M14` 中，我们掌握了单机数据库如何利用锁与日志实现 ACID 特性；在 `L18-01` 中，我们看到了发件箱模式在单库内的原子性威力。然而，当业务边界迫使我们必须跨越两个或多个完全自治的存储引擎时，单机事务边界荡然无存。

工程师通常会走向三个典型方案，但每一个方案都伴随着深刻的权衡与限制（`EC-CON-006 Trade-off`）：
1. **两阶段提交（2PC）的阻塞陷阱**：在本课 classic 2PC 模型里，参与者投 `YES` 并进入 `PREPARED` 后，如果全局 decision 对它不可获知，它不能仅凭沉默安全推断 Commit 或 Abort；它需要等待 decision 恢复或适用的 termination/recovery protocol；
2. **Saga 补偿事务的隔离边界**：本课 Saga 将工作拆成多个已经各自生效的局部步骤；失败后再执行显式 compensation。步骤之间的中间状态可能被其他观察者看到，这说明 Saga 本身不自动提供一个覆盖整条 workflow 的 ACID Isolation。这里不是数据库 isolation level 中“读取未提交事务”的 dirty read；观察到的是跨步骤已生效但以后可能被补偿的状态；
3. **时间租约式锁的陈旧持有者风险**：客户端可能在 lease 过期后继续使用旧的本地 authority 假设。**Fencing token + protected-resource monotonic validation** 是一种重要缓解模式：一旦资源已经看到更高 token，旧 token 写可以被拒绝。它不是唯一协调设计，也不能仅靠“生成 token”自动保护一个不会校验 token 的资源。

本课将带领学习者拆解分布式协调与状态同步的物理边界，推导 2PC 阻塞区间、Saga 隔离缺失反例以及防护令牌在资源边界的严密防线。

## 3. 机制模型 (Mechanism Model)

### (1) 两阶段提交 (Two-Phase Commit, 2PC) 及其阻塞不确定性

两阶段提交（Gray 1978）是最经典的分布式原子性协议。系统包含一个**协调者（Coordinator）**与若干**参与者（Participants）**。

#### 协议两阶段交互：
1. **阶段 1：准备阶段（Prepare Phase）**
   - 协调者向所有参与者广播 `PREPARE` 消息；
   - 参与者按实现检查并保留提交所需的本地状态/资源；投 `YES` 前必须进入可恢复的 prepared obligation，使自己能够服从后续全局 decision。具体是否持行锁、使用哪种日志格式属于数据库实现细节，不是 2PC 定义本身。
2. **阶段 2：提交/决断阶段（Decision Phase）**
   - **协调者决策规则**：若且仅若所有参与者均投 `VOTE_YES`，协调者在本地日志中持久化 `COMMIT` 决断，向所有人广播 `COMMIT`；若有任意参与者投 `VOTE_NO`（或等待超时），协调者持久化 `ABORT` 决断并广播 `ABORT`；
   - 参与者收到决断后，执行实际的提交或回滚并释放资源，向协调者回复 `ACK`。

```
====================================================================================================
                        FIG-M18-02 (PANEL A): 2PC PREPARED BLOCKING STATE
====================================================================================================

      Coordinator                         Participant 1 (Bank A)           Participant 2 (Bank B)
           │                                        │                                │
  Phase 1  ├─────── PREPARE ───────────────────────>│                                │
           ├─────── PREPARE ────────────────────────────────────────────────────────>│
           │<────── VOTE_YES (Enters PREPARED) ─────┤                                │
           │<────── VOTE_YES (Enters PREPARED) ──────────────────────────────────────┤
           │
           * Coordinator logs COMMIT durably!
           │
           ✘ COORDINATOR CRASHES / NETWORK DROPS!
           │ (Decision unavailable to Participant 1)
           │
           ▼
   [Participant 1 Inquiry]:
   - Can I unilaterally COMMIT? ──> NO! (From P1's local PREPARED state + silence, global COMMIT is not established.)
   - Can I unilaterally ABORT?  ──> NO! (A durable COMMIT may already have been chosen/delivered elsewhere.)
   * STATE: BLOCKED_IN_PREPARED_DECISION_UNKNOWN (Cannot decide from silence alone; retained prepared resources/obligations are implementation-specific.)

   [CONTRAST CASE: If Participant 1 had voted NO]:
   - A participant that voted NO can IMMEDIATELY and UNILATERALLY ABORT! (Unanimous YES is broken).
   * Proves: Not every coordinator crash blocks every participant forever.
====================================================================================================
```

#### 核心困境：参与者在 `PREPARED` 状态下的不可自决性
当参与者投了 `YES` 并进入 `PREPARED` 状态后，若协调者突然崩溃且未将决断送达该参与者：
- **参与者不能单方面提交**：因为协调者可能由于另一个参与者超时或投了反对票，已经判定了 `ABORT`；
- **参与者不能单方面中止**：因为协调者可能已经将 `COMMIT` 送达了其他参与者并对外生效；
- **结论**：在本课 classic model 的这个 `PREPARED + decision unavailable` 状态里，参与者**不能从超时/沉默单方面选择 Commit 或 Abort**。它需要从协调者恢复日志或适用的 termination/recovery protocol 获得足够信息。实现可能在此期间保留锁或其他 prepared resources，但“永远持某种锁”不是 2PC 的通用定义。

### (2) Saga 模式：长事务拆解与隔离性缺失 (Saga Pattern & Lack of Isolation)

面对 2PC 的阻塞风险与长时间持锁导致的极差吞吐，Garcia-Molina & Salem (1987) 提出了 **Saga 模式**。

Saga 将一个长分布式事务拆解为一系列局部事务：
$$T_1, T_2, \dots, T_n$$
每个正向局部事务 $T_i$ 都有一个对应的**补偿事务（Compensating Transaction）** $C_i$。
- 若所有 $T_i$ 均成功执行，整个 Saga 顺利完成；
- 若某个步骤 $T_k$ 失败，Saga 设计必须为已经生效的步骤定义**显式补偿/恢复策略**。本课 fixture 为了可追踪性配置成 reverse order；其他 Saga 可以有不同依赖图、并行补偿、不可补偿步骤或人工恢复，因此 reverse order 不是通用定律。

```
====================================================================================================
                        FIG-M18-02 (PANEL B): SAGA COMPENSATION & ISOLATION GAP
====================================================================================================

  Normal Path:
  [ T1: Create Order ] ──> [ T2: Reserve Inventory ] ──> [ T3: Process Payment (FAILS!) ]
        (PENDING)                  (Stock: 10 -> 9)                         ✘
                                          │
                                          │  [ CONCURRENT OBSERVER QUERY! ]
                                          └─► Reads: Order=PENDING, Stock=9! (INTERMEDIATE STATE VISIBLE)
                                              * Workflow-wide isolation is NOT provided by this Saga.

  Compensating Path (Configured Reverse Order):
  [ C2: Release Inventory ] ─────────────────────────> [ C1: Cancel Order ]
       (Stock: 9 -> 10)                                     (Order -> CANCELLED)

  * MANDATORY AXIOMS:
    1. Compensation is SEMANTIC FORWARD RECOVERY, NOT physical snapshot rollback!
    2. Compensation CANNOT erase historical visibility: the intermediate state was real and observed.
====================================================================================================
```

#### 核心边界：补偿不是时间倒流，Saga 不自动提供 workflow-wide ACID Isolation
很多初学者误以为“Saga 既然能补偿，那就等价于回滚”。**这是极其危险的错误！**
1. **语义前向修复 vs 物理镜像回滚**：
   数据库事务 `ROLLBACK` 的语义是让该事务不作为已提交事务生效；底层如何使用 WAL/undo/MVCC、磁盘上是否仍留历史字节是实现细节。Saga compensation 则是一个**新的业务操作**（例如退款、释放库存），具有自己的失败与可见性。
2. **中间状态可能可见（Lack of workflow-wide Isolation）**：
   在 $T_2$（锁定库存）执行完毕、$T_3$（支付失败）尚未触发补偿的物理时间窗口内，外部并发观察者（如另一个用户的查询、或者风控扫描）可以直接读取到被扣减后的库存和中间状态！
   后续即使执行了补偿 $C_2$，**也无法抹杀“该中间状态曾被外部真实系统读取并可能做出决策”的客观事实**。
3. **不可逆副作用与补偿失败**：
   一些副作用不可真正撤销，只能做语义补偿；compensation 自身也可能失败。此时系统可能需要重试、对账、人工干预或其他 reconciliation，不能把一次 compensation 失败直接等同于“永久不一致”。

### (3) 分布式锁、时间租约与防护令牌 (Leases & Fencing Tokens)

当多个节点需要互斥访问同一共享存储（如一个共享文件或数据库记录）时，系统常引入基于租约（Lease / TTL）的分布式锁。

#### 时间租约的失效时序（GC 停顿引发脑裂）：
1. 客户端 1 获取了锁，租约时长为 10 秒；
2. 客户端 1 运行在 JVM 或带有垃圾回收器的运行时中，在第 9 秒突然陷入了长达 15 秒的 **Stop-The-World（全停顿）垃圾回收或宿主机操作系统线程调度卡顿**；
3. 在本教学时间线的 lease deadline 到达后，锁服务按其协议将旧 lease 视为不再有效并允许新的 acquisition；这不等于它证明客户端物理死亡；
4. 客户端 2 请求获取锁，成功拿到锁（拥有有效租约），向共享存储写入新配置；
5. 旧客户端恢复执行时，**如果应用没有重新验证 lease/authority**，它可能继续使用暂停前缓存的“我仍持锁”假设；
6. 客户端 1 将其滞后的脏数据发往共享存储，**瞬间无情覆盖了客户端 2 的新写入**！

```
====================================================================================================
                        FIG-M18-02 (PANEL C): LEASE EXPIRY & FENCING TOKENS
====================================================================================================

  Time (s)    Client 1 (Lease Holder)       Lock Service                   Client 2         Storage Engine
  scenario     Acquires Lease (older token) ─> Issues older token                         (resource has not seen a newer token)
  later        [ SCRIPTED CLIENT PAUSE / NETWORK STALL ]
  later                    │                 * Lease expires under scenario policy
  later                    │                 Issues newer token ──────────> Acquires lease
  later                    │                                                 Writes Data ──> Validates newer token
  later                    │                                                 (newer token)   (highest token advances)
  later        Old client resumes after its lease expired                                  [ newer write accepted ]
              Attempts Write (older token) ───────────────────────────────────────────────► Storage Check:
                                                                                            older < highest
                                                                                            [ REJECTED! ]
  * CONCLUSION:
    A time-based lease ALONE cannot prevent stale writes.
    In this scenario, resource-side monotonic fencing rejects the old token after a newer token has taken precedence.
====================================================================================================
```

#### 一种资源边界缓解模式：Fencing Tokens
如何阻止苏醒后的“僵尸”客户端 1 搞破坏？
Martin Kleppmann (2016) 的工程分析提出 fencing token 思路：不要只依赖客户端自律，而让被保护资源能够拒绝已被更高 token 超越的旧请求。该文章是有影响力的工程分析，不是分布式锁的规范或“唯一正确设计”证明。

**防护令牌机制三要素**：
1. **锁服务派发单调递增令牌**：每次授予锁租约时，锁服务随租约下发一个严格单调递增的数字令牌（如 Token = 1, 2, 3...）；
2. **客户端写请求携带令牌**：客户端向存储发起写操作时，必须在请求中带上当前获得的令牌；
3. **存储端原子拦截（Storage Boundary Check）**：
   存储系统维护一个自身记录的最高有效令牌 `highest_token`。
   当收到写请求携带 `presented_token` 时：
   $$\text{若 } \text{presented_token} < \text{highest\_token} \implies \text{直接拒绝并报错（STALE\_TOKEN\_REJECTED）}$$
   $$\text{若 } \text{presented_token} \ge \text{highest\_token} \implies \text{接受写入，并更新 } \text{highest\_token} = \text{presented\_token}$$

在上述案例中：
- 客户端 2 写入时带入 Token 2，存储记录 `highest_token = 2` 并接受；
- 在**这个既定顺序**中，Client 2 的 Token 2 已先到达存储并把 `highest_token` 推进到 2，所以随后 Token 1 被拒绝。若资源从未看到更高 token，仅靠旧 lease “理论上过期”并不会让这个简单 storage checker 自动知道它已失效。

> **边界认知**：防护令牌是**资源边界的重要缓解模式（Mitigation Pattern）**，绝不是唯一万能的分布式锁设计（例如，必须要求后端存储具备按令牌比较或乐观锁版本检查的能力）。

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 在本课 classic 2PC 模型里，已投 `YES` 并进入 `PREPARED` 的参与者，在全局 decision 不可获知时不能从沉默单方面推断 Commit/Abort；它需要 decision recovery/termination information 来继续；
   - 投反对票的参与者可单方面安全回滚，证明协调者故障并非无条件导致所有节点永久停机；
   - 本课 Saga 的 compensation 是后续业务操作；各局部步骤之间的已生效中间状态可被观察，因此该 fixture 不提供覆盖整个 workflow 的 ACID Isolation；
   - 基于时间流逝的租约不能保证无界延迟客户端的互斥性；资源边界的单调防护令牌是防止陈旧持有者并发写破坏的关键防线。
2. **具名规范与实证 (Specification & Evidence)**：
   - 经典文献：Gray (1978) *Notes on Data Base Operating Systems*（2PC 协议最初形式化）；
   - Garcia-Molina & Salem (1987) *Sagas*（长事务的局部解耦与补偿理论）；
   - Martin Kleppmann (2016) *How to do distributed locking*（工程分析 / fencing-token 讨论；不是分布式锁规范，也不作为唯一正确方案的证明）；
   - 课程实验：通过 `labs/foundations/m18/activity_l18_02.py` 验证本地状态机里的 2PC prepared uncertainty、Saga 中间状态可见性，以及资源端 fencing token 的具名拒绝规则。
3. **推论边界与当前实践 (Current Practice & Inference Limits)**：
   - lease/pause 的具体时长、clock-skew budget 与网络延迟都属于环境/实现输入；Core 图只依赖“旧 lease 已失效、更新 authority 被授予、更新 token 先到达资源”这一场景顺序，不把固定秒数作为课程常量；
   - 防护令牌要求被保护资源能**原子地执行所需 token 顺序校验并拒绝旧请求**。CAS/conditional write/版本校验是可能实现机制，不是唯一 API 形式；单纯生成 token 不会自动保护一个不执行该检查的资源。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效示范：将“时间租约”当成“物理互斥”导致的生产脑裂覆盖

审查以下分布式锁保护文件的逻辑：

```python
# 致命缺陷代码：完全信任本地租约，缺乏资源边界防护
def sync_inventory_bad(lock_service, storage, client_id):
    lease = lock_service.acquire("inventory_lock", ttl_seconds=5)

    # 模拟发生未预期的长时间停顿（如垃圾回收、宿主机卡死、慢网络）
    time.sleep(10)  # 租约在第 5 秒已在服务端过期！

    # 客户端苏醒，无脑发起写入（无防护令牌）
    storage.raw_write("inventory_count", 0)  # 致命：覆盖了别人在第 6 秒写的新值！
```

**失效剖析**：
仅凭客户端上一次成功续租/时钟检查，不能推出“下一次 I/O 发出时 lease 仍有效”；执行可能在两者之间暂停或通信状态可能改变。资源端 fencing 是处理陈旧 authority 的一种重要模式，但并非所有协调系统都必须采用同一 token 方案。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“只要协调者挂了，2PC 里的所有机器就永远彻底死锁，谁也动弹不得。”**
  - **纠正**：不准确！若某个参与者投了反对票（`VOTE_NO`），它完全可以立即单方面安全中止；若参与者之间能够互相通信，并且有某个参与者已经获知了 Commit 决策或投了 No，参与者群体可以通过协作终止协议打破阻塞。唯有“全体投了赞成票且无法获知任何外部决断信息”的节点才必须保持阻塞。
- **谬误 2：“Saga 模式既然支持补偿，那它就是微服务环境下更好、更先进的分布式 ACID 事务。”**
  - **纠正**：Saga pattern 本身不自动给整条跨服务 workflow 提供一个 ACID transaction 的 Isolation。是否、哪些中间状态可见取决于局部事务与额外协调设计；本课 fixture 明确让中间库存/订单状态可见。Compensation 是后续业务动作，不等同事务 rollback。
- **谬误 3：“只要生成了单调递增的防护令牌，分布式写操作就自动并发安全了。”**
  - **纠正**：错！防护令牌本身只是一个整数数字。如果接收写入的存储服务（如某个裸磁盘或不校验版本的数据库表）根本不支持检查“当前版本必须大于已存版本”，那么令牌毫无意义。防护能力产生于**资源边界的强制校验机制**。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
在两阶段提交（2PC）中，假设协调者在收到所有参与者回复的 `VOTE_YES` 后立刻在本地日志写下了 `COMMIT`，但紧接着在向网络发送任何提交指令前发生物理断电。此时，某个参与者因为迟迟收不到决断而发生超时，为什么该参与者**绝对不能**单方面自作主张执行 `ABORT`（中止回滚）？

<details>
<summary>Hint 1</summary>
回想原子性（Atomicity）与一致性（Consistency）的底线：一个分布式事务能否允许一部分节点提交，而另一部分节点回滚？
</details>

<details>
<summary>Hint 2</summary>
协调者重启恢复时，会读取它自己的本地日志。它在本地日志里写的是什么？如果参与者擅自回滚，后续协调者重发 Commit 时会发生什么？
</details>

<details>
<summary>Expected Observation</summary>
参与者在收到协调者指令前，无法得知协调者本地已经记录了 `COMMIT`。若参与者因超时单方面回滚，而协调者重启后根据本地持久化日志向全网广播 `COMMIT`，或者其他参与者已经通过恢复流程执行了提交，系统将直接出现数据状态撕裂，彻底粉碎一致性。
</details>

<details>
<summary>Full Explanation</summary>
2PC 的不可自决性是由其严格的正确性目标决定的。当参与者投下 `VOTE_YES` 后，它就已经让渡了自己的单方面处置权，做出了“服从全局决断”的严肃承诺。由于无界网络延迟的存在，参与者“等不到消息”并不代表“决断是中止”。协调者完全可能在崩溃前瞬间做出了 Commit 决断并持久化在本地。因此，处于 `PREPARED` 状态的节点在无法确证全局决断前，为了避免产生致命的裂脑不一致，只能选择就地阻塞、等待决断恢复。现代系统可以通过复制 coordinator state、consensus-backed metadata、termination protocols 等方式改善 coordinator 单点故障恢复，但这不把 2PC 与共识简单等同，也不意味着所有系统都用一种替代架构。
</details>

## 15. 核心概念引用与重温 (Concepts & Revisits)

- **`EC-CON-006 Trade-off (权衡)`**: 深刻理解 2PC（以可用性和延迟为代价换取一致性）与 Saga（以牺牲隔离性换取可用性）之间的经典架构权衡；
- **`EC-CON-015 Concurrency (并发)`**: 扩展并发冲突至无共享内存、依赖网络租约与分布式时钟不确定性下的并发写竞争；
- **`EC-CON-009 Correctness (正确性)`**: 强化防护令牌单调递增约束与资源端原子校验对维护分布式状态正确性的决定性作用。

## 17. 严格推论边界 (Exact Inference Limits)

- 本实验基于 Python 进程内状态机模拟的 2PC 与 Saga 轨迹，**仅用于澄清协议决策分支与隔离性概念边界，绝不可外推宣称为高可用分布式数据库核心引擎的工业实现**；
- 本课不把 lease TTL、pause duration、网络延迟或 clock-skew 数值冻结成通用设计常量；真实系统必须按具名实现、时钟模型与实测环境给出参数；
- 防护令牌的有效性**严格依赖资源边界具备原子性比较与拒绝的能力**；若目标底层存储不支持条件写入，生成令牌本身并不能消除并发冲突。
