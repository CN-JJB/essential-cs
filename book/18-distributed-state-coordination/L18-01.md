## 1. 学习者核心问题 (Learner Question)

> “在分布式微服务架构中，当我们不能也不该通过同步 RPC 阻塞等待下游处理时，服务之间究竟该如何安全地委托工作？消息队列真的能彻底消除背压吗？为什么在本地数据库执行写入后顺手向消息队列发送一条消息（双写），无论谁先谁后都会在进程崩溃时引发毁灭性的数据不一致？所谓的‘至少一次交付’与‘精确一次处理’，其边界到底落在哪里？”

在 `M16` 中，我们掌握了同步 RPC 在物理网络中的本质：网络静默无法区分远端执行状态，超时只代表本地放弃等待。在 `M17` 中，我们推导了多副本复制、法定人数与共识协议的开销与一致性边界。

然而，在大量真实业务场景中，调用方根本不需要、也不应该同步等待耗时下游（如邮件发送、库存划扣、风控审核）的完成。系统需要**异步工作委托（Asynchronous Work Delegation）**。
但引入消息代理（Message Broker）并非银弹：
1. **队列不是背压消除器**：队列只能削峰填谷（缓冲瞬时流量突刺）。如果消费者的平均吞吐率长期低于生产者的生成率，队列只会无限制膨胀直至耗尽内存或磁盘；
2. **双写困境（Dual-Write Problem）**：单机数据库写入与外部消息投递是两个独立的非事务操作。只要进程在两步之间发生物理崩溃或网络中断，系统就会陷入要么“扣了款没发货”、要么“发了货没扣款”的状态分裂；
3. **交付语义的具名契约**：消息代理声称的“At-Least-Once”或“Exactly-Once”，充其量只是其传输或内部主题间的投递标签，绝不自动等于下游业务系统最终副作用的“精确一次应用”。

本课将带领学习者拆解异步通信模型，透视双写失效窗口，并掌握在无外部重型中间件依赖下，如何利用单机事务边界实现标准的**事务性发件箱模式（Transactional Outbox Pattern）**与具名去重消费。

## 3. 机制模型 (Mechanism Model)

### (1) 为什么需要异步工作委托？(Why Delegate Asynchronously?)

服务间异步委托的核心驱动力包含四个工程维度：
1. **时间解耦（Temporal Decoupling）**：生产者发出工作指令时，消费者甚至不需要处于在线运行状态；
2. **速率不匹配缓冲（Rate-Mismatch Buffering）**：应对突发瞬时流量波峰，将消费速率与生产峰值解耦（注意：仅限波峰缓冲，无法解决平均速率倒挂导致的永久堆积）；
3. **独立进度与故障/重试边界（Failure & Retry Boundary）**：异步队列可以让某些下游故障不必直接占用上游同步调用路径；是否因此避免级联超时，仍取决于上游超时、队列容量、重试与背压策略；
4. **工作模型分流**：
   - **竞争消费者工作队列（Competing-Consumer Work Queue）**：点对点分发，多个 Worker 竞争拉取无序或粗粒度任务（如 Celery, RabbitMQ）；
   - **分区事件日志模型（Partitioned Event Log）**：基于追加日志与消费者偏移量（Offset），可支持多独立消费组和分区内顺序。若业务声称“同 Key 保序”，还必须说明该 Key 如何稳定映射到同一分区以及生产/重试规则。

```
====================================================================================================
                        WORK QUEUE VS. PARTITIONED EVENT LOG
====================================================================================================

  1. COMPETING CONSUMERS (Work Queue):
     [ Producer ] ─── Enqueue ───> [ Message Queue ] ──┬──> [ Worker A ] (Pulls msg 1)
                                                       ├──> [ Worker B ] (Pulls msg 2)
                                                       └──> [ Worker C ] (Pulls msg 3)
     * Characteristics: Task distribution; ACK 后删除/确认只是某些 work-queue 实现的策略示例。多个 worker 并发消费时，不能默认推导出全局 FIFO。

  2. PARTITIONED EVENT LOG (Pub-Sub Stream):
     [ Producer ] ─── Append(key="user_42") ───> [ Partition 0 (Ordered Log) ] [0][1][2][3][4]
                                                                                   ▲     ▲
                                                       Consumer Group 1 (Offset 3) ┘     │
                                                       Consumer Group 2 (Offset 4) ──────┘
     * Characteristics: Append-only log, multiple independent consumer groups, replayable by offset.
     * ORDERING GUARANTEE SCOPE: Strictly scoped to the PARTITION / KEY, NOT a universal global FIFO!
====================================================================================================
```

> **铁律：保序性必须具名其作用域（Ordering Scope）！**
> 任何关于“消息保序（FIFO）”的论述，必须显式声明其边界：是“单队列 FIFO”、“分区内（Partition）按 Key 保序”，还是“单消费者保序”。严禁在分布式上下文中默认假设存在“全局端到端无条件 FIFO”。

### (2) 双写困境：为什么两阶段无协调写入存在分裂窗口？(The Dual-Write Problem)

考虑一个经典电商下订单场景：
```python
# 致命的直觉代码：无协调的双写操作
def handle_order(order_data):
    db.execute("INSERT INTO orders ...")  # 操作 1: 本地数据库写入
    # === 物理崩溃 / 网络分区 / OOM 致命窗口 ===
    broker.send("OrderPlaced", order_data)  # 操作 2: 外部网络消息投递
```

分析以下两种确定性失效路径：
1. **先写数据库，后投递消息**：
   数据库事务成功 `COMMIT`，但在执行 `broker.send()` 之前，宿主机遭遇断电、OOM 终止或网络不可达。
   **本脚本故障点的后果**：数据库业务行已提交，而该次 enqueue 尚未发生。后续是否通过人工修复、扫描或其他恢复机制补发，不由这段无协调双写代码保证。
2. **先投递消息，后写数据库**：
   `broker.send()` 成功，但在执行 `db.commit()` 时，数据库因为唯一键冲突、磁盘满或连接超时而发生 `ROLLBACK`。
   **该类故障窗口的风险**：外部消费者可能已经根据事件产生效果，而本地数据库事务未提交。具体是否已经出库、能否撤销，取决于下游协议与业务补偿，不能从 `broker.send()` 成功单独推出。

**本质**：两个异构存储系统（数据库与消息代理）缺乏跨系统原子性协调。这就是双写困境（`EC-CON-010 Failure`）。

### (3) 事务性发件箱模式 (The Transactional Outbox Pattern)

本课采用一个**具名、受限的解决路径**：不要让业务变更与“待发送事件记录”成为两个无协调资源写；把它们放进**同一个 SQLite 事务域**。这只解决生产端“业务状态 + outbox 记录”的本地原子性窗口，后续 relay/消费仍有独立失败语义。

```
====================================================================================================
                        FIG-M18-01: DUAL-WRITE FAILURE VS. TRANSACTIONAL OUTBOX
====================================================================================================

  [PANEL A: UNCOORDINATED DUAL-WRITE (BROKEN PATH)]
   Client ─── Write ───> [ Service ]
                            │
                            ├── 1. DB Commit ────────> [ Database: Orders Table ] (COMMITTED)
                            │
                            ✘ CRASH / NETWORK DROP! (Fatal divergence window!)
                            │
                            └── 2. Enqueue (LOST!) ──> [ Message Broker ] (EMPTY!)
   * Result: Inconsistent state! Business row exists, but message was never enqueued.

 --------------------------------------------------------------------------------------------------

  [PANEL B: THE TRANSACTIONAL OUTBOX PATTERN (SAFE PATH)]
   Client ─── Write ───> [ Service ]
                            │
                            └── Single SQLite Transaction (BEGIN IMMEDIATE ... COMMIT)
                                 ├── Insert: orders table
                                 └── Insert: outbox_events table (dispatched = 0)
                                        │
                                        ▼ (Durable Atomic Boundary!)
                               [ SQLite Storage Engine ]
                                        │
                                        │ (Independent Relay Polling / CDC)
                                        ▼
                                [ Outbox Relay ] ─── At-Least-Once Delivery ───> [ Worker ]
                                        │                                           │
                                        │ (Mark dispatched = 1 upon ACK)            │ (Single Tx)
                                        ▼                                           ▼
                                [ outbox_events ]                        [ processed_events ]
                                                                                +
                                                                         [ fulfillments ]
  * MANDATORY INFERENCE LIMIT:
    Local SQLite duplicate-safe effect DOES NOT equal arbitrary external exactly-once!
====================================================================================================
```

#### 模式核心三构件：
1. **发件箱表（Outbox Table）**：
   在业务数据库同实例、同库中建立一张专用表 `outbox_events (id, event_type, payload, dispatched, created_at)`。
2. **原子事务写入（Atomic Local Transaction）**：
   生产端在执行业务操作（如插入 `orders`）时，在**同一个数据库事务**（`BEGIN IMMEDIATE ... COMMIT`）中向 `outbox_events` 插入一条状态为 `dispatched = 0` 的待投递记录。
   在本课 SQLite 事务模型里：订单行与 outbox 行要么同一事务提交，要么同一事务回滚。它关闭的是**这两个本地表之间**的原子性窗口，不等于整个端到端投递链路已经原子化。
3. **独立中继进程（Outbox Relay）**：
   一个独立的后台进程轮询 `outbox_events WHERE dispatched = 0`（或读取数据库 CDC 日志），负责将事件发送给下游消费者或真实消息系统。
   当下游成功处理后，Relay 更新 `dispatched = 1`。

### (4) 交付语义与消费端去重 (Delivery Semantics & Scoped Deduplication)

在**本课脚本的恢复策略**中，中继若在“Worker 已处理、`dispatched=1` 尚未记录”这个点失败，下一次扫描仍会看到该 outbox 行，因此会再次尝试交付。同一事件出现重复尝试，是这个具名 retry/mark 顺序的结果；不是所有所谓 At-Least-Once 系统都必须使用这一实现。

因此，**交付语义是分层的契约**：
1. **At-Most-Once（至多一次）**：在所声明的 transport/processing contract 下不进行会导致重复的重试，或只允许一次尝试；因此可能丢失工作。它不是“物理世界绝无重复”的无条件保证。
2. **At-Least-Once（至少一次）**：在所声明的存储、重试与可恢复性假设下持续重试，允许同一逻辑消息出现多次 delivery attempt；是否最终交付仍依赖这些假设成立。
3. **具名 Exactly-Once / exactly-once processing**：
   - 必须说明**作用域与参与的事务资源**。例如 Kafka producer idempotence/transactions 约束的是 Kafka 自身的记录写入、事务分区以及可与事务绑定的 consumer offsets；
   - 外部 MySQL、支付网关或邮件系统若不参与同一事务/幂等协议，Kafka/SQS 等代理标签本身不能把这些外部效果变成同一原子事务；
   - 本课展示的“at-least-once-style 重试 + 本地 dedup/effect 单事务”只是实现**这个 SQLite 业务效果 duplicate-safe**的一种模式，不是所有 exactly-once 效果的唯一实现公式。

#### 消费端的单事务去重判定：
消费者如何做到幂等？
消费者维护 `processed_events (msg_id PRIMARY KEY, processed_at)`。
在消费者自己的**单笔本地数据库事务**中：
```sql
BEGIN IMMEDIATE;
-- 1. 尝试插入处理记录或查询记录
INSERT INTO processed_events (msg_id, processed_at) VALUES ('evt-123', CURRENT_TIMESTAMP);
-- 若唯一键冲突，说明该消息已被处理，立即 ROLLBACK 并确认成功（忽略重复项）
-- 2. 应用实际业务副作用
INSERT INTO fulfillments (order_id, status) VALUES ('ord-456', 'FULFILLED');
COMMIT;
```
**关键**：记录消息已被消费与业务副作用必须绑定在**同一个本地原子事务**中！如果两者分开，又会退化为双写问题。

### (5) 架构辨析：Event Log 不是 Event Sourcing！

| 维度 | 事件日志 (Event Log) | 事件溯源 (Event Sourcing) |
| :--- | :--- | :--- |
| **本质属性** | 一种底层的、追加写入的**存储/通信数据结构**或组件 | 一种高级的**应用软件架构模式** |
| **状态权威** | 系统的主权威状态依然存储在可变业务表（如 `orders.status = 'PAID'`）中，日志仅作为流转通知 | 系统**不存在可变状态表**；系统的唯一权威事实就是不可变事件的历史流（Append-Only Stream） |
| **状态重建** | 无需从头回放事件，直接读取当前状态快照 | 实体的当前状态是通过按序回放该实体自产生以来的所有历史事件（`Replay`）计算得出的 |
| **本课归属** | 本课 Outbox 演练的是带有事件日志特性的异步解耦，**绝非事件溯源** | 学习者严禁将发件箱中的日志记录与事件溯源体系混为一谈 |

## 4. 认知声称层 (Claim Layer)

1. **核心系统不变式 (Core Invariants)**：
   - 无协调的两系统双写必存在不一致物理窗口；
   - 事务性发件箱模式通过将待发事件与业务变更并入单机单数据库同一个 ACID 事务，消除了生产端的双写暴露面；
   - 消费端的去重能力，仅在“消息去重主键认领”与“业务副作用操作”处于同一个原子事务时成立；
   - 交付语义标签属于传输层或特定中间件内部拓扑，不自动延展至任意外部第三方的副作用执行。
2. **具名规范与实证 (Specification & Evidence)**：
   - 经典文献：Enterprise Integration Patterns (Gregor Hohpe & Bobby Woolf)；
   - Chris Richardson (2018): *Microservices Patterns*，系统阐述了 Transactional Outbox 与 Polling Publisher / Transaction Log Tailing；
   - Apache Kafka current official docs（Implementation/Lead recheck 2026-09-05）：启用 producer idempotence 时，Kafka 对 producer 写入提供具名的幂等记录语义；Kafka transactions 可跨 Kafka partitions/topics 组成事务，并可将 consumer offsets 纳入该 Kafka transaction。它们**不自动把外部数据库、支付或邮件效果纳入同一事务**。
   - 课程实验：通过 `labs/foundations/m18/activity_l18_01.py`，完整重现“双写断裂导致状态分裂”与“发件箱+单事务去重抗击重试重复”的确定性机器实证。
3. **推论边界与当前实践 (Current Practice & Inference Limits)**：
   - 实验在单机 SQLite 上证明的是“受限的作用域内原子性”，绝不可将该结论推广为“无需协调即可让跨机两个独立数据库实现分布式事务”；
   - 消息代理吞吐率（如几十万 TPS）或网络往返延迟受硬件和网络拓扑影响极大，严禁在理论推导中假定一个通用的毫秒或吞吐量数值。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

### 失效示范：伪幂等设计——去重检查与业务变更脱离同一事务

审查以下常见错误实现：

```python
# 严重缺陷代码：将去重检查与业务更新拆分成两个独立事务
def process_order_event_bad(conn, msg_id, order_id):
    # 事务 1: 检查并记录已处理
    with conn:
        already_done = conn.execute("SELECT 1 FROM processed_events WHERE msg_id = ?", (msg_id,)).fetchone()
        if already_done:
            return
        conn.execute("INSERT INTO processed_events VALUES (?, CURRENT_TIMESTAMP)", (msg_id,))

    # === 致命崩溃窗口：标记已完成，但业务更新尚未提交！ ===

    # 事务 2: 应用业务副作用
    with conn:
        conn.execute("INSERT INTO fulfillments VALUES (?, 'FULFILLED')", (order_id,))
```

**失效剖析**：
若进程在事务 1 提交后、事务 2 提交前物理断电，`processed_events` 表中已永久记录了该 `msg_id`。
重试机制再次投递该消息时，由于事务 1 检查命中，直接提前返回，**导致真正的发货业务变更永久丢失**！
**核心原则**：去重认领必须与所保护的业务副作用锁死在**同一个单机 ACID 事务**之内。

## 9. 常见认知谬误 (Common Misconceptions)

- **谬误 1：“只要加了消息队列，系统的吞吐量就会无限提升，再也不用担心服务被打挂。”**
  - **纠正**：错！队列仅提供短时间的排队削峰能力。若上游平均产生速率长期大于下游处理能力，队列长度将单调递增直至耗尽存储或触发限流丢弃，背压并未消失，只是被转移到了队列存储层。
- **谬误 2：“某队列/流系统声明 Exactly-Once，所以消费者调用任意第三方退款接口也自动精确一次。”**
  - **纠正**：错误。必须先看该产品 exactly-once 声明覆盖哪些记录、offset、事务资源和失败模型。第三方 HTTP/支付/邮件效果若不参与同一事务或幂等契约，就不能从代理标签推出其效果次数；业务流水号幂等是常见做法之一，但不是唯一可能协议。
- **谬误 3：“只要都叫 Outbox，业务表与事件表放在两个彼此无协调的存储里也自动原子。”**
  - **纠正**：不成立。本课模式要求 `orders` 与 `outbox_events` 参与**同一个 SQLite transaction**。若换成两个独立资源而没有额外原子提交/协调协议，就重新出现双写窗口；如果另有明确的跨资源原子协议，则必须按那个协议重新分析。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

### Checkpoint Investigation

#### Question
在**本课 SQLite Transactional Outbox fixture**中，为什么 `outbox_events` 与 `orders` 必须参加同一个本地事务？如果把 outbox 改成一个独立 Redis 写、又没有额外跨资源原子协议，会重新出现什么故障窗口？

<details>
<summary>Hint 1</summary>
回顾单机 ACID 事务（`M14`）的基本定义。一个事务的原子性（Atomicity）能够跨越两个完全独立的进程或网络物理机吗？
</details>

<details>
<summary>Hint 2</summary>
如果你先向 MySQL 提交订单，再向 Redis 插入待发事件，如果进程在两者之间崩溃，系统状态是什么？
</details>

<details>
<summary>Expected Observation</summary>
若将 `outbox_events` 移至独立的 Redis 集群，写入 MySQL 与写入 Redis 变成了两段独立的网络操作。在进程崩溃或网络抖动时，依然会产生“MySQL 订单已提交但 Redis 未写入”或“Redis 已写入但 MySQL 回滚”的分裂，双写困境在异构系统间重新复现。
</details>

<details>
<summary>Full Explanation</summary>
本课证明的是一个更窄的事实：`orders` 与 `outbox_events` 参加**同一个 SQLite transaction**，所以这两项本地状态拥有同一 commit/rollback 边界。若 outbox 被改成另一个独立资源、又没有新的原子协调协议，这个共同边界就不存在，故障可能落在两个写之间。实际系统也可以采用其他协调/日志捕获方案；不要把“同一个 SQLite 事务”提升成所有系统唯一合法架构。
</details>

## 15. 核心概念引用与重温 (Concepts & Revisits)

- **`EC-CON-010 Failure (故障)`**: 重温部分失效，拓展为异构存储系统间由于缺乏原子协调而引发的确定性双写断裂窗口；
- **`EC-CON-009 Correctness (正确性)`**: 强化系统在故障重发场景下必须满足具名的交付与去重契约；
- **`EC-CON-014 Consistency (一致性)`**: 重温最终一致性在异步工作委托中的具象化体现（生产者与消费者状态在有限重试时间后的状态收敛）。

## 17. 严格推论边界 (Exact Inference Limits)

- 本实验基于单机 SQLite 构造的本地发件箱与中继逻辑，**仅用于证明单机事务边界对消除双写窗口的有效性，绝不可外推宣称本实验消除了物理网络上的全部重试与延迟**；
- 实验中测得的中继轮询微秒级延迟属于本进程调度开销，**绝不可作为衡量生产级分布式消息队列端到端投递延迟的基准数据**；
- 本实验证明的“去重安全性”，严格限定在消费端以单一事务包裹去重表与履约表的 SQLite 本地作用域内，**绝不能外推为该方案可无条件防止向外部第三方银行接口发起的重复网络 HTTP 扣款**。
