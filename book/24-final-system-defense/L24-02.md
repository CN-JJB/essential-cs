## 1. 学习者核心问题 (Learner Question)

> “为什么在 CI/CD 流水线中所有的单元测试和集成测试都跑绿（100% 测试通过）了，软件一推向生产环境却依然会发生灾难性的数据库死锁、内存泄露或不可逆的数据损坏？为什么‘回滚代码（Rollback）’绝不仅仅是重新部署上一版本的 Git Commit 那么简单？如果新版本执行了修改数据库表结构的破坏性迁移（Schema Migration），或者向磁盘写入了旧版本无法反序列化的新格式数据，仅仅重新运行旧代码会导致怎样的灾难？在发布前，我们究竟应该把有限的工程精力投入到哪些验证上？什么是必须度量（Must Measure）、必须测试（Must Test）、必须人工审查（Must Inspect）的，而什么又是可以被明确接受的未知（Acceptable Unknown）？我们如何为一次发布声明诚实的数据丢失上限（Data-Loss Bound），而不是虚假地承诺‘绝对零数据丢失’？”

在通过了 L24-01 的宏观架构防御后，软件工程走向生产上线的最后一道闸口是：**投产发布验证（Pre-Ship Verification）**。

初级工程师常常抱有一种天真的“全绿幻觉”：
1. **测试覆盖率等同于安全感**：以为测试覆盖率达到 95% 或 100% 就可以安全发布，完全忽视了单元测试无法覆盖网络延迟抖动、跨进程锁争用、资源耗尽与第三方服务偶发超时；
2. **忽视代码与数据的时空演化割裂**：把代码回滚当成万能撤销键，不知道数据具有不可逆的状态累积性，导致在发布失败回滚时瞬间摧毁旧版服务；
3. **把生产指标教条化**：以为任何系统都必须达到“99.99% 可用性”或“p99 < 10ms”，不结合真实业务场景制定有意义的 SLO 与错误预算；
4. **教条化套用迁移模式**：盲目认为所有数据库变更都必须进行复杂的“扩展-收缩（Expand-and-Contract）”多阶段迁移，无法在单实例停机维护窗口与多实例滚动更新之间做出恰当权衡；
5. **虚假的零数据丢失承诺**：在没有配置两阶段提交或异地强同步日志的单机架构上，轻率宣称“本系统保证零数据丢失”，掩盖物理磁盘断电或不可逆故障时的真实风险。

本课确立软件发布的核心本质：**发布是对风险的受控释放（Shipping is a controlled release of risk）**。学习者将掌握构建**风险分级证据矩阵（Risk-Prioritized Evidence Matrix）**的科学方法，建立涵盖代码兼容性、数据库演化、可逆性回滚预案与可观测健康信号的完整生产把关能力。

### (2) 风险分级四大类证据 (The 4 Risk-Prioritized Evidence Classes)

1. **必须度量 (Must Measure)**：
   - 无法通过静态代码走查或单次功能运行获知、必须在真实或受控负载下经过经验采样的性质；
   - *典型对象*：持续压力下的内存驻留集（RSS）增长趋势（排查内存泄露）、开环到达调度下的 p95/p99 延迟分布、并发连接池与线程池的饱和水位；
2. **必须测试 (Must Test)**：
   - 违背将直接导致灾难性数据损坏、安全越权或服务不可用的硬性不变式；
   - *典型对象*：身份验证与 Token 篡改防御、数据库外键级联与唯一性约束、故障注入下的原子回滚、超时的 Fail-closed 行为；
3. **必须审查 (Must Inspect)**：
   - 工具难以自动理解业务语义、但包含极高战略风险的人工走查项；
   - *典型对象*：配置文件与历史记录中的私钥或凭据明文、数据库破坏性 DDL 语句（如直接 `DROP COLUMN`）、第三方依赖库的版本与许可证合规性；
4. **可接受未知 (Acceptable Unknown)**：
   - 团队经过深思熟虑后，明确声明**在当前项目阶段与资源预算下暂不予以技术覆盖、但已知其风险边界**的领域；
   - *典型对象*：对于单机系统，底层物理机机房级光纤被挖断或遭遇多小时断电的应对；在当前非分布式架构下，由宿主操作系统极端内核崩溃导致的服务瞬时中断；
   - *边界规则*：可接受未知必须是有界的、显式记录在案的，严禁将不可接受的核心缺陷假冒为可接受未知！

### (3) 代码回滚 vs. 数据库演化的深层机制 (Code Rollback vs. Database Evolution)

必须彻底粉碎“代码回滚就等于系统还原”的迷信：

1. **为什么代码与数据是不对称的？**
   - 代码是**无状态且幂等替换的**：部署旧版容器或重启旧版可执行文件，内存中的指令立刻恢复为旧版；
   - 数据是**有状态且时间单向累积的**：一旦新版本上线并在数据库中插入了新格式的数据，或者将现有列进行了拆分合并，这些变更就沉淀在物理磁盘中。
2. **破坏性变更导致的回滚崩溃场景**：
   - *步骤 1*：v2.0 代码上线，执行了 `ALTER TABLE users RENAME COLUMN email TO user_email`；
   - *步骤 2*：v2.0 在运行 10 分钟后由于前端渲染 bug 决定紧急“回滚”；
   - *步骤 3*：运维人员重新拉起 v1.0 代码；
   - *步骤 4*：v1.0 代码执行 `SELECT email FROM users`，直接遭遇 `no such column: email` 异常崩溃，导致整个服务发生完全不可用的生产雪崩！
3. **可逆性演化策略矩阵 (Conditional Reversal Strategies)**：
   - **代码回滚候选 (Code Rollback Candidate)**：只有在旧代码、实际 schema/data、client contract 与 side effects 都经过兼容性验证时才能采用；“新增 nullable 字段”只是一个可能兼容的例子，不能单独证明 whole-application rollback safe；
   - **前滚修复 (Roll-Forward / Fix-Forward)**：当已经写入了大量无法平滑反向迁移的数据时，迅速在现有版本上打补丁修复问题，而不是盲目倒退；
   - **模式反向迁移 (Migration Reversal)**：如果编写了完备的 `down_migration` 逻辑，且能证明逆向执行不破坏已产生的数据；
   - **快照与时间点恢复 (Snapshot / Point-in-Time Recovery)**：最后兜底手段。恢复到变更前的数据库全量快照，**但必须明确接受并声明由此带来的已提交数据丢失窗口（Data-Loss Window）**。

### (4) 数据库模式演化的上下文约束：何时必须扩展收缩，何时允许停机变更？

在业界实践中，Martin Fowler 的**扩展-收缩模式（Expand-and-Contract，亦称并行运行 Parallel Run）**是解决多版本共存的经典模式：
- **阶段 1 (Expand)**：增加新列或新表（允许为空），写入双写，读取兼容；
- **阶段 2 (Backfill)**：后台脚本批量刷数据；
- **阶段 3 (Contract)**：全量切换到新结构；
- **阶段 4 (Cleanup)**：删除旧结构。

**但是，重要工程推断边界在于**：
- 扩展-收缩模式是为了解决**多实例滚动更新期间，新老代码实例同时访问同一个数据库**的极端并发兼容性问题而设计的；
- 如果系统本身是一个**单实例服务**，或者业务模型明确允许**在业务低峰期进行 5 分钟计划内停机维护（Maintenance Window）**，那么直接维护窗口迁移可能成为更简单的候选方案；是否更安全/更便宜仍取决于数据量、DDL 行为、备份/恢复、客户端兼容性与实际验证。
- **严禁将扩展收缩当成无条件的教条**，必须根据部署拓扑、可用性要求与运维复杂度进行审慎决策。

## 4. 主张层 (Claim Layer)

1. **测试通过非安全证明主张 (Test PASS != Production Safety)**：单元测试与集成测试通过仅证明系统在受控预设输入下表现符合编写者的预期，绝不能推论出系统在生产并发、时延突变或破坏性迁移下的安全性；
2. **数据演化独立性主张 (Schema Compatibility Independence)**：数据库与持久化格式的兼容性必须脱离应用程序代码独立进行双向审查（新代码读老数据、老代码读新数据）；
3. **可逆性条件主张 (Conditional Reversibility)**：回滚、前滚、反向迁移和快照恢复是依赖系统状态的条件性策略，不存在通用的银弹方案；
4. **数据丢失上限主张 (Explicit Data-Loss Bound)**：如果某个 failure model 可能造成持久状态丢失，就应给出 evidence-backed data-loss bound；如果数据丢失在该场景确实不适用，也应写出 N/A rationale。**不要**在未定义 failure model / persistence configuration / evidence 时宣称 universal zero loss。

## 5. 观察前预测 (Prediction-Before-Observation)

在运行本课提供的上线前验证与迁移测试夹具前，学习者必须在工作簿中记录预测：

1. **非空列新增破坏性预测**：在 SQLite 数据库中，如果一个迁移直接尝试执行 `ALTER TABLE orders ADD COLUMN status TEXT NOT NULL;`（没有提供 `DEFAULT` 默认值），且表中已有 1000 条历史数据，SQLite 会直接报错阻断还是静默填空？如果报错，这会对发布造成什么后果？
2. **内存泄露检测预测**：在模拟连续运行 1000 次请求的压测中，如果某个模块在全局列表中不断追加上下文而不清理，操作系统的内存指标（RSS）会呈现什么样的函数曲线？单次运行仅耗时 2ms 的测试能否捕获这个潜在的 OOM 隐患？
3. **回滚时效预测**：如果新版本上线后生成了包含新字段的 500 条新订单，此时强制恢复变更前的物理数据库快照，这 500 条新订单的状态将会发生什么变化？

## 6. 动手实践活动 (Hands-on Activity)

### (1) 审计 synthetic pre-ship matrix

```bash
python labs/foundations/m24/activity_l24_02.py \
  --matrix labs/foundations/m24/sample_preship.json
```

机器只检查：

- Must Measure / Must Test / Must Inspect / Acceptable Unknown 四类都存在；
- 每项都有 `severity`、`criticality`、`evidence_gap`、`blast_radius_if_omitted`；
- compatibility / recovery rationale 字段非空；
- data loss applicable 时有 bound；不适用时有 N/A reason；
- 没有明显的 universal “100% coverage = safe” / “all failures zero loss” 口号。

输出 `PRE_SHIP_STRUCTURAL_CHECK_PASS` 只代表这些结构字段成立。

### (2) 运行 bounded SQLite DDL/query examples

```bash
python labs/foundations/m24/activity_l24_02.py --simulate-migration
```

三个例子只回答各自的**一个问题**：

1. 指定旧 query 在“add nullable column”后是否仍能执行；
2. 指定旧 query 在“rename referenced column”后是否仍能执行；
3. 当前 SQLite 是否接受“向有数据的表添加无默认值 NOT NULL column”这一 DDL。

不要从这些结果推断：
- 整个应用一定可以 rollback；
- 所有 destructive change 都必须 roll-forward；
- 所有数据库引擎行为相同。

真正的 recovery strategy 还要分析 client/API compatibility、schema/data version、side effects、backup/restore、traffic topology 和 failure model。

## 7. 受控破坏与失效模式 (Controlled Break / Failure Mode)

1. **删除风险优先级字段**：从 synthetic JSON 的某个 Must Test item 删除 `evidence_gap` 或 `severity`。Validator 应输出 `PRE_SHIP_STRUCTURAL_CHECK_FAILED`。
2. **写入 universal overclaim**：将 success criterion 写成 “100% test coverage means safe to ship”。机器应拒绝这个明显口号，但这不代表机器能判断所有更微妙的 release risk。
3. **不做破坏性生产实验**：migration examples 只在 in-memory SQLite fixture 中执行。不要 chmod/delete learner database、不要切断真实生产依赖来“演示健康检查失败”。

## 9. 常见认知误区 (Common Misconceptions)

- **误区 1**：“所有线上变更必须保证零数据丢失（Zero Data Loss），否则架构就是失败的。”
  - *正解*：错误。“zero data loss”只能在**明确 failure model 与 evidence**下讨论。例如 SQLite 官方说明：WAL + `synchronous=NORMAL` 在 application crash 下与 power loss/system crash 下的 durability 边界不同，后者可能回滚已 commit 的事务；官方并未给出一个通用“最多最后 1 次事务”常数。成熟做法是记录实际 configuration、failure model 与验证边界。
- **误区 2**：“微服务或 Web 系统的 SLO 必须统一设定为 99.99%。”
  - *正解*：错误。SLO（服务等级目标）是业务场景驱动的权衡。一个内部报表离线生成服务的 SLO 设定为 95% 或 99% 完全合理且极其省钱；而一个支付扣款网关设定为 99.99% 则需要付出成倍的冗余计算与监控成本。脱离具体业务与场景卡谈论固定 SLO 百分比是典型的教条主义。
- **误区 3**：“任何时候只要上线出问题，第一反应就必须无脑回滚代码。”
  - *正解*：错误。如果问题发生在部署后数小时，新老数据已经混杂，或者本次上线包含了结构性不可逆的数据库变更，盲目回滚代码只会导致更严重的全面瘫痪。此时必须依据部署前制定的可逆性分析，判断是前滚打补丁、执行特定的数据修复脚本，还是进行受控降级。

## 11. 渐进式支持阶梯 (Progressive Support Ladder)

- **思考问题 (Question)**：一个需要滚动多版本部署的应用准备拆分持久 schema。为什么“能执行 ALTER TABLE”并不等于“旧版本代码可安全运行/回滚”？
- **提示 1 (Hint 1)**：分别列出旧代码读取/写入的字段、新代码读取/写入的字段，以及部署窗口中会并存的版本。
- **提示 2 (Hint 2)**：哪些 migration 是 additive，哪些会改变旧代码依赖的名称/类型/语义？backup/reversal/forward repair 的 evidence 在哪里？
- **预期观察 (Expected Observation)**：只有在**确实存在多版本并存/无停机约束**时，expand-contract/parallel change 才成为重要候选；单实例维护窗口可能允许别的策略。策略必须由 topology、compatibility、data volume 与 recovery evidence 驱动。
- **完整解释 (Full Explanation)**：
  <details>
  <summary>展开查看深入解析</summary>

  1. 先定义 deployment topology 与 availability requirement，判断是否存在 V1/V2 concurrency。
  2. 对每个 schema/data change 建立 compatibility matrix：old-code→new-schema、new-code→old-schema、read/write semantics、side effects。
  3. 若需要 parallel change，可考虑 expand/backfill/switch/contract，但每一阶段都需自己的 rollback/roll-forward evidence。
  4. 若允许维护窗口，直接 migration + verified backup/restore 也可能更合适。
  5. SQLite fixture 的一个 query PASS/FAIL 只是局部 evidence；最终 strategy 仍由 actual-system review 决定。
  </details>

## 17. 精确推断边界与禁止事项 (Exact Inference Limits)

1. **绝对禁止宣称“100% 测试通过等于绝对安全”**：测试仅证明已知断言，无法完全排除未知并发冲突与物理环境异常；
2. **绝对禁止脱离架构虚构零数据丢失**：若 data loss 对该 failure model 适用，必须给出由实际 persistence configuration/evidence 支持的 bound；若不适用则写明理由，禁止无条件 zero-loss 口号；
3. **绝对禁止将回滚代码视同于回滚数据**：在没有分析 Schema 兼容性之前，严禁直接对包含数据库变更的版本实施纯代码回滚；
4. **场景卡与 SLO 指标为上下文特定参数而非通用教条**：场景卡中的目标数字（如 99.9% 或 500 req/s）仅为本次演练的目标输入，严禁将其凝固为整套课程的硬性常数；
5. **严禁将机器验证通过冒充为评审者上线批准**：验证器输出的结构性合规仅证明格式完备，最终的上线风险决策由评审者或项目负责人最终把关。
