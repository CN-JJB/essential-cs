# L10-03｜为什么我的请求会超时：网络故障谱系与部分失败

## 学习者问题

你在网页上点击“确认支付 1000 元”，或者在命令行运行一个 API 调用脚本。程序没有任何报错，光标在屏幕上停滞旋转了 10 秒钟，随后终端吐出一行冰冷刺眼的红色日志：

```text
[示意] <runtime-specific timeout disposition>
```

**在这个瞬间，到底哪里出了问题？**
是你的本地 Wi-Fi 断了？还是服务端的机房着火断电了？最致命的问题是：**服务端的银行系统究竟有没有扣掉你那 1000 块钱？**
如果此时自动化脚本因为超时就盲目重试，业务操作会不会被执行两次？为什么同样是“请求没成功拿到结果”，不同宿主机与网络路径可能给出不同异常类型、错误码和耗时？

## 为什么重要

在单机程序中，函数的执行结果通常是确定二元的：要么成功返回结果，要么抛出异常中断并留在本地栈中。但只要跨入网络与分布式系统的世界，这种舒适的确定性就会被瞬间撕得粉碎：
- **超时即未执行误区**：许多开发者潜意识里认为“既然超时报错了，说明服务端肯定没有执行我的业务”，随后在代码中无脑加入自动重试，导致下游系统产生可怕的重复扣款、重复创建资源或脏数据覆盖；
- **错误信息单一归因误区**：看到“Connection Refused”就断定“远程服务器已经彻底关机关停”，不知道在现代网络中防火墙策略、端口未监听或负载均衡器过载都会导致类似的拒绝表现；
- **异常类型/耗时绝对化误区**：误以为“拒绝一定是某个异常类且必定很快，超时一定是另一固定异常且必定更慢”，忽视了运行时、操作系统与网络策略差异；
- **网络故障确定性幻想**：误以为每一次网络故障都会精准返回一个 HTTP 500 或 RST 状态码，无法理解分布式系统最根本的特质——**部分失败（Partial Failure）与状态不可知（State Ambiguity）**。

要成为一名具备独立技术判断力的系统工程师，必须系统化建立网络故障的分类诊断能力与防御性架构直觉。本课正式复访核心系统概念：**故障（Failure，EC-CON-010）**。

## 学习目标

完成本课后，你应能：
- **Diagnose**：使用**网络故障谱系（Failure Spectrum）**把客户端观测定位到解析、连接、已建连读取或断连等阶段，同时说明一个 client-visible disposition 往往不能唯一确定底层根因；
- **Explain**：深刻阐明分布式系统的核心困境——**客户端观测到的超时（Timeout）本质上只是“本地计时器到期”，绝不能作为远端服务端执行状态的唯一定论**；
- **Observe**：使用 `labs/foundations/m10/failure_fixture.py` 分别观测受控未绑定端口拒绝、静默服务端读超时以及 RFC 2606 保留域名 `.invalid` 的真实故障表现，如实记录宿主机异常与耗时；
- **Judge**：评估超时后的重试安全边界，要求明确的应用级 retry/outcome contract；可讨论天然幂等语义、唯一操作标识 + 去重、查询/对账确认等方案，但不把某一种 HTTP 方法或 Idempotency-Key 实现写成唯一答案；
- **Estimate**：基于显式给定或真实记录的延迟分布、资源预算与业务容忍度，比较不同 deadline 设定的工程权衡；不采用固定 P99 倍数作为普遍公式。

## Mental Model｜网络故障谱系与客户端观测歧义性

网络通信是一条由多个独立脆弱节点串联而成的链条。故障可以发生在链条的任何一个环节，而在客户端看来，外部世界往往只暴露给它一个笼统的异常类型。

### 1. 网络故障谱系（The Network Failure Spectrum）

```text
[客户端应用发起请求]
         |
         +---> (1) 名称解析阶段: 解析失败 -----------> [本地可见: resolver failure disposition]
         |
         +---> (2) 连接阶段: 受控未监听端点 ---------> [本地可见: connect failure/refusal disposition]
         |
         +---> (3) 连接阶段: SYN 丢失 / 防火墙静默丢弃 -> [连接超时 (Connect Timeout)]
         |
    [TCP 握手成功: ESTABLISHED]
         |
         +---> (4) 传输阶段: 请求送达，服务端处理中 / -> [读取超时 (Read Timeout)]
         |                  或回包丢失在途                    (【核心重点】远端状态完全不可知！)
         |
         +---> (5) 已建连后异常关闭/复位 -----------> [本地可见: EOF/reset/other close disposition]
```

### 2. 客户端观测无法唯一锁定根本原因（Observation != Cause）

这是网络故障诊断中最重要的一条不变量：**客户端观察到的同一种表象，其底层的物理原因可能有完全不同的解释**：

| 客户端观察到的表象 | 可能的底层原因 A | 可能的底层原因 B | 可能的底层原因 C |
|---|---|---|---|
| **Connection Refused** | 目标端口当前没有进程监听 | 目标主机防火墙显式配置了 REJECT 策略 | 本地回环或容器网络端口映射配置错误 |
| **Connect Timeout** | 远端机器断电完全下线 | 跨机房路由器断纤，分组被丢入黑洞 | 目标机防火墙安全组规则静默 DROP 了 SYN |
| **Read Timeout** | 服务端处理耗时超过了预期（慢 SQL） | 服务端已成功扣款，但回复时网络中断 | 服务端在收到请求后突然 OOM 崩溃挂死 |
| **Connection Reset** | 服务端进程在处理途中突然 Crash | 两个主机之间的 NAT 网关超时清理了流表项 | 防火墙 DPI 规则触发，主动伪造 RST 切断 |

## Mechanism｜部分失败的本质与超时语义

### 1. 超时（Timeout）到底是什么？

> **核心定义**：
> **超时不是一种网络协议状态，而是客户端本地单方面设定的“耐心倒计时（Local Deadline）”**。
> 当客户端设置了 `socket.settimeout(5.0)` 并发起读取时，它实际上是在对本地操作系统内核说：“如果 5 秒之内我的套接字接收队列里依然没有任何来自对端的新字节到达，请中断我的阻塞等待，抛出一个异常通知我。”

这就引出了分布式系统最经典、最残酷的核心推论：
**超时发生时，这次调用至少可以确认“本地 deadline 到期前没有获得所需结果”；仅凭这个 timeout disposition，通常不足以唯一确定远端服务器是否接收、执行或提交了操作。**

```text
场景 1（未执行）：
[客户端] --- 请求在出本地网卡前丢失 ---> [路由器 (丢包)]   [服务端 (从未见过该请求)]

场景 2（半执行）：
[客户端] --- 请求成功送达 ---> [服务端 (开始扣款...突然服务器停电 Crash!)]

场景 3（全执行但未送达）：
[客户端]                      [服务端 (扣款 100% 成功! 写入磁盘! 生成流水号!)]
   x <--- 回包在光纤中被丢弃 --- [服务端发送确认 HTTP 200]
[客户端超时崩溃报错: "操作超时!"]
```

在场景 3 中，服务端的业务逻辑已经完美执行，但客户端因为读超时而收到了错误。**如果此时客户端天真地认为“超时 = 没执行”，从而在重试代码中再次发起扣款，用户的账户就会被扣款两次！**

### 2. 重试判定准则：应用级 Retry / Outcome Contract

网络层不会替应用决定“现在能否安全重试”。需要由**应用级契约**回答：重复提交是否具有相同预期效果？服务端能否识别同一逻辑操作？客户端能否查询最终结果？

可用策略包括：
- 操作本身具有明确的幂等语义；
- 使用唯一 operation/request identifier，并由服务端提供去重语义；
- 超时后先查询/对账/恢复已有结果，再决定是否重试；
- 对无法安全重复的操作，返回“结果未知/待确认”而不是自动再次执行。

> **边界**：Idempotency Key 是一种常见实现模式，但不是唯一方案，也不保证在缺少原子性、持久化、过期策略与作用域定义时自动正确。HTTP 方法的 safe/idempotent 规范语义将在 M11 系统学习，本课不提前把 `GET/PUT/DELETE` 简化成“盲目重试一定安全”。

## 边界警示｜受控实验与宿主机不变量

在设计网络故障实验时，必须严格遵守以下事实边界：
1. **拒绝/失败耗时不是课程常数**：课程 fixture 只要求“旧 loopback 端点没有建立新连接”这一语义，并记录原始 `connect_ex`/异常与 elapsed sample。不同运行时、操作系统与安全策略可能给出不同错误码与耗时；测试不得规定固定阈值或比例；
2. **切勿硬编码错误码或异常类**：学习者记录实际 runtime disposition、错误码/文本（若有）与 elapsed sample；这些都属于 host evidence，而不是跨平台验收值；
3. **保留顶级域名的纪律**：测试 DNS 失败时，必须使用 RFC 2606 规定的保留顶级域名 `.invalid`（例如 `test.invalid`）。绝对不要随意输入一个现实中可能存在的域名进行测试，也不要依赖公网未知的外部域名黑洞。

## Hands-on Progression

### 1. Observe：运行受控网络故障套件

运行 M10 故障观察脚本：

```bash
python labs/foundations/m10/failure_fixture.py
```

观察终端中记录的三类受控故障：
1. **Case 1 (受控未绑定 loopback 端点)**：连接刚释放的动态端口，如实记录 `connect_ex` 结果或实际异常、错误信息与耗时；只机器检查“没有建立到该旧 course endpoint 的新连接”；
2. **Case 2 (静默超时)**：服务端接受连接后故意不发送应用层字节。客户端配置一个有界 read deadline 并记录运行时的 timeout disposition 与实际 elapsed sample；deadline 数值是 fixture 配置，不是课程时延常数；
3. **Case 3 (保留域名 DNS 观察)**：向 `m10-lookup-test.invalid` 发起 capability-gated 解析并记录真实 resolver disposition。若 live observation 不可用，输出 `NO LIVE DNS FAILURE OBSERVATION`；不要求固定 `gaierror`、errno 或 NXDOMAIN 文本。

### 2. Build：给客户端装上“看门狗”定时器

在 Python 中如何规范地为网络读取设置有界截止时间（Deadline）？

```python
import socket

def safe_network_fetch(host, port, timeout_seconds=2.0):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    # 教学策略：为这次阻塞式网络操作设置有界本地 deadline，避免无界等待
    sock.settimeout(timeout_seconds)

    try:
        sock.connect((host, port))
        sock.sendall(b"PING\n")
        response = sock.recv(1024)
        return response
    except socket.timeout:
        # 捕获本地计时器到期
        print(f"[WARN] Read deadline {timeout_seconds}s expired! Remote state UNKNOWN.")
        raise
    finally:
        sock.close()
```

### 3. Break：模拟服务端断电与拔网线（Silent Blackhole）

- **正常有序关闭**通常会通过 TCP close/FIN 语义让对端最终观察到 EOF；**异常/abortive close** 可能表现为 reset 或其他错误。具体时序与错误形式依赖协议栈和路径，不能写成“进程一退出就必定立即得到 FIN/RST”。
- 如果故障发生时没有可传递的关闭信号（例如路径静默失效），客户端可能只能依赖自身 deadline/keepalive/应用协议来发现长期无响应。课程不做真实拔网线或断电实验。

### 4. Explain：为什么客户端看到的超时无法指示服务端动作？

解释为什么在微服务架构中，“调用下游超时”不能直接给用户返回“操作失败，请重试”：
- 用户看到“失败”，往往会下意识重新点击按钮；
- 如果下游实际上已经成功扣款，第二次点击将导致二次扣款；
- **可行做法**：把“结果未知”作为应用状态处理，并通过已有 operation identifier、查询/对账接口或去重记录确认最终结果；具体交互协议由应用契约决定。

### 5. Judge：超时时间（Timeout Threshold）应该设多长？

评估超时阈值设定的两难工程权衡（Trade-off）：
- **较短 deadline**：更快释放等待资源，但可能把正常的长尾响应判成超时，并在存在自动重试时放大负载；
- **较长 deadline**：减少一部分过早超时，但会让调用方更久地持有连接、任务、内存或其他资源；具体是否占用“线程”取决于同步/异步架构。
- **选择方法**：用真实或显式给定的延迟分布、调用方资源预算、用户/SLO 目标、下游容量与 retry/outcome contract 做权衡。不存在通用的 `P99 × 2~3` 公式。

## Checkpoint Investigation

### Question

某大型外卖系统的高峰期发生了严重的重复扣款故障：
当晚由于网络波动，许多用户的客户端 App 在提交订单结算时触发了 `Read Timeout: 5000ms`。App 的默认逻辑是：“如果超时，自动重试 3 次”。
第二天客服收到成千上万条投诉：“我的银行卡被连续扣了 3 笔外卖费，但 App 里只显示了一份外卖！”
故障复盘会上，新手工程师小张建议：“既然 5 秒超时了导致扣款重复，那我们把客户端的超时时间直接调大到 60 秒，这样就不会超时间断，也就不会发生重复扣款了。”

请结合本课所学的部分失败本质与故障谱系，一针见血地指出小张建议中的重大隐患，并给出真正的系统级解决方案。

<details>
<summary>Hint 1</summary>
调大超时时间能改变“网络可能在回包途中中断”的物理现实吗？
</details>

<details>
<summary>Hint 2</summary>
当大量用户的 App 都挂起等待 60 秒时，后端的 Web 服务器连接池和工作线程会遭遇什么？
</details>

<details>
<summary>Expected Observation</summary>
把示例 deadline 从 5 秒改成 60 秒不能消除部分失败的歧义：如果再次超时，客户端仍然需要处理“远端结果未知”。较长等待还会延长连接、请求状态与下游容量的占用，在给定并发/资源预算下**可能**放大级联风险。根本问题是缺少“重复提交时如何识别同一逻辑操作、如何确认最终结果”的应用级契约。唯一 operation ID + 持久化去重是一种可行设计；查询/对账确认或业务本身的幂等语义也可能适用。课程不要求分布式锁作为唯一实现。
</details>

<details>
<summary>Full Explanation</summary>
小张的提议犯了典型的“用延长忍耐时间掩盖分布式本质缺陷”的架构错误。

1. **不能消灭结果歧义**：
   改大本地 deadline 不能消除请求/响应丢失或远端执行跨越 deadline 的可能。再次发生 timeout 时，仅凭该调用仍无法唯一判定远端 outcome；如果应用在没有 retry contract 的情况下重复提交可能产生重复效果。

2. **引发级联雪崩（Cascading Failure）**：
   在高并发系统中，较长 deadline 会延长每个未完成请求占用资源的时间；同步线程模型可能占用工作线程，异步模型也会占用连接、任务状态、内存与下游容量。具体容量影响需要用实际并发、资源与延迟分布估算，不能从一个固定 60 秒数字推出必然雪崩。

3. **正道：明确 retry / outcome contract**：
   - 给逻辑操作一个稳定身份（例如业务订单号或 operation ID），并定义重复请求的语义；
   - 服务端如采用去重，需要定义原子性、持久化、作用域与过期策略；
   - 客户端超时后可先查询/对账确认已有结果，再按契约决定是否重试；
   - backoff/jitter 可以控制重试负载，但不能消除部分失败或替代正确性契约。
</details>

## Common Misconceptions

- **“请求超时了，就说明服务端什么事情都没干。”** 错。超时仅仅代表客户端本地计时器到期。服务端可能完全没有收到请求，也可能正在执行，甚至可能已经成功执行完毕但回包丢失。
- **“连接拒绝（Connection Refused）说明目标物理服务器关机了。”** 错。在受控环境中，连接一个操作系统处于开机运行状态但目标端口未监听的地址，内核会直接响应拒绝。
- **“只要代码里加上重试（Retry），系统就具备了高可用。”** 错。盲目对非幂等接口进行重试是制造数据灾难的温床；在服务过载时盲目重试更会瞬间演变成压垮系统的重试风暴。
- **“拒绝连接必然比超时快成千上万倍。”** 错。课程只记录当前宿主机的 raw disposition 与 elapsed sample；不同运行时/OS/策略可表现不同，机器测试不比较固定速度比。

## Exit Criteria

- 能准确画出网络故障谱系图，指出故障可能发生在解析、连接、传输与断连的哪个具体阶段；
- 能深刻解释为什么“客户端读取超时”绝不等于“服务端未执行业务”，并列举出导致该现象的至少两种不同物理场景；
- 能说明为什么 transport timeout 不能自动授权重试，并提出至少一种明确的应用级 outcome/retry 方案（如 operation ID + 去重、查询/对账确认或天然幂等业务语义）；
- 能独立运行 `failure_fixture.py` 并解释未绑定端口拒绝、静默超时与保留域名 DNS 失败的机制成因。
